# Первый запуск и обслуживание сетки

Production новый первый Bootstrap выполняет genesis/account/process/activation/enable; E1–E4 второго выполняет accepted trust/admission, файловую установку и двусторонние peer probes. Его runtime остаётся закрыт до 05. ManagedRestart первого требует целый прежний storage/sealed checkpoint и новый Enable после majority; старые grants не восстанавливаются. Нельзя подменять authority ручным CA/orphan leaf/double. Renew/issuer replacement рабочего managed протокола ещё требуют завершения 04. [Точное состояние](Onboarding%20contracts.md#промежуточная-граница-этапа-04-2026-11-03); legacy runbooks не служат обходом gates.

## Новая первоначальная настройка (этап 03)

Автоматический Bootstrap начинается через отдельный setup login и общий admin, подготовленный E0. Заранее подготовить актуальную schema с AddEnrollmentTrust, HTTPS Browser/Direct Peer endpoints, четыре постоянных непересекающихся локальных пути и защищённые BootstrapAdmin credentials; [Configuration.md](Configuration.md#явная-локальная-настройка-этап-03). InstallationIntent=Setup задаётся до запуска версии. Конфигурация установки не менялась, окружение не переключалось; реальная внешняя приёмка ещё нужна.

Посторонние аккаунты, рабочие shared/local queues, identity/cursor и старый storage вызывают отказ. Ничего не удалять для обхода preflight; действующий первый standalone направляется в 03а/03б. Второй не становится независимым Bootstrap. При неизвестном результате сохранять прежние AttemptId/OperationIds, не создавать новую попытку и не усыновлять orphan keys. До реализации 04 production authority/activation закрыты; до 05а новый sender не работает. Ручные legacy-процедуры ниже не являются обходом нового setup. [Фазы, inventory, locks и остановка](Local%20installation%20setup.md).

Реализован controlled enable поверх DotNext 6.10.0, accepted pipeline и сценарных UoW. По умолчанию `Cluster:Mode=Disabled`. Этот документ описывает будущие действия оператора; команды здесь не выполнялись и не дают разрешения запускать установку. [Форматы файлов](Cluster%20control%20files.md), [restore и аварийное восстановление](Cluster%20recovery.md), [проверки этапа 10](Testing.md#проверка-этапа-10).

## Полномочия и общие условия остановки

Любой действующий общий Administrator подаёт membership/trust/maintenance через защищённый API с cookie и antiforgery. Сервер заново проверяет принятый аккаунт при подаче и принятии. Локальный ключ подписи разрешений и фактическое обслуживание ОС принадлежат ответственному специалисту/разработчику; дополнительной роли приложения нет. Приватный ключ подписи не устанавливается на узлы. Локальные секреты, SQL и действия окружения требуют отдельного разрешения владельца установки.

Перед каждым сценарием зафиксировать ClusterId, Generation, NodeId, StorageGeneration, адрес, версии бинарника/схемы/протокола и digest выбранного snapshot. При неизвестном результате команды сначала найти её OperationId, затем повторять исходный запрос с тем же ID и payload. Новый смысл требует нового ID. `202 LocalPending` означает очередь, а не изменение состава или отправку Telegram. Остановиться при несовпадении идентичности, SQL schema, cursor/hash, отсутствующем majority, просроченном доверии, неизвестном результате membership либо неполной изоляции. Не удалять `started`, WAL, membership или latch ради обхода отказа.

## Адреса, сертификаты и секреты

Каждый узел имеет постоянный HTTPS DNS-адрес вида `https://node.example/internal/raft` и отдельный peer listener. VPN необязателен. Оператор обеспечивает DNS, публичный server TLS, renew до истечения, firewall и mTLS client CA. Peer certificate содержит clientAuth и URI SAN `urn:uptimeharbor:<ClusterId:D>:<Generation>:<NodeId:D>`; SHA256 pin, credential ID и storage generation должны совпасть с принятым реестром. Отдельный browser listener не принимает peer certificate headers. Для Nginx нужны изолированный ingress, точный proxy allowlist, CRL и запрет early data; см. [Cluster runtime.md](Cluster%20runtime.md).

Для нового managed пути токен требуется только будущему явно назначенному sender; несендеры/Join/CanWork/consensus от него не зависят. Первый заранее получает публичный BotId из ExpectedBotId либо getMe своего локального токена. В legacy ручном sender-сценарии ExpectedBotId должен совпасть с принятым BotId. Токен не входит в команды, snapshot, диагностику или аудит. Cookie/keyring/session/lockout и приватные ключи узла остаются локальными. Защитить ACL каталоги SQL backup, WAL/snapshot, control и отдельный bootstrap keyring; snapshot содержит защищённые данные общих аккаунтов и не является браузерным DTO. Выпуск сертификатов, renew и реальные права бота к чатам здесь не проверялись.

## Первый узел

Предпосылки: новая пустая схема разрешена владельцем; нет другой работающей копии этих IDs; версии совместимы, DNS/TLS готовы. Не использовать непустую несвязанную БД. Владелец отдельно разрешает создание схемы и migrations по [Database migrations.md](Database%20migrations.md); запуск Web может выполнять startup migration, поэтому это отдельная внешняя операция.

1. Подготовить уникальные IDs, сертификаты, каталоги и локальные конфигурации. Создать ключ управления и provision manifest [офлайн-командами](Cluster%20control%20files.md#офлайн-команды). `Bootstrap` разрешён только этому первому узлу; начальное native membership version равно 0, voter один, majority 1.
2. Подготовить точную команду BootstrapAccount, защитить её отдельным локальным Data Protection keyring. В seed Operations включить только первый неготовый voter, его настоящий native member ID, действующий публичный credential и BotId. Не ставить Activated/Sender/Ready вручную.
3. После отдельного разрешения запустить установку в карантине. Прочитать свежие `challenge.json`/`status.json` из control directory. Ответственный специалист проверяет отсутствие второго экземпляра/автозапуска/ingress у копий и подписывает свежий Admission для этого challenge, IDs и seed. Скопировать результат как `admission.json`. Plain BootstrapAccount запрещён: только ProtectedBootstrapCommand.
4. Runtime проверяет схему, local identity, сертификат, genesis, затем открывает WAL. Точная bootstrap-команда проходит существующий accepted pipeline; повтор не создаёт второго администратора. Если SQL не пуст, неизвестны manifest/provenance или apply fault — остановиться, не очищать данные.
5. После подтверждённых replay/projection/account state подписать `Activate` с текущими RecoveryVersion/OperationsRevision. Leader принимает ActivateNode только после strong read barrier. Дождаться следующего `status.json`, затем подписать отдельный `Enable` по новой ревизии. Изменившаяся ревизия требует нового запроса; restart не переносит разрешение.
6. Проверить защищённый вход, роль/term, singleton majority, committed/applied, свежесть компонентных checks. Monitoring и Telegram readiness должны подтвердиться настоящими probes. Sender epoch принимается лидером только после recovery/delivery validation; все sends используют прежний единый gate. Реальный test-send — отдельно разрешённая внешняя проверка, его 202 не считать успехом Telegram.

Фактический первый запуск, SQL и сеть не выполнялись. Полноту окружения изолированные тесты не доказывают.

## Самостоятельная проверка: ПК разработчика, затем production

Порядок подготовлен 2026-10-30 в этапе 10; фактических результатов запуска пока нет. Каждый следующий шаг выполняет пользователь после успешного предыдущего. При остановке сохранить файлы и диагностику, устранить причину и повторить проверку предпосылок; не подменять отказ ручными Ready/Accepted/Administrator или примерным fencing proof. Запуск из Visual Studio без ошибок, о котором сообщил пользователь, не подтверждает эти шаги.

Выбран непрерывный ввод одной сетки: ПК временно остаётся первым voter, production-узлы входят только через Join. Поэтому уже на ПК нужны постоянный доступный будущим peers HTTPS-адрес, TLS/mTLS и отдельные listeners. Loopback-адрес не подходит для последующего межузлового ввода. Не создавать независимый Bootstrap на первом production-узле и не переносить туда диск/NodeId ПК. Если будущая связность ещё не готова, остановиться после локальной проверки до изменения membership.

## Пустой join и изменение состава

Предпосылки: действующая сетка с majority и активным Administrator; новый узел пуст, новые NodeId/StorageGeneration/credential, локальные секреты и TLS готовы. Клон действующего NodeId запрещён, даже с другой БД.

1. Получить безопасный реестр `GET /api/admin/cluster/lifecycle` и диагностику. Подать `AdmitNode` с актуальными OperationsRevision и native MembershipVersion, NodeId, StorageGeneration, Address, CredentialId и PublicCertificate. Проверить accepted result. Приглашение ограничено 15 минутами; одного локального Pending недостаточно.
2. Снять подтверждённый snapshot после AdmitNode существующим механизмом. Офлайн `checkpoint` проверяет compatibility/hash и извлекает seed без account hashes. Выполнить `provision` для Mode Join и перенести snapshot с прежними именем и digest в `StoragePath/snapshots/<SnapshotId:N>.snapshot`. Установить свежий Admission с точными Nodes/Operations выбранного среза и minimum committed index; независимого BootstrapAccount нет.
3. После отдельного разрешения запустить quarantined Join. Local initialization отвергает несвязанные общие строки/cursor/identity; snapshot восстанавливает общие аккаунты, единственную роль и защищённые данные входа. Native membership перед первым Start заполняется точным набором voters из snapshot. Сам joining node туда ещё не входит. Cookies, sessions, keyrings, Pending и токены не копируются.
4. Administrator принимает `RequestMembership` с Remove=false. Worker после повторной проверки аккаунта/trust и drain вызывает только DotNext AddMember; native majority обязательна. До ConfirmMembership accepted voter не появляется. Если аккаунт инициатора изменился в процессе, другой действующий Administrator принимает `AuthorizeMembership` с MembershipChangeId и актуальной native version; worker сверяет уже выполненный результат, не создаёт второй consensus.
5. Дождаться snapshot/replay/catch-up, точного native/accepted состава, затем отдельно Activate и Enable на новом узле по свежему status. Проверить вход теми же общими аккаунтами и отсутствие переноса локальных сессий/секретов. Просроченное приглашение или неизвестный результат требуют остановки и сверки, а не повторного независимого Bootstrap.

Удаление: принять RequestMembership с Remove=true, дождаться native RemoveMember и принятого ConfirmMembership; credentials узла отзываются, sender epoch закрывается. Последнего voter удалить нельзя. Общие аккаунты, история и deliveries сохраняются. При потере majority состав автоматически не уменьшается. Удалённый NodeId повторно не допускается; возврат — с новой идентичностью.

Замена адреса выполняется контролируемым удалением прежнего узла и пустым join нового NodeId/StorageGeneration на новом адресе, последовательно при сохраняющемся majority. In-place изменение адреса живого voter не поддерживается. Для renew секрета сначала принять TrustCredential нового сертификата того же NodeId/storage, остановить только этот экземпляр, заменить локальный ключ/credential ID, получить свежий Restart admission, проверить rejoin, затем принять RevokeCredential старого ID. Не отзывать последнюю рабочую связь majority до проверки новой. Токен бота меняется только локально у всех возможных отправителей во время общей остановки; BotId сохраняется.

## Обслуживание, обновление и rollback

Предпосылки: majority и актуальный Administrator, согласованный комплект бинарников/схемы/backup. Принять EnterMaintenance с новым MaintenanceId. На всех узлах дождаться принятой записи и durable control marker `maintenance`; UI/checks/sender закрываются, native runtime останавливается. Если узел не получил запись, специалист отдельно блокирует его ingress и автозапуск. До общей остановки доказать отсутствие in-flight transport: отмена HTTP не отменяет уже случившийся внешний эффект. Лимита длительности обслуживания нет.

Во время остановки выполнить только отдельно разрешённые backup/update/schema-действия. Restart, таймер и окончание обновления не снимают latch. Для продолжения **разработчик вручную** на каждом экземпляре проверяет совместимость, изоляцию старых копий, свежий challenge и подписывает Admission/ResumeConsensus с точным MaintenanceId. После запуска достаточного состава лидер принимает LeaveMaintenance. Затем отдельно подписать Enable каждого узла по новой ревизии; при необходимости Activate. Только реальные свежие checks открывают рабочие gates.

Rollback бинарника допустим, только если он читает текущие protocol/command/snapshot/password formats, схему и всю уже принятую историю, включая lifecycle и recovery provenance. Одна строка Compatibility не заменяет проверку поддержки новых команд бинарником. При несовместимости остановить **всю** сетку, сохранить новый принятый срез и выбрать согласованный forward fix либо ручное аварийное восстановление с подтверждением потерь. Downgrade одной SQL-проекции в работающей новой сетке не является безопасным rollback. Старые аккаунты/пароли/отмены/успешные deliveries не возвращать из старой БД. Конкретный release/rollback/backup не выполнялся; реальная SQL atomicity, TLS, процессы и внешние sends остаются отдельной приёмкой.
