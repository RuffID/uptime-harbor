# Связь узлов, Raft и готовность

## Подготовительный onboarding protocol v2 (2026-11-03)

OnboardingAcceptance назначает подтверждённое время через существующий strong barrier и ClusterRaftHandle; RevisionDispatcher/reducer/apply сохраняют новые команды в прежнем WAL/projection. Request digest исключает coordinator stamp, WAL/receipt покрывают полные байты. Snapshot строго проверяет manifest/body и onboarding, включая recovery ancestors. Старый membership/Activate не обходит новую delegation/process модель. Настоящие issuer, enrollment proofs, новый native Join и activation остаются закрытыми. [Реализованные контракты](Onboarding%20contracts.md).

## Controlled enable и эксплуатация (09)

SignedRecoveryAdmission проверяет локальную ECDSA-подпись/pinned SPKI, process challenge, UTC freshness, manifest и настоящий client certificate/private key/CA/SAN/pin. Bootstrap разрешает только точную защищённую команду singleton account; Join использует принятый snapshot без независимого аккаунта. AcceptedPeerTrustSource читает общий публичный реестр с отзывом/expiry. ClusterDatabaseProbe требует CanConnect и отсутствия pending migrations, ничего не применяет.

ClusterOperationReducer принимает lifecycle-команды в том же Raft log/SQL projection: admitted nodes/trust, serialized membership intents/results, activation, maintenance и sender epoch. User actions требуют актуального accepted Administrator; internal actions — настоящего local recovered leader/term/storage provenance, peer batch их отвергает. Перед native Start сверяются durable membership и принятый набор; первый Join инициализирует native voters/version из проверенного snapshot. Проверенный старый prefix допускает только catch-up без доступа до minimum committed index. ClusterRuntimeState добавляет operational proof лишь поверх реального recovery, точного native/accepted состава и DeliveryQueue.Validate; один RevisionClusterRecovery.Accepted работу не открывает.

Signed Activate и отдельный Enable связаны с текущими версиями. Точный переход native состава, соответствующий одному принятому membership intent, сохраняет доступ уже активированных узлов для повторной авторизации результата; посторонний voter закрывает работу, sender остаётся закрытым до подтверждения перехода. Maintenance durable, останавливает native runtime и рабочие роли; restart/таймер его не снимают. ResumeConsensus разработчика разрешает только восстановление consensus, затем accepted LeaveMaintenance и новый Enable. EmergencyRecoveryOrchestrator готовит карантинную новую identity из явно выбранного среза с ручным isolation attestation, reauthentication и loss acknowledgement; второй consensus и SQL WAL не создаются. [Runbooks](Cluster%20operations.md), [recovery и границы ручного fencing](Cluster%20recovery.md), [файлы и команды](Cluster%20control%20files.md).

## Безопасная диагностика в браузере (08)

ClusterBrowserDiagnostics проверяет accepted Administrator и проецирует только явный ClusterDiagnosticDto: текущий узел/главный, роль/majority, applied/commit/lag, local Pending/held/delivery backlog, БД и Telegram readiness. ClusterHealthWorker хранит последний authenticated health и monotonic возраст в одном singleton, используемом hosted polling и query; browser GET не вызывает сеть/БД. Сырые Components и health payload не сериализуются.

Follower, исправная локальная БД без peer-связи и известная неисправность БД показаны раздельно. Нет свежего matching term/membership health главного — Telegram Unknown; свежая проверка Telegram без sender readiness не означает Available. Причины — закрытый набор, без exception/секретов/обещанного срока. Majority подтверждается текущим локальным лидерским consensus; у follower без такого доказательства Unknown. UI не подтверждает activation/delivery или controlled enable; gates этапов 03–07 сохранены.


## Sender lifecycle этапа 07

Web регистрирует production DeliverySenderConsensus, AcceptedDeliveryDispatcher и ClusterDeliveryWorker рядом с существующим журналом. Самостоятельный AddClusterInfrastructure сохраняет UnavailableSenderConsensus до сборки Web graph. ClusterRaftHandle хранит текущий native экземпляр для writer, устраняя цикл runtime → gate → dispatcher → writer → runtime; наличие handle не означает readiness.

Worker ничего не делает в Disabled. Enabled сначала проверяет восстановленную очередь по accepted image, затем независимо обновляет authority примерно раз в 5 секунд и запускает dispatcher. Перед transport повторяются проверки SenderAuthorityGate, RecoveryVersion, cancellation и текущего intent/configuration; неизвестные условия закрывают gate. Реальные renewal/attempt решения принимаются существующим DotNext writer, а transport results передаются через тот же revision transport.

RevisionClusterRecovery самостоятельно не подтверждает activation/manual enable/sender epoch/delivery proof. Эти зависимости собирает production lifecycle 09 только по проверенным предпосылкам; фактического включения установки не было. [Контракт доставки](Notifications.md#принятая-доставка-этапа-07), [проверки](Testing.md#проверка-этапа-09).

## Monitoring reconciliation (06)

`ObservationReplicationPump` и `MonitoringCoordinator` используют существующие RevisionDispatcher/transport/DotNext apply. Первый передаёт durable capture по принятому sequence ACK; второй допускается только локальным текущим leader с актуальным term и uncancelled leadership/consensus tokens после recovery/catch-up. История до watermark обрабатывается bounded и с ротацией целей, затем принимается live evaluation и состав backlog. DeliveryStateConfirmed проверяется отдельно до summary planning; неизвестный порт не заменяется Ready.

Внутренняя monitoring provenance имеет admitted OriginNodeId/storage generation и системный source, без Administrator actor. Пользовательские команды сохраняют accepted Administrator authorization. Trusted RecoveryAdmission содержит MonitoringNodes; snapshot должен совпадать с ним, SQL recovery дополнительно сверяет ClusterMember и monitoring projections. Membership provisioning и подтверждение native результата подключены через lifecycle 09.

`ClusterMonitoringWorker` зарегистрирован в Web composition root; cycle/capture имеют инфраструктурные scoped границы. Peer health включает безопасный MonitoringProgress без payload. Capture не требует главного, рабочие checks требуют CanWork и сохраняют RecoveryVersion. Успешный CanConnect или replay без ConfirmRecovery не снимает latched apply fault. Disabled завершает новый worker без действий. Activation/browser/sender gates открывает только controlled lifecycle после проверки всех зависимостей; текущая установка не включалась; детали — [Monitoring.md](Monitoring.md#распределённый-путь-этапа-06).

## Реализованная граница этапов 03–07

`Application/Cluster` содержит независимые recovery/accepted-state/trust/consensus контракты, readiness, membership coordinator, окно подтверждённой готовности главного и sender gate. `Infrastructure/Cluster` содержит DotNext adapter, state machine boundary, защиту дискового состояния, mTLS/envelope/replay и probes. `Web/Cluster` управляет отдельным peer-периметром и жизненным циклом DotNext.

Этап 04 подключил `RevisionClusterRecovery`, production reducer, SQL apply/replay, очередь Pending и streaming snapshot; 05.1 — чтение принятого аккаунта и active Administrator policy. 05.2–05.4 подключили общий sign-in/сессии и команды аккаунтов; 06 подключил monitoring capture/reducer/coordinator; delivery worker подключён в 07; UI и включение — 08/09. Production graph использует SignedRecoveryAdmission, AcceptedPeerTrustSource и AcceptedClusterAdministrationState; Unavailable-реализации не являются доказательством готовности. Web graph использует DeliverySenderConsensus, самостоятельный Infrastructure module сохраняет UnavailableSenderConsensus. Admission требует настоящих identity/checkpoint и подписанного подтверждения ручной изоляции до создания WAL; без них enabled-конфигурация Raft не запускает.

`Disabled` сохраняет однопроцессное поведение. Любой enabled-режим не регистрирует прежние monitoring/outbox workers, блокирует прежний `INotificationSender`. Browser endpoints закрыты до подтверждённого controlled enable; peer-perimeter проверяется отдельно. Legacy startup migrations/bootstrap пропускаются: заранее подготовленная схема и точный accepted bootstrap account не подменяются прежним startup. Наличие классов этапа 03 не разрешает controlled enable.

## Долговременный Raft

Используются `DotNext.Net.Cluster` и `DotNext.AspNetCore.Cluster` **6.10.0**, upstream commit `3499aedecf58b3c27a5d87af700d99e6b973cfde`. Majority commit, prevote/election, term и step-down выполняет DotNext. Production adapter вызывает `IReplicationCluster<IRaftLogEntry>.ReplicateAsync`, затем ждёт фактического apply через Context и `WaitForApplyAsync`; собственных Append/Commit или второго алгоритма согласования в adapter нет.

Порядок старта:

1. Проверить локальные БД и часы. `IClusterRecovery.RestoreAsync` обязан подтвердить identity/storage generation, отсутствие клона/fencing и checkpoint, восстановить snapshot **до** создания `WriteAheadLog`.
2. Захватить эксклюзивный `instance.lock`, проверить офлайн provisioned `manifest.json`. Только первый `Bootstrap` с непустым BootstrapId разрешает ColdStart. Маркер `started` записывается с flush; повторный запуск требует прежних `wal/state` и `membership`. Отсутствующие/усечённые файлы не превращают старый узел в новую сетку.
3. Создать отдельный DI-контейнер DotNext без запуска host. `WriteAheadLog` использует CRC64, `FlushInterval=0`, `FlushOnCommit=true`; term/vote/log и persistent configuration расположены под отдельным `StoragePath`, вне SQL и wwwroot.
4. Инициализировать WAL/replay; `ConfirmLocalReplayAsync` должен проверить committed/applied index и persisted membership version. Только затем вызвать DotNext Start и открыть native RPC. Неподтверждённый replay закрывает старт.

Storage имеет процессный lock; доверенная пара NodeId–URI и storage generation не допускают второго адреса с тем же NodeId. Копирование всей машины вместе с ключами/lock-файлами на другой диск не решается локальным FileShare.None: recovery-порт обязан потребовать внешний fencing, а 09 — обеспечить процедуру. Полный клон не признаётся безопасным автоматически. Прерванный первый bootstrap с `started`, но неполным WAL требует отдельного восстановления; автоматической очистки нет.

Новая provisioned сетка начинает с одного голосующего и большинства 1. Restart сохраняет принятый состав; отсутствие двух узлов трёхузловой сетки не позволяет пересоздать singleton. Failure detector с удалением участников не регистрируется. Состав меняется по одному через DotNext Add/Remove, с проверкой persisted version под lock, leader/consensus cancellation и request timeout. Сохраняемый membership не выводится из health.

`MembershipCoordinator` требует достоверный UserId, принятого active Administrator и подтверждённое принятое право/trust/предыдущую сверку из `IClusterAdministrationState`. Запрещены удаление последнего, подмена адреса и клон NodeId. Перед операцией закрывается sender, выдерживается 22 с drain; после drain повторяется проверка принятого аккаунта; после операции нужны strong read barrier, ожидаемый состав/версия и подтверждение принятого результата. При неопределённости sender остаётся закрыт до сверки и нового принятого sender epoch. Логи содержат только actor/node/change IDs и закрытый outcome; успех не пишется до подтверждения. Создания/отзыва trust credentials через старую cookie нет: изменения trust проходят принятый lifecycle с повторной авторизацией, используя тот же журнал.

## Peer transport

Peer host и локальный порт отделены от browser host/порта. `ConfigureClusterListeners` требует именованные Kestrel endpoints `Peer` и `Browser`, заранее проверяет локальный client key/certificate/CA и SAN identity. Прямой HTTPS требует client certificate; цепочка проверяется по закреплённому private CA с clientAuth/revocation. Middleware до forwarded headers и cookie authentication дополнительно проверяет SHA-256 pin принятого credential, SAN URI `urn:uptimeharbor:{ClusterId}:{Generation}:{NodeId}`, validity и accepted trust.

Для `NginxIsolatedHttp` TLS/mTLS завершается на отдельном Nginx peer virtual host. Внутренний HTTP доступен только Nginx через loopback/изолированную сеть; firewall и запрет прямого ingress обязательны. Приложение доверяет certificate headers только от точного IP allowlist на peer-порту, при `Ssl-Client-Verify: SUCCESS`; URL-encoded `Ssl-Client-Cert` содержит публичный PEM. Nginx должен перезаписывать эти headers, проверять CA/CRL и отключать TLS early data. Обычные forwarded headers такого доверия не дают. Browser virtual host не запрашивает client certificate. Проверка server hostname/публичного TLS certificate в исходящем клиенте не отключена.

`X-UptimeHarbor-Peer` ограничен 4096 символами; содержит ClusterId/generation, sender/recipient NodeId, storage generation, CredentialId, compatibility, RequestId, timestamp и challenge. Совместимость строго `1.0/1/1/1/1/6.10.0`; время ±30 с. Ответ обязан совпасть по request/challenge и принятой идентичности. Cookies/Authorization, redirects, proxy и HTTP logging исходящего peer-клиента отключены. Native `X-Raft-Node-ID` связан с accepted URI, term/state version проверяются отдельно; admission не имеет права голосовать. Native retries остаются в журнале DotNext.

Прикладной health nonce сохраняется на 2 минуты в эксклюзивном локальном inbox с flush/atomic replace; дубль получает 409. Nonce не является бизнес-идемпотентностью. Health ограничен 64 KiB, application entry — 256 KiB; envelope/options ограничивают batch 1 MiB/100, command 256 KiB и snapshot chunk 16 KiB–1 MiB. Native HTTP имеет отдельный предел 64 MiB: это не прикладной batch/chunk API. Kestrel ограничивает входящий поток, health reader ограничивает фактически прочитанные байты. Ответ native ошибки не передаёт текст исключения. Peer health содержит только reason codes, IDs, term/indices и возраст, без credentials, token и payload.

Доменные сертификаты обновляются независимо от NodeId. Ротация client CA/credential требует принятого trust и процедуры 04/09; секретный CA key не находится на узлах, приватные ключи не реплицируются. Реальная настройка Nginx/CRL/renewal не выполнялась.

## Диагностика и lifecycle

`NodeReadiness` хранит известный результат и monotonic age. Просроченный результат становится Unknown/Stale. `ClusterDatabaseProbe` проверяет собственную БД с timeout; отказ немедленно закрывает CanWork/CanSend и новые ACK/vote/writers. Supervisor закрывает RPC и останавливает DotNext, сохраняя файлы и состав. Старое доказательство recovery инвалидируется. После ремонта нужны restore/replay и новое подтверждение accepted applied prefix; прежняя sender authority не восстанавливается. Восстановленный узел начинает обычное участие как follower, роль далее определяет DotNext.

Отсутствие peer-ответа означает только PeerUnavailable, без утверждения об удалённой БД/боте. Результаты прямых polls имеют возраст; health-quorum требует одинаковых term/membership/leader и свежих взаимных прямых подтверждений одного большинства. Одна жалоба, односторонняя связь или partial-доступность обычной monitoring-цели не дают права сменить исправного главного.

Apply fault в state machine сохраняется отдельно от connectivity probe: успешный CanConnect не снимает запрет native ACK/vote. Снять fault может только достоверное подтверждение Restore/replay и SQL cursor после проверки committed/applied/membership. Сам Restore оставляет Projection=Unknown; аккаунты во время replay недоступны. `Invalidate` удерживает accepted reader закрытым до подтверждения восстановления даже после следующего Publish. Подтверждение recovery привязано к RecoveryVersion начала проверки: новый отказ во время SQL verify не позволяет устаревшему результату открыть reader. Recovery сверяет полный account/role/credential/tombstone набор с принятым образом; одного совпадения cursor недостаточно. Исключение reducer/provider заменяется безопасным сообщением без исходного inner payload до передачи DotNext и HTTP middleware.

`TelegramHealthProbe` использует только `getMe`, максимум раз в минуту, timeout 5 с, body 64 KiB, health lifetime 90 с; BotId должен совпасть с configured ожидаемым общим ботом. Чатовые Forbidden/ChatNotFound/InvalidChat и rate limit не объявляются общим outage. `getMe` не доказывает доступность каждого чата и не отправляет тестовых сообщений. Готовность worker не выводится из HTTP 200: `MonitoringProgressWatchdog` ждёт реальный завершённый цикл; ClusterMonitoringWorker подключён к этому контракту.

## Главный и sender authority

Таймеры DotNext: election 30000–36000 мс, HeartbeatThreshold=1/6, RPC 3 с, request 10 с, AggressiveLeaderStickiness=true, встроенная lease выключена. Health polls — 5 с. Последнее подтверждение готовности обновляет только свежий matching ready proof текущего лидера. Без успеха 30 с одно и то же подтверждённое большинство инициирует relinquish и блокирует старые RPC лидера этого term; дальше выбирает DotNext. Неуспешные проверки окно не сдвигают. При известной собственной неисправности gate закрывается и лидер resign немедленно. Это не норматив срока избрания/восстановления.

`SenderAuthorityGate` требует текущие cluster/generation/term/membership/sender epoch, leader и consensus cancellation tokens, accepted account/snapshot/catch-up/activation/manual enable/delivery state и свежую readiness. Ни Leader, ни локальная lease сами по себе недостаточны. После смены роли/epoch/состава — drain 12 с; renewal с уникальным round должен быть принят/применён, срок считается от начала запроса и не превышает 10 с. ClusterDeliveryWorker обновляет authority примерно раз в 5 с. BeginAttempt тоже требует принятого applied результата, а финальная проверка выполняется не позднее 2 с от начала. Потеря условий закрывает новые попытки и отменяет in-flight scopes best effort; внешняя отправка не атомарна с отменой.

Monotonic watchdog проверяется каждую секунду; pause более 5 с или wall-clock drift более 2 с закрывает gate, clock fault требует сверки/перезапуска и повторного recovery. Обнаружение скачков не доказывает внешнюю синхронизацию часов и предел относительной скорости 1.1 из протокола. Authority не сохраняется в snapshot/SQL. Renewal worker и transport распределённой доставки подключены в 07; реальные отправки требуют controlled enable и всех настоящих проверок, в этой задаче не запускались.

## Команды, очередь и snapshot

`PendingCommandService` получает actor/origin из доверенного контекста и сохраняет защищённый Data Protection payload локальным UoW. `RevisionDispatcher` передаёт команды единственному DotNext writer. `RevisionReducer` детерминированно решает commands/controls: active accepted Administrator и actor revision, base, уникальность, зависимости, конфликты и tombstones. SQL changes/receipt/cursor фиксируются одной транзакцией; `RevisionApplyEngine` публикует immutable образ после commit. Повтор OperationId возвращает прежнее решение без новой entity revision и side effect.

`PendingAdmissionGate` сериализует локальный приём между scopes: максимум 10000 незавершённых записей, из них 1000 зарезервировано для cancel/replace. Retry известного ID не занимает новое место; при заполнении новая заявка получает PendingQueueFull. Это backpressure одного экземпляра NodeId, не multi-process locking. `PendingReplicationPump` выбирает ограниченные SQL-страницы. Account.*, Delete/Cancel/Replace идут каждую секунду; настройки — раз в `ConfigurationIntervalSeconds` (60–3600, кратно минуте). Retry 1/2/5/10/30 секунд с jitter до 20%; batch ≤100/1 MiB, actual stream bounded. Весь входной пакет проверяется до dispatch, весь ответ — до локального разрешения Pending. Нет общей транзакции для нескольких Raft-команд: после частично принятого пакета retry возвращает прежние решения. Неверный ответ не сдвигает local result state. Порядок committed log обеспечивает DotNext; error apply закрывает cursor/readiness.

`ReplicationProgress` в peer health содержит только backlog/counts, oldest age, applied index и reason code. Browser UI использует безопасную проекцию после accepted authorization и controlled enable. Три узла и около 30 приложений с минутными проверками — проектный ориентир; часовая цель фактически не наблюдалась.

`RevisionSnapshotStore` пишет bounded streaming files: magic/manifest/body, revision/term/compatibility, SHA-256 тела/файла и chunks. Receiver использует chunk size manifest. Max 64 MiB с резервом под native envelope, проверка дискового места, WriteThrough/Flush(true), atomic file move. Это настройки реализации, не доказательство power-loss durability. Current меняется только после SQL checkpoint/install; failed import удаляет temp. `SnapshotProjectionUnitOfWork` заменяет whitelist общих rows одной внешней транзакцией; локальные counters, SessionEpoch, сессии, ключи и Pending сохраняются. Stale credentials/account history и cursor отвергаются.

Recovery до native Raft устанавливает snapshot, затем воспроизводит принятый WAL; SQL может опережать snapshot, поэтому receipts проверяют повтор apply. Только подтверждённый committed/applied/membership и SQL cut открывает accepted account state. Старый backup сначала сверяет OperationId/decisions/controls; неизвестные Pending удерживаются до новой авторизованной Replace-команды с актуальной базой. Обычный restart актуального состояния не требует подтверждения.

DotNext watermark и latest snapshot ограничивают reclaim файлов. Decisions/controls/tombstones и версии сохраняются в образе на срок generation; отставший узел без WAL получает snapshot. Календарная история очищается отдельной policy/query, cleanup worker не добавлен. Открытые incidents/conflicts, Pending, intents и необходимые summary dependencies не удаляются.

## Проверка и пределы доказательств

Фактические команды и результаты — [Testing.md](Testing.md#проверка-этапа-10). Изолированные тесты вызывают production gate/perimeter/probes и настоящий DotNext WAL/configuration. ## Аккаунтный bootstrap и восстановление (05.4)

`ClusterAccountBootstrapper.PrepareAsync` доступен только Bootstrap и готовит точную команду с защищённым credential; он не сохраняет её самостоятельно и не является эксплуатационной процедурой. Внешний trusted lifecycle обязан долговременно сохранить подготовленную команду и включить её в RecoveryAdmission. До native Raft recovery связывает образ с её digest; reducer разрешает BootstrapAccount только при точном совпадении и отсутствии любой истории аккаунтов. Join/Restart берут общие ID из snapshot/replay.

После подтверждённого replay локальный Bootstrap leader может подать только эту команду через существующий DotNext writer. Узкое исключение требует единственного voting NodeId, проверенных snapshot/catch-up/membership и исправных Database/Storage/Clock/Projection. Payloadless native no-op учитывается proven applied index. Общий CanWork/browser/worker/sender от этого не открывается. Admission/trust/activation/delivery по умолчанию остаются закрыты; фиктивных аккаунтов или proof нет.

Обычный разрыв peer-связи не инвалидирует достоверный принятый account image. Неизвестное восстановление или локальная неисправность закрывают account reader и отзывают сессии/SignalR; успешный CanConnect лишь сообщает connectivity. Возврат доступа требует достоверного recovery и сверки проекции/догона. Старый snapshot с последующим WAL replay не возвращает старые credentials или удалённый аккаунт.
