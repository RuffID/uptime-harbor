# Локальная первоначальная настройка

## Дополнения этапа 04: текущая граница

Добавлены локальные issuer/signing repositories/UoW и AES purpose `issuer` с AAD по epoch. `ReconcileAll` проверяет exact installation/cluster/generation/node/storage issuer refs, отвергает duplicate/foreign refs и неизвестные файлы. Production Bootstrap использует эти refs; самостоятельное создание issuer key не разрешает restart и не активирует credential. Private material не попадает в shared snapshot.

InstallationLease создаёт новый 256-bit BootChallenge на каждый процесс. Schema-3 accepted attempt сохраняет challenge и authorization index. Production ISetupAuthority/IManagedRuntimeAdmission подключены для нового первого и узкого trust/admission второго; resume сверяет прежние IDs/key и новый accepted ProcessEpoch после старой lease. ManagedRestart целого sealed storage подключён к новому первому, без повторного BootstrapAccount и без majority до карантинного native Start; CommonOpen требует свежего barrier/Enable. Для завершённого Join этот путь ещё не доведён. [Точная реализованность 04 и оставшийся объём](Onboarding%20contracts.md#промежуточная-граница-этапа-04-2026-11-03).

Поверх подготовительного этапа 03 подключён production Bootstrap нового первого: отдельный common account, quarantine singleton, accepted baseline/account/process/activation/enable и отзыв setup перед CommonOpen. Join проходит dedicated E1–E4 trust/admission и peer probes, но его runtime/snapshot/membership остаются закрыты до 05. Этап 04 ещё выполняется; точная текущая граница и собственные gaps — [Onboarding contracts](Onboarding%20contracts.md#промежуточная-граница-этапа-04-2026-11-03). Evidence от double и local save не являются production authority.

Работа над 04 приостановлена по просьбе пользователя 2026-11-03. [Точка возобновления](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust.md#результат) содержит обязательный остаток, известные проблемы seal/роста steps/порядка Mode-проверки и незакрытый повтор preflight. Минимальный Setup UI ещё не вызывает Join enrollment и сохраняет устаревший текст о закрытом доверии; API и UI пока не согласованы полностью. Реальная SQL/Ubuntu/TLS/fsync приёмка не выполнена.

## Вход и границы доступа

До Build `ConfigureLocalInstallation` читает явный `Installation:InstallationIntent=Setup`, получает installation/storage locks и задаёт DP application identity по постоянной InstallIdentity. Legacy initialization не выполняется. В Setup обязательны заранее подготовленная SQL schema и защищённые BootstrapAdmin credentials; приложение не применяет migrations, не делает backup, не переписывает конфигурацию.

Под lock создаётся ровно одна LocalSetupAccount вне users/roles: Identity V3 hash, stamp, lockout, CreatedForInstallIdentity. Пустой, короткий или примерный initial password отвергается. Нет register/first-visitor endpoint; первый посетитель не выбирает пароль. Повторный initialization не читает новый config как команду сброса/включения аккаунта. Посторонний legacy admin не преобразуется в setup identity. Потеря локального доступа требует отдельного обслуживания по месту установки.

Cookie: scheme `LocalSetup`, name `__Host-UptimeHarbor.Setup`, Secure/HttpOnly/Strict, session cookie без remember-me. Отдельный DP purpose `LocalSetup/{InstallIdentity:N}` + `Cookie/v1`; idle 15 минут со sliding expiration, абсолютный TTL 30 минут по неизменному StartedAtUtc. Каждый запрос с setup cookie проверяет InstallIdentity, stamp, epoch, BootId, phase и отсутствие disabled/hash removal. Смена процесса повышает epoch/generation и отзывает прежнюю cookie, сохраняя попытку.

`/api/setup/session` выдаёт antiforgery token текущей identity. После login клиент получает новый token. Login/prepare/logout требуют antiforgery; boundary дополнительно сверяет точный HTTPS Origin и Host с BrowserOrigin. Rate limit — 10 запросов в минуту на IP; local lockout — 5 ошибок / 5 минут. Все setup routes/assets имеют no-store и общие security headers. Разрешён только точный whitelist страницы, API и её ресурсов. Setup cookie не принимается common API; common cookie не даёт setup-права.

При финальном переходе `AwaitingActivation → ClusterReady` production authority сверяет accepted online Enable текущего процесса после отдельной activation. В одной локальной транзакции удаляется setup hash, устанавливается Disabled, меняется stamp/epoch и профиль. После durable результата runtime повторяет admission/CanWork и публикует CommonOpen. Сбой оставляет FailedNeedsAction и закрытый доступ; config не восстанавливает hash. Этот путь подключён для нового первого, доставка Telegram остаётся закрыта до 05а.

## Preflight и локальное состояние

Минимальный preflight читает pending migrations и каждый корневой mapped EF entity/table, включая shared account/role/claim/login/token/membership, identity/cursor, Pending/capture/results/outbox и остальные очереди. Любая рабочая строка блокирует новый путь. Разрешены только четыре собственные локальные setup/progress-таблицы и локальные data_protection_keys; их принадлежность и согласованность проверяются отдельно. Проверяются единственный профиль/account, InstallIdentity, попытка/шаги/OperationIds и key references. Чужая identity, orphan progress/account или старый storage/manifest не очищаются и не объединяются. Непустой первый standalone направляется в 03а/03б.

Проверяются версии `2.0/2/2/2/1/6.10.0`, заранее подготовленный отдельный Direct peer endpoint, абсолютные непересекающиеся state/secret/key/storage пути, отсутствие symlink/reparse ancestors, права и минимум 64 MiB свободного места на каждом томе. В новом cluster storage допускается только installation.lock. Недостающий listener — отказ preflight, не restart из HTTP.

URI обязан быть canonical HTTPS `/internal/raft`, без userinfo/query/fragment. Loopback/link-local/metadata/multicast запрещены; private/VPN IP допускается только AllowedPeerNetworks. Managed outbound ConnectCallback заново разрешает DNS на каждом connect, отвергает весь набор при запрещённом IP и соединяется с выбранным проверенным IP, сохраняя TLS SNI. Redirect/cookies/proxy отключены. Локальная проверка конфигурации **не является двусторонней TLS-пробой**: настоящая проверка доступности enrollment/peer и authenticated descriptor выполняется реальной authority этапа 04 перед выдачей evidence/допуска. В этом объёме такой production adapter отсутствует, поэтому доступ закрыт.

LocalInstallationProfile/LocalAttemptStep содержат immutable mode/phase, revisions/generation, InstallIdentity/BootId/lease/epoch, AttemptId/NodeId/storage, request digest, исходные OperationIds, expected result и evidence. LocalSetup и OnboardingProgress используют раздельные сценарные UoW на существующей EF session; глобального UoW нет. CAS запрещает замену чужой revision или изменение исходной request/key/operation identity. Начальный local intent и authority step сохраняются **до** внешнего эффекта. Network timeout — 10 секунд, неизвестный ответ сохраняется как AuthorityResultUnknown; повтор использует прежние IDs и исходные revision/generation authority step. Поздний callback не публикует результат нового поколения.

Новый первый подготавливает отдельный UUID/роль/credential/BootstrapAccount digest, зашифрованный локальный command reference и собственный ClusterId. Setup account в accepted users не копируется. Публичный BotId берётся из положительного локального ExpectedBotId либо bounded getMe локального токена будущего sender; браузер не задаёт BotId. Отсутствие обеих возможностей блокирует только подготовку первого. Join сохраняет собственные NodeId/storage/AttemptId/private key, не создаёт Bootstrap/common account и не задаёт ClusterId/BotId самостоятельно. Их authenticated получение относится к 04/05; Join authority-порт уже принимает контракт LocalOnboardingAttempt этапа 02.

ProtectedInvitation хранится AES-GCM envelope непосредственно в локальной SQL attempt, привязанный к InstallIdentity/AttemptId. После подтверждённого reserve поле удаляется; encrypted invitation не создаёт отдельный orphan-файл. Accepted reserve не меняет исходные IDs/request/key. Эти локальные таблицы, setup credentials, DP keyring и private references не входят в общие replication/snapshot whitelist.

## Файлы и восстановление

Wrapping key (32 bytes) создаётся автоматически под installation lock в отдельном persistent secret volume. Private PEM и отдельный BootstrapAccount command шифруются AES-256-GCM; AAD включает InstallIdentity/AttemptId/purpose/file ID. SQL reference содержит случайный file ID и SHA256 envelope. Путь из reference не принимается; размер/version/digest/AAD/права проверяются до использования. DPAPI не применяется. DP keyring находится в защищённом state/data-protection, его не переопределяет SQL key repository.

Linux private directories/files — 0700/0600; Windows ACL разрешает service identity и Administrators. Уже существующие неверные права вызывают отказ. Запись: случайный temp → Flush(true) → rename без overwrite → Linux directory fsync → SQL ref. После сбоя сверяются SQL/files; повреждённый ref, пропавший wrapping key при существующих keys, неизвестный файл или orphan temp требуют действий. Они не выбираются по дате/имени, не усыновляются и не удаляются автоматически. Перезапуск сохраняет ту же попытку; новый BootId ждёт expiry прежней двухминутной локальной lease, прежние grants не переиспользует. Supervisor обновляет локальную lease каждые 30 секунд; это не accepted ProcessEpoch/renewal будущей authority.

Locks на state, secret, keys и storage удерживаются весь срок процесса с FileShare.None до чтения install.id и preflight. SQL identity/revision защищает согласование локальных путей с профилем. Полный побитовый клон с ключами на другом диске криптографически неотличим; он не получает isolation proof. Реальная authority дополнительно проверяет registry/address/SPKI/ProcessEpoch; до неё production runtime закрыт. Clone/backup/rejoin не являются свежим Join.

## Inventory runtime и остановка

Root hosted owner один — ManagedWorkerSupervisor. ManagedWorkerCatalog разрешает конкретные workers только после выбора группы/admission. В Setup при старте рабочих loops и WAL нет. В обычном Disabled работают только прежние monitoring/outbox; их singleton registration не означает запуск. DI selectors sign-in/account/administration/recipients выбирают adapter по immutable active profile в новом scope; singleton компоненты читают актуальный профиль через ActiveClusterOptions. Operator config не мутируется.

| Компонент | Владелец задач и освобождение |
| --- | --- |
| MonitoringWorker → MonitoringCycleRunner | Legacy group; await всех per-target checks через WhenAll; отдельные scopes, keyed entries удаляются в finally, передаётся cancellation |
| TelegramOutboxWorker → TelegramOutboxDispatcher | Legacy group; await DispatchDueAsync и отменяемого poll delay; DB gate/результат завершаются до выхода |
| ClusterHealthWorker → Database/Telegram probes, PeerObservationCapture | Quarantine group; using PeriodicTimer, await bounded Parallel.ForEachAsync/probes/capture; HTTP responses/streams/CTS/scopes освобождаются; stale callbacks не публикуют Ready/connection |
| ClusterPeerRuntime → child DotNext, WAL/configuration, inbox, storage lease | Quarantine group; checkpoint/recovery до resolve WAL; native Stop await под lifecycle/membership locks, child provider DisposeAsync, inbox/lease Dispose в finally; RPC/sender закрываются перед stop |
| ClusterLifecycleWorker → MembershipCoordinator/dispatcher | Quarantine group; await текущего цикла, membership lock освобождается в finally. Managed path не создаёт прежний sender epoch |
| ClusterRevisionWorker → PendingReplicationPump | Quarantine group; последовательный await RunOnce, bounded batches и scopes; pump не имеет отдельного detached loop |
| ClusterSnapshotWorker → RevisionClusterRecovery/RevisionSnapshotStore | Quarantine group; await snapshot/reclaim, cancellation timer; temporary streams/files имеют finally; generation проверяется до rename/publication |
| ClusterMonitoringWorker → ClusterMonitoringCycle/ObservationReplicationPump/MonitoringCoordinator | Только Ready group; await cycle/pump/coordinator, per-target scopes и cancellation. Дочерних hosted registrations нет |
| ClusterDeliveryWorker → AcceptedDeliveryDispatcher/consensus/transport | Старый enabled path сохранён. В новом managed Setup worker не запускается, dispatcher дополнительно закрыт до 05а |

Переходы: `SetupReady/StandaloneReady → Preparing → Quiescing → LocalPrepared → ClusterQuarantine → CatchingUp → AwaitingActivation → ClusterReady`, отдельно Paused/FailedNeedsAction. Поддержанный вход текущего этапа — новая SetupReady; действующий standalone проходит 03а/03б. Одна смена mode не включает runtime.

Порядок locks: installation transition → supervisor lifecycle → PeerRuntime lifecycle → membership → scoped projection/write operation. RuntimeWriteGate закрывается перед cancel/drain; leases охватывают HTTP/worker operation до commit/transport. SQL transaction не удерживается во время network/runtime/file effect. Quiescing повышает RuntimeGeneration, supervisor отменяет и ждёт все прежние tasks максимум 10 секунд. Failed drain запрещает новый старт. Частично запущенная группа закрывает gate и останавливается; неизвестный effect сохраняет FailedNeedsAction. Неожиданное завершение managed loop закрывает gate, сохраняет failed профиль и дренирует группу; Web-host не перезапускается как способ перехода.

Каждый loop захватывает неизменное поколение в AsyncLocal context. Перед sync/async EF SaveChanges, transaction commit, peer/Telegram send, accepted/health/snapshot publication проверяется generation. Старый callback не открывает Ready и не выполняет запись/отправку нового поколения. Одновременный или повторный start до полного stop запрещён; расширение quarantine → Ready в том же поколении не стартует прежние loops второй раз.

## TLS, логи и пределы проверки

Peer socket Direct/TLS passthrough готовится до Build. DynamicPeerTls отдаёт certificate/trust snapshot только для текущего поколения и разрешённой фазы; пустой provider закрывает TLS, HTTP gate остаётся закрытым до quarantine/admission. Managed HTTP повторно проверяет accepted pin, CA fingerprint, SAN/EKU/expiry. Dynamic chain использует offline revocation и закрывается при отсутствии нужных revocation данных; accepted validator этапа 04 обязан проверять актуальную revocation/purpose. Пулы нового пути не переиспользуются. Legacy Direct online CRL и NginxIsolatedHttp proxy allowlist/headers/CRL не ослаблены; приложение не управляет Nginx.

Setup/preflight/runtime/authority события используют существующий ILogger/Serilog после соответствующего durable результата: SetupPrepared, SetupPreflightCompleted/Rejected, SetupLoginAccepted/Rejected/Locked, RuntimeTransitionStarted/Committed/Resumed/Failed, SetupAccessRevoked, SetupAuthorityDeferred/EvidenceRecorded. Только безопасные ID, phase, revisions/generation, evidence kind и закрытый reason code. Пароли, hashes/stamps/cookies, invitation/verifier, private material, connection strings, URL токена и payload не журналируются. EvidenceRecorded — не Bootstrap/Join/Ready success.

Изолированно проверены takeover/config reset, cookie/CSRF/Origin/Host, непустота mapped таблиц и orphan local state, exclusive file handle, failed drain/double start/stale callbacks, restart с прежними IDs, потеря authority ответа, удаление protected invitation после reserve, AES/ref corruption/orphans, отдельный common account, отзыв setup до runtime publication, closed default authority/DI и независимость consensus от Telegram. Точные команды/счётчики — [Testing.md](Testing.md#локальный-setup-этап-03).

E4 хранит immutable trust intent/ref в LocalOnboardingAttempt и protected manifest на state volume; частичный файловый эффект завершается только повтором того же intent. Startup сверяет refs/leaf/key/registry и запрещает orphan files. Managed restart нового первого читает AEAD `managed-storage.seal`, точные snapshot/SQL head/manifest и целый WAL. SetupInitialization сначала читает прежний profile, затем preflight; обычный restart не направляется в перенос standalone. Supervisor запускает карантин без majority, позднее новый process grant/Enable открывает доступ. Old grants не читаются как локальная authority. Текущий checkpoint обновляется после каждого apply; нагрузочная стоимость и crash/fsync требуют отдельной проверки.

Не проверены SQL provider locking/atomicity/DDL, настоящий второй OS-процесс, Ubuntu ACL/fsync/power loss, Kestrel bind/горячая TLS-замена/CRL/DNS и двусторонняя сеть, browser rendering и переключение работающего окружения. Полный Join/snapshot/membership — 05, перенос — 03а/03б, sender — 05а, мастер — 06; оставшиеся обязательства 04 перечислены в актуальных контрактах.
