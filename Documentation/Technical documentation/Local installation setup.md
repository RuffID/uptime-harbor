# Локальная первоначальная настройка

## Дополнения этапа 04: текущая граница

### Подготовка локальной ротации voter до Bind (04.09-B2a)

`Installation/Renewal/LocalVoterCredentialPreparation` использует прежние InstallationLease/InstallationState.Transition, LocalSecretStore и ProtectedInstallationFiles. Подготовка сохраняет новую P-256 пару, подписанный CSR, исходные OperationId/IssueId/serial/template и references прежнего ключа **одним immutable AEAD bundle** до передачи intent наружу. Секретный PKCS#8 — бинарная часть защищённого bundle; публичные модели, логи, SQL и общий snapshot его не содержат. Прежний ключ/профиль не изменяются и не удаляются. Подготовку вызывает scoped проход worker после рабочего допуска.

Локальный slot — domain-separated SHA-256 от installation/cluster/generation/node/storage/previous credential. Он находится в `SecretDirectory/voter-renewal/<slot>/`; файлы `intent`, `authorization`, `artifact` используют отдельные stage bindings внутри AEAD purpose `voter-renewal`. После защищённого temp/Flush(true)/rename выполняется прежний Linux directory fsync; новые родительские каталоги и повторное чтение также синхронизируются. Windows использует существующий WriteThrough/Flush primitive; физическая power-loss durability этим не доказана. SQL schema и migrations не изменены; SQL reference/активный профиль ещё не публикуются.

`PinAuthorizationAsync` и `PinArtifactAsync` сами вызывают прежний B1 `ConfirmSigningAsync` с новым majority barrier и точными saved NodeId/storage/request/CSR. До записи проверяются current voter/revision/process/old-key proof и exact committed Authorize/result/index/digest, активный issuer, ответ и X.509. Authorization pin сохраняет исходный public anchor и accepted rotation; artifact pin — точные DER/fingerprint/template/request digests. Другой даже валидный DER с тем же template не заменяет сохранённый файл. Повтор после неизвестного результата записи возвращает прежние bytes; изменённые payload/ref/key/CSR/index отвергаются. События IntentSaved/AuthorizationPinned/ArtifactPinned содержат только безопасные IDs/index после записи и проверочного чтения; повтор не создаёт второй success.

`ReadAsync` заново проверяет AEAD/install/slot, private/public key, подписанный CSR, historical authorization/issuer/template и DER/SAN/fingerprint. Чтение не вызывает signer или сеть и возможно после Bound/retirement/expiry для последующей reconciliation; это **не полномочие использовать credential**. Missing intent в существующем slot, missing authorization при наличии artifact, orphan temp, missing/corrupt wrapping/previous/new key и повреждённые pins закрывают чтение. Отсутствующий последний artifact до Bind остаётся незавершённой стадией, а не успешной установкой. Полный согласованный откат/удаление всех файлов и ключей локально неотличимы от отсутствующего store: перед любым внешним продолжением обязательно сверять accepted state. В B2a нет автоматического восстановления по новому signer request.

Bind intent/result (B2b1) и установка по прежнему материалу (B2b2) описаны ниже. Runtime TLS/pools/wire/DI/scheduler/retirement остаются B3. [Проверки B2a](Testing.md#voter-credential-local-prebind-0409b2a-2026-11-18).

В legacy Direct подготовка и pre-Bind используют принятый manual leaf и прежний защищённый reference ключа. Перед авторизацией и отправкой Bind проверяется настроенный ручной CA с online CRL. После принятого Bind reconciliation проверяет exact решение и dedicated leaf по принятому issuer epoch и revocation. Уже принятый Bind восстанавливается при потере ответа без повторного Send, даже если CRL для старого leaf недоступна. [Проверка legacy Direct](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09-b3b2-legacy-direct-and-nginx.md#voter-credential-legacy-direct-trust-0409b3b2).

### Локальные Bind intent и result voter (04.09-B2b1)

`LocalVoterCredentialBindingCoordinator` использует тот же InstallationState.Transition, защищённый slot и IRevisionTransport. До Send сохраняется `bind-intent`: исходная unstamped Bind-команда с отдельным OperationId, exact DER, ссылкой на Authorize OperationId/index и digests request/artifact. До каждого Send выполняется свежая B1 authority; после Send/restart — прежний majority barrier через `ReadBindingAsync`, с проверкой local node/storage/cluster и recovery version. Production DI/routes и RevisionDispatcher deny не меняются; обычный transport не получает новой dispatch capability.

`bind-result` сохраняет полный accepted CommandResult, digest всего локального Bind intent, BoundAtUtc/OverlapUntilUtc; CredentialRevision берётся только из accepted Bind index. Проверяются committed outcome/OperationId/digest/index/applied revision/term, exact rotation и реестр credential, issuer/template, private/public key/CSR/DER и текущая usable credential revision. После записи следует новая reconciliation. Transport response, подпись, локальный pin и один result-файл не означают установленную revision или Ready; local profile/common gate не меняются.

Неизвестный commit до принятого Bind допускает повтор только исходной команды. Lost response при уже accepted Bound восстанавливает result по прежнему intent и свежему срезу, включая retirement/expiry старого leaf. Missing intent/pins после Bound, повреждение ключей/DER, чужой result/revision или откат accepted cut ниже сохранённого result вызывают отказ. `ReadBoundAsync` требует обе записи и fresh evidence. `BindAsync` может восстановить отсутствующий result до начала локальной установки. Если стадии установки уже существуют, пропавшая Bind-запись закрывает recovery. Старые keys/refs/profile сохраняются. Физический fsync/power-loss, реальный второй OS-процесс, SQL/native majority/TLS/Ubuntu ACL требуют отдельных проверок.

[Проверки B2b1](Testing.md#voter-credential-local-bind-0409b2b1-2026-11-18).

### Локальная установка CredentialRevision voter (04.09-B2b2)

`LocalVoterCredentialInstallationCoordinator` использует тот же installation lock, Transition и AEAD slot. Manifest связывает slot с точным intent, authorization, CSR/SPKI, template, DER fingerprint, Bind evidence, IssueId и CredentialRevision. `install-reference` связывает установленную ревизию с digest manifest. `install-confirmation` закрепляет digest installed reference. Все три записи immutable и содержат accepted cut. Новый ключ остаётся в прежнем защищённом bundle.

`InstallAsync` сначала перечитывает исходные key/CSR/DER/template, exact committed Bind и fresh accepted evidence. После каждой записи проверка повторяется. Пропуск предшественника, изменение material/Bind, откат индекса или терма и конфликт digest на том же индексе прерывают операцию. Неполный хвост после сбоя возобновляется только явным InstallAsync по прежним данным. `ReadInstalledAsync` работает без recovery-записей и требует всю цепочку и свежий срез. При утрате Bind записей в slot с признаками установки даже BindAsync отказывает.

Старый материал сохраняется. Вызовы signer и Bind transport отсутствуют, включая recovery после retirement. Для полностью согласованного отката файлов и источника accepted evidence требуется независимый доверенный источник: файловая цепочка не различает такую копию и прежнее корректное состояние. Локальное подтверждение возвращает CredentialRevision и предшествует публикации. UI-приёмка ожидает пользователя в 07. [Проверки B2b2](Testing.md#voter-credential-local-installation-0409b2b2-2026-11-18).

### Локальная установка ContinueCredential (04.09.04)

`ClusterPeerRuntime.StartNodeAsync` уже владеет Transition. После проверки native membership и WAL ветка с истёкшим managed Bootstrap Direct leaf использует `RevisionClusterRecovery.VerifyManagedContinuationReplayAsync` и `VoterContinuationClient.ReadAcceptedSliceAsync`. `ManagedContinuationReplay` привязывает чтение к профилю, boot и recovery version. Для этого входа принятие локальных записей и первая публикация работают под тем же Transition на узком HTTPS срезе. [Контракт среза](Onboarding%20contracts.md#доказательство-continuecredential-040904).

Startup закрепляет в AEAD slot OperationId, IssueId, новый ключ, CSR и точный контекст исходного boot до первой отправки. После подтверждённого Request записывает его exact result и журналирует только `RequestId` в событии `VoterContinuationRequestAccepted` журнала восстанавливаемого узла. После принятого подтверждения общего администратора startup выполняет Register, получает DER, закрепляет регистрацию и DER перед Bind и устанавливает точный результат Bind. При неопределённом исходе следующий проход того же boot перечитывает защищённые записи и свежий срез перед очередным действием.

При смене boot после Bind startup читает тот же slot. Сначала связывает исходный Bind с сохранёнными Register и DER, затем после истечения прежней lease сохраняет отдельный AEAD intent и квитанции Request, Authorize и Register нового boot. После подтверждения общего администратора и точной регистрации он завершает Bind result и префикс установки с прежней выдачей. Свежий срез обязателен между durable записями и непосредственно перед публикацией. Путь работает и когда локальный replay уже содержит действующий bound leaf. [Проверки восстановления](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.04-continue-credential.md#nui-04-20261121-21).

Первая публикация в `DynamicPeerTls` привязана к проверенному локальному replay, свежему срезу и действующей continuation lease. Снимок становится недействительным при смене профиля, boot, recovery или истечении окна. До следующего этапа восстановления закрыты native Start, приём peer TLS, принятая локальная проекция, Ready и CommonOpen. [Проверки и стык startup](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.04-continue-credential.md#nui-04-20261121-19).

`LocalVoterContinuationInstallation` использует отдельный AEAD slot на ту же установку, кластер, NodeId, storage и прежний credential. До принятия запроса `PinIntentAsync` закрепляет исходные OperationId/IssueId, BootId/challenge, ссылки, ключ и CSR. После выдачи и до Bind `PinBindIntentAsync` закрепляет точную принятую регистрацию, DER и принятый срез. Вход установки сопоставляет полученную квитанцию с точным решением Bind в свежем срезе. При потере ответа `RecoverAsync` берёт тот же результат из accepted журнала. Сохранённая запись регистрации должна точно совпадать. Истечение её срока после принятого Bind допускает завершение локального хвоста в пределах действительности нового credential.

Результат Bind, manifest, installed reference и confirmation записываются по очереди под `InstallationState.Transition`. Продолжение перечитывает ключи, CSR, DER, неизменные NodeId/storage, accepted регистрацию, отзыв и CredentialRevision до подтверждения каждого шага. `ReadInstalledAsync` требует полный префикс плюс свежий срез. Подмена, дыра в префиксе и откат среза относительно сохранённых свидетельств закрывают установку. Полностью согласованный откат файлов и accepted источника требует независимого свидетельства. [Проверки локальной установки](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.04-continue-credential.md#nui-04-20261121-15).

`LocalVoterContinuationPublication.PublishAsync` требует подтверждённый slot, текущий профиль managed Bootstrap Direct, локальные BootId/challenge и свежий majority read. Публикация под тем же Transition импортирует закреплённый ключ и переключает TLS leaf, credential ID и выбор handler через общий `DynamicPeerTls`. До принятия точного ProcessRenewal снимок остаётся в транспортном карантине. Повтор после принятого Process заново сверяет тот же slot и accepted cut, сохраняя IssueId и CredentialRevision. Управление CommonOpen и Ready остаётся у штатного Activation/Enable lifecycle. Соединение первой startup-публикации с native Raft и отправкой ProcessRenewal удалённому лидеру остаётся открытым. ### Публикация CredentialRevision в managed Direct

`LocalVoterCredentialPublication` выполняется явно под `InstallationState.Transition`. Она заново проходит B2b2, сверяет подтверждение, исходный material, профиль, installation lease и прежний trust anchor. Импортирует pinned P-256 key и соединяет его с принятым leaf DER. Атомарная смена снимка допускается только пока тот же объект accepted image и RecoveryVersion актуальны под lock `RevisionStateStore`; stale runtime generation тоже запрещает публикацию. Повтор сохраняет снимок той же CredentialRevision. При закрытом состоянии успех создаёт снимок заново после полной проверки.

Повтор с новым lease, secret store и accepted store читает тот же slot. Повреждение/неполная цепочка, stale/conflicting cut или сбой закрывают managed peer. Публикация не дописывает B2b2 и не вызывает signer, Bind transport, активацию или изменение профиля. Прежний материал сохранён. Использование прежнего снимка прекращается по accepted overlap и trust policy. Каждый снимок имеет собственные исходящие TLS-наблюдения и пулы. Опубликованный снимок заново удостоверяет server leaf для своей локальной пары. [Привязка typed renewal](Onboarding%20contracts.md#voter-credential-typed-direct-0409b3b2).

В Bootstrap ManagedRestart исходный профиль и seal подтверждают восстановление прежнего storage. После replay WAL и проверки SQL/membership последнее committed Bind определяет точный slot по прежнему credential. Restart сверяет защищённый Bind intent, key/CSR/DER, exact accepted Bind и все имеющиеся стадии установки. Допустим непрерывный префикс стадий, начиная с bind-result. Если replay ещё не содержит Bind, допускается только точный защищённый префикс до Bind intent включительно с подтверждённым Authorize и действующим прежним leaf. Любая стадия результата или установки впереди replay, отсутствие исходных pins, повреждение и пропуск стадии закрывают запуск.

До majority снимок разрешён только для native Raft. После свежего majority, в том числе на follower, ManagedRestart повторно сверяет exact Bind и прежний slot. Он дописывает отсутствующий хвост bind-result/manifest/reference/confirmation, перечитывая материал и проверяя accepted cut после каждой записи. Рабочая TLS-публикация следует подтверждению установки. Обычный peer RPC использует рабочий снимок, а новый Process/Enable остаётся отдельным условием CommonOpen. Полностью согласованный откат accepted источника и всех локальных файлов остаётся за границей локальной проверки. [Проверки ManagedRestart](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09-b3c1-renewal-and-restart.md#voter-credential-managed-restart-0409b3c1).

### Изолированный сценарий renewal (04.09-B3c1)

В managed Bootstrap Direct координатор повтора получает исходный previous credential ID и issuer epoch. Для первого PoP используется профильный protected peer key, для следующего — ключ из защищённого bundle опубликованной CredentialRevision. Выбор требует рабочий снимок, exact accepted Bind, fingerprint и цепочку установки предыдущей ротации. После принятого нового Bind восстановление идёт по сохранённым pins и Bind intent до установки и публикации, с проверкой действующего нового leaf и свежим majority.

Изолированный тест координатора подставляет доступный accepted store. Отдельные тесты ManagedRestart открывают прежний локальный WAL на новых lease и проверяют прерывание после accepted Bind и после каждой последующей durable стадии. Оба пути сохраняют исходные IDs, key и DER. Штатная композиция использует те же pins и отдельный typed admission 04.09.03. [Граница и проверки](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09-b3c1-renewal-and-restart.md#voter-credential-managed-restart-0409b3c1).

### Worker расписания ротации

В рабочем managed Bootstrap Direct `ManagedWorkerSupervisor` выбирает `VoterCredentialRotationWorker` из каталога после допуска рабочей группы. Worker использует `RestartableWorker`, действующий RuntimeWriteGate и отдельный scope для каждого прохода. Первый проход выполняется при старте, следующие через одну минуту после предыдущего. До получения CommonOpen при ClusterReady Bootstrap Direct рабочие зависимости ротации не разрешаются. Проход начинает renewal в пределах 7 дней до expiry и ждёт quorum и нужный issuer. Локальные записи, отправка и TLS-публикация проверяют поколение и CommonOpen. Отмена после принятого Bind сохраняет прежнее решение для reconciliation. Готовность, Process и Enable сверяют действующую опубликованную CredentialRevision и используют новый ключ после Bind, включая свежий Bootstrap.

Если bind-intent опережает replay, прежний leaf сначала доступен только для native Raft. На свежем majority сверяются исходные OperationId и digest. При принятом Bind восстанавливается exact результат и прежняя цепочка установки. При непринятом Bind сохраняются прежние pins и intent, затем штатный Process/Enable открывает CommonOpen и worker может отправить ту же команду. Если исходный Bind применяется в ходе Process/Enable, его результат сверяется до рабочего допуска с новым leaf. [Матрица 04.09.02](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.02-automatic-rotation.md#nui-04-20261121-03).

После окончания overlap изолированный проход сверяет защищённый slot, опубликованную TLS-пару и exact Bind по свежему принятому срезу. В составе с несколькими voters нужен успешный Direct HANDOFF с действующим другим voter. Единственный принятый voter подписывает одноразовый challenge новым приватным ключом и проверяет подпись публичным ключом leaf. Если другой voter недоступен, проход откладывает retirement. Старый leaf теряет доступ на границе overlap независимо от этой проверки.

Перед отправкой `RetireOldCredential` проход фиксирует исходный envelope в защищённом `retire-intent` того же slot. При повторе сверяет exact accepted результат. Для непринятой команды typed клиент заново получает handoff evidence и отправляет тот же ID и payload. В singleton typed вход подтверждает ключ опубликованного снимка локально. В multi-voter принимающий лидер сверяет отдельное свидетельство другого voter. После принятия следующая ротация использует опубликованный slot для PoP. Рабочий проход использует типизированные Authorize, Bind и Retire и направляет выдачу только принятому владельцу issuer epoch. [Контракт typed приёма](Onboarding%20contracts.md#voter-credential-typed-retirement), [проверки](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.03-production-admission.md#nui-04-20261121-08).

### Повтор Authorize после потери связи

Исходный защищённый bundle `intent` хранит ключ и CSR для всей ротации. После подтверждённого отказа для истёкшего запроса `LocalVoterCredentialPreparation` под общим Transition сохраняет один защищённый `retry-<OperationId>` с решением и новым шаблоном. Новый Authorize отправляется после записи. Чтение связывает записи по OperationId, проверяет прежний ключ и неизменяемые поля, отклоняет разрыв цепочки и сверяет действующий запрос с authorization/DER/Bind pins. Ту же цепочку читают публикация и PoP следующей ротации. Защищённые слоты с одним `intent` читаются прежним способом. Подключённый допуск сохраняет exact terminal Rejected в accepted журнале. [Механизм и матрица проверки](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.01-authorize-retry.md#механизм-и-порядок-записей).

## Вход и границы доступа

До Build `ConfigureLocalInstallation` читает явный `Installation:InstallationIntent=Setup`, получает installation/storage locks и задаёт DP application identity по постоянной InstallIdentity. Legacy initialization не выполняется. В Setup обязательны заранее подготовленная SQL schema и защищённые BootstrapAdmin credentials; приложение не применяет migrations, не делает backup, не переписывает конфигурацию.

Под lock создаётся ровно одна LocalSetupAccount вне users/roles: Identity V3 hash, stamp, lockout, CreatedForInstallIdentity. Пустой, короткий или примерный initial password отвергается. Нет register/first-visitor endpoint; первый посетитель не выбирает пароль. Повторный initialization не читает новый config как команду сброса/включения аккаунта. Посторонний legacy admin не преобразуется в setup identity. Потеря локального доступа требует отдельного обслуживания по месту установки.

Cookie: scheme `LocalSetup`, name `__Host-UptimeHarbor.Setup`, Secure/HttpOnly/Strict, session cookie без remember-me. Отдельный DP purpose `LocalSetup/{InstallIdentity:N}` + `Cookie/v1`; idle 15 минут со sliding expiration, абсолютный TTL 30 минут по неизменному StartedAtUtc. Каждый запрос с setup cookie проверяет InstallIdentity, stamp, epoch, BootId, phase и отсутствие disabled/hash removal. Смена процесса повышает epoch/generation и отзывает прежнюю cookie, сохраняя попытку.

`/api/setup/session` выдаёт antiforgery token текущей identity. После login клиент получает новый token. Login/prepare/logout требуют antiforgery; boundary дополнительно сверяет точный HTTPS Origin и Host с BrowserOrigin. Rate limit — 10 запросов в минуту на IP; local lockout — 5 ошибок / 5 минут. Все setup routes/assets имеют no-store и общие security headers. Разрешён только точный whitelist страницы, API и её ресурсов. Setup cookie не принимается common API; common cookie не даёт setup-права.

При финальном переходе `AwaitingActivation → ClusterReady` production authority сверяет accepted online Enable текущего процесса после отдельной activation. В одной локальной транзакции удаляется setup hash, устанавливается Disabled, меняется stamp/epoch и профиль. После durable результата runtime повторяет admission/CanWork и публикует CommonOpen. Сбой оставляет FailedNeedsAction и закрытый доступ; config не восстанавливает hash. Этот путь подключён для нового первого, доставка Telegram остаётся закрыта до 05а.

Потеря ответа после InitializeCluster, BootstrapAccount, RegisterOnlineProcess, авторизации/consumption activation или Enable не создаёт вторую операцию: повтор использует сохранённые IDs и accepted результаты. Если ответ локального commit отзыва setup потерян, durable профиль может уже быть ClusterReady при ещё закрытом CommonOpen текущего процесса; sealed restart сохраняет genesis/account/issuer и проходит новый ProcessEpoch/Enable. Ошибка последующей публикации Ready оставляет FailedNeedsAction, setup hash не восстанавливается. Все промежуточные этапы до CommonOpen возвращают 503 на common routes; после открытия собственные setup routes закрываются с 404.

Прерванный первый Bootstrap без первого seal сейчас не продолжает native startup автоматически: восстановление закрыто без нового genesis или аккаунта. Это безопасный отказ, а не подтверждённое автоматическое resume произвольной ранней границы. Проверка этой границы и последующее восстановление относятся к оставшемуся crash/reconciliation объёму этапа 04. [Изолированные проверки нового первого](Testing.md#bootstrap-и-приглашение-0405-2026-11-15).

## Preflight и локальное состояние

Минимальный preflight читает pending migrations и каждый корневой mapped EF entity/table, включая shared account/role/claim/login/token/membership, identity/cursor, Pending/capture/results/outbox и остальные очереди. Любая рабочая строка блокирует новый путь. Разрешены только четыре собственные локальные setup/progress-таблицы и локальные data_protection_keys; их принадлежность и согласованность проверяются отдельно. Проверяются единственный профиль/account, InstallIdentity, попытка/шаги/OperationIds и key references. Чужая identity, orphan progress/account или старый storage/manifest не очищаются и не объединяются. Непустой первый standalone направляется в 03а/03б.

LocalSetupAccountStore.ValidateProgressAsync обходит всю историю шагов без tracking страницами по 256. Каждая следующая страница использует Id последней проверенной записи; WHERE и ORDER BY выполняются одним SQL Server provider по первичному ключу, без OFFSET и без общего предела числа шагов. В память загружается только ограниченная страница. Страницы не фильтруются по попытке: чужой AttemptId должен быть обнаружен. Сохраняются проверки row/payload identity и command digest, cluster/node/storage identity, profile/runtime revisions; исходные фиксированные OperationIds обрабатываются по прежнему контракту. Отмена прерывает чтение и проверку. Startup выполняет этот обход под installation/storage lock до возобновления writers; параллельная запись во время обхода не является поддерживаемым сценарием. Схема, первичный ключ Id и CAS записи не меняются.

Проверяются версии `2.0/2/2/2/1/6.10.0`, заранее подготовленный отдельный Direct peer endpoint, абсолютные непересекающиеся state/secret/key/storage пути, отсутствие symlink/reparse ancestors, права и минимум 64 MiB свободного места на каждом томе. В новом cluster storage допускается только installation.lock. Недостающий listener — отказ preflight, не restart из HTTP.

URI обязан быть canonical HTTPS `/internal/raft`, без userinfo/query/fragment. Loopback/link-local/metadata/multicast запрещены; private/VPN IP допускается только AllowedPeerNetworks. Managed outbound ConnectCallback заново разрешает DNS на каждом connect, отвергает весь набор при запрещённом IP и соединяется с выбранным проверенным IP, сохраняя TLS SNI. Redirect/cookies/proxy отключены. Локальная проверка конфигурации **не является двусторонней TLS-пробой**: production enrollment authority этапа 04 проверяет authenticated descriptor и обе peer-пробы до выдачи итоговой E4 evidence. При этом обычные runtime/common gates второго остаются закрытыми до полного Join этапа 05.

LocalInstallationProfile/LocalAttemptStep содержат immutable mode/phase, revisions/generation, InstallIdentity/BootId/lease/epoch, AttemptId/NodeId/storage, request digest, исходные OperationIds, expected result и evidence. LocalSetup и OnboardingProgress используют раздельные сценарные UoW на существующей EF session; глобального UoW нет. CAS запрещает замену чужой revision или изменение исходной request/key/operation identity. Начальный local intent и authority step сохраняются **до** внешнего эффекта. Network timeout — 10 секунд, неизвестный ответ сохраняется как AuthorityResultUnknown; повтор использует прежние IDs и исходные revision/generation authority step. Поздний callback не публикует результат нового поколения.

Новый первый подготавливает отдельный UUID/роль/credential/BootstrapAccount digest, зашифрованный локальный command reference и собственный ClusterId. Setup account в accepted users не копируется. Публичный BotId берётся из положительного локального ExpectedBotId либо bounded getMe локального токена будущего sender; браузер не задаёт BotId. Отсутствие обеих возможностей блокирует только подготовку первого. Join сохраняет собственные NodeId/storage/AttemptId/private key, не создаёт Bootstrap/common account и не задаёт ClusterId/BotId самостоятельно. Их authenticated получение относится к 04/05; Join authority-порт уже принимает контракт LocalOnboardingAttempt этапа 02.

ProtectedInvitation хранится AES-GCM envelope непосредственно в локальной SQL attempt, привязанный к InstallIdentity/AttemptId. После подтверждённого reserve поле удаляется; encrypted invitation не создаёт отдельный orphan-файл. Accepted reserve не меняет исходные IDs/request/key. Эти локальные таблицы, setup credentials, DP keyring и private references не входят в общие replication/snapshot whitelist.

## Файлы и восстановление

Wrapping key (32 bytes) создаётся автоматически под installation lock в отдельном persistent secret volume. Private PEM и отдельный BootstrapAccount command шифруются AES-256-GCM; AAD включает InstallIdentity/AttemptId/purpose/file ID. SQL reference содержит случайный file ID и SHA256 envelope. Путь из reference не принимается; размер/version/digest/AAD/права проверяются до использования. DPAPI не применяется. DP keyring находится в защищённом state/data-protection, его не переопределяет SQL key repository.

Linux private directories/files — 0700/0600; Windows ACL разрешает service identity и Administrators. Уже существующие неверные права вызывают отказ. Запись: случайный temp → Flush(true) → rename без overwrite → Linux directory fsync → SQL ref. После сбоя сверяются SQL/files; повреждённый ref, пропавший wrapping key при существующих keys, неизвестный файл или orphan temp требуют действий. Они не выбираются по дате/имени, не усыновляются и не удаляются автоматически. Перезапуск сохраняет ту же попытку; новый BootId ждёт expiry прежней двухминутной локальной lease, прежние grants не переиспользует. Supervisor обновляет локальную lease каждые 30 секунд; это не accepted ProcessEpoch/renewal будущей authority.

Locks на state, secret, keys и storage удерживаются весь срок процесса с FileShare.None до чтения install.id и preflight. SQL identity/revision защищает согласование локальных путей с профилем. Полный побитовый клон с ключами на другом диске криптографически неотличим; он не получает isolation proof. Реальная authority дополнительно проверяет registry/address/SPKI/ProcessEpoch; до неё production runtime закрыт. Clone/backup/rejoin не являются свежим Join.

## Inventory runtime и остановка

Root hosted owner один — ManagedWorkerSupervisor. ManagedWorkerCatalog разрешает конкретные workers только после выбора группы/admission. В Setup при старте рабочих loops и WAL нет. В обычном Disabled работают только прежние monitoring/outbox; их singleton registration не означает запуск. DI selectors sign-in/account/administration/recipients выбирают adapter по immutable active profile в новом scope; singleton компоненты читают актуальный профиль через ActiveClusterOptions. Operator config не мутируется.

| Компонент | Владелец задач и освобождение |
| --- | --- |
| MonitoringWorker → MonitoringCycleRunner | Legacy group; await всех per-target checks через WhenAll; отдельные scopes, keyed entries удаляются в finally, передаётся cancellation |
| TelegramOutboxWorker → TelegramOutboxDispatcher | Legacy group; await DispatchDueAsync и отменяемого poll delay; DB gate/результат завершаются до выхода |
| ClusterHealthWorker → Database/Telegram probes, PeerObservationCapture | Quarantine group; using PeriodicTimer, await bounded Parallel.ForEachAsync/probes/capture; HTTP responses/streams/CTS/scopes освобождаются; stale callbacks не публикуют Ready/connection |
| ClusterPeerRuntime → child DotNext, WAL/configuration, inbox, storage lease | Quarantine group; checkpoint/recovery до resolve WAL; native Stop await под lifecycle/membership locks, child provider DisposeAsync, inbox/lease Dispose в finally; RPC/sender закрываются перед stop |
| ClusterLifecycleWorker → MembershipCoordinator/dispatcher | Quarantine group; await текущего цикла, membership lock освобождается в finally. Managed path не создаёт прежний sender epoch |
| ClusterRevisionWorker → PendingReplicationPump | Quarantine group; последовательный await RunOnce, bounded batches и scopes; pump не имеет отдельного detached loop |
| ClusterSnapshotWorker → RevisionClusterRecovery/RevisionSnapshotStore | Quarantine group; await snapshot/reclaim, cancellation timer; temporary streams/files имеют finally; generation проверяется до rename/publication |
| ClusterMonitoringWorker → ClusterMonitoringCycle/ObservationReplicationPump/MonitoringCoordinator | Только Ready group; await cycle/pump/coordinator, per-target scopes и cancellation. Дочерних hosted registrations нет |
| ClusterDeliveryWorker → AcceptedDeliveryDispatcher/consensus/transport | Старый enabled path сохранён. В новом managed Setup worker не запускается, dispatcher дополнительно закрыт до 05а |

Переходы: `SetupReady/StandaloneReady → Preparing → Quiescing → LocalPrepared → ClusterQuarantine → CatchingUp → AwaitingActivation → ClusterReady`, отдельно Paused/FailedNeedsAction. Поддержанный вход текущего этапа — новая SetupReady; действующий standalone проходит 03а/03б. Одна смена mode не включает runtime.

Порядок locks: installation transition → supervisor lifecycle → PeerRuntime lifecycle → membership → scoped projection/write operation. RuntimeWriteGate закрывается перед cancel/drain; leases охватывают HTTP/worker operation до commit/transport. SQL transaction не удерживается во время network/runtime/file effect. Quiescing повышает RuntimeGeneration, supervisor отменяет и ждёт все прежние tasks максимум 10 секунд. Failed drain запрещает новый старт. Частично запущенная группа закрывает gate и останавливается; неизвестный effect сохраняет FailedNeedsAction. Неожиданное завершение managed loop закрывает gate, сохраняет failed профиль и дренирует группу; Web-host не перезапускается как способ перехода.

Каждый loop захватывает неизменное поколение в AsyncLocal context. Перед sync/async EF SaveChanges, transaction commit, peer/Telegram send, accepted/health/snapshot publication проверяется generation. Старый callback не открывает Ready и не выполняет запись/отправку нового поколения. Одновременный или повторный start до полного stop запрещён; расширение quarantine → Ready в том же поколении не стартует прежние loops второй раз.

## TLS, логи и пределы проверки

Peer socket Direct/TLS passthrough готовится до Build. DynamicPeerTls отдаёт certificate/trust snapshot только для текущего поколения и разрешённой фазы; пустой provider закрывает TLS, HTTP gate остаётся закрытым до quarantine/admission. Managed HTTP повторно проверяет accepted pin, CA fingerprint, SAN/EKU/expiry. Dynamic chain использует offline revocation и закрывается при отсутствии нужных revocation данных; accepted validator этапа 04 обязан проверять актуальную revocation/purpose. Пулы нового пути не переиспользуются. Legacy Direct online CRL и NginxIsolatedHttp proxy allowlist/headers/CRL не ослаблены; приложение не управляет Nginx.

Setup/preflight/runtime/authority события используют существующий ILogger/Serilog после соответствующего durable результата: SetupPrepared, SetupPreflightCompleted/Rejected, SetupLoginAccepted/Rejected/Locked, RuntimeTransitionStarted/Committed/Resumed/Failed, SetupAccessRevoked, SetupAuthorityDeferred/EvidenceRecorded. Только безопасные ID, phase, revisions/generation, evidence kind и закрытый reason code. Пароли, hashes/stamps/cookies, invitation/verifier, private material, connection strings, URL токена и payload не журналируются. EvidenceRecorded — не Bootstrap/Join/Ready success.

Изолированно проверены takeover/config reset, cookie/CSRF/Origin/Host, непустота mapped таблиц и orphan local state, exclusive file handle, failed drain/double start/stale callbacks, restart с прежними IDs, потеря authority ответа, удаление protected invitation после reserve, AES/ref corruption/orphans, отдельный common account, отзыв setup до runtime publication, closed default authority/DI и независимость consensus от Telegram. Точные команды/счётчики — [Testing.md](Testing.md#локальный-setup-этап-03).

E4 хранит immutable trust intent/ref в LocalOnboardingAttempt и protected manifest на state volume; частичный файловый эффект завершается только повтором того же intent. Startup сверяет refs/leaf/key/registry и запрещает orphan files. Managed restart нового первого читает AEAD `managed-storage.seal`, точные snapshot/SQL head/manifest и целый WAL. SetupInitialization сначала читает прежний profile, затем preflight; обычный restart не направляется в перенос standalone. Supervisor запускает карантин без majority, позднее новый process grant/Enable открывает доступ. Old grants не читаются как локальная authority.

### Целостность WAL и публикация seal

До загрузки sealed snapshot и создания WAL `ManagedWalValidation` под installation lock проверяет исходные метаданные закреплённого DotNext 6.10.0: точную длину state (vote flag + ClusterMemberId + term), checkpoint v1 (20 байт), term ≥ SQL term, committed ≥ SQL index и last ≥ committed. Отсутствие, усечение, неизвестная версия или откат закрывают admission/TLS до native open. Это необходимо, поскольку конструктор DotNext обнуляет короткий state и поднимает индексы WAL до восстановленного snapshot; проверка после конструктора потеряла бы исходную evidence. При обновлении DotNext нужно пересмотреть этот адаптер. Pages после snapshot дополнительно проверяются самим WAL с CRC64.

Каждый дальнейший durable apply сохраняет полный snapshot → SQL checkpoint → AEAD seal → Current. Публикации сериализуются checkpointSerial; capture экспортирует согласованный cut под apply mutex, затем обычный apply может продвинуть SQL, пока сохраняется прежний cut. Seal запрещает снижение index/term и другой term/head digest на том же index. Ошибка публикации при существующем managed seal закрывает accepted recovery и рабочее право до Restore/replay; предыдущий Current/seal не заменяется неподтверждённым результатом. Orphan `.next` требует offline recovery. После записи seal и до Current перезапуск выбирает snapshot из seal, не последний файл каталога.

Стоимость одного apply линейна полному объёму образа: SQL export, сериализация body и запись packaged snapshot (примерно два полных объёма записи), несколько полных чтений/hash/проверок, SQL checkpoint и малая запись seal. До watermark/reclaim сохраняются полные файлы каждого cut; повторы того же index могут оставаться до продвижения cut. Задержка snapshot входит в apply; частота не уменьшена, так как разреженные seals потребовали бы отдельного доказательства защиты промежуточного префикса. Изолированный interleaving подтверждает две публикации для одновременных ручного snapshot и одного apply, но не даёт throughput/latency production.

При аварийном завершении сохранённый native commit может отстать от SQL/seal: такой результат теперь консервативно требует offline recovery, даже если snapshot позволяет восстановить данные. Физические fsync/power loss и нагрузка не проверены. Согласованный полный побитовый откат/клон вместе с ключами и всеми sealed данными локально неотличим; markers, identity и новые process epochs сохраняются, автоматического isolation proof для клона нет.

Не проверены SQL provider locking/atomicity/DDL, настоящий второй OS-процесс, Ubuntu ACL/fsync/power loss, Kestrel bind/горячая TLS-замена/CRL/DNS и двусторонняя сеть, browser rendering и переключение работающего окружения. Полный Join/snapshot/membership — 05, перенос — 03а/03б, sender — 05а, мастер — 06; оставшиеся обязательства 04 перечислены в актуальных контрактах.
