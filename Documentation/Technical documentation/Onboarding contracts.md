# Приглашения и контракты подключения

Этот документ описывает прежние интерфейсы и форматы подключения. Код чтения снимков и WAL сохраняет проверки совместимости принятых данных. Действующие операции инженера описаны в [Cluster operations.md](Cluster%20operations.md).

Реализованы контракты этапа 02, локальный setup/runtime этапа 03 и выполняемый production путь нового первого Bootstrap этапа 04. Dedicated enrollment второго доходит до accepted nonvoter admission, файловой установки trust и двух peer TLS-проб; runtime второго остаётся закрыт до snapshot/membership этапа 05. Полный этап 04 ещё не завершён: оставшийся собственный объём указан ниже. Перенос, sender и полный мастер не реализованы. [Локальное устройство](Local%20installation%20setup.md).

## Промежуточная граница этапа 04 (2026-11-03)

Работа возобновлена 2026-11-15; 04.01–04.08, ограниченная accepted-часть 04.09-A и изолированный authority/signing core B1 завершены в своих объёмах, весь этап остаётся `in-progress`. [Остаток и известные проблемы](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/main.md#результат), [изолированная проверка E1–E4](Testing.md#enrollment-e1e4-0406-2026-11-15), [manual issuer](Testing.md#issuer-ручного-кластера-0407-2026-11-15), [remote routing](Testing.md#удалённый-issuer-и-follower-routing-0408-2026-11-17), [проверки ротации A](Testing.md#voter-credential-rotation-0409a-2026-11-18), [проверки B1](Testing.md#voter-credential-authority-0409b1-2026-11-18). Этот раздел отражает частичную production integration, а не полную приёмку 04.

`EnrollmentCertificates` создаёт новый специализированный P-256/SHA-256 application CA с critical pathLen=0, keyCertSign/cRLSign и фиксированными purpose/cluster/generation/epoch в URI SAN. CSR проверяется по PKCS#10 signature, P-256/SPKI/digest; requested extensions отвергаются. Leaf имеет точные SAN DNS/IP/node/storage/credential, critical CA=false/digitalSignature/clientAuth/serverAuth, serial и срок. Проверки выполняются локально без загрузок и изменения system trust. Dedicated helper не использует CRL: действующий managed RPC boundary повторно проверяет accepted node/credential/issuer revocation через DynamicPeerTls и EnrollmentLiveTrust. Полная orchestration отзыва остаётся отдельной задачей 04.10; legacy Direct CRL не отключён.

Schema-3 `InitializeCluster`, `RegisterEnrollmentIssuer`, `RetireEnrollmentIssuer`, `RevokeEnrollmentIssuer` проходят прежний WAL/reducer/projection. Public issuer хранится в `OnboardingContracts.Issuers` и `enrollment_issuers`; snapshot сверяет projection/owner/revision/digests и recovery ancestors. Registration требует актуального accepted Administrator, reauthentication ≤5 минут и voting owner; retired/revoked epoch не разрешает новую выдачу. Genesis требует **уже закреплённого** точного GenesisAuthorization в trusted initial image, пустой новой сетки, отдельного account digest и создаёт Node прежде credential. Он не выводит разрешение из своего входящего payload. Trusted genesis image и production lifecycle подключены для нового первого. В 04.07 подключён первоначальный manual provisioning/Register; replacement/retirement orchestration остаётся 04.11.

### Первоначальный issuer ручного кластера (04.07)

`EnrollmentIssuerAdministration` обслуживает локальный leader ручного Legacy-кластера. До файловых эффектов проверяет accepted Administrator, пароль через прежний local login, точную revision и свежий `EnrollmentIssuerRegistrationBarrier`. Он выполняет native strong majority до и после authenticated health каждого удалённого voter: точная trust-v3 envelope compatibility, EnrollmentTrustVersion=1, NodeId/BootId/term/leader/membership, совпадение native и accepted состава. Majority не заменяет capability оставшегося voter. Register через peer batch повторяет тот же barrier в OnboardingAcceptance.

Новый CA/ключ создаёт `EnrollmentIssuerProvisioning`; epoch равен исходному OperationId. AES-GCM key file и local signing SQL ref сохраняются до protected Pending, затем передаётся только public anchor прежним transport/dispatcher/reducer/apply. Legacy CA/operator key не импортируются, существующие Operations/credentials/pins не меняются. До accepted регистрации и отдельной exact accepted issuance signer отказывает; каждая подпись требует своего свежего majority. После commit readiness проверяется заново после локального чтения ключа. Structured IssuerRegistered/IssuerRejected пишутся по accepted итогу; известный ID не дублирует событие.

Повтор использует исходные local key/ref/DER и protected command с прежними reauthentication/ActorRevision/IDs/digest. Он не переавторизует устаревшую команду новым stamp. Held после restore не освобождается автоматически. Нужны исходный Pending и локальный key ref; неизвестный/orphan commit не выбирается как новая authority. При неуспешном локальном save команда не отправляется. Самостоятельная подготовка второго epoch и replacement отвергаются. Общий Join/Ready этим не открывается.

`GenesisWriterPermit` допускает только два заранее привязанных payload/OperationId: InitializeCluster и затем точный BootstrapAccount. Account result закрывает permit; повтор результата обслуживает dispatcher. DotNext adapter дополнительно требует реального singleton leader/term, recovered prefix, membership и Database/Projection/Storage/Clock. Общий CanWork от permit не открывается; import marker/перенос не реализованы. Permit в production DI создаётся невооружённым; Web не может его вооружить произвольной командой.

`EnrollmentSigner` принимает только request/template/CSR. Под issuer lock `EnrollmentSigningAuthorization` выполняет native linearizable barrier и сверяет текущую принятую выдачу, delegation, process lease, issuer owner/epoch/pins и отсутствие maintenance. DotNext 6.10.0 документирует linearizable read на follower; изменения term/leader/membership закрывают результат. Private key читается только из локального AES-GCM ref. `EnrollmentSigningJournal` фиксирует DER по IssueId до ответа; retry сохраняет прежние DER и authorization index. Это public artifact, не operational credential. Register/Authorize сами ключ не создают; production enrollment controller подключён.

### Удалённый issuer и follower routing (04.08)

`EnrollmentPeerClient` отправляет отдельные typed `coordinate/issue/grant` на `/internal/cluster/v1/enrollment` через прежний named authenticated peer transport. Периметр принимает только accepted voter/storage на peer listener; cookie, browser listener, pending/nonvoter и произвольный `/sign` закрыты. Запросы ограничены strict JSON, 64 KiB и 10 секундами. Передаются CSR/template/public DER и purpose-bound grant proof; invitation plaintext, private key и setup credentials не пересылаются. Proxy-секреты не вводятся.

Ingress voter сохраняет прежнюю immutable команду, повторяет PoP и направляет её текущему native leader. `EnrollmentCommandReceiver` сверяет source/storage, cluster, request/process/digest, whitelist action и leaf artifact до узкой capability; обычный peer batch её не получает. После RPC caller требует новый linearizable cut и локальный accepted result с исходным digest. HTTP DTO не публикуется как projection. Descriptor возвращает исходный browser origin.

`EnrollmentIssuanceRouter` выбирает signer только по accepted issuer epoch/owner. Удалённый signer повторяет exact template/authorization index/CSR, свежий barrier и owner checks под issuer lock; caller отдельно проверяет DER/template/digests и текущий accepted binding. Outage не создаёт другой CA/identity. Lost response, concurrent IssueId и смена leader сохраняют исходные bytes; до отдельного Bind они authority не дают.

Для remote Process/Activation/Enable `OnlineGrantRequests` сохраняет unsigned grant и отдельный peer-key ProcessProof в локальном `LocalAttemptStep` до RPC. Подпись покрывает фиксированный domain и весь template. Signer сверяет authenticated source с grant target, accepted process/delegation/versions, issuer owner и majority; CatchUp/snapshot/emergency/maintenance не разрешаются. Local Bootstrap/ManagedRestart source остаётся обязательным. Повтор существующего intent сохраняет GrantId, MinimumIndex и время даже при росте accepted cut; expiry не продлевается. Подпись не заменяет accepted authorization/consumption и не открывает Enable. Настоящий lifecycle последующих voters и завершённого Join остаётся в 04.12/04.13, replacement issuer — в 04.11; synthetic accepted fixtures этого не доказывают.

### Accepted-ротация credential voter (04.09-A)

`OnboardingContractImage.VoterCredentialRotations` хранит ротации по новому IssueId отдельно от invitation/attempt, в прежнем RevisionImage/WAL/snapshot. Optional rotation payload schema-3 команд не меняет сериализацию прежних команд с отсутствующим payload. Новых SQL-таблиц и migrations нет; Bind добавляет credential прежним write set. Identity, storage, адрес и membership узла не меняются.

| Переход | Accepted-инварианты |
| --- | --- |
| AuthorizeVoterCredential | Старый credential действующего voter жив и не отозван; до expiry осталось ≤7 дней. Intent закрепляет прежний CredentialId/fingerprint/SPKI/revision, новый ключ и exact issuance template активного issuer/owner. Свежесть intent ≤10 секунд; leaf заканчивается через 30 дней от времени выдачи, NotBefore допускает до 2 минут clock tolerance. Один незавершённый переход на узел; IssueId и ключи истории повторно не используются. OperationalCredential ещё не создаётся. |
| BindVoterCredential | Повторно проверяются старый expiry, текущий credential/revision, issuer и неизменный accepted intent. Сохраняются исходные public DER/fingerprint. Начальная CredentialRevision равна 0, после Bind — его accepted index. OverlapUntilUtc равен min(Bind+24 часа, expiry старого leaf). |
| RetireOldCredential | Сохраняются отдельные accepted retirement index/time и InstallationProofDigest. Это не compromise revocation: RevokedAtUtc не подменяется. Следующая ротация начинается только после retirement, с текущими ключом/revision. Digest сам по себе не доказывает установку. |

`VoterCredentialPolicy.IsUsable` исключает прежний credential на точной границе overlap даже без принятого Retire и никогда не продлевает expired leaf. Policy используется на границах принятого реестра и управляемого Direct TLS. Reducer использует только accepted CoordinatorAtUtc/Term. Replay известного OperationId возвращает прежний result без новых DER/revision/deadline; изменённый payload под тем же ID отвергается.

`VoterCredentialSnapshot` проверяет committed decision links, поля стадий и цепочку revision/ключей, включая recovery ancestors через прежний snapshot validator. `VoterCredentialArtifacts` локально сверяет public DER/SPKI/fingerprint/expiry и exact issuer/leaf template на historical BoundAtUtc без текущих часов и сети. Поздний отзыв с тем же UTC timestamp не делает прежний исторический Bind недействительным. Audit CertificateAuthorized/Bound/Retired/Rejected связан с accepted result и фактической границей состояния; повтор не создаёт второй success, DER/SPKI/proof не журналируются.

**Рабочая ротация доступна в managed Bootstrap Direct.** Общий RevisionDispatcher отвергает новые и повторные rotation-команды, а обычный peer batch отклоняется до dispatch. SystemSource, coordinator stamp, сертификат и proof digest сами по себе не дают authority. Обычный Renew expired leaf закрыт. [Изолированные доказательства A](Testing.md#voter-credential-rotation-0409a-2026-11-18).

### Доказательство ContinueCredential (04.09.04)

`VoterContinuationClient` использует фиксированные machine HTTPS POST на заданном `Installation:CredentialContinuationOrigin`, системное TLS-доверие browser origin и адресную политику enrollment. Подписанный challenge связывает точную peer-аудиторию. Квитанции сверяются с защищённым локальным префиксом и точными принятыми решениями. Клиент доступен в setup DI. [Адрес в конфигурации](Configuration.md).

`accepted-slice` доступен до native Start для managed Bootstrap Direct. Подпись прежним ключом покрывает purpose, audience, intent, nonce, boot/process, локальный `index/term/digest`, native term и digest voting identity. Лидер сверяет локальный срез с точной записью в своём accepted префиксе и подтверждает strong majority до чтения и после формирования ответа. При отставании replay точная запись должна находиться в сохранённых результатах. Отсутствие записи закрывает чтение.

Ответ содержит head и authority term/membership/recovery, identity двух участников, прежний публичный leaf, две выбранные публичные записи issuer, lease субъекта и точные команды/решения Request, Authorize, Register и Bind текущей операции. Для запроса с `BoundSource` ответ также содержит исходную цепочку, а `Bind` относится к исходной выдаче и хранится в `History`. Принятый Bind содержит публичный DER. Клиент проверяет digest текущего запроса, окно 10 секунд, монотонность среза за попытку запуска, локальную историю, цепочку решений и новый leaf. Общая проекция, другие операции, записи аккаунтов и секреты исключены из DTO. Startup использует проверенный срез для локальных записей и первой карантинной публикации. [Контракт локального запуска](Local%20installation%20setup.md#voter-continuation-local-installation-040904).

Для managed leaf proof использует отдельный домен, текущие accepted voter/storage/credential, CSR и кандидата process lease. DER проверяется на исторический момент перед истечением с учётом принятых отзывов. [Проверки proof](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.04-continue-credential.md#nui-04-20261121-09).

Отдельный typed вход на текущем лидере принимает команды schema 3 в прежний WAL. `RequestVoterContinuation` фиксирует точный запрос и принятый proof digest. `AuthorizeVoterContinuation` фиксирует подтверждение этого запроса реальным ActorId общей сессии и его accepted ревизией после проверки пароля. `RegisterVoterContinuationProcess` требует это разрешение и новый PoP/nonce для того же процесса. Fresh majority и совместимый с принятым составом native term обязательны перед каждым переходом и точным повтором. Digests связывают NodeId/storage, старый credential и его ревизию, оба issuer epoch/revision, ключи, CSR, nonce и аудиторию. Разрешение сохраняется для исходного term/membership/recovery. Пароль, CSR и байты подписи в WAL не записываются.

Регистрация занимает общий OnlineProcesses отдельной lease. Тот же активный boot сохраняет прежнюю границу. Для нового нужны следующие epoch и разные BootId/BootChallenge после истечения прежней lease. Такая запись не даёт обычного peer/activation доступа. Кодек и snapshot проверяют цепочку решений и provenance lease, в том числе в архивных срезах recovery. Общий dispatcher и peer batch отклоняют этот набор команд.

Отдельный machine HTTPS ingress подключён к текущему лидеру работающей managed установки. POST nonce принимает подписанное прежним ключом доказательство с отдельным доменом, назначением и адресом peer принимающего лидера. Одноразовый серверный nonce связывает назначение, exact intent, boot и текущую authority, включая ревизии прежнего и целевого issuer. Для status он также привязан к digest принятого запроса, для register — к digest принятого admin approval. POST request, status и register проверяют свежий PoP и подписанный CSR до ответа. Status возвращает решение только по exact принятому запросу и при доступных действующих полномочиях возвращает digest подтверждения и принятое решение регистрации. Повтор с уже потреблённым nonce закрыт. После потери ответа новый status nonce и свежий PoP позволяют прочитать исходное принятое решение. [Матрица HTTPS](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.04-continue-credential.md#nui-04-20261121-11).

Административное чтение и подтверждение точного запроса другого voter выполняются в общем интерфейсе действующего лидера. DI-порт актора принимает проверенный Identity application ticket с ролью Administrator. На свежем accepted срезе проверяются majority, контекст запроса и актуальный аккаунт. Подтверждение связывает ID принятого запроса, его digest и принятые ActorId/ревизию после штатной проверки пароля. Повтор с действующими полномочиями возвращает исходный ID принятого решения. Пятиминутное окно регистрации и выдачи отсчитывается от исходной реаутентификации. [Административный Web API](Web%20application.md).

Выдача и повтор до Bind требуют новый issue nonce, прежний PoP с исходным CSR и digest принятого решения регистрации. Signer проверяет цепочку решений и текущую lease, identity/storage, credential и ревизии issuer, полномочия исходного администратора, term/membership/recovery и fresh majority. Принимающий лидер должен владеть тем же accepted issuer и его локальным ключом. DER сохраняются в прежнем signing journal по исходному IssueId. AttemptId хранит исходный OperationId, RequestDigest связывает immutable intent с digest принятой регистрации отдельным доменом, AuthorizationIndex хранит индекс регистрации. Перед ответом полномочия проверяются повторно. После потери ответа в пределах действующих полномочий возвращаются сохранённые байты. Изменение term/membership/recovery требует нового accepted запроса. [Проверки выдачи](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.04-continue-credential.md#nui-04-20261121-13).

`BindVoterContinuation` использует deterministic Bind OperationId, отличный от исходных OperationId/IssueId. Вход проверяет отдельный Bind nonce, PoP прежним ключом и исходный CSR, затем читает DER только из signing journal по IssueId. После чтения повторно подтверждает majority и сверяет DER, шаблон, issuer и provenance регистрации. Reducer проверяет действующие approval, lease и authority на принятом времени, сохраняет public credential в accepted registry и присваивает CredentialRevision по индексу Bind. Граница overlap равна прежнему expiry. Snapshot связывает Bind, регистрацию и credential, включая recovery archive. Повтор требует свежий Bind nonce, возвращает первоначальное решение и ревизию и читает тот же артефакт без вызова signer. Аудит фиксирует безопасные ID и фактический исход без DER, CSR, ключей и nonce. [Проверки Bind](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.04-continue-credential.md#nui-04-20261121-14).

Запрос допуска нового boot после Bind использует новый RequestId и включает `BoundSource` с исходным RequestId, digest Bind и CredentialRevision в подписываемом intent. Текущий лидер проверяет исходный Bind, неизменный шаблон с IssueId, прежний ключ/CSR и актуальность credentials и issuer. Общий администратор подтверждает новый RequestId. Register требует истёкшую continuation lease этой же цепочки, другой boot/challenge и следующий epoch. Прежние решения и DER сохраняются. WAL и snapshot связывают обе цепочки. Допуск резервирует карантинную lease. Accepted-slice discovery по исходному intent и PoP дополнительно подписывает digest исходного Register и DER. Он читает точный исходный Bind и регистрацию текущей continuation lease, включая истёкшую. Свежий срез нового запроса проверяет обе цепочки, действующий Bind и текущий процесс на одном подтверждённом head. Выдача и Bind для запроса восстановления закрыты.

Локальная установка и публикация исходного boot сверяют регистрационную цепочку, точный accepted Bind и CredentialRevision на свежем срезе. Передача живой continuation lease в обычную проходит через `RenewOnlineProcess` с подписью установленным ключом. Поле `SnapshotDigest` подписанного grant содержит digest принятого Bind. Принимающая сторона сверяет NodeId/storage, новый leaf/SPKI, BootId/challenge, epoch и recovery version. `RegisterOnlineProcess` не заменяет continuation lease. Activation и Enable требуют уже обычную lease. [Локальная установка и публикация](Local%20installation%20setup.md#voter-continuation-local-installation-040904).

### Authority и signing ротации voter (04.09-B1)

`VoterCredentialRequest` не содержит invitation/attempt: version/cluster/generation/OperationId и immutable renewal (прежние credential/fingerprint/SPKI/revision, новый IssueId/issuer epoch/exact template). Его отдельный domain digest сохраняется при смене лидера, новом PoP и replay. `VoterCredentialAuthorizationCommand` создаёт исходный exact Authorize envelope без coordinator stamp; Prepare не выполняет dispatch. Существующие reducer/codec/WAL formats A не менялись.

`VoterCredentialProof` подписывается прежним operational P-256 key и покрывает immutable intent digest, фиксированный scope RenewVoterCredential, authenticated subject NodeId/storage, BootId/BootChallenge/ProcessEpoch/RecoveryVersion, MembershipVersion, nonce и UTC issuance. Prepare после fresh majority сверяет известный voting node/адрес/storage/cluster/current CredentialRevision, действующий старый leaf и новый подписанный PKCS#10 CSR без extensions; принимает nonce один раз, не позднее 60 monotonic секунд. Короткий PoP действителен <60 UTC секунд и только для текущей online process lease. Время proof не продлевает leaf, accepted template или overlap.

`VoterCredentialSigner` принимает только `VoterCredentialSigningRequest`: exact committed Authorize operation/result/digest/index/renewal, новый PoP/CSR и fresh majority внутри прежнего общего issuer lock. Проверяет accepted owner/epoch/purpose/сроки и exact local protected issuer key/ref. Typed `IVoterCredentialSignerClient` и router выбирают только accepted owner, без fallback и произвольного Sign(bytes). Вызов server method требует аутентифицированных subject NodeId/storage от transport, отдельно от тела. Подпись сама не выполняет Bind/Ready.

Прежний `EnrollmentSigningJournal.SaveVoterIssueOnceAsync` сохраняет DER через прежний signing UoW до ответа. Domain-separated voter intent digest и exact template/index неизменны; прежняя локальная correlation-колонка AttemptId содержит **OperationId**, не ссылку на onboarding attempt (FK на attempt нет). При lost response/unknown commit/смене leader/конкуренции тот же IssueId возвращает исходные DER; изменение intent/OperationId/template/index отвергается. Старый proof можно заменить свежим для той же identity/intent. После durable commit signer повторяет majority/crypto checks; caller также повторяет их после RPC. При потере условий DER могут остаться orphan в journal, но наружу не выдаются и operational credential не создаётся. Повтор после Bound/retirement закрыт; дальнейшее восстановление установки принадлежит B2.

Production Setup использует B1 authority для сверки Bind при ManagedRestart, типизированной выдачи и рабочего допуска managed Bootstrap Direct. B1 проверял удалённого signer с double, B3a проверяла конкретный signer через peer framework. Для ручного и dedicated trust действуют правила Direct, описанные ниже. [Проверки B1](Testing.md#voter-credential-authority-0409b1-2026-11-18).

### Локальная Bind evidence voter (04.09-B2b1)

`Installation/Renewal` сохраняет immutable Bind operation intent до отправки через типизированный вход, затем exact accepted Bind/result/index/CredentialRevision после нового majority barrier. Accepted CommandResult и rotation/credential должны совпасть с исходными request/Authorize/DER; подпись и transport response отдельно успех не дают. Повтор/reopen/unknown commit сохраняет команду, OperationId, key/CSR/template/DER/correlation. После Bound/retirement signer и повторный dispatch не вызываются; чтение текущей evidence не требует живого старого leaf/process proof, но требует прежний локальный material и usable новый credential/fresh accepted cut. Локальный result не является installed revision/confirmation и не открывает common gate. Missing/corrupt pins/intent, altered result/revision или согласованный rollback закрываются. [Порядок, файлы и оставшаяся B2b2](Local%20installation%20setup.md#локальные-bind-intent-и-result-voter-0409-b2b1).

B2b2 дополняет Bind evidence подтверждённой локальной установкой и её recovery. Bootstrap ManagedRestart сверяет цепочку с sealed WAL до native Start и после свежего majority дописывает отсутствующий хвост по тем же pins и exact Bind. Принятый Bind восстанавливается отдельно от отправки новой команды. [Локальная установка и публикация](Local%20installation%20setup.md#voter-credential-local-publication-0409b3b2).

<a id="voter-credential-peer-0409b3a"></a>

### Изолированная последовательность ротации (04.09-B3c1)

Перед отправкой Authorize координатор сохраняет intent с исходными OperationId, IssueId и CSR, подтверждает majority и формирует PoP в scope RenewVoterCredential с текущими BootId/challenge, ProcessEpoch и membership. При возобновлении accepted Authorize сверяется по исходной операции, digest и индексу. Typed signing выбирает прежний accepted issuer epoch и использует DER journal. Сохранённый DER проверяется до Bind. После принятого Bind используются прежний durable Bind intent и reconciliation без нового вызова signer или отправки Bind.

Изолированная композиция использует IRevisionTransport с подставным применением exact Authorize/Bind. Production dispatcher сохраняет запрет. [Установка и ограничения ManagedRestart](Local%20installation%20setup.md#изолированный-сценарий-renewal-0409-b3c1).

Перед локальной отправкой Bind на Direct координатор повторно подтверждает exact accepted Authorize, PoP старого ключа, CSR и signed artifact. Каноническая команда строится из того же запроса и DER и сравнивается целиком с защищённым Bind intent. Проверка завершается сверкой текущего среза и recovery generation. Для восстановления принятого Bind используются прежние durable pins и exact accepted решение. Общий dispatcher закрывает новые команды ротации и повтор известных решений. Обычный peer batch с командой ротации целиком отклоняется до dispatch. [Граница production admission](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.03-production-admission.md#nui-04-20261121-05).

В рабочей композиции managed Bootstrap Direct клиент обращается к локальному лидеру с опубликованным TLS-снимком или к удалённому через прежний authenticated peer transport. Фиксированные POST под `/internal/cluster/v1/enrollment/rotation/` доставляют nonce, Authorize, Bind и Retire. Nonce для новой записи Authorize привязан к intent, TLS-паре, term, membership и восстановлению принимающего лидера. Для Bind отдельный PoP старого ключа покрывает digest команды с DER и индекс accepted Authorize. Лидер проверяет доказательства под сериализацией записи и сам ставит время и term. Редьюсер решает, уложился ли Authorize в окно приёма.

Клиент подтверждает ответ по свежему локальному журналу. Точный повтор Authorize или Bind возвращает прежние OperationId, digest и index. Принятый Bind сохраняет исходные IssueId и DER. Повтор с прежним leaf возможен в пределах его действующего overlap. После этого восстановление использует точные локальные pins и принятый Bind. Переоформление 04.09.01 опирается на сохранённый exact Rejected. [Проверки Authorize/Bind](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.03-production-admission.md#nui-04-20261121-06).

<a id="voter-credential-typed-retirement"></a>

Для Retire `POST /internal/cluster/v1/enrollment/retirement-handoff` даёт другому действующему voter подтвердить exact команду после overlap. Он сверяет новый client leaf и свой server leaf на свежем accepted срезе и подписывает свидетельство ключом предъявленного server leaf. Подпись покрывает IssueId, CredentialRevision, fingerprint, Bind digest, исходные Retire OperationId и digest, identity свидетеля, term, membership и время. Клиент связывает подписанта с server leaf конкретного соединения.

Лидер принимает Retire на отдельном managed Bootstrap Direct входе. В multi-voter он сверяет источник по текущему новому leaf, состав с native consensus, свидетельство другого активного voter и его leaf. Окно свидетельства составляет до 30 секунд назад и до 5 секунд вперёд по часам принимающей стороны. В singleton лидер сверяет точный опубликованный снимок и проверяет подпись одноразового challenge новым ключом. В обоих случаях он восстанавливает канонический Bind по принятому DER, сверяет старый leaf по историческим pins, проверяет exact Retire и срок overlap под serial lock. Доступ старого leaf закрывается в min(Bind + 24 ч, expiry) независимо от handoff. Повтор может получить свежее свидетельство в новом term и возвращает прежнее принятое решение без новой записи. Production DI подключает signer, nonce, Authorize, Bind и Retire только для рабочего managed Bootstrap Direct. Перед запросом проверяются CommonOpen и актуальное поколение, входящие RPC требуют предъявленную TLS-пару. Вручную управляемые и прочие неподдерживаемые топологии не получают этого допуска. [Проверки typed Retire](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09.03-production-admission.md#nui-04-20261121-07).

При неизвестном результате координатор повторяет exact Authorize под свежей проверкой PoP/CSR и majority. Если окно истекло, reducer на позиции принятия возвращает прежнее решение либо записывает отказ. Решение закреплено за OperationId и digest, поэтому поздний повтор сохраняет результат победившей записи и исключает принятие после зафиксированного отказа. Только свежий срез с точным отказом разрешает сохранить замену с прежним ключом. [Локальное хранение](Local%20installation%20setup.md#повтор-authorize-после-потери-связи).

### Peer signing ротации voter (04.09-B3a)

Запрос `VoterCredentialSigningRequest` направляется по принятому peer адресу владельца issuer epoch через существующий authenticated client. Локальный NodeId/storage/credential должны совпадать с субъектом и прежним credential ротации. Issuer проверяет verified envelope, текущий term, свой NodeId/storage/credential и exact accepted Authorize. B1 сверяет текущий operational key PoP, CSR, process/membership, operation ID, digest и индекс принятого результата. Стороны повторяют majority и проверку accepted authority после подписи/обмена.

Ответ `EnrollmentIssuedArtifact` принимается при совпадении peer challenge/request ID/term, выбранного issuer credential, принятых authority и шаблона. DER проверяется по digest, цепочке и ожидаемому leaf. После потери ответа повтор того же intent при свежей authority возвращает те же сохранённые DER. Успешная подпись оставляет Bind и Ready самостоятельными переходами.

B3a проверена с подставным обменом на dedicated цепочке и одним доверенным credential на issuer endpoint. При неоднозначности adapter закрывается. Рабочие регистрации managed Bootstrap Direct добавлены в 04.09.03. Общий dispatcher сохраняет отказ. Legacy CRL/proxy, dedicated runtime policy и TLS/pool switch при overlap относятся к B3b. [Проверки и ограничения](Testing.md#voter-credential-peer-0409b3a-2026-11-18).

<a id="voter-credential-overlap-0409b3b1"></a>

### Доверие к предъявленному voter credential при overlap

Accepted peer registry и dedicated TLS применяют общую политику ротации. После Bind прежний leaf допустим до `min(Bind + 24 ч, expiry)` при действующем credential и отсутствии accepted retirement. На самой границе доверие закрывается. Отсутствующая или противоречивая граница также закрывает доверие. Legacy Direct сохраняет требование CRL, proxy требует доверенный источник и `Ssl-Client-Verify: SUCCESS`. Эти проверки продолжают действовать независимо от accepted registry.

Dedicated TLS сверяет exact DER и issuer, а `DynamicPeerTls` на одном принятом срезе сопоставляет предъявленный leaf с ID, fingerprint и node/storage/address из authenticated peer envelope. `PeerServerPin.ResolvePresentedAsync` после проверки цепочки возвращает exact accepted credential по fingerprint и host/port, допускает overlap только для одной identity и повторяет lookup по ID.

<a id="voter-credential-managed-response-0409b3b2"></a>

### Привязка ответа managed peer RPC к TLS-сертификату

В действующем managed Direct клиенте `PeerClientHandler` указывает ожидаемые NodeId/storage/address. До отправки HTTP он проверяет предъявленный server leaf через `PeerServerPin` и сохраняет результат проверки для этого запроса. ID из ответного envelope должен совпасть с ID предъявленного leaf. При получении ответа повторно читается accepted registry и проверяется совпадение всей записи, включая fingerprint. Старый и новый leaf проходят в пределах согласованного overlap при совпадении всех проверок.

Обычный managed peer RPC использует HTTP/1.1 и закрывает соединение после обмена. `PlaintextStreamFilter` получает только первый запрос соединения. Его проверенное наблюдение voting server leaf может подготовить пул для последующего typed renewal.

<a id="voter-credential-typed-direct-0409b3b2"></a>

Для typed renewal на managed Direct адрес, NodeId и storage issuer берутся из accepted voter. Клиент сверяет SHA-256 фактического `SslStream.LocalCertificate` с предыдущим credential из accepted renewal proof. `PeerServerPin` разрешает точный ID по фактическому server leaf и accepted registry, включая два разных допустимых leaf одного voter при overlap. После проверки имени и цепочки клиент сверяет exact ID/fingerprint и accepted signing evidence до HTTP и повторяет сверку после ответа и majority barrier. Issuer использует ID/fingerprint client leaf, удостоверенные middleware текущего запроса, и сверяет их со свежими accepted данными до и после signer.

Для typed renewal в managed Direct первое проверенное наблюдение TLS закрепляет отдельный HTTP/1.1 pool за парой из локального снимка и точного server ID/fingerprint для выбранного NodeId/storage/address. При отсутствии наблюдения используется существующий свежий путь. Каждый новый handshake пула сохраняет DNS/name/chain проверки, отключает TLS resumption и сверяет оба предъявленных leaf до HTTP. При reuse транспорт сверяет срок и accepted запись pin, а Web проверяет exact signing evidence на текущем срезе до отправки и после ответа с повторным majority barrier. ID из reply envelope обязан совпасть с pin.

Истечение срока, потеря exact accepted записи или предъявление другого удостоверенного leaf той же accepted identity закрывают выбранный пул. Вызов возвращает отказ. Только отдельный последующий вызов может заново удостоверить сервер на свежем TLS. Сетевой отказ и ID из ответа сами по себе pin не заменяют. Тело одного typed запроса передаётся сериализатору для записи один раз. [Изолированные проверки и границы](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09-b3b2-managed-direct.md#voter-credential-managed-pool-0409b3b2).

Legacy Direct typed renewal использует тот же механизм фиксированной пары. Первый typed запрос удостоверяет оба leaf на новом соединении. Новые соединения пула повторно удостоверяют пару с выбранной политикой цепочки. Отказ проверки цепочки или exact accepted pin прекращает текущий вызов и закрывает данный пул. Обычные исходящие legacy запросы используют отдельный прежний handler. Входящий `RENEW` и исходящий запрос с обязательной привязкой требуют `TlsBoundary=Direct`. TCP TLS passthrough передаёт исходное TLS-соединение Direct listener со всеми его проверками. `NginxIsolatedHttp` сохраняет ручной процесс и существующие [mTLS/CRL и proxy gates](Cluster%20runtime.md).

На входе legacy Direct handshake и каждый RPC выбирают политику по удостоверяемому credential. Для ручного leaf сохраняются настроенный client CA, EKU, SAN и online CRL. Для leaf ротации обязательны exact accepted Bind, DER/pin, NodeId/storage/address, issuer epoch/purpose и accepted revocation. Dedicated проверка цепочки выполняется локально без AIA и CRL fetch. Отказ выбранной политики завершает проверку. Для RENEW и HANDOFF middleware также берёт оба leaf из фактического `SslStream`, сверяет remote с проверенным клиентом и разрешает local по accepted fingerprint и identity для reply. TLS resumption и renegotiation отключены на legacy Direct listener.

Изолированный `POST /internal/cluster/v1/enrollment/handoff` использует typed Direct transport и ограничения peer enrollment. Запрос связывает IssueId, CredentialRevision, принятый Bind digest и fingerprint нового leaf. Другой работающий voter сверяет предъявленный client leaf и свой server leaf текущего соединения с принятым состоянием после majority barrier. Клиент проверяет pin предъявленного server leaf и принятые доказательства до отправки и после ответа. Порт подтверждает сверенный запрос. Публикация leaf и accepted retirement выполняются отдельными шагами. [Локальная оркестрация](Local%20installation%20setup.md#worker-расписания-ротации).

B1 old-key PoP, подпись, проверка артефакта и pre-Bind используют ту же развилку доверия. Pre-Bind требует живой старый leaf, а повтор exact committed Bind сверяет новый leaf по принятой ревизии. При исходящем typed RPC предварительная проверка TLS сохраняет проверку имени и обходится без сетевых загрузок. Ручная ветка строит системную serverAuth цепочку с online CRL и фиксирует её для пула. Dedicated ветка сверяет exact accepted Bind и живое доверие перед повторным использованием соединения. Bootstrap ManagedRestart сверяет latest Bind в локальном replay для native Start. Рабочий TLS и новый Process/Enable используют установленный leaf после свежей сверки с majority. [Проверки и продолжение B3b2](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust/04.09-credential-renewal/04.09-b3b2-managed-direct.md#voter-credential-managed-restart-0409b3b2).

Явная managed Direct публикация использует подтверждённую CredentialRevision для исходящего envelope/TLS/handler, входящего TLS, issuer evidence и reply envelope. [Локальная публикация и восстановление](Local%20installation%20setup.md#voter-credential-local-publication-0409b3b2).

### Остальные enrollment и runtime boundaries

Pre-Bind локальная часть **04.09-B2a** сохраняет исходный voter intent/новый key/CSR и exact accepted authorization/DER pin в защищённом local storage, без onboarding attempt и без Bind/Ready. Каждая запись pin повторяет B1 fresh majority/PoP/accepted checks. Offline read после Bound/retirement использует исторически проверенные сохранённые bytes и не вызывает signer; он не устанавливает CredentialRevision. Bind evidence/reconciliation предоставляет B2b1; post-Bind manifest/ref/install/confirmation и recovery — B2b2, затем B3 подключает trust/runtime. [Формат, порядок и ограничения локального хранения](Local%20installation%20setup.md#подготовка-локальной-ротации-voter-до-bind-0409-b2a), [проверки Bind evidence](Testing.md#voter-credential-local-bind-0409b2b1-2026-11-18).

`EnrollmentProofs` подписывает canonical request/action/IDs/BootId/256-bit BootChallenge/ProcessEpoch/server nonce/request digest. Nonce одноразовый, 60 секунд monotonic, максимум 512; restart очищает cache. Schema-3 reservation сохраняет BootChallenge и issuance authorization index; resume ждёт прежнюю двухминутную lease, меняет BootId/challenge и повышает ProcessEpoch. Старый challenge/epoch отвергается. Proof helpers соединены с production enrollment authority для E1–E4/resume; это не полный Join.

`EnrollmentTransport` — отдельный bounded browser HTTPS client: fixed endpoint enum, тот же выбранный origin, system TLS name/chain, connect 3 секунды/request 10 секунд, request/response ≤64 KiB, strict JSON, без redirect/cookies/proxy/compression/logging. DNS/IP policy проверяет **весь** resolved набор на каждом dial и соединяется с проверенным IP при сохранении SNI; private/VPN CIDR разрешаются только установкой. `PeerServerPin` отдельно связывает TLS server certificate с точной accepted authority (host+port) до отправки managed peer HTTP. Server routes, authenticated descriptor и двусторонние probes подключены отдельно от этого transport; их наличие не подтверждено реальной сетью.

Новая trust compatibility — `3.0/3/3/3/1/6.10.0`. V1/V2 остаются только для прежних контрактов; trust state и его исторические ancestors требуют v3. Новый Web acceptance не принимает schema-2 onboarding на v3; старый WAL остаётся читаемым. Defaults и конфигурация установки не менялись. До включения нужны согласованная схема и все voters одной версии.

`GenesisPreparation` сохраняет intent до native эффекта; `GenesisRuntimePreparation` вооружает exact permit только для этой identity/account. `ManagedBootstrapLifecycle` проходит quarantine, accepted baseline/account, fresh majority barrier, process registration, отдельные activation/enable grants и атомарный отзыв setup. `ISetupAuthority`, `IManagedRuntimeAdmission` и узкая `EnrollmentAuthority` подключены production DI. Подпись CA или local save сами Ready не открывают.

После Enable нового первого InvitationAdministration выдаёт schema-3 команду через существующие protected Pending/dispatcher/WAL. Нужны accepted common Administrator и повторная проверка его пароля; setup identity этого права не получает. Код возвращается только с первоначальным подтверждённым ответом: при потере ответа принятый результат сохраняется, повтор того же OperationId не делает новый native effect и не раскрывает code. Новый код получается явной заменой приглашения. Sealed restart сохраняет принятое приглашение и после нового ProcessEpoch/Enable позволяет выдать замену по schema3 без повторного genesis/account. [Проверки 04.05](Testing.md#bootstrap-и-приглашение-0405-2026-11-15); это не приёмка существующего ручного кластера или полного Join.

Dedicated browser HTTPS `/internal/enrollment/v1/{discovery,nonce,state,reserve,issue,admit,resume,renew,probe}` использует strict canonical JSON, 64 KiB/10 секунд, 30 запросов и 5 отказов/минуту. Invitation передаётся только исходному system-TLS origin. Authenticated descriptor связывает request/nonce/process/issuance/registry. Journal сохраняет исходные команды до consensus, DER до ответа. Read-state после fresh barrier разрешает потерянный reserve response; protected invitation удаляется до issue после доказанного reserve. Resume требует прежний key/CSR/IDs, новый BootChallenge, истечение старой lease и accepted ProcessEpoch+1.

Клиент закрепляет полученные IssueId и весь issuance template, затем DER: другой даже корректный leaf от прежнего CA отвергается. До Bind допустимо отсутствие уже полученного DER только в CertificateAuthorized ответах read-state/resume/process-renew, пока сервер не включает artifact в descriptor. Bound возвращает проверенный descriptor с прежними DER; клиент сохраняет именно его. Поэтому повтор Bind, в том числе после process renewal, не теряет pin. Admitted descriptor требует leaf, точный registry fingerprint и nonvoter без activation.

E4 сохраняет SQL trust intent перед protected content-addressed manifest в `StateDirectory/enrollment-trust`. Manifest содержит исходный leaf, anchor и registry/pins. Digest/ref/install/attempt/key/identity сверяются при чтении и startup; неизвестный файл, повреждённый ref или orphan credential не активируются. Повтор завершает только тот же сохранённый intent. Peer-пробы используют отдельный фиксированный `/internal/enrollment-peer/v1/probe` на Direct mTLS listener, проверяют обе стороны, имя/chain/pin/SAN/identity и текущую process lease. Узкий pending TLS session живёт ≤2 минут и обслуживает только probe: Raft/commands/common gates не открываются. HTTP/DNS/TLS проверены doubles и локальной криптографией, не реальной сетью.

При отказе любого направления итоговая E4 evidence не сохраняется. Прежний accepted E3 nonvoter и локальный trust intent могут остаться для повторения той же попытки; это не успешное завершение E4, не snapshot grant, membership или Ready. Изолированные проверки 04.06 подтверждают также закрытый ordinary RPC при активном pending TLS session и SQL intent до файлового эффекта; provider atomicity и настоящие TLS handshakes не подтверждены.

`ManagedStorageSeals` связывает AEAD seal с InstallIdentity/profile sequence/manifest и настоящим snapshot/SQL checkpoint. Новый первый создаёт его до CommonOpen; после дальнейшего durable apply checkpoint обновляется. `ManagedRestartPreparation` восстанавливает только целый прежний storage без majority до native Start; прежний account не создаётся повторно. Общий доступ требует новый barrier/ProcessEpoch/Enable. Missing/truncated WAL, другой manifest, SQL rollback, revoked/removed identity и offline markers закрывают этот путь. Полный клон всех файлов/keys остаётся неотличимым при компрометации ОС и не получает isolation proof. Изолированный тест повторно открывает WAL и проходит новый Enable; выборы и Ubuntu/SQL не проверены.

Оставшийся обязательный объём **этого этапа 04**: replacement/retirement issuer; полный renewal/rotation/retirement leaf с overlap; законные process/activation/enable exchanges для последующих voters; вся negative/crash матрица и минимальное подключение Join UI. Первоначальный manual provisioning/Register завершён в 04.07, typed remote routing — в 04.08. Текущий ManagedRestart подключён к новому первому Bootstrap; завершённый Join ещё не существует. Это не переносится в 05: там только snapshot/membership orchestration полного Join. Этап остаётся `in-progress`.

## Принятое состояние и секрет

[OnboardingReducer](../../UptimeHarbor.Application/Cluster/Onboarding/OnboardingReducer.cs) работает внутри прежних RevisionDispatcher → RevisionReducer → RevisionApplyEngine → projection UoW. Отдельного журнала/глобального UoW нет. Приглашение хранит типизированный статус, OperationId выдачи, accepted delegation и verifier; попытка — точный EnrollmentRequest, digest, AttemptId, исходный reserve OperationId, шаги, ProcessEpoch и отдельные сроки. Допустимо одно неиспользованное приглашение и один незавершённый Join.

Код — криптографически случайный RFC UUID v4. SHA-256 verifier разделён доменом `UptimeHarbor.Invitation.v1`, ClusterId/Generation/InvitationId; сравнение constant time. Plaintext существует только в памяти первоначальной выдачи и её первом подтверждённом HTTP-ответе. Protected Pending содержит verifier, а не код. Потеря ответа, deferred acceptance или retry возвращает состояние без восстановления plaintext; новое приглашение требует отдельного OperationId и явной замены. Замена отзывает Unused/Reserved до Admit, после Admit сохраняет прежнюю попытку и не освобождает её Join slot.

Reserve атомарно связывает NodeId/storage generation/canonical HTTPS peer URI/SPKI/CSR digest с AttemptId и exact request digest. Другой запрос/identity/key не получает эту reservation. Оригинальный OperationId возвращает прежний результат; новый reserve-запрос не продлевает истёкшее полномочие. Terminal invitation никогда не становится Unused повторно. Неизвестный результат обозначается Unconfirmed; LocalPending выдаётся только для реально сохранённой заявки.

## Время и продолжение

| Полномочие | Правило |
| --- | --- |
| Invitation | 15 минут от accepted coordinator time; при `now >= expiry` код закрыт |
| Reservation | 30 минут до первого Admit; истечение требует Pause/Continue той же identity либо отмены |
| Admission | 10 минут от accepted Admit/Renew; renew при остатке строго меньше 3 минут, возможно после expiry через будущий enrollment proof |
| Reauthentication | Не старше 5 минут и не из будущего; действующий accepted Administrator и точная credential revision |
| Process | BootId + ProcessEpoch, lease 2 минуты; новый BootId ждёт истечения старой lease и повышает epoch ровно на один |
| Inactivity | 24 часа без нового подтверждённого progress index → PauseAwaitingAdministrator; renew/poll не являются прогрессом |

OnboardingAcceptance назначает CoordinatorAtUtc/Term после majority strong barrier, проверки native term/tokens, текущего instance и accepted recovery/readiness. Произвольный CreatedAtUtc не управляет новыми сроками. Immutable request digest исключает только stamp; digest WAL/receipt покрывает полные принятые байты. Replay не читает локальные часы.

На reserve и критичных продолжениях reducer проверяет accepted enabled/role/credential revision автора delegation. Continue требует нового пароля действующего администратора и заменяет delegation revision без смены identity. Непрерывный catch-up с новым доказанным прогрессом не имеет общего ограничения 24 часа. Enrollment authority должна доказать содержательность progress/PoP; сам номер индекса от клиента такого права не даёт.

AuthorizeIssue/Bind/Admit и подготовленные process-bound Request/Authorize/ConfirmMembership используют прежние проверки и reducer состава. Admit одним write set потребляет приглашение, создаёт nonvoter и связывает credential. Legacy команды не могут обойти новые сроки/delegation. До принятой заявки состава Cancel отзывает credential, сохраняет tombstone nonvoter и освобождает попытку. При незавершённой заявке либо принятом voter возвращается MembershipPreservedRemovalRequired; нужна штатная сверка/операция удаления. Старый Activate не активирует новую onboarding identity.

## Хранение и совместимость

OnboardingImage и data contracts включены в RevisionImage; [OnboardingSnapshot](../../UptimeHarbor.Application/Cluster/Onboarding/OnboardingSnapshot.cs) проверяет состояния, binding, результаты и projection payload. `onboarding_invitations` хранит одну OnboardingProjection на приглашение с version/status constraints, canonical payload и concurrency по LogIndex. Decision/receipt/cursor сохраняются прежним projection UoW. Схема требует подготовленной [миграции](Database%20migrations.md#приглашения-2026-11-03), к БД она не применялась.

Поддерживается точная compatibility `2.0/2/2/2/1/6.10.0`: ProtocolMajor/CommandSchema/SnapshotFormat/SqlSchema = 2, SerializerVersion = 1, DotNext = 6.10.0. Старый набор v1 остаётся допустим для прежних сценариев, но новый command/snapshot отвергается до изменения состояния. Defaults и установка не менялись. Перед включением нужны согласованное обновление всех voters и отдельная подготовка схемы; mixed rollout не поддерживается.

Strict codecs ограничивают размер/глубину, отвергают duplicate/unknown/missing/null required fields, неизвестные версии и неканонические digest/UTC. Ошибки не содержат исходный JSON или inner exception. Snapshot manifest и body проверяются до install; потоковый body имеет ограничение отдельного JSON token. RecoveryBaseline сохраняет onboarding/contracts всех предыдущих generations как историю; новый active root их не наследует. Compatibility и validation обходят также Ancestors.

[ILocalOnboardingAttemptRepository](../../UptimeHarbor.Application/Abstractions/Persistence/ILocalOnboardingAttemptRepository.cs) и IOnboardingProgressUnitOfWork — подготовленные независимые локальные порты CAS/сохранения шага до сети. LocalOnboardingAttempt.Reserved удаляет protected invitation и сохраняет IDs. Их persistence adapter и управление локальными ключами принадлежат этапу 03; в 02 реализации нет.

## HTTP и production gates

`/api/admin/cluster/invitations` предоставляет Issue/Replace и защищённое чтение; подмаршруты — Revoke/Continue/Cancel. Все mutations имеют Administrator, antiforgery, лимит 4096 байт и 5 запросов в минуту на IP. Password reauthentication использует существующий ILocalAccountLogin с lockout; после await и при accepted apply права проверяются снова. Actor из JSON не принимается. DTO и ServiceResult envelope не выдают verifier/credentials/payload; ответ Code имеет no-store, не передаётся через URL/SignalR.

InvitationAdministration регистрируется в AddWebPresentation, acceptance/transport — AddClusterWeb; полный production graph включает оба модуля. Acceptance использует ClusterRaftHandle без зависимости dispatcher → runtime → sender gate. Peer batch отвергает coordinator onboarding/чужой storage/stamp до dispatch.

Production IEnrollmentAuthority использует EnrollmentAuthority с exact command digest capability только внутри проверенного dedicated gateway. Enrollment endpoints/descriptor, nonce, limiter и E1–E4 подключены; они не разрешают последующие online grants, native Join или activation новой попытки. UnavailableEnrollmentAuthority остаётся закрытой реализацией для неполного графа; production registrations не используют doubles. Полный жизненный цикл issuer и последующих voters остаётся собственным объёмом 04.

OnboardingAudit журналирует безопасные IDs и принятые переходы Issued/Replaced/Revoked/Reserved/Consumed/Expired/Paused/Continued после apply; обычный replay известного OperationId не пишет второй success. Отказы не журналируют пароль/code/verifier, URI, CSR, сертификат, payload или raw exception. Exactly-once текстовых логов при аварии между apply и записью не обещается.
