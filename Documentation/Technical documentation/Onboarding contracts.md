# Приглашения и контракты подключения

Реализованы контракты этапа 02, локальный setup/runtime этапа 03 и выполняемый production путь нового первого Bootstrap этапа 04. Dedicated enrollment второго доходит до accepted nonvoter admission, файловой установки trust и двух peer TLS-проб; runtime второго остаётся закрыт до snapshot/membership этапа 05. Полный этап 04 ещё не завершён: оставшийся собственный объём указан ниже. Перенос, sender и полный мастер не реализованы. [Локальное устройство](Local%20installation%20setup.md).

## Промежуточная граница этапа 04 (2026-11-03)

Работа приостановлена по просьбе пользователя; этап остаётся `in-progress`. [Зафиксированный остаток и известные проблемы](../Plans/node-onboarding-ui-2026-11-02-%28in-progress%29/04-enrollment-and-trust.md#результат), [проверки и незакрытый повтор preflight](Testing.md#точка-остановки-этапа-04-2026-11-03). Этот раздел отражает частичную production integration, а не полную приёмку 04.

`EnrollmentCertificates` создаёт новый специализированный P-256/SHA-256 application CA с critical pathLen=0, keyCertSign/cRLSign и фиксированными purpose/cluster/generation/epoch в URI SAN. CSR проверяется по PKCS#10 signature, P-256/SPKI/digest; requested extensions отвергаются. Leaf имеет точные SAN DNS/IP/node/storage/credential, critical CA=false/digitalSignature/clientAuth/serverAuth, serial и срок. Проверки выполняются локально без загрузок и изменения system trust. Dedicated helper не использует CRL: он требует будущей accepted application revocation на RPC boundary; legacy Direct CRL не отключён.

Schema-3 `InitializeCluster`, `RegisterEnrollmentIssuer`, `RetireEnrollmentIssuer`, `RevokeEnrollmentIssuer` проходят прежний WAL/reducer/projection. Public issuer хранится в `OnboardingContracts.Issuers` и `enrollment_issuers`; snapshot сверяет projection/owner/revision/digests и recovery ancestors. Registration требует актуального accepted Administrator, reauthentication ≤5 минут и voting owner; retired/revoked epoch не разрешает новую выдачу. Genesis требует **уже закреплённого** точного GenesisAuthorization в trusted initial image, пустой новой сетки, отдельного account digest и создаёт Node прежде credential. Он не выводит разрешение из своего входящего payload. Trusted genesis image и production lifecycle подключены для нового первого; полный provisioning/replacement issuer существующего кластера ещё не доведён.

`GenesisWriterPermit` допускает только два заранее привязанных payload/OperationId: InitializeCluster и затем точный BootstrapAccount. Account result закрывает permit; повтор результата обслуживает dispatcher. DotNext adapter дополнительно требует реального singleton leader/term, recovered prefix, membership и Database/Projection/Storage/Clock. Общий CanWork от permit не открывается; import marker/перенос не реализованы. Permit в production DI создаётся невооружённым; Web не может его вооружить произвольной командой.

`EnrollmentSigner` принимает только request/template/CSR. Под issuer lock `EnrollmentSigningAuthorization` выполняет native linearizable barrier и сверяет текущую принятую выдачу, delegation, process lease, issuer owner/epoch/pins и отсутствие maintenance. DotNext 6.10.0 документирует linearizable read на follower; изменения term/leader/membership закрывают результат. Полный production путь удалённого issuer/follower ещё не завершён. Private key читается только из локального AES-GCM ref. `EnrollmentSigningJournal` фиксирует DER по IssueId до ответа; retry сохраняет прежние DER и authorization index. Это public artifact, не operational credential. Register/Authorize сами ключ не создают; production enrollment controller подключён.

`EnrollmentProofs` подписывает canonical request/action/IDs/BootId/256-bit BootChallenge/ProcessEpoch/server nonce/request digest. Nonce одноразовый, 60 секунд monotonic, максимум 512; restart очищает cache. Schema-3 reservation сохраняет BootChallenge и issuance authorization index; resume ждёт прежнюю двухминутную lease, меняет BootId/challenge и повышает ProcessEpoch. Старый challenge/epoch отвергается. Proof helpers соединены с production enrollment authority для E1–E4/resume; это не полный Join.

`EnrollmentTransport` — отдельный bounded browser HTTPS client: fixed endpoint enum, тот же выбранный origin, system TLS name/chain, connect 3 секунды/request 10 секунд, request/response ≤64 KiB, strict JSON, без redirect/cookies/proxy/compression/logging. DNS/IP policy проверяет **весь** resolved набор на каждом dial и соединяется с проверенным IP при сохранении SNI; private/VPN CIDR разрешаются только установкой. `PeerServerPin` отдельно связывает TLS server certificate с точной accepted authority (host+port) до отправки managed peer HTTP. Server routes, authenticated descriptor и двусторонние probes подключены отдельно от этого transport; их наличие не подтверждено реальной сетью.

Новая trust compatibility — `3.0/3/3/3/1/6.10.0`. V1/V2 остаются только для прежних контрактов; trust state и его исторические ancestors требуют v3. Новый Web acceptance не принимает schema-2 onboarding на v3; старый WAL остаётся читаемым. Defaults и конфигурация установки не менялись. До включения нужны согласованная схема и все voters одной версии.

`GenesisPreparation` сохраняет intent до native эффекта; `GenesisRuntimePreparation` вооружает exact permit только для этой identity/account. `ManagedBootstrapLifecycle` проходит quarantine, accepted baseline/account, fresh majority barrier, process registration, отдельные activation/enable grants и атомарный отзыв setup. `ISetupAuthority`, `IManagedRuntimeAdmission` и узкая `EnrollmentAuthority` подключены production DI. Подпись CA или local save сами Ready не открывают.

Dedicated browser HTTPS `/internal/enrollment/v1/{discovery,nonce,state,reserve,issue,admit,resume,renew,probe}` использует strict canonical JSON, 64 KiB/10 секунд, 30 запросов и 5 отказов/минуту. Invitation передаётся только исходному system-TLS origin. Authenticated descriptor связывает request/nonce/process/issuance/registry. Journal сохраняет исходные команды до consensus, DER до ответа. Read-state после fresh barrier разрешает потерянный reserve response; protected invitation удаляется до issue после доказанного reserve. Resume требует прежний key/CSR/IDs, новый BootChallenge, истечение старой lease и accepted ProcessEpoch+1.

E4 сохраняет SQL trust intent перед protected content-addressed manifest в `StateDirectory/enrollment-trust`. Manifest содержит исходный leaf, anchor и registry/pins. Digest/ref/install/attempt/key/identity сверяются при чтении и startup; неизвестный файл, повреждённый ref или orphan credential не активируются. Повтор завершает только тот же сохранённый intent. Peer-пробы используют отдельный фиксированный `/internal/enrollment-peer/v1/probe` на Direct mTLS listener, проверяют обе стороны, имя/chain/pin/SAN/identity и текущую process lease. Узкий pending TLS session живёт ≤2 минут и обслуживает только probe: Raft/commands/common gates не открываются. HTTP/DNS/TLS проверены doubles и локальной криптографией, не реальной сетью.

`ManagedStorageSeals` связывает AEAD seal с InstallIdentity/profile sequence/manifest и настоящим snapshot/SQL checkpoint. Новый первый создаёт его до CommonOpen; после дальнейшего durable apply checkpoint обновляется. `ManagedRestartPreparation` восстанавливает только целый прежний storage без majority до native Start; прежний account не создаётся повторно. Общий доступ требует новый barrier/ProcessEpoch/Enable. Missing/truncated WAL, другой manifest, SQL rollback, revoked/removed identity и offline markers закрывают этот путь. Полный клон всех файлов/keys остаётся неотличимым при компрометации ОС и не получает isolation proof. Изолированный тест повторно открывает WAL и проходит новый Enable; выборы и Ubuntu/SQL не проверены.

Оставшийся обязательный объём **этого этапа 04**: production provisioning/register/replacement issuer в работающем ручном кластере и выдача через удалённый issuer; полный renewal/rotation/retirement leaf с overlap; законные process/activation/enable exchanges для последующих voters; вся negative/crash матрица и минимальное подключение Join UI. Текущий ManagedRestart подключён к новому первому Bootstrap; завершённый Join ещё не существует. Это не переносится в 05: там только snapshot/membership orchestration полного Join. Этап остаётся `in-progress`.

## Принятое состояние и секрет

[OnboardingReducer](../../UptimeHarbor.Application/Cluster/Onboarding/OnboardingReducer.cs) работает внутри прежних RevisionDispatcher → RevisionReducer → RevisionApplyEngine → projection UoW. Отдельного журнала/глобального UoW нет. Приглашение хранит типизированный статус, OperationId выдачи, accepted delegation и verifier; попытка — точный EnrollmentRequest, digest, AttemptId, исходный reserve OperationId, шаги, ProcessEpoch и отдельные сроки. Допустимо одно неиспользованное приглашение и один незавершённый Join.

Код — криптографически случайный RFC UUID v4. SHA-256 verifier разделён доменом `UptimeHarbor.Invitation.v1`, ClusterId/Generation/InvitationId; сравнение constant time. Plaintext существует только в памяти первоначальной выдачи и её первом подтверждённом HTTP-ответе. Protected Pending содержит verifier, а не код. Потеря ответа, deferred acceptance или retry возвращает состояние без восстановления plaintext; новое приглашение требует отдельного OperationId и явной замены. Замена отзывает Unused/Reserved до Admit, после Admit сохраняет прежнюю попытку и не освобождает её Join slot.

Reserve атомарно связывает NodeId/storage generation/canonical HTTPS peer URI/SPKI/CSR digest с AttemptId и exact request digest. Другой запрос/identity/key не получает эту reservation. Оригинальный OperationId возвращает прежний результат; новый reserve-запрос не продлевает истёкшее полномочие. Terminal invitation никогда не становится Unused повторно. Неизвестный результат обозначается Unconfirmed; LocalPending выдаётся только для реально сохранённой заявки.

## Время и продолжение

| Полномочие | Правило |
| --- | --- |
| Invitation | 15 минут от accepted coordinator time; при `now >= expiry` код закрыт |
| Reservation | 30 минут до первого Admit; истечение требует Pause/Continue той же identity либо отмены |
| Admission | 10 минут от accepted Admit/Renew; renew при остатке строго меньше 3 минут, возможно после expiry через будущий enrollment proof |
| Reauthentication | Не старше 5 минут и не из будущего; действующий accepted Administrator и точная credential revision |
| Process | BootId + ProcessEpoch, lease 2 минуты; новый BootId ждёт истечения старой lease и повышает epoch ровно на один |
| Inactivity | 24 часа без нового подтверждённого progress index → PauseAwaitingAdministrator; renew/poll не являются прогрессом |

OnboardingAcceptance назначает CoordinatorAtUtc/Term после majority strong barrier, проверки native term/tokens, текущего instance и accepted recovery/readiness. Произвольный CreatedAtUtc не управляет новыми сроками. Immutable request digest исключает только stamp; digest WAL/receipt покрывает полные принятые байты. Replay не читает локальные часы.

На reserve и критичных продолжениях reducer проверяет accepted enabled/role/credential revision автора delegation. Continue требует нового пароля действующего администратора и заменяет delegation revision без смены identity. Непрерывный catch-up с новым доказанным прогрессом не имеет общего ограничения 24 часа. Enrollment authority должна доказать содержательность progress/PoP; сам номер индекса от клиента такого права не даёт.

AuthorizeIssue/Bind/Admit и подготовленные process-bound Request/Authorize/ConfirmMembership используют прежние проверки и reducer состава. Admit одним write set потребляет приглашение, создаёт nonvoter и связывает credential. Legacy команды не могут обойти новые сроки/delegation. До принятой заявки состава Cancel отзывает credential, сохраняет tombstone nonvoter и освобождает попытку. При незавершённой заявке либо принятом voter возвращается MembershipPreservedRemovalRequired; нужна штатная сверка/операция удаления. Старый Activate не активирует новую onboarding identity.

## Хранение и совместимость

OnboardingImage и data contracts включены в RevisionImage; [OnboardingSnapshot](../../UptimeHarbor.Application/Cluster/Onboarding/OnboardingSnapshot.cs) проверяет состояния, binding, результаты и projection payload. `onboarding_invitations` хранит одну OnboardingProjection на приглашение с version/status constraints, canonical payload и concurrency по LogIndex. Decision/receipt/cursor сохраняются прежним projection UoW. Схема требует подготовленной [миграции](Database%20migrations.md#приглашения-2026-11-03), к БД она не применялась.

Поддерживается точная compatibility `2.0/2/2/2/1/6.10.0`: ProtocolMajor/CommandSchema/SnapshotFormat/SqlSchema = 2, SerializerVersion = 1, DotNext = 6.10.0. Старый набор v1 остаётся допустим для прежних сценариев, но новый command/snapshot отвергается до изменения состояния. Defaults и установка не менялись. Перед включением нужны согласованное обновление всех voters и отдельная подготовка схемы; mixed rollout не поддерживается.

Strict codecs ограничивают размер/глубину, отвергают duplicate/unknown/missing/null required fields, неизвестные версии и неканонические digest/UTC. Ошибки не содержат исходный JSON или inner exception. Snapshot manifest и body проверяются до install; потоковый body имеет ограничение отдельного JSON token. RecoveryBaseline сохраняет onboarding/contracts всех предыдущих generations как историю; новый active root их не наследует. Compatibility и validation обходят также Ancestors.

[ILocalOnboardingAttemptRepository](../../UptimeHarbor.Application/Abstractions/Persistence/ILocalOnboardingAttemptRepository.cs) и IOnboardingProgressUnitOfWork — подготовленные независимые локальные порты CAS/сохранения шага до сети. LocalOnboardingAttempt.Reserved удаляет protected invitation и сохраняет IDs. Их persistence adapter и управление локальными ключами принадлежат этапу 03; в 02 реализации нет.

## HTTP и production gates

`/api/admin/cluster/invitations` предоставляет Issue/Replace и защищённое чтение; подмаршруты — Revoke/Continue/Cancel. Все mutations имеют Administrator, antiforgery, лимит 4096 байт и 5 запросов в минуту на IP. Password reauthentication использует существующий ILocalAccountLogin с lockout; после await и при accepted apply права проверяются снова. Actor из JSON не принимается. DTO и ServiceResult envelope не выдают verifier/credentials/payload; ответ Code имеет no-store, не передаётся через URL/SignalR.

InvitationAdministration регистрируется в AddWebPresentation, acceptance/transport — AddClusterWeb; полный production graph включает оба модуля. Acceptance использует ClusterRaftHandle без зависимости dispatcher → runtime → sender gate. Peer batch отвергает coordinator onboarding/чужой storage/stamp до dispatch.

IEnrollmentAuthority реализован UnavailableEnrollmentAuthority и всегда отказывает. Signer/nonce/transport и issuer registry описаны выше; enrollment endpoint, authenticated descriptor, grants и реальный допуск ещё отсутствуют. Limiter 5/origin, 30/endpoint в минуту пока не подключён к выделенному server endpoint. Native Join/activation новой попытки закрыты. Тестовые reducer fixtures создают записи; production registrations не используют doubles.

OnboardingAudit журналирует безопасные IDs и принятые переходы Issued/Replaced/Revoked/Reserved/Consumed/Expired/Paused/Continued после apply; обычный replay известного OperationId не пишет второй success. Отказы не журналируют пароль/code/verifier, URI, CSR, сертификат, payload или raw exception. Exactly-once текстовых логов при аварии между apply и записью не обещается.

## Общие форматы будущих этапов

Version 1 data contracts: GenesisAuthorization связывает install/node/storage/issuer/account-or-import digest; ImportBaselineRef — migration/genesis/cut/manifest/baseline; LegacyHistory сохраняет versioned read-only partitions с исходным payload и digest. SenderAssignment определяет generation/BotId/node/storage/revision/epoch; SenderOutage, SummaryCut и CoverageReceipt задают outage, immutable cut/frontiers и IDs частей/принятых результатов покрытия чата. OnboardingDataCodec проверяет версии, IDs, границы и digest; OnboardingContractSnapshot — ссылки между форматами. Они не исполняют импорт, не назначают sender authority и не создают успех доставки.
