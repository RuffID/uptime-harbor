# Техническое задание на разработку UptimeHarbor

## 1. Общие сведения

### 1.1. Назначение

UptimeHarbor — простое Web-приложение для централизованного контроля доступности серверов и запущенных на них приложений в Docker-контейнерах посредством периодических HTTP GET-запросов.

Система должна:

- показывать текущее состояние серверов и контейнеров;
- получать фактическое имя контролируемого объекта из его HTTP endpoint;
- позволять администратору управлять объектами мониторинга, пользователями и уведомлениями;
- ограничивать видимость серверов и контейнеров для обычных пользователей;
- отправлять уведомления в Telegram при недоступности и восстановлении объекта;
- обновлять открытый Web-интерфейс без перезагрузки страницы.

### 1.2. Границы первой версии

Система развёртывается в одном экземпляре на одном Linux-сервере. Высокая доступность самого UptimeHarbor не обеспечивается.

Если сервер UptimeHarbor, приложение или PostgreSQL недоступны:

- Web-интерфейс не работает;
- проверки объектов не выполняются;
- Telegram-уведомление о падении самого UptimeHarbor не отправляется;
- работа возобновляется после восстановления инфраструктуры и запуска контейнеров.

### 1.3. Ожидаемая нагрузка

- до 10 серверов;
- до 20 контейнеров;
- до 10 пользователей;
- до 3 одновременно работающих пользователей.

## 2. Технологические ограничения

- платформа: ASP.NET Core 10;
- язык серверной части: C#;
- UI: Razor Pages;
- обновление данных в реальном времени: SignalR;
- СУБД: PostgreSQL;
- доступ к данным: Entity Framework Core с провайдером PostgreSQL;
- аутентификация и хранение паролей: ASP.NET Core Identity;
- целевая ОС: Linux;
- приложение поставляется как Docker-контейнер;
- PostgreSQL запускается отдельным контейнером;
- внешний вход: Nginx как reverse proxy;
- TLS-сертификаты выпускаются и обновляются владельцем сервера через Certbot;
- конфигурация и секреты первой версии задаются в JSON-файле, который монтируется в контейнер и не включается в Docker image.

## 3. Термины и роли

### 3.1. Объекты мониторинга

**Сервер** — логическая запись о Linux-сервере или виртуальном хостинге. Доступность определяется по вручную заданному HTTP endpoint.

**Контейнер** — контролируемое приложение, логически принадлежащее одному серверу. Доступность определяется по собственному вручную заданному HTTP endpoint.

UptimeHarbor не подключается к Docker API и не проверяет фактическое состояние Docker-контейнера.

### 3.2. Роли пользователей

**Администратор:**

- видит все серверы и контейнеры;
- создаёт и удаляет пользователей;
- назначает пользователям доступные серверы и контейнеры;
- добавляет, изменяет и удаляет объекты мониторинга;
- включает и выключает мониторинг;
- настраивает Telegram-чаты и привязки уведомлений;
- отправляет тестовые Telegram-сообщения.

**Пользователь:**

- авторизуется в системе;
- видит только разрешённые серверы и контейнеры;
- использует поиск;
- не может изменять данные и настройки.

Самостоятельная регистрация пользователей отсутствует.

## 4. Функциональные требования

### 4.1. Управление серверами

Администратор должен иметь возможность:

- добавить сервер;
- указать URL HTTP endpoint;
- указать описание;
- включить или выключить мониторинг;
- изменить URL и описание;
- удалить сервер после подтверждения.

Каждому серверу при создании присваивается GUID. Совпадающие имена серверов допускаются.

Имя сервера берётся из последнего успешного ответа endpoint. До первого успешного ответа вместо имени отображается сообщение «Имя не получено» и сокращённый GUID.

Удаление сервера должно каскадно удалять:

- принадлежащие ему контейнеры;
- разрешения пользователей;
- привязки Telegram-уведомлений;
- сохранённое текущее состояние и счётчики проверок.

Интерфейс подтверждения удаления должен показывать количество удаляемых контейнеров.

### 4.2. Контракт endpoint сервера

Endpoint вызывается методом GET и не требует авторизации.

Ожидаемый ответ:

```json
{
  "name": "vps-msk-01"
}
```

Требования к ответу:

- HTTP-статус находится в диапазоне `200–299`;
- тело является корректным JSON;
- поле `name` обязательно и содержит непустую строку.

Пример статического endpoint в Nginx:

```nginx
location = /monitor-health {
    default_type application/json;
    add_header Cache-Control "no-store";
    return 200 '{"name":"vps-msk-01"}';
}
```

Endpoint подтверждает доступность Nginx и сетевого пути до сервера. Он не предоставляет uptime Linux, загрузку CPU, память или состояние дисков.

### 4.3. Управление контейнерами

К одному серверу можно прикрепить любое количество контейнеров в пределах ожидаемой нагрузки.

Администратор должен иметь возможность:

- добавить контейнер к выбранному серверу;
- указать полный URL HTTP endpoint;
- указать описание;
- включить или выключить мониторинг;
- изменить URL и описание;
- удалить контейнер после подтверждения.

Каждому контейнеру при создании присваивается GUID. Совпадающие имена контейнеров допускаются.

Имя контейнера всегда берётся из последнего успешного ответа его endpoint и не задаётся вручную. До первого успешного ответа отображается сообщение «Имя не получено» и сокращённый GUID.

### 4.4. Контракт endpoint контейнера

Endpoint вызывается методом GET и не требует авторизации.

Ожидаемый ответ:

```json
{
  "name": "Orders API",
  "startedAtUtc": "2026-08-04T08:15:30Z"
}
```

Требования к ответу:

- HTTP-статус находится в диапазоне `200–299`;
- тело является корректным JSON;
- `name` содержит непустую строку;
- `startedAtUtc` содержит дату и время в формате ISO 8601 с UTC-маркером `Z`;
- время запуска не находится в будущем.

При успешной проверке система сохраняет последнее полученное имя и время запуска. Текущий uptime контейнера рассчитывается как разница между текущим временем UTC и `startedAtUtc`.

### 4.5. Адреса проверок

- URL задаётся администратором вручную;
- разрешены схемы HTTP и HTTPS;
- разрешены публичные адреса, адреса локальной сети и адреса Docker-сети, доступные из контейнера UptimeHarbor;
- серверы и контейнеры проверяются независимо;
- недоступность сервера не останавливает проверки его контейнеров;
- выключение мониторинга сервера не изменяет настройки его контейнеров;
- контейнер имеет собственный независимый переключатель мониторинга.

### 4.6. Выполнение проверок

Для каждого включённого объекта применяются следующие правила:

- интервал запуска проверок — 30 секунд;
- timeout одного HTTP-запроса — 30 секунд;
- одновременно выполняется не более одной проверки одного объекта;
- разные объекты могут проверяться параллельно;
- после завершения неудачной проверки система продолжает проверки без ограничения количества попыток;
- отдельные немедленные повторные запросы внутри одного цикла не выполняются.

Неудачной считается проверка, при которой:

- не удалось установить соединение;
- превышен timeout;
- получен HTTP-статус вне диапазона `200–299`;
- получен некорректный JSON;
- отсутствует обязательное поле;
- обязательное поле имеет некорректное значение.

### 4.7. Статусы объектов

Допустимые статусы:

- **Неизвестно** — мониторинг выключен либо первая проверка ещё не завершена;
- **Доступен** — последняя проверка успешна;
- **Недоступен** — получены три последовательные неудачные проверки.

Правила переходов:

1. Новый объект получает статус «Неизвестно».
2. Первая успешная проверка переводит объект в «Доступен».
3. Неудачная проверка увеличивает счётчик последовательных ошибок.
4. Успешная проверка обнуляет счётчик ошибок.
5. После третьей последовательной ошибки объект становится «Недоступен».
6. Одной успешной проверки достаточно для перехода из «Недоступен» в «Доступен».
7. Выключение мониторинга переводит объект в «Неизвестно», обнуляет счётчик ошибок и завершает текущий инцидент без уведомления о восстановлении.
8. После повторного включения цикл начинается как для нового объекта.

В PostgreSQL хранится только текущее состояние. История отдельных проверок и переходов статусов не сохраняется.

### 4.8. Главная страница

После входа пользователь видит единую главную страницу со списком доступных ему серверов и вложенных контейнеров.

Для сервера отображаются:

- имя;
- описание;
- текущий статус;
- время последней проверки.

Для контейнера отображаются:

- имя из endpoint;
- описание;
- текущий статус;
- время запуска в UTC;
- рассчитанный uptime;
- время последней проверки.

Требования к странице:

- тёмное оформление по умолчанию без светлой темы;
- адаптация под настольный компьютер и мобильный экран;
- поиск одной строкой по именам и описаниям серверов и контейнеров;
- поиск выполняется только среди доступных пользователю объектов;
- изменение статусов отображается без перезагрузки страницы через SignalR;
- при разрыве SignalR-соединения клиент пытается переподключиться и после подключения перечитывает актуальное состояние.

Графики, SLA и история инцидентов отсутствуют.

### 4.9. Административный интерфейс

Помимо главной страницы должны существовать доступные только администратору экраны для:

- управления серверами и контейнерами;
- управления пользователями;
- назначения видимости;
- управления Telegram-чатами;
- настройки привязок уведомлений.

Все изменяющие HTTP-запросы должны быть защищены antiforgery-проверкой и серверной проверкой роли администратора.

### 4.10. Пользователи и видимость

- начальный администратор создаётся при первом запуске из JSON-конфигурации;
- bootstrap выполняется только при отсутствии администратора в базе;
- повторный запуск не изменяет существующий пароль;
- пароль хранится в PostgreSQL только в виде хеша ASP.NET Core Identity;
- администратор создаёт обычных пользователей и задаёт им начальные пароли;
- обычный пользователь не может менять собственную роль или права;
- администратор всегда видит все объекты.

Видимость назначается отдельно:

- на конкретный сервер;
- на конкретные контейнеры этого сервера.

Доступ к серверу не предоставляет автоматический доступ ко всем его контейнерам. Для упрощения первой версии контейнер можно назначить пользователю только вместе с его родительским сервером.

Backend обязан фильтровать данные по правам пользователя. Скрытия элементов только на стороне браузера недостаточно.

### 4.11. Telegram-уведомления

В первой версии поддерживается один Telegram-бот и любое количество зарегистрированных Telegram-чатов.

Токен бота хранится в JSON-конфигурации. В PostgreSQL хранятся:

- идентификаторы чатов;
- понятные администратору названия чатов;
- привязки серверов и контейнеров к чатам.

Один объект может быть привязан к нескольким чатам. Один чат может получать уведомления от нескольких объектов.

Уведомление о недоступности отправляется один раз после перехода в статус «Недоступен». Повторные сообщения во время продолжающейся недоступности не отправляются.

После первой успешной проверки недоступного объекта отправляется одно сообщение о восстановлении. Сообщение о восстановлении отправляется только тогда, когда ранее для текущего инцидента было отправлено сообщение о недоступности.

Если объект привязан к нескольким чатам, сообщение отправляется в каждый из них. Отказы разных объектов не группируются.

Администратор должен иметь возможность отправить тестовое сообщение в выбранный чат.

Email, webhook, Discord, Slack, расписания тишины, эскалации и повторные напоминания в первую версию не входят.

## 5. Хранение данных

PostgreSQL должна хранить:

- серверы;
- контейнеры и их связь с серверами;
- пользователей и роли Identity;
- разрешения видимости;
- Telegram-чаты;
- привязки объектов к чатам;
- текущий статус каждого объекта;
- число последовательных ошибок;
- последнее полученное имя объекта;
- последнее полученное время запуска контейнера;
- время последней проверки и последней успешной проверки;
- признак отправленного уведомления о текущей недоступности.

История проверок, инцидентов, действий пользователей и доставки уведомлений не хранится.

Все даты и время в базе и серверной логике обрабатываются в UTC.

## 6. Конфигурация

JSON-конфигурация должна предусматривать как минимум следующие группы:

```json
{
  "ConnectionStrings": {
    "PostgreSql": "Host=postgres;Port=5432;Database=uptime_harbor;Username=...;Password=..."
  },
  "BootstrapAdmin": {
    "Login": "admin",
    "Password": "change-me"
  },
  "Monitoring": {
    "IntervalSeconds": 30,
    "TimeoutSeconds": 30,
    "FailuresBeforeUnavailable": 3
  },
  "Telegram": {
    "BotToken": "..."
  }
}
```

Каждая группа прикладных настроек должна быть представлена отдельным options-типом и валидироваться при запуске. Отсутствие обязательной настройки должно приводить к понятной ошибке запуска, а не маскироваться запасным значением.

## 7. Архитектурные требования

- решение разделяется на четыре основных проекта: `UptimeHarbor.Domain`, `UptimeHarbor.Application`, `UptimeHarbor.Infrastructure` и `UptimeHarbor.Web`;
- `UptimeHarbor.Domain` содержит доменные сущности, value object, статусы и инварианты и не зависит от остальных проектов решения, ASP.NET Core и EF Core;
- `UptimeHarbor.Application` содержит use case, прикладные сервисы, DTO и абстракции репозиториев/Unit of Work и зависит только от `UptimeHarbor.Domain`;
- `UptimeHarbor.Infrastructure` содержит EF Core, ASP.NET Core Identity, PostgreSQL, HTTP- и Telegram-адаптеры и зависит от `UptimeHarbor.Application` и `UptimeHarbor.Domain`;
- `UptimeHarbor.Web` является исполняемым ASP.NET Core Razor Pages-проектом, содержит composition root, Pages и SignalR hubs и зависит от `UptimeHarbor.Application` и `UptimeHarbor.Infrastructure`;
- зависимости между проектами направлены внутрь: `Web → Infrastructure → Application → Domain`; обратные ссылки запрещены;
- разделение на проекты используется для компиляционного контроля архитектурных границ, а не для выделения распределённых сервисов;
- `Program.cs` используется как composition root и не содержит прикладной логики;
- регистрации сервисов группируются в extension-методах `IServiceCollection` по ответственности;
- прикладные сервисы зависят от типизированных options, а не от `IConfiguration`;
- проверки выполняются фоновым сервисом;
- HTTP-клиенты создаются через `IHttpClientFactory`;
- текущий статус сначала сохраняется в PostgreSQL, затем изменение публикуется подключённым клиентам через SignalR;
- отправка Telegram не должна блокировать цикл проверок других объектов;
- ошибки одного объекта не должны останавливать мониторинг остальных объектов;
- доменные переходы статусов должны быть покрыты unit-тестами;
- серверная авторизация проверяется для каждого административного действия и чтения ограниченных данных.

## 8. Логирование и обработка ошибок

Приложение пишет структурированные логи в стандартный вывод контейнера.

Должны логироваться:

- запуск и штатная остановка приложения;
- ошибки подключения к PostgreSQL;
- ошибки фонового цикла;
- ошибки отдельных HTTP-проверок без вывода секретов;
- изменения статусов;
- ошибки отправки Telegram-сообщений;
- ошибки bootstrap администратора.

Ошибка проверки одного объекта является ожидаемым результатом мониторинга и не должна завершать фоновый сервис.

Пароли, токен Telegram, строка подключения и содержимое authentication cookies не должны попадать в логи.

## 9. Развёртывание

Минимальная схема развёртывания:

```text
Internet
   |
 Nginx + Certbot
   |
 UptimeHarbor container
   |
 PostgreSQL container + persistent volume
```

Требования:

- приложение и PostgreSQL запускаются через Docker Compose;
- данные PostgreSQL хранятся в persistent volume;
- JSON-конфигурация монтируется в контейнер UptimeHarbor как внешний файл;
- наружу публикуется только Nginx;
- порт PostgreSQL не публикуется в Internet;
- контейнер приложения имеет доступ к внешним и локальным endpoint, которые требуется проверять;
- после перезапуска контейнера сохранённые пользователи, настройки и текущие состояния не теряются;
- для приложения предоставляется внутренний endpoint `/health`, подтверждающий готовность Web-приложения принимать запросы.

Резервное копирование, автоматическое обновление и развёртывание без простоя не входят в первую версию.

## 10. Требования безопасности

- весь пользовательский Web-интерфейс доступен только после аутентификации;
- административные функции защищены ролью администратора;
- пароли хешируются ASP.NET Core Identity;
- cookies имеют флаги `HttpOnly`, `Secure` в production и подходящий `SameSite`;
- ключи ASP.NET Core Data Protection сохраняются вне временной файловой системы контейнера;
- изменяющие запросы защищены antiforgery-токенами;
- URL объектов задаёт только администратор;
- endpoint объектов не требуют авторизации, поэтому не должны раскрывать чувствительные сведения;
- секреты не включаются в исходный код, Docker image и клиентский JavaScript.

## 11. Не входит в первую версию

- несколько экземпляров UptimeHarbor;
- автоматический failover;
- Cloudflare Load Balancing и Cloudflare Tunnel;
- репликация PostgreSQL;
- мониторинг самого UptimeHarbor извне;

## 12. Критерии приёмки

Первая версия считается соответствующей ТЗ, если выполняются все условия:

1. Приложение и PostgreSQL запускаются на Linux через подготовленную Docker Compose-конфигурацию.
2. Начальный администратор создаётся из JSON при пустой базе и не пересоздаётся при повторном запуске.
3. Администратор может управлять серверами, контейнерами, пользователями, правами видимости, чатами и привязками уведомлений.
4. Обычный пользователь не видит запрещённые объекты и не может вызвать административные операции прямым HTTP-запросом.
5. Серверы и контейнеры проверяются GET-запросами каждые 30 секунд с timeout 30 секунд.
6. Три последовательные ошибки переводят объект в «Недоступен».
7. Одна успешная проверка восстанавливает статус «Доступен».
8. Выключенный объект не проверяется и имеет статус «Неизвестно».
9. Имя сервера и контейнера обновляется из успешного ответа соответствующего endpoint.
10. Для контейнера сохраняется `startedAtUtc` и рассчитывается текущий uptime.
11. Переходы статусов появляются на открытой главной странице через SignalR без ручной перезагрузки.
12. Поиск фильтрует доступные пользователю серверы и контейнеры по имени и описанию.
13. Telegram сообщает о недоступности и последующем восстановлении ровно по одному разу на инцидент в каждый настроенный чат.
14. Удаление сервера каскадно удаляет его контейнеры и связанные настройки.
15. Перезапуск приложения не удаляет настройки, пользователей и текущее состояние.
