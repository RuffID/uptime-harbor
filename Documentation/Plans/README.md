# Планы UptimeHarbor

Каталог предназначен разработчику и содержит планы работ с зависимостями, критериями приёмки и результатами проверок.

## Активные планы

- [Несколько узлов, синхронизация и общие администраторы](multi-node-sync-and-permissions-2026-10-18-%28in-progress%29/main.md) — `in-progress`: завершены 01–04 и ранний 05.1; этап 05 — in-progress, 05.2–05.4 и 06–10 не начаты. Реализованы accepted Administrator, durable Pending/reducer/UoW, очередь и snapshot/replay; admission/trust/activation/delivery остаются закрытыми. Схема не применялась; реальные узлы, SQL Server, отправки и внешняя приёмка не запускались. Изолированные тесты не доказывают crash/fsync, живую сеть или часовую цель догона.

## Новые самостоятельные планы

- Создавать папку `<name>-YYYY-MM-DD-(<status>)`; дата создания неизменна, имена новых файлов и папок — по-английски, содержание — по-русски.
- В `main.md` указывать цель, основание, границы, дату, общий статус и таблицу всех этапов со ссылками, зависимостями и статусами.
- Общие статусы: `not-started`, `in-progress`, `completed`, `cancelled`. Статусы этапов дополнительно включают `verification` и `blocked`.
- В файле этапа описывать работы, затрагиваемые части, проверки, критерии и фактический результат. Поддерживать его статус и строку таблицы `main.md` согласованными.
- Обязательно сохранять `open-questions.md` с разделами «Вопросы клиенту» и «Технические вопросы разработчику» в этом порядке. Пустой раздел содержит «Открытых вопросов нет».
- Решённый вопрос встраивать в требования и незавершённые этапы, затем удалять из вопросов без журнала ответов. Клиентский раздел не должен содержать внутренние технические решения.
- При смене общего статуса синхронизировать имя папки, ссылки и solution items. Для `completed` нужны все обязательные работы и проверки согласованного объёма.
- Новую работу отражать в новом плане; фактическое устройство — в [Technical](../Technical%20documentation/README.md). Завершённые этапы сохранять как историю.

Описанная в плане команда сама по себе не разрешает её запуск. Проверки БД, HTTP runtime, браузера, Telegram и deployment фиксируются отдельно от сборок и изолированных тестов.
