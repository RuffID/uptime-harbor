# 03а. Подготовка переноса первого сервера

Статус: `not-started`. Зависимости: [01](../01-scenarios-and-decisions/main.md).

Граница после 03: новый Setup отвергает рабочие таблицы, legacy-аккаунты и старый storage без очистки. Это не preflight переноса; действующий первый standalone сохраняет Disabled-поведение и требует настоящего результата этого этапа.

## Цель

Подготовить полный проверяемый перенос действующего первого standalone в кластер без потери данных и без слияния двух самостоятельных установок.

## Работы

1. Инвентаризировать фактические standalone-данные: пользователи/роли/параметры входа, объекты/связи/настройки проверок, чаты/привязки, наблюдения, инциденты, история и незавершённые задания уведомлений. Определить владельца каждого набора, соответствие новой модели, сохранение IDs и происхождения.
2. Спроектировать типизированные preflight и migration manifest с ID попытки, версией источника, контрольным срезом, счётчиками и проверками связности. Не считать отсутствие объектов доказательством пустоты; обнаруженные неподдержанные данные явно блокируют переключение.
3. Определить начальный accepted baseline для первого узла и сохранение исторических данных. Не выдавать старые наблюдения/доставки за новые accepted-команды и не отправлять заново уже доставленные уведомления. Незавершённую очередь и неизвестный исход попыток явно сопоставить с будущей общей доставкой и сводками этапа 05а.
4. Спроектировать сохранение пользователей и возможности входа без открытых паролей, проверки коллизий и связей. Локальные credentials, SQL-пароль, keyring и токен единственного бота остаются на первом сервере; общий snapshot не становится архивом локальных секретов.
5. Определить короткую паузу изменений/проверок/старого отправителя для контрольного среза, повторную проверку перед переносом и границы возврата. До начала работ на реальных данных нужны отдельно разрешённые backup и проверка восстановления; этот документ не выполняет их.
6. Подготовить отчёт preflight для администратора: что сохраняется, найденные препятствия, этап перехода и допустимое следующее действие. До подтверждённого cutover исходная установка остаётся единственным источником записи.
7. Логировать начало preflight и подтверждённый результат с migration ID, actor ID и безопасными счётчиками. Не включать имена пользователей, account hashes, снимки данных и секреты.

## Затрагиваемые части

### Контракт, разработанный этапом 01

Выполнить [mapping данных и M0–M3](../technical-design.md#migration): типизированный manifest/partition hashes/FK/source watermark, shadow baseline и delta всех writers, backup/restore receipts. Реализовать preflight/report и format baseline, а не повторно выбирать политику сохранения. Существующий legacy hash/stamps/disabled state сохраняется, setup identity отсутствует; claims/logins/tokens/неизвестные таблицы требуют адаптера либо явного отказа. У standalone нет полного check/per-attempt журнала: сохранять имеющееся, не выдумывать историю. Legacy outbox/markers переносятся с точным provenance, unknown sends не становятся success.

Негативные проверки: один и тот же count при изменённых значениях/links, коллизии, unsupported hash/роль/table, stale watermark/schema/backup receipt, большой delta и active transport. Логи — safe MigrationId/counts/reason, без account digests/истории. Само исследование 01 не выполняет provider inventory/backup; конкретную пользовательскую копию проверяет 07 по отдельному разрешению.

Application migration/preflight contracts, Infrastructure standalone persistence и сценарные UoW, Web status DTO и будущий мастер. По фактическим изменениям обновить ближайшие AGENTS.md, Shared cluster storage, Cluster operations, Configuration и Testing. Не изменять исторические этапы прежнего плана.

## Проверки и приёмка

- Состав и связи всех перечисленных данных сопоставлены целевому хранению; нет молча пропущенных таблиц или истории.
- Контрольный срез меняется при конкурирующей записи; устаревший manifest не допускает cutover.
- Изолированные проверки охватывают пустой/непустой источник, коллизии, неподдержанные данные и очередь с известным/неизвестным исходом доставки.
- Нет SQL, применения migrations, backup/restore или запуска приложения в рамках автоматического планирования/изолированной проверки; provider-level подтверждение выполняется отдельно в этапе 07 с разрешением.

## Результат

Пока не выполнен. Успешный preflight не означает перенесённые данные и не разрешает выдавать приглашение от непереключённого standalone. Перенос выполняет этап 03б.
