## Один процесс поверх существующего кластера

Основой остаются принятый журнал, сценарные Unit of Work, admission/trust, recovery и lifecycle. Мастер координирует существующие действия; он не пишет общий состав напрямую в SQL и не вызывает отдельный consensus. Направление зависимостей сохраняется: Web → Infrastructure → Application → Domain.

Application получает типизированные сценарии создания приглашения, начала подключения, чтения состояния, повтора и отмены. Domain отвечает за одноразовость и допустимые переходы без I/O. Infrastructure хранит защищённое локальное состояние, выполняет enrollment и адаптирует существующие lifecycle-команды. Web даёт статические Razor-контейнеры, контроллеры, безопасные DTO и TypeScript. Конкретные имена новых типов и HTTP-пути последующих этапов определяются при реализации; API приглашений 02 уже зафиксировано в актуальной технической документации.

## Два контура доступа

**Рабочий контур.** На готовом узле выдача и отзыв приглашения, чтение списка и управление подключением требуют актуального принятого Administrator и antiforgery. Во время обычного standalone — только соответствующая авторизация явно согласованного перехода, без притворного accepted account.

**Контур первоначальной настройки.** Подключение запускается после входа локальным администратором второй установки. Для этого нужны минимальные локальные login/setup-страница и API, доступные до общего аккаунта и рабочих gates. Подготовка локального администратора использует защищённый установочный путь; первый посетитель, пустая БД, публичный NodeId и приглашение чужого кластера права на локальную настройку не дают. Дополнительный отдельный setup-секрет пользователю не требуется.

Локальная setup-учётная запись и её сессия изолируются от будущей общей проекции. Не копировать её на другие узлы, не сливать с общим Administrator и не считать рабочей непустотой только её наличие. Этап 03 реализует подготовку по [контракту runtime](#runtime) до legacy bootstrap. После Join setup-сессии теряют права; требуется обычный общий вход. Рабочие объекты, посторонние аккаунты или старый cluster storage на втором остаются основанием отказа.

Setup не получает общий административный доступ, данные пользователей или универсальный proxy. Его исключения в middleware — точные маршруты и assets, а не `/Admin/*` или всё `/api`. Peer listener остаётся отдельным; browser-cookie и certificate headers не превращаются в peer trust. Setup mutation использует свою проверенную схему аутентификации, защиту от межсайтовой подачи, rate limit и ограничение размера. После готовности и при повторном открытии setup нельзя создать новый кластер поверх прежнего.

## Приглашение и идентичность попытки

Код — криптографически случайный GUID v4 с удобным копированием, сроком 15 минут и ограничением попыток. Он одноразовый, виден только авторизованному администратору при выдаче. Код не передаётся в URL, query, referrer, SignalR и логах; на сервере хранится verifier, а не открытый секрет. Истёкший код закрывается; кнопка новой выдачи отзывает предыдущий неиспользованный код. Для уже зарезервированной попытки проверяются отдельные полномочия продолжения; новая выдача не удаляет принятый узел и не разрешает повторно использовать старый код.

Если ответ с новым кодом потерян, повтор выдачи с тем же ID возвращает факт и состояние созданного приглашения, но не восстанавливает plaintext из verifier. UI предлагает явно отозвать его и создать новое. Нельзя молча выпускать второй код или хранить открытый первый ради повторного показа.

Приглашение имеет собственный ID, кластер/поколение, автора, срок, состояние и разрешение только на новый пустой Join. Различаются выдача, резервирование конкретной попыткой и окончательное использование. Переходы сериализуются и долговременны; две конкурентные установки не используют один допуск. Отзыв закрывает будущую выдачу полномочий, но не объявляется удалением уже принятого voter.

Вторая установка создаёт NodeId, StorageGeneration, локальный приватный ключ и AttemptId до отправки. Повтор после потери ответа использует те же ID и ключ; код не поглощается заново. Сервер связывает резервирование с открытым ключом узла и exact request digest. Другой payload под тем же AttemptId отвергается. Локальная запись о ходе подключения сохраняется до внешнего эффекта; хранение кода допускается только защищённо и только пока необходимо для незавершённого handshake.

Приглашение создаётся только через существующий общий принятый pipeline. Запрос к не-лидеру использует существующий путь доставки команд. Локальный Pending и HTTP 202 не означают, что код уже можно успешно предъявить. При перезапуске, смене лидера, backup/replay использованный или отозванный код не оживает. Новые общие поля включаются в snapshot/schema/compatibility и применяются атомарно с результатом; локальная попытка и её private material остаются локальными.

## Проверка адресов и первый защищённый обмен

Администратор вводит browser HTTPS-адрес первого сервера. Из него нельзя произвольно вывести peer-порт или предположить одинаковую конфигурацию Nginx. Проверенный ответ даёт отдельные browser/enrollment/peer адреса и identity кластера; второй узел сообщает свой заранее настроенный доступный peer-адрес.

Проверять HTTPS-сертификат, назначение endpoint, версии и совпадение ClusterId/Generation на всех шагах. Не отключать проверку TLS. Запретить URL с credentials, fragment и неизвестной схемой, недоверенные redirect, пересылку кода на другой origin, доступ к metadata/link-local и обход ограничений через DNS rebinding. Не запрещать все частные адреса: два Ubuntu могут находиться в разрешённой локальной/VPN-сети. Адресная политика задаётся установкой, проверяется после DNS resolution и применима также к обратным проверкам связи.

Есть две независимые проверки: второй достигает первого по enrollment HTTPS, а узлы достигают друг друга по нужным peer endpoints. Успех browser GET не подтверждает двусторонний mTLS/Raft. Endpoint до общего доверия имеет фиксированное назначение, ограниченные тела/таймауты и не исполняет произвольные HTTP-запросы от имени браузера.

## Автоматическая сертификатная авторизация

Существующий `SignedRecoveryAdmission` проверяет подпись внешнего оператора, challenge процесса и ручное подтверждение изоляции. Просто генерировать `admission.json` с `FencingConfirmed=true` из Web запрещено. Нельзя копировать приватный ключ оператора или корневого CA на узлы ради удобства мастера.

Постоянный peer-обмен сохраняет сертификаты/mTLS; замена на bearer-токены не планируется. После ввода адреса и приглашения приложение само создаёт ключ нового узла, передаёт CSR, проверяет принятое приглашение, выдаёт и устанавливает сертификат и сведения доверия. Пользователь не изготавливает сертификаты и не переносит файлы. Внешний сервис выдачи и ручная криптографическая подготовка после ввода кода не являются предпосылками.

Проверяемая модель ограниченного issuer и точные изменения validators определены [ниже](#enrollment): genesis/accepted registration, начальное HTTPS-доверие, CSR/PoP, цепочки/SAN/pin, attempt/process-bound grants, выдача/обновление/отзыв/активация. Приватные ключи узлов локальны; offline operator/root CA key не переносится. Обычный HTTPS-сертификат не даёт права подписывать peer-сертификаты.

Полученный допуск не разрешает emergency recovery, восстановление backup, снятие maintenance, присоединение старого клона или обычный Restart. Локальные приватные ключи создаются на новом узле; CSR содержит проверяемые identity/public key. Нельзя выдавать NodeId, адрес или сертификат, отличные от зарезервированной попытки. Ручная операционная процедура остаётся доступной для своих сценариев. Способ доказать допустимость автоматического свежего Join без фиктивного isolation proof фиксируется отдельно и проверяется тестами.

## Подготовка локального режима

Сейчас `Program.cs` читает внешний JSON с `reloadOnChange:false`, затем до DI настраивает listeners, а часть workers завершает работу при Disabled. Это исходное ограничение кода, которое этап 03 должен изменить. Целевой переход setup/standalone → Bootstrap/Join выполняется без перезапуска Web-приложения; hot reload одного option недостаточен.

Локальная БД хранит профиль режима, identity references, AttemptId и прогресс; этот профиль не реплицируется как общая конфигурация. Приватные ключи и keyring остаются в защищённом локальном хранилище с постоянными путями и правами. Конфигурация оператора определяет базовые endpoints/HTTPS и расположение хранения, не переписывается из HTTP. При старте восстанавливается тот же профиль; разрешение прошлого процесса не переиспользуется.

Управляемый lifecycle останавливает standalone workers, допускает короткую паузу операций, подготавливает локальную проекцию и запускает cluster workers ровно один раз. Peer endpoints и безопасная загрузка актуальных credentials должны поддерживать переход без перестройки Web-host; до готовности peer-доступ закрыт. Смена профиля сериализуется с фоновыми операциями и сохраняется до внешнего эффекта. После сбоя повторяется проверка фактического шага, не создаётся новый Bootstrap. Контракт runtime-переключения, тома/ACL и восстановление после внешнего рестарта фиксируются этапом 01, реализуются этапом 03 и проверяются этапом 07; supervisor не используется для штатного подключения.

На новом первом узле setup готовит BootstrapAccount и начальную сетку через существующие инварианты, затем позволяет войти администратору и выдать приглашение. Наличие подготовленной SQL-схемы проверяется отдельно; Web setup не исполняет произвольный SQL.

На действующем первом standalone переход выполняется только после этапов [03а](03a-standalone-migration-preflight.md)/[03б](03b-standalone-migration-cutover.md). Сначала инвентаризируются пользователи, объекты, чаты, bindings и история, фиксируются источник/контрольный срез и план возврата. Затем на коротком согласованном cutover блокируются конкурирующие изменения, сохраняется полный источник, формируется проверенный начальный кластерный baseline и выполняется сверка. Исторические наблюдения/доставки сохраняют происхождение и не превращаются в фиктивные accepted-команды или новые задания на отправку. Миграция не сливает второй рабочий сервер, не удаляет исходные данные и не возвращает автоматически standalone-запись после начала общих изменений.

## Долговременный координатор подключения

| Шаг | Подтверждение перед переходом |
| --- | --- |
| Проверка локальной установки | Совместимые версии, допустимое содержимое БД/storage, настроенные endpoints и защищённый setup-доступ |
| Резервирование приглашения | Принятое решение, привязка к AttemptId/NodeId/public key, отсутствие отзыва/expiry |
| Допуск и credentials | Проверенные полномочия, CSR/certificate, challenge текущего запуска и принятый AdmitNode |
| Подготовка снимка | Срез после AdmitNode; точные SnapshotId/digest/index/membership/Operations |
| Установка и catch-up | Проверенный снимок, локальный manifest и SQL cursor, карантин до доказанного восстановления |
| Добавление voter | Принятый RequestMembership, native AddMember и принятый ConfirmMembership |
| Активация | Свежие версии, отдельное законное основание Activate/Enable, реальные recovery/readiness checks |
| Завершение | Совпавший состав, доказанный applied cut, рабочая готовность и свежая связь; локальные исключения показаны отдельно |

Для каждого шага сохраняются текущая попытка, исходный payload, связанные OperationId, наблюдаемый результат, безопасная причина и следующее разрешённое действие. Нет транзакции SQL + Raft + HTTP + filesystem. Перед повтором внешний результат сверяется по прежнему ID; неизвестность не маскируется новым Bootstrap/NodeId или новым membership change. Snapshot может готовиться повторно только как новый явно связанный срез с повторной проверкой полномочий и срока.

Приглашение имеет окно использования, но уже законно начатый долгий догон не обязан уложиться в 15 минут. Reservation/admission/resume имеют [отдельные параметры](#parameters); нельзя продлевать их по факту нахождения в очереди. Для нового process challenge требуется новый валидный допуск в рамках той же попытки. Offline/resume не равен аварийному rejoin.

До принятого RequestMembership возможна атомарная CancelAttempt с отзывом credentials/grants, tombstone неактивного nonvoter и освобождением active-join slot; identity повторно не используется. С момента принятой заявки состав сначала сверяется под membership lock, остановка не обещает предотвратить native эффект. После принятого состава нужна стандартная операция удаления с большинством. UI не обещает мгновенный rollback, WAL/SQL автоматически не очищаются.

## Общие данные, проверки и Telegram

Join получает общие аккаунты, настройки и принятую историю через существующий snapshot/replay. Сразу после синхронизации новый observer не назначается автоматически: UI открывает шаг выбора объектов, а подтверждение создаёт отдельные общие команды. Ошибка или пропуск назначения не отменяют успешную синхронизацию. Историю наблюдений не переписывать от имени нового узла.

BotId, чаты и привязки общие. Единственный токен находится только на назначенном отправителе; Join не передаёт и не требует токен на других узлах. Назначение отправителя — принятое общее состояние с версией/epoch; оно не следует автоматически за Raft-лидером. Текущая проверка `IsLeader` в sender gates должна быть заменена отдельной проверяемой authority, поддерживающей отправителя-follower; одного удаления проверки недостаточно. Право отправки, очередь, BeginDelivery и результаты по-прежнему подтверждаются действующим большинством.

При недоступности отправителя новые отправки ждут без автоматического failover. События продолжают попадать в доступную общую историю; восстановившийся отправитель сначала догоняет её и подтверждает актуальное право. После этого строится сводка по чату за подтверждённый период простоя: какие проблемы возникли, какие устранены и какие остаются. Размер и разбиение используют существующий механизм summaries. Стабильные IDs и принятый срез фиксируют состав сводки; покрытые неначатые устаревшие задания закрываются атомарно с планом сводки, без фиктивного success и удаления исходной истории. Действующие отмены, удаления и bindings учитываются перед внешней отправкой; события после среза обрабатываются отдельно. Неизвестный исход ранее начатой попытки сохраняет существующие ambiguous/retry-правила, а не обещание exactly-once. Этап [05а](05a-telegram-sender-and-backlog.md) владеет этой переработкой и её проверками.

Целевой состав — три voters с большинством два. Проверка отказа любого одного узла включает продолжение общих изменений и назначенных проверок, но не обещает доступность Telegram при отказе назначенного отправителя. Промежуточный состав из двух требует обоих узлов и явно показан в UI.

## Диагностика, совместимость и документация

Логировать безопасные события выдачи/отзыва приглашения, резервирования, изменения этапа подключения, отказа, принятого membership и готовности. Для пользовательских действий брать actor ID из доверенной авторизации; системным переходам сохранять связь с исходной принятой попыткой без фиктивной Administrator-cookie. Успех фиксируется после соответствующего durable/accepted результата, один раз; обычный poll не создаёт Information-лог.

Планировать versioned enrollment contract и проверку capabilities до изменения хранения. Узел старой версии получает понятный отказ; старые бинарники не должны молча пропускать новые authority/invitation поля. Новые persistence-типы и migrations оформляются по EF-правилам, без применения к БД в задаче разработки по умолчанию.

В каждом этапе обновлять ближайшие затронутые AGENTS.md и актуальные тематические документы. Будущую функцию нельзя описывать как реализованную до выполнения этапов. Заключительная инструкция должна отделять установочные предпосылки, действия в UI, нормальные статусы и восстановление после ошибки.

## Автоматический сертификатный протокол

### Подготовка ограниченного issuer

На первом сервере после разрешённого создания сетки или cutover приложение создаёт **новый специализированный** enrollment issuer: ECDSA P-256, self-signed CA certificate, critical BasicConstraints CA=true/pathLen=0, keyCertSign/cRLSign, фиксированные ClusterId/Generation/issuer-purpose. Это отдельный application trust anchor; существующий root CA и ключ аварийного оператора не импортируются и не копируются. Системный trust store не меняется. Закрытый ключ хранится только на назначенном issuer node в защищённом локальном volume, не в общем snapshot и не на остальных узлах.

Для новой сетки локальный GenesisAuthorization фиксирует genesis/migration ID, ClusterId, issuer SPKI/cert digest, единственный NodeId/storage/address и точный account/import digest. Его создаёт локальный controller только после login, свежего preflight и exclusive lock. Публичный anchor сначала закрепляется в том же genesis manifest, затем в первом accepted InitializeCluster baseline. До этого нет приглашений/общих writers. Это отдельная узкая операция создания новой сетки, а не вывод accepted Administrator из пустой SQL.

В уже работающем ручном кластере свежий accepted Administrator подаёт RegisterEnrollmentIssuer прежним защищённым pipeline. Сначала все voters обновлены до новой capability/schema, затем принимают публичный anchor при сохранении старого CA для существующих credentials. Выдача включается только после commit/apply и fresh majority barrier. Ротация старых leaf — по одному с overlap. Недоступный issuer блокирует новую выдачу/renew, но не работу действующих сертификатов. Потеря issuer key: при большинстве администратор регистрирует replacement issuer с новым локальным ключом и ротацией leaf, без большинства действует прежняя emergency процедура. Rollover начать за 90 дней до expiry; старый anchor не удалять до смены всех credentials.

Signer принимает только типизированные leaf/grant requests, не Sign(bytes). Перед подписью сверяет accepted authorization через majority barrier, issuer epoch/purpose, CSR digest и exact approved template, держит локальный issuer lock. Произвольный даже подписанный leaf бесполезен без accepted fingerprint; CA chain сама не предоставляет peer authority. Никаких emergency/backup/maintenance полномочий issuer не имеет.

### Первое доверие и последовательность

EnrollmentContractVersion=1. Canonical payload: UTF-8 JSON с фиксированными полями version/action/ClusterId/Generation/InvitationId/AttemptId/NodeId/StorageGeneration/peerUri/SPKI digest/CSR digest, ключи ordinal-sort, GUID lower-case D, integers decimal без exponent, UTC ровно `yyyy-MM-ddTHH:mm:ss.fffffffZ`, bytes base64 DER, URI абсолютный canonical без userinfo/query/fragment. Null/omitted различаются по schema; duplicate/unknown fields запрещены, лимиты проверяются до parse. RequestDigest = SHA-256(`UptimeHarbor.Enrollment.v1` + canonical payload). Для первого Reserve неизвестные ClusterId/InvitationId берутся из TLS discovery, code verifier сверяется сервером; код передаётся отдельным secret field и не включается в loggable payload.

Transport auth envelope отделён от immutable payload: RequestId, BootId, nonce, RequestDigest, PoP P-256 signature SHA-256 в DER формате. Подпись покрывает domain/action/IDs/BootId/nonce/digest, CSR дополнительно имеет собственную PKCS#10 signature. На retry auth nonce новый, **payload/digest/OperationId прежние**; использованный nonce не запускает второй эффект. Grant/descriptor имеют собственные фиксированные domain/version и canonical bytes; подпись X.509 — стандарт DER. Это позволяет проверить exact business request без ложной ошибки из-за обновлённого challenge и не переиспользовать challenge прежнего процесса.

Discovery выполняется по введённому browser HTTPS origin с системной проверкой TLS chain/имени. Преддоверенный ответ не устанавливает trust. После успешного reserve authenticated enrollment descriptor содержит protocol/capabilities, ClusterId/Generation, issuer cert/digest, отдельные enrollment/peer addresses, invitation/attempt binding, reservation index, nonce и request digest. Его аутентифицирует TLS выбранного origin; он связывается с PoP нового узла и локальной попыткой. Код не пересылается на другой origin. После сохранения descriptor подмена anchor/ClusterId/endpoint под тем же AttemptId запрещена.

Обычный HTTPS удостоверяет выбранную установку, но не делает её HTTPS cert удостоверяющим CA. При недоверенном browser TLS — отказ **до** передачи кода; кнопки «всё равно доверять» нет. Доверенный browser HTTPS — предпосылка обычной установки, не ручная выдача peer cert после ввода приглашения.

### Grants, resume, rotation и отзыв

OnlineGrant: version/purpose, ClusterId/Generation, AttemptId, ReservationId/AdmitOperationId, NodeId/storage/address, SPKI/leaf digest, issuer epoch, GrantId, request digest, BootId/BootChallenge, RecoveryVersion/operations/membership, minimum index/snapshot digest при необходимости, issued/expiry UTC, signature. Подписи недостаточно без corresponding accepted record/scope. FreshJoin разрешает только впервые зарезервированную этим журналом identity с локальным свежим setup и без старых manifest/WAL. Здесь **нет** FencingConfirmed: это не свидетельство физической изоляции прежней машины.

После обрыва незавершённой попытки сохраняются profile/key/IDs. Новый процесс создаёт новый BootChallenge; PoP старым ключом, сверка durable progress с leader/registry/revocation, accepted ResumeAttempt повышает ProcessEpoch. Ждать истечения прежней process lease, не запускать два runtime. Старые grants закрыты, OperationIds и выданный cert прежние. После membership resume не делает новый Admit/не требует код, а сверяет состав и проходит E7. После 24 часов inactivity — ContinueAttempt после admin reauthentication, не self-renew из poll.

Если admission уже истёк и peer gate nonvoter закрыт, Resume/Renew доступен только на enrollment HTTPS с PoP прежнего привязанного ключа и fresh nonce; он проверяет accepted attempt/delegation/revocation и inactivity. Не требуется открыть обычный peer RPC или вернуть invitation в Unused. При конкурирующем reissue/cancel сначала читается принятый результат. До Admit reservation >30 минут требует нового admin разрешения той же попытке либо её отмены и нового кода; истёкший code сам не продлевается.

После Completed invitation не участвует в запуске. ManagedRestart — **отдельный** proof штатного запуска: sealed InstallIdentity, неизменные manifest/WAL/checkpoint/storage, последовательность profile, accepted credential, exclusive lock, нет backup/recovery/maintenance markers. Он разрешает восстановление и quarantined native Start **до** получения большинства: иначе одновременный restart всех voters зависел бы от уже работающего лидера. После consensus нужны новый barrier и online Enable текущего процесса; singleton получает их от локального избранного leader. Старый process grant не переиспользуется. Старый backup, утраченный/усечённый WAL, removed NodeId, другая storage identity — только offline recovery. Разделить proof для восстановления и proof для CanWork, не создать startup cycle.

Renew leaf: PoP старым неотозванным ключом + новый CSR, accepted Authorize/Bind, установка новой CredentialRevision, взаимная проверка и RetireOldCredential после overlap. Без quorum/issuer renewal ждёт, expired leaf не получает исключения. Для известного voter с пропущенным expiry возможен HTTPS ContinueCredential только по общему admin reauthentication, same identity/key proof и accepted authorization; membership не меняется, emergency restore не выполняется. Compromise → accepted RevokeCredential/issuer epoch и немедленное закрытие gates/pools по apply. Отзыв приглашения после Admit выполняется отдельной CancelAttempt, не удалением voter.

Полный побитовый клон с keys/sealed state на другом диске не различим одной криптографией/FileShare.None. Автопуть не поддерживает клонирование или restore backup и не выдаёт им isolation proof. Проверяются уникальность identities/address/SPKI, tombstones и concurrent process epochs; признак клона → карантин/ручной fencing. Владелец ОС, копирующий всю установку и секреты, вне гарантии свежего Join. Это явная граница, а не фиктивная галочка изоляции.

## Локальный администратор и переключение runtime

### Безопасная подготовка и хранение

Новая установка получает явный `InstallationIntent=Setup` при обычной подготовке окружения. Существующие BootstrapAdmin:Login/Password поступают из защищённого локального config/secret mount; это credentials локального администратора, не дополнительный setup token. До legacy initialization под exclusive installation lock создаётся ровно одна LocalSetupAccount: Identity V3 hash, stamp, lockout, CreatedForInstallIdentity. Она находится в **локальных отдельных таблицах**, не users/roles/общей проекции. Нет публичного register/setup-admin POST. Пустые/примерные credentials — fail-fast, первый посетитель не задаёт пароль. После создания изменение config не сбрасывает пароль и не включает аккаунт; утраченный доступ восстанавливается по месту установки отдельной процедурой.

У уже работающего Disabled setup-account автоматически не создаётся: перенос требует существующего локального Administrator и fresh password reauthentication. Обычный legacy-admin на втором не превращается в SetupAccount, непустота блокирует Join. Для новой первой сетки мастер отдельно запрашивает **нового общего** администратора и его пароль: отдельный UUID/credential/BootstrapAccount digest; setup account не сливается с ним и не копируется в accepted users.

Setup cookie: отдельные scheme/name и DP purpose `LocalSetup/{InstallIdentity}`, Secure/HttpOnly/SameSite=Strict, абсолютный TTL 30 минут/idle 15 минут, без remember-me. Каждая mutation проверяет local stamp/SetupEpoch/profile phase, antiforgery и exact Origin/Host. Смена процесса отзывает cookie, но не попытку. После E8 в одной локальной транзакции disabled + удаление setup hash + epoch increment; только затем common routes. Setup cookie не принимается common controllers, common cookie не даёт setup прав. Нужные pre-ready login/status/assets сохраняют security headers/rate limit/no-store, без секретов в URL. Progress переноса во время паузы защищён отдельной локальной migration session существующего администратора; обычные рабочие routes закрыты.

LocalInstallationProfile в локальной БД: InstallIdentity, Mode/Phase, ProfileRevision concurrency token, AttemptId/MigrationId, identity/storage/address, credential/issuer refs, request/operation IDs, durable evidence/progress UTC, setup/session epoch, RuntimeGeneration и безопасный error code. LocalAttemptStep хранит исходные IDs/payload digest/expected result. Code до reserve шифруется локально, затем удаляется. Эти таблицы не наследуют общую ProjectionRecord и исключены из SnapshotSchema. Сценарные UoW LocalSetup/OnboardingProgress/MigrationCutover раздельны; status query не получает глобальный UoW.

Private PEM шифруются AES-256-GCM; wrapping key приложение автоматически генерирует при первом локальном initialization под lock в отдельном persistent secret volume service identity, вручную изготавливать/вводить его не требуется. Linux directory 0700/file 0600, Windows ACL только service account/оператор; Windows DPAPI не вводить. DP keyring локален. Files: temp → flush/fsync → atomic rename → fsync directory, затем SQL ref с проверенным digest. После crash orphan file не становится активным credential, сверка pending ref обязательна. Один процесс на локальные БД/volume; второй instance lock — отказ. SQL/Telegram/operator secrets не входят в общий snapshot.

### Машина переходов и workers

`SetupReady/StandaloneReady → Preparing → Quiescing → LocalPrepared → ClusterQuarantine → CatchingUp → AwaitingActivation → ClusterReady`; отдельно Paused/FailedNeedsAction. Mode не заменяет Phase. Переход — expected ProfileRevision/RuntimeGeneration + supervisor mutex + durable owner/lease; межпроцессная защита — exclusive installation/storage lock. Process lease для onboarding — 2 минуты, renew только с доказанным действующим ProcessEpoch; новый BootId ждёт expiry прежней lease, старые grants при этом не переиспользуются.

| Фаза | Действие и восстановление |
| --- | --- |
| Preparing | Сохранить intent/IDs, read-only preflight, подготовить temp credentials/listeners. У standalone единственные старые workers ещё работают; у Setup рабочих нет. Повтор сверяет files/SQL/remote result |
| Quiescing | Повысить generation, закрыть legacy writes/test-send; отменить и await **все** scheduler/outbox tasks в бюджете. Перед commit/transport старый worker проверяет generation под общим write gate. Не завершённый drain запрещает переход. Login/progress/static доступны |
| LocalPrepared | Final cut/manifest/checkpoint. Для Join snapshot → SQL до WAL, для первого import baseline отдельным контрактом. Нет общей транзакции SQL+HTTP+FS+Raft; у каждого шага intent/evidence, повтор по digest/cursor |
| ClusterQuarantine | Child DotNext runtime после Restore и lock; voters точно из checkpoint; WAL/native сверены; Start один раз на generation. RPC только scoped catch-up, browser/common writers/monitoring/sender закрыты |
| CatchingUp/AwaitingActivation | Admission renew/resume и membership reconcile; реальные probes/projection verification. Leader Activate + local online Enable по свежим версиям. Telegram и отсутствие observer assignments не блокируют общий вход |
| ClusterReady | Durable профиль + отзыв setup до публикации immutable active profile, затем запуск cluster workers. Старые loops не возобновляются. Потерянный Completion response восстанавливается чтением результата |
| Failure/restart | Gates закрыты, load profile → files/SQL/WAL/accepted step сверены → прежние IDs. Повреждение/rollback требует действий, не нового Bootstrap. Не очищать источник/WAL; удалять лишь явно неиспользуемые temp files своей попытки |

В DI обе стратегии sign-in/administration/monitoring/delivery регистрируются именованными adapters; selector читает immutable active profile. Root hosted supervisor/probes живут весь срок host; mode-specific loops управляются start/stop, не return навсегда при Disabled. Полный inventory этапа 03: legacy MonitoringWorker/TelegramOutboxWorker и cluster PeerRuntime/Health/Lifecycle/Revision/Snapshot/Monitoring/Delivery, pumps/coordinators и их disposal/cancellation. Устранить startup-only service selection, singleton cached ClusterOptions и HttpClient certificate handlers. DP application identity задаётся постоянной InstallIdentity до Build, режим отзывает сессии через epoch, ключи не переносятся в общую проекцию.

Порядок locks: transition → runtime lifecycle → membership → scoped projection/write gate. Не держать SQL transaction во время сети и не брать transition lock из reducer callback. Все callbacks несут RuntimeGeneration, устаревший не пишет Ready/новый результат. Stop/cancel сериализован; зависший транспорт остаётся Unknown. Lock нужен **до** чтения/изменения локальной identity, а не только при создании WAL.

### Listener и предпосылки установки

Автопуть поддерживает Direct peer TLS либо заранее настроенный TCP TLS passthrough; browser может остаться за Nginx. Browser/peer endpoints известны до Build, отдельный peer socket привязан уже в Setup/Standalone поддерживающей версии. В карантине TLS selector не выдаёт рабочий cert/client validator отказывает всем; если Kestrel требует временный локальный startup cert, он не публикуется как trust и HTTP gate всё равно закрыт. После install selector атомарно получает согласованный credential/trust snapshot. Outbound pools получают новый cert; старые закрываются при retire/revoke. Перестройка host/config reload не требуется.

Текущий NginxIsolatedHttp с proxy-terminated mTLS/CRL не умеет принимать новый CA из приложения без управления proxy. Он остаётся ручным legacy путём. Для автоматического мастера Direct/TLS passthrough готовится **до запуска поддерживающей версии**; адаптер атомарного reload proxy trust в этот план не входит. Мастер не запускает Nginx из HTTP и не ослабляет проверку headers/CRL. Отсутствующий peer endpoint нельзя добавить простой сменой профиля: отказ preflight «Нужны действия при подготовке установки», без скрытого штатного restart. Join на подготовленном сервере проходит без перезапуска.

Установка обеспечивает совместимую SQL schema, persistent volumes/ACL и отдельный secret volume для автоматически создаваемого wrapping key, browser HTTPS, доступные enrollment/peer адреса, DNS/firewall/ingress. Preflight проверяет schema/capabilities, Identity dependents и **все локальные queues**, manifests/storage/место, DNS/IP и двусторонний TLS. Мастер не применяет migrations/SQL/backup scripts, не меняет operator config, не выдаёт public TLS и не исправляет сеть. Разрешённые private/VPN CIDR задаёт address policy; metadata/link-local/loopback запрещены, DNS result проверяется при каждом connect, IP закрепляется с сохранением SNI, redirects выключены. Browser GET не доказывает обратную mTLS-связь.

Immutable operator options — endpoints/paths/address policy; ClusterId/Generation/NodeId/credential/ExpectedBotId берутся из активного local profile. Новый Join получает публичный BotId из authenticated descriptor и accepted registry, без требования token в config. Новый первый genesis берёт BotId из локально настроенного положительного ExpectedBotId либо getMe локального токена будущего sender с совпадением настроенного ID, если он задан. Если оба отсутствуют — понятный preflight отказ подготовки **первого** кластера, без выпуска peer trust для неизвестного бота. На несендерах token не нужен; общая BotId identity не является секретом.

Создание нового первого узла не зависит от уже работающего consensus: GenesisAuthorization разрешает issuer подписать **только** свой exact leaf/genesis template и подготовить non-working singleton registry. Recovery принимает этот genesis proof без FencingConfirmed, native singleton стартует в карантине, затем InitializeCluster/BootstrapAccount проходят единственный журнал и replay. Только после этого fresh majority barrier/Activate/Enable открывают работу. GenesisIntent фиксируется до первого native эффекта; после `started` неполный WAL не очищается и не превращается в повторный ColdStart.

## Сохранение первого сервера и границы возврата

Источники исследования — UptimeHarborDbContext, MonitoredServer/MonitoredObject, ApplicationUser/Role, TelegramChat/NotificationBinding, NotificationOutboxJob. У standalone нет полного журнала каждого check/per-attempt Telegram message_id: сохраняются **все имеющиеся** записи, отсутствующие факты не выдумываются. Inventory сравнивает фактическую модель/схему с whitelist, неизвестные данные блокируют cutover до адаптера.

| Набор | Перенос и сверка |
| --- | --- |
| users/roles/user_roles | Прежние UUID/login/normalized login, enabled/deleted, password hash/format/stamps и Administrator сохраняются. Disabled не включается. Новый accepted revision отделён от legacy version. Не требовать открытых паролей/rehash; обеспечить verifier фактического Identity hash format, проверить uniqueness/роль/ссылки и вход |
| Локальное Identity состояние | Counters/lockout/keyring остаются у первого, cookies отзываются cutover epoch. Claims/logins/tokens/role claims, если не пусты, требуют явного адаптера: не молча отбросить и не объявить общими. Setup account здесь отсутствует |
| MonitoredServer Server/Application | Прежние IDs/parent links/names/endpoints/settings/version/check generation, последнее состояние/name/StartedAtUtc/counters/incident ID сохраняются. Accepted config через ImportBaseline, старый check — `LegacyImported`, не новая observation. Проверявшиеся первым объекты получают явные baseline observer assignments первого; disabled сохраняется |
| TelegramChat/NotificationBinding | IDs/chat ID/name/связи/revisions/generations сохраняются; пустая legacy generation получает стабильное mapping в manifest. BotId сверяется с локальным token. Markers — legacy evidence прежней точности, не accepted DeliveryAttempt |
| Outbox/история | Все jobs: исходный payload/attempt count/lease/terminal/cancellation сохраняются в versioned read-only LegacyHistory части baseline и последующих snapshot. Имеющиеся поддержанные observations/incidents/delivery rows — по IDs/provenance. Чужие cluster identity/cursor/storage блокируют сценарий |
| Pending/unknown доставка | Completed/Failed/Cancelled не создают sends. Остальные jobs отображаются в backlog по JobId+chat+incident без reset attempts/выдуманного message_id. | Секреты/файлы | SQL/BootstrapAdmin secrets, keyring/wrapping key/token локальны; только отдельно защищённый внешний backup может содержать их, не общий snapshot. Источник/архив мастером не удаляются |

MigrationManifest: MigrationId, schema/app version, whitelist table/field, row counts, canonical SHA-256 bounded partitions, FK mapping, source watermark/versions, baseline digest, InstallIdentity/storage, backup/validated-restore receipts. Codec фиксирует ordering/UTC/nulls. Account digests в UI/логи не выводить. Сверять значения/ссылки, не только counts. Shadow baseline строится до паузы; все standalone writers (admin/identity/monitoring/outbox) повышают migration watermark и записывают bounded delta в своих транзакциях. Недоказанный delta capture — отказ preflight, не неполный перенос.

До final cut требуются отдельно разрешённые full backup SQL/volumes и **проверенное восстановление копии** совместимой версией. Checkbox/VERIFYONLY не доказывают restore. Receipt связан с backup digest/schema/source и фактическим результатом; последующие изменения учитывает delta/source archive. Schema/identity change делает preflight receipt устаревшим. UI только показывает проверенный результат, не подменяет его обещанием. Сейчас backup/SQL/restore не выполняются.

1. **M0 Live**: старый standalone — единственный writer, shadow не принят; остановка подготовки безопасна.
2. **M1 Frozen**: write gate закрыт, workers drained, source cut C закреплён; final delta/baseline/source archive fsync, counts/hashes/FK/credentials/queue сверены. До M2 разрешён атомарный MigrationAborted и открытие **только** прежнего writer, если источник не менялся и genesis/import commit точно отсутствует.
3. **M2 CutoverCommitted**: durable ClusterIntent с baseline digest/запретом старых writers **до** native эффекта. Единственный genesis runtime принимает versioned ImportStandaloneBaseline через Raft и atomic SQL projection/cursor. Неизвестный commit запрещает возврат до read/replay доказательства отсутствия. Это явная baseline-команда с provenance, не фабрика старых accepted-команд и не обход nonempty guard. Account set строго из manifest, отдельный BootstrapAccount не добавляется.
4. **M3 Verified**: replay/SQL values совпали с baseline, native singleton точен, online activation/enable законны. Открыть общий login/проверки первого и invitations. Первое sender assignment явно подтверждено в manifest с прежним BotId/token, доставка ждёт 05а.

Import имеет отдельный genesis-only typed recovery path для **этой** непустой SQL, защищённый MigrationId/source-cut/baseline digest и exclusive freeze. Обычный ClusterLocalInitializationUnitOfWork для Join сохраняет запрет непустоты. Начальная baseline может устанавливаться потоково в shadow storage; рабочая SQL переключается одной проверяемой транзакцией/публикацией, без смешения старых writers. Старый источник остаётся неизменяемым архивом и не подаётся как новая accepted history.

Baseline не помещать целиком в обычную команду: действуют нынешние CommandMaxBytes 256 KiB и лимит state machine. До M2 подготовить sealed bounded-stream genesis blob + SQL shadow и immutable GenesisImportState по manifest digest. Это **provisional genesis state**, не accepted snapshot с выдуманным index/term и не JournalPosition(0). Quarantined singleton replay до первого marker использует только этот точный genesis source. Первая ImportStandaloneBaseline команда ≤256 KiB содержит MigrationId/cut/manifest/baseline digest; reducer детерминированно принимает уже проверенный genesis state, без чтения файлов/сети. Atomic projection commit устанавливает данные/cursor/result на реальном Raft index marker. Отсутствие/несовпадение blob закрывает recovery. Blob/manifest сохраняются вместе с WAL до полноценного snapshot ≥import index; при restart нельзя повторно взять изменившийся standalone SQL как genesis. Перед выдачей приглашения обязательно создать и проверить обычный accepted snapshot со **всеми** данными baseline/LegacyHistory, чтобы следующий Join не зависел от непереданного genesis blob. Проверить объём >256 KiB, bounds snapshot, потерю blob и crash между marker/SQL/snapshot; не расширять command limit ради импорта.

После M2 автоматически вернуть backup как standalone нельзя: потеряются новые accepted изменения либо появятся два writer. Нужен отдельный recovery с остановкой/изоляцией участников и сохранением нового журнала; UI предлагает продолжение/диагностику. Пауза 30 секунд достигается предварительным shadow/delta; превышение до M2 возвращает источник единственным writer, после M2 оставляет безопасно закрытое восстановление с честным прогрессом.

<a id="telegram"></a>
## Отправитель независимо от лидера и сводка простоя

### Назначение и authority

Accepted SenderAssignment = BotId/SenderNodeId/StorageGeneration/AssignmentRevision/SenderEpoch, ровно одно на generation. Первое/следующее назначение — явная admin команда с reauthentication (при переносе часть подтверждаемого manifest). Token только локально у sender; getMe сверяет BotId. Остальные узлы — NotSender/TokenNotRequired, startup валидация токена им не нужна. CanWork/consensus health не требуют Telegram. ClusterPeerRuntime resign/Resign RPC и LeaderFailureWindow используют consensus/monitoring readiness отдельно: отказ sender не заставляет исправного лидера без токена уступать роль.

Ключ authority попытки: ClusterId/Generation, SenderNodeId/storage, AssignmentRevision/SenderEpoch, CoordinatorTerm, MembershipVersion, ProcessEpoch. Elections меняют coordinator term, не назначение sender. Follower RenewSender/BeginDelivery передаёт через revision transport; peer batch принимает только typed delivery сообщения с authenticated NodeId/storage, не arbitrary internal lifecycle. Reducer проверяет assignment/revision/origin/term/membership, отсутствие maintenance/pending membership. Leader без назначения permit не получает.

SenderAuthorityGate связывается с local consensus-contact/assignment/recovery cancellation, а не LeadershipToken follower. Перед HTTP обязательны: accepted RenewSender и apply на sender, monotonic authority <10 секунд, accepted/apply BeginDelivery того же sender/epoch/process, permit ≤2 секунд, current eligibility/token/Database/Clock/Storage/queue readiness. Unknown закрывает gate; renewal не ждёт HTTP. Без quorum нет нового BeginDelivery. Уже начатый HTTP после потери связи может иметь неизвестный результат — его не отменить задним числом. Смена assignment ждёт expiry прежней lease и 30-секундного reconcile старых attempts; failover автоматически нет. Ручной перенос токена при явной смене — отдельное обслуживание, не Join.

RecordDelivery сохраняется локально независимо от leadership cancellation и идёт к текущему лидеру до принятого результата. Сверка — по настоящему AttemptId и **историческим SenderNodeId/storage/epoch**, не текущему лидеру. Поздний success монотонен. Старые реальные attempts сохраняют прежний authority variant при schema upgrade, LeaderNodeId задним числом не переписывается. Snapshot/queue validation понимают обе исторические формы. Telegram остаётся at-least-once без внешнего idempotency key.

### Устойчивый срез

SenderOutage — accepted OutageId/assignment revision/нижняя delivery coverage граница/состояние Open, Planning, Delivering, Acknowledged. Leader открывает его при expiry renewal (10 секунд) либо принятой локальной ошибке sender. Это время обнаружения, не точное время падения машины. Нижняя граница backlog — последнее **полностью подтверждённое покрытие по чату**, а не wall-clock outage: события до обнаружения не теряются. При elections эпизод восстанавливается из accepted state. Отдельная ошибка чата остаётся его retry, не общим outage.

После возврата sender сначала передаёт results, reconciles unknown attempts/queue, догоняет конфигурацию, получает новую authority. До плана обычный backlog dispatch закрыт. Leader делает strong barrier и принимает SealOutageCut(OutageId, C, source-frontiers, assignment revision): все accepted events/config/results ≤C и известные обязательные capture frontiers. Недоступного observer бесконечно не ждать; не принятые raw facts неизвестны, в сводке указывается «нет свежих данных», поздние facts входят в следующий cut. Immutable versioned state на C сохраняется до окончания плана; фильтрации сегодняшнего state лишь по intent.Index недостаточно.

SummaryPlanId = stable(OutageId, ChatId, BindingCoverageRevision, C), part ID по стабильному номеру, порядок opened/event index + IncidentId. План хранит C/предыдущую coverage boundary, source event/intent IDs, binding/check generations, current-state rows на C, canonical text/digest. Части ≤3500 UTF-16 units вместе с заголовком, без разрыва surrogate pair. Категории: «Возникли», «Устранены», «Актуальны на момент среза». Возникшая и устранённая за простой проблема отмечается в обеих временных категориях с одним IncidentId; открытая до простоя проблема включается в актуальные даже без нового intent. Stale/unknown coverage не означает recovery; направления/observer и чаты не смешиваются.

PlanSummary одним accepted reducer/projection commit сохраняет части/источники и SuppressedBySummary покрытых **неначатых** Planned/RetryDue problem/update/recovery intents. Не создаёт fake Delivered/BeginDelivery/evidence. AttemptStarted/Unknown и terminal failed сохраняются; known success не повторяется. Завершённая авария без confirmed problem допустима в summary «возникла и устранена» по accepted events, это отдельная summary semantics; обычный recovery entitlement не ослабляется. Legacy backlog сохраняет provenance без фиктивного accepted message_id.

До BeginDelivery части заново проверяются текущие chat/target/check generation/disable/binding/NodeChatRoute. Recovery ранее уведомлённому чату сохраняет нынешнее ограниченное право после unbind, но не после delete/disable. Изменившаяся область отзывает **всю неначатую часть**, replacement строится из допустимых источников того же C; исторический состав не меняется. При переработке MonitoringBacklog.RevokeUnstarted источники не возвращать в live individual dispatch: они остаются outage-planning до replacement/cancel. In-flight часть получает настоящий result и диагностику позднего изменения.

### Подтверждение и события после C

Каждая часть имеет настоящие DeliveryIntent/BeginDelivery/RecordDelivery. Accepted success подтверждает часть, не весь период. AcknowledgeSummaryCut допускается, когда все части чата успешны либо законно cancelled/superseded финальным планом; coverage cursor продвигается до C, receipt содержит part/results IDs. Это подтверждение системой доставки, не обещание прочтения человеком. UI: «План принят», «Доставлено N из M», «Ошибка части», «Сводка подтверждена». Failed часть не продвигает покрытие; ручной повтор — отдельная команда с сохранением прежних attempts, не silent reset пяти попыток.

Events после C не подавляются прежним планом; пока доставляется сводка, они накапливаются в следующем cut. После ACK — следующий план либо live delivery после закрытия backlog. Новый простой продолжает известные PlanId/part/attempt, новые события получают следующий sequence cut, успешные части не пересоздаются. Два планировщика по одной coverage revision: один accepted результат. Crash после plan, между частями, после Telegram до capture/commit или ACK до ответа не меняет состав; ambiguous transport может дать дубль, но не ложный ACK/потерю истории. Retention не удаляет зависимые events/frontiers/versions/plans; storage pressure даёт backpressure, не отбрасывание.
