# Ручная настройка трёх узлов UptimeHarbor для MVP

Дата создания: 2026-11-02. Статус: `in-progress`. Объём пересмотрен с пользователем 2026-11-21.

Цель MVP — при остановке одного из трёх серверов продолжать назначенные проверки и дать инженеру вручную переключить Telegram. Начинаем с пустой базы, действующих установок нет.

## Как работает MVP

| Узел | Проверки | Telegram |
| --- | --- | --- |
| №1 | Вместе с №2 проверяет заранее выбранные важные объекты. | Основной отправитель. |
| №2 | Продолжает собственные проверки при остановке №1. | Резервный отправитель. Инженер включает его вручную. |
| №3 | Постоянно участвует в кластере. Собственные проверки по назначению, их может не быть. | Отправка запрещена, токен отсутствует. |

Инженер вручную настраивает адрес, идентификатор и сертификат каждого узла. Кластер проверяет идентичность нового участника и синхронизирует общие данные. Для работы нужны любые два узла из трёх. Если сертификат мешает подключению, затронутый узел останавливает попытку и сообщает причину. Инженер исправляет конфигурацию и повторяет запуск.

При отказе №1 инженер видит, какой узел недоступен. №2 и №3 сохраняют большинство. Проверки, заранее назначенные №2, продолжаются. Для Telegram допустима пауза до ручного переключения. Одновременно отправляет один разрешённый узел. После возврата №1 инженер сам выбирает момент передать ему отправку обратно.

## Итог сверки с кодом

Ручное подключение в режиме `Legacy`, назначение проверок нескольким узлам и диагностика связи уже реализованы. В админке видны идентификатор узла, последний контакт и время проверки. Текущая реализация разрешает отправку Telegram только лидеру кластера. Если лидером станет №3 без токена, инженер пока не сможет передать отправку №2. [Инструкция ручного подключения](../../Technical%20documentation/Cluster%20operations.md).

На ранее собранных тестовых сборках прошли 39 изолированных тестов. Проверка на трёх реальных серверах с доставкой в Telegram остаётся открытой.

## Дальнейшие действия

1. **Удалить лишнюю автоматику подключения.** Первым делом убрать выдачу веб-приглашений, автоматическую настройку нового узла и продолжение после сбоя при смене сертификата. Проверить, что ручной допуск узла по сертификату, загрузка снимка, назначение проверок и диагностика сохранились.
2. **Реализовать ручное переключение Telegram.** Инженер выбирает одного отправителя из №1 и №2 независимо от лидерства. Выбор сохраняется при смене лидера и возврате №1. Для №3 отправка запрещена.
3. **Подготовить короткую инструкцию и передать сценарий на приёмку.** Описать ручное подключение, сопоставление серверов с идентификаторами, исправление ошибки сертификата и передачу отправки туда и обратно.

### Приёмка пользователем — открыта

- По инструкции подключить три узла. Убедиться, что состав и общие настройки синхронизировались. Назначить один тестовый объект №1 и №2. На №3 токена Telegram нет.
- Остановить №1. На оставшемся узле определить, что недоступен именно №1. Увидеть результат проверки тестового объекта от №2 с временем **после** остановки №1.
- Вручную передать отправку №2. Вызвать одно тестовое событие и получить одно уведомление. Вернуть №1 в работу и убедиться, что без команды инженера отправка остаётся у №2. Затем вручную вернуть её №1 и проверить новым событием.

## Вне объёма MVP

Перенос действующей базы не требуется. Мастер в браузере, автоматический выбор Telegram-отправителя, сводки за простой и работа единственного узла после двух отказов в MVP не входят.
