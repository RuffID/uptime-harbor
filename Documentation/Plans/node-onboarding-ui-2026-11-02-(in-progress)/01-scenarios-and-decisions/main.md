# 01. Сценарии и решения

Статус: `completed` (2026-11-03). Зависимости: требования [основного плана](../main.md). Завершены исследование и проектирование; реализация остальных этапов не начата.

## Цель

Детализировать принятые требования для действующего первого сервера и общей сетки из трёх узлов без скрытой ручной подготовки после ввода кода.

## Работы

1. Разработать переходы для готового кластера, новой первой установки и действующего standalone с сохранением пользователей, объектов, чатов и истории. Отделить изолированную локальную setup-учётную запись второго от рабочих данных; наличие обычного legacy-admin само по себе не доказывает допустимость Join. Работы переноса выполняются этапами 03а/03б.
2. Описать экраны «Узлы», «Добавить узел», первоначальную настройку второй установки, возобновление и ошибки. Основной путь остаётся «адрес + приглашение».
3. Описать три voters с большинством два, промежуточный состав из двух, отдельный выбор проверяемых объектов и одного назначенного Telegram-отправителя независимо от лидерства. Зафиксировать ожидание отправителя и сводку после простоя; отсутствие токена на остальных узлах не является ошибкой Join.
4. Разработать проверяемые контракты встроенной автоматической выдачи сертификатов без внешнего сервиса и ручных файлов, локального административного login/setup и переключения runtime без перезапуска приложения. Указать автоматическую подготовку issuer, начальное доверие, обновление/отзыв ключей, точные validators, границы данных и восстановление AttemptId. Внести дизайн в technical-design.md до зависимой реализации; согласование направления не заменяет доказанный протокол.
5. Разделить установочные предпосылки и действия пользователя: адреса, обратная связность, SQL-схема, storage, сертификаты и поддерживаемый способ запуска. Определить, что проверяется автоматически и что приложение не может исправить самостоятельно.
6. Детализировать одноразовый GUID v4 на 15 минут, замену старого кода кнопкой, отдельные reservation/admission lifetime, отмену до и после membership, reauthentication инициатора, недоступность лидера и актуальность «Синхронизирован». Длительный законный catch-up не отключается только из-за истечения кода. Остальные сроки обосновать как проектные параметры.
7. Согласовать перечень критичных событий и безопасных данных логирования со ссылкой на действующие правила; не вводить отдельную систему аудита без необходимости.

## Затрагиваемые части

Документы нового плана; исследование текущих Web/Infrastructure/Application Cluster contracts. Код приложения на этом этапе меняется только по отдельному поручению, охватывающему начало реализации.

## Проверки и приёмка

- Для каждого экрана указаны входное состояние, права, действие, результат, отказ и следующий шаг.
- Нет действий «получить доступ к ещё не готовому общему аккаунту» и «войти в закрытый readiness UI».
- Истёкший код, использованный код, непустой второй сервер, обрыв, restart и уже принятый voter имеют понятное поведение.
- Показано, как встроенный issuer безопасно готовится без внешнего сервиса и ручной криптографической подготовки; ограничения нынешних validators не замалчиваются.
- Есть контракт запуска/остановки workers и загрузки credentials без перезапуска Web-host, с короткой паузой и восстановлением после внешнего рестарта.
- Спроектирован независимый от лидера отправитель с единственным токеном, подтверждённым правом и долговременной сводкой после простоя.
- Этапы 03а/03б содержат сохранение, перенос, сверку и границы возврата. Планирование не разрешает фактический импорт.

## Результат

Исследованы реальные auth/setup, trust/admission/activation, startup/workers, snapshot/membership и sender paths; источники и конкретные изменения перечислены в [проектном описании](../technical-design.md#source-map). Разработаны сертификатный протокол, локальный профиль/runtime, изолированный setup, перенос первого, независимый sender и подтверждаемый срез сводки. Параметры/негативные проверки распределены по незавершённым этапам; зависимости не требуют реализации будущего этапа для завершения предыдущего. Ни одно ограничение кода не принято за новое бизнес-правило.

Проверены ссылки, статусы, отсутствие циклов, согласованность требований, UTF-8/LF. Проверка статическая; приложение, scripts, Git, builds/tests, БД, сеть, TLS, браузер и Telegram не запускались. Доказательство исполнения протокола и внешняя приёмка остаются в этапах 02–07. Новых блокирующих вопросов проектирования нет. Предпосылки установки и границы полного клона/неизвестной доставки явно описаны, требования не ослаблены.

## Запланированные экраны и переходы

Ниже текстовые макеты будущего UI. Технические ID и индексы доступны только в безопасной диагностике; обычные действия не требуют их ввода. Таблицы загружаются TypeScript через существующий HTTP helper/единый ServiceResult envelope, Razor содержит статические контейнеры. Mutations — AJAX/antiforgery, без reload, poll не повторяет команды. Секреты не попадают в URL/history/localStorage/SignalR. После истечения cookie сначала вход, затем чтение прежней попытки; нет обязанности заново начинать Join.

### «Узлы»

```text
Узлы                                  [Добавить узел]
Состав: 2 из целевых 3. Для работы нужны оба сервера.
Сервер       Адрес       Связь       Подключение       Проверки
Первый       …           Доступен   Синхронизирован    12 объектов
Новый        …           Доступен   Получение данных  Не назначены
Telegram: отправитель — Первый; роль follower допустима.
Подтверждено: …        [Подробности] [Продолжить попытку]
```

| Исходное состояние | Права | Действие | Результат | Отказ | Следующий шаг |
| --- | --- | --- | --- | --- | --- |
| Готовый кластер | Accepted Administrator | Открыть/добавить | Список из accepted registry + свежесть, setup попытки отдельно от voters | Нет роли → 403; нет majority → изменения закрыты, известный состав помечен устаревшим | Добавить после восстановления authority |
| Новый first после Bootstrap | Общий Administrator | Добавить второй | Тот же мастер; singleton явно не отказоустойчив | Bootstrap ещё не завершён → безопасный progress вместо закрытой общей страницы | Дождаться 03+04, общий вход |
| Действующий standalone | Локальный Administrator | Добавить | Предложение «Сначала перевести этот сервер в кластер с сохранением данных» | Нет preflight/backup → нет кода | Мастер переноса |
| Три voters | Accepted Administrator | Смотреть/управлять | Большинство 2, связь/lag отдельно от назначения объектов/Telegram | age ≥10/30 секунд → устарело/нет связи, не автоудаление | Проверить связь, штатное управление составом при необходимости |

### «Добавить узел»

```text
Добавить узел
Адрес этого сервера: https://…        [Копировать адрес]
Приглашение: xxxxxxxx-…               [Копировать код]
Действует до … (15 минут). Одно подключение.
На новом сервере войти локальным администратором,
выбрать «Подключиться», ввести адрес и приглашение.
[Отозвать] [Создать новый код] [Закрыть]
```

| Исходное состояние | Права | Действие | Результат | Отказ | Следующий шаг |
| --- | --- | --- | --- | --- | --- |
| Ready, нет активного Join | Accepted Administrator + password ≤5 минут | Создать код | После accepted Issue показать plaintext ровно в response, expiry и copy | Pending → «Ожидается подтверждение», majority/issuer/capability не готовы → причина без кода | Дождаться либо исправить предпосылку |
| Unused/Reserved без Admit | Те же | Новый код/отзыв | Accepted replace/revoke закрывает прежний допуск | Конкурирующий reserve/Admit → перечитать итог, не обещать отмену voter | Показать попытку/её отдельную остановку |
| Ответ issuance потерян | Те же | Вернуться/повторить ID | Показать факт созданного кода без восстановления plaintext | Код недоступен для копирования | Явно отозвать/создать новый |
| Код истёк/использован | Те же | Посмотреть | «Истёк»/«Использован», кнопка новой выдачи при свободном слоте | Активный Join занимает слот | Продолжить/остановить прежнюю попытку; не выключать принятый voter |

При закрытии modal secret удаляется из DOM/памяти UI, не хранится для повторного показа. Создание следующего кода после Admit не отзывает принятого участника.

### Локальный вход и setup новой установки

```text
Локальная настройка этого сервера
Логин [             ] Пароль [             ] [Войти]
После входа: [Создать новый кластер] [Подключиться]
Подключиться: Адрес первого сервера [https://…]
             Приглашение [xxxxxxxx-…]     [Подключить]
```

| Исходное состояние | Права | Действие | Результат | Отказ | Следующий шаг |
| --- | --- | --- | --- | --- | --- |
| Явный Setup profile, local account подготовлен установкой | Пока anonymous только login | Войти известными локальными credentials | Изолированная setup cookie, собственные формы | Неверный/disabled/lockout → единое сообщение, без раскрытия аккаунта | Повтор после лимита/восстановление по месту установки |
| SetupReady | LocalSetupAdministrator | Адрес + код → Подключить | Local preflight, durable AttemptId, E0–E3 | Рабочие users/objects/queues/storage → «Эта установка содержит данные»; TLS/address/version → конкретная причина | Использовать новую пустую установку/исправить окружение; очистки нет |
| SetupReady первого | LocalSetupAdministrator | Создать кластер; отдельно указать общий admin login/password | Отдельная common account command, новый genesis/issuer, карантин → activation | Неподготовленная schema/endpoint либо старый storage → отказ | Исправить установку, повтор того же genesis intent |
| ClusterReady | Setup cookie отозвана | Открыть старую вкладку setup | «Подключение завершено. Войти общим аккаунтом» | Старый POST → unauthorized/closed setup, не новый Bootstrap | Обычный общий login, без переноса cookies первого |

Нет публичной регистрации первого admin/дополнительного setup token; источник credentials и изоляция таблиц определены в [runtime](../technical-design.md#runtime). Invitation чужого кластера не предоставляет локального login. Во время pre-ready доступен ровно setup/progress allowlist, общий API не открывается.

### «Перевести первый сервер в кластер»

```text
Перевод первого сервера
Сохранятся: пользователи …; объекты …; чаты/привязки …;
имеющаяся история и очередь …
Резервная копия и проверка восстановления: подтверждены …
Короткая пауза записи, проверок и отправки; страница останется доступна.
Пароль администратора [        ]  [Начать переход] [Закрыть]
Ход: подготовка → контрольный срез → перенос → сверка → готово
```

| Исходное состояние | Права | Действие | Результат | Отказ | Следующий шаг |
| --- | --- | --- | --- | --- | --- |
| Рабочий standalone/M0 | Local Administrator + fresh password | Проверить перенос | Инвентаризация/manifest/preflight, источник работает | Неизвестные данные/роль/коллизии/нет проверенного backup | Конкретное препятствие; ручные внешние действия отдельно |
| Preflight актуален | Те же | Начать | M1 pause, final delta и сверка, M2 import/cluster intent, M3 readiness | До M2 budget/сверка провалены → старый единственный writer; unknown commit → карантин | Прочитать прежний MigrationId и продолжить |
| После M2 | Защищённая migration session/общий admin после открытия | Продолжить | Recovery того же migration, без restart Web-host | Автоматического «вернуть standalone» нет | Диагностика/отдельная recovery при необходимости |
| M3 | Общий Administrator | Войти/добавить | Данные сохранены, прежние проверки назначены первому | Сверка/activation не доказаны → код не показывать | После готовности выдать приглашение; Telegram отдельно |

Нет галочки, заменяющей проверенный restore. После перехода требуется общий login прежним перенесённым аккаунтом, старые cookies отозваны. Архив/источник не удаляются.

### «Ход подключения» и возврат после обрыва

```text
Подключение к …
✓ Проверка установки    ✓ Подключение разрешено
→ Получение данных     · Включение в состав
· Синхронизация        · Готовность
Данные получены: … (без выдуманного процента/срока)
Последнее подтверждение: …
[Остановить — до принятой заявки включения] [Подробности]
```

| Исходное состояние | Права | Действие | Результат | Отказ | Следующий шаг |
| --- | --- | --- | --- | --- | --- |
| E0–E5 | Local setup session | Начать/открыть progress | Сервер продолжает сохранённые IDs независимо от вкладки | Неверный/expired/used код до reserve → отказ; TTL после законного Admit не отключает catch-up | До Admit новый код; после Admit renew/resume той же попытки |
| Обрыв/смена лидера/внешний restart | Local setup login либо общая admin delegation для Continue | Вернуться | GET прежнего AttemptId, новый process challenge при restart | Нет majority/issuer → ожидание, нет нового Bootstrap/NodeId | Автоматический bounded retry до inactivity; >24 часа подтверждение admin |
| Actor изменён/отозван | Local setup видит только status; общий admin управляет delegation | Продолжить | AwaitingAdministrator, same attempt | Один local login не подменяет общий authority | Действующий общий admin повторно авторизует ContinueAttempt |
| До принятого RequestMembership | Local setup + принятая cancellation | Остановить | Grants/credentials закрыты, nonvoter tombstone, slot освобождён, source storage сохранён | Заявка состава уже принята/эффект мог произойти → сначала reconcile под membership lock | Показать точный результат, при voter штатное удаление |
| Native/accepted voter уже существует | Admin общего кластера | Остановить | «Узел уже включён. Для отключения требуется изменение состава» | Нет quorum → удаление ожидает, локального rollback нет | Штатное RemoveMember с большинством |
| E7/E8 | Системный coordinator по принятым grants | Подтвердить готовность | Только доказанный cut/readiness → «Синхронизирован» | Stale health/lag → ожидание/догон | Общий login, отдельно выбор объектов |

### «Объекты для проверок»

```text
Узел подключён. Проверки ещё не назначены.
[ ] Объект A    [ ] Объект B    …
[Сохранить выбранные] [Настроить позже]
```

| Исходное состояние | Права | Действие | Результат | Отказ | Следующий шаг |
| --- | --- | --- | --- | --- | --- |
| E8 завершён, нет назначений | Общий accepted Administrator | Выбрать/сохранить | Отдельные accepted observer assignments с текущими версиями | Deleted/stale object, нет quorum/роль отозвана → выбор не принят | Перечитать объекты/повторить с новой версией |
| То же | Те же | Позже/пустой выбор | Join остаётся успешным, 0 назначений | Нет автоматического назначения всех | Открыть назначения позже |
| Назначения Pending | Те же | Смотреть | «Изменения ожидают подтверждения», проверки только после apply | Частичный результат отображается по операции, не rollback Join | Дождаться результата |

### Telegram

```text
Общий бот: …  Отправитель: Первый (follower)
Связь отправителя: Нет связи
Уведомления ожидают сервер отправки. Автоматической замены нет.
После возврата: сводка за … — доставлено 2 из 3 частей
Актуальное состояние: …   [Подробности]
```

| Исходное состояние | Права | Действие | Результат | Отказ | Следующий шаг |
| --- | --- | --- | --- | --- | --- |
| Назначен sender, majority есть | Общий Administrator | Просмотреть | Sender identity/связь/authority/token readiness отдельно от лидерства | Не sender → «Токен не требуется», не ошибка Join | Никаких действий на остальных узлах |
| Sender недоступен | Те же | Просмотреть | Ожидание, нет failover/предложения копировать token | Потеря quorum показана отдельно | Восстановить назначенный сервер |
| Sender вернулся | Системная authority, UI read admin | Дождаться | Catch-up → cut/plan → part successes → ACK | Unknown transport/ошибка части → честный статус, не «доставлено» | Reconcile/retry; terminal error требует явного действия |
| Назначение ещё не принято | Accepted admin + reauthentication | Назначить конкретный сервер | Versioned assignment, локальный BotId/token probe | TokenMissing/BotMismatch только у выбранного sender, без токена в UI | Настроить secret по месту установки, повторить |

Назначение sender не меняется от смены лидера. В сводке запланированы возникшие/устранённые/актуальные проблемы; сообщение после среза относится к следующему плану. Пользователь не подтверждает фиктивную доставку кнопкой.
