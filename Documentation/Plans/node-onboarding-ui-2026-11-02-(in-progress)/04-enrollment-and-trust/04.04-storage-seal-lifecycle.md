# 04.04. Storage seals: конкурентность и стоимость

Статус: `completed`. Зависимости: [04.01](04.01-preflight-recheck.md), [04.02](04.02-restart-mode-before-effects.md), [04.03](04.03-unbounded-progress-validation.md)

Выполнено 2026-11-15 по поручению продолжить план и запускать только затронутые тесты. Результат ограничен изолированными проверками; внешняя приёмка остаётся в этапе 07.

## Цель и результат

Проверенный протокол seal и обоснованная стоимость без ослабления recovery.

Основание: [обзор этапа](main.md), [общий план](../main.md), [согласованный контракт](../technical-design.md#enrollment). При расхождении краткой задачи с полным объёмом этапа требования не ослаблять; противоречие зафиксировать до зависимой работы.

## Границы и работы

- Исследовать публикацию snapshot/checkpoint/seal при каждом durable apply в ManagedStorageSeals: блокировки, рост и crash boundaries.
- Зафиксировать инвариант rollback detection и реалистичную стоимость; менять механизм только при необходимости с доказанным сохранением sealed-state binding.

Затрагиваемые части: Application trust/admission, Infrastructure Installation/Cluster/Identity/crypto/HTTP, Web setup/enrollment, тесты и актуальная техническая документация.

## Проверки и критерии готовности

- Изолированно проверить конкурентный apply/seal, crash между snapshot/checkpoint/seal и stale/усечённый WAL.
- Любое ускорение сохраняет отказ старому backup/clone/rollback; реальные fsync/нагрузка не объявляются проверенными.

Использовать только разрешённые статические, compile-check и изолированные проверки. Приложение, БД, Docker, сеть, браузер и Telegram этим файлом не разрешаются; внешнее подтверждение относится к этапу 07.

## Фактический результат

Подтверждены и исправлены три дефекта: усечённые/stale state/checkpoint принимались до открытия WAL, ошибка отдельного snapshot оставляла recovery готовым, seal разрешал снижение term и изменение head/term на том же index. До исправления регрессии воспроизведены на production коде; штатный Restart и новый Enable сохранены.

ManagedWalValidation до загрузки snapshot/native open проверяет точные метаданные DotNext 6.10.0, term/committed не ниже SQL head и last ≥ committed. Snapshot не подменяет утраченный native checkpoint. Публикация сохраняет порядок snapshot → SQL checkpoint → seal → Current под checkpointSerial; ошибка при существующем seal закрывает accepted recovery до Restore/replay. Seal не понижает index/term и сохраняет head при том же index.

В ManagedStorageSealTests — 21 проверка: усечение state/checkpoint, неизвестная версия/missing checkpoint, stale term/commit/last и настоящий старый checkpoint при новом snapshot, законный новый election term без apply, монотонность seal, сбой перед SQL checkpoint и orphan после SQL, seal до публикации Current и управляемый concurrent snapshot/apply. Последний выполняет apply после capture старого cut, но до его checkpoint; проверяет следующий seal и повторное открытие настоящего WAL. Проекция/majority — doubles, native Start и БД отсутствуют.

Финальный затронутый Web-фильтр (ManagedStorageSeal/ManagedRestart/ManagedBootstrap/ManagedInvitation/EnrollmentGateway/EnrollmentClient): **42 успешно, 0 ошибок/пропусков**. RevisionRecoveryTests: **6 успешно, 0 ошибок/пропусков**. Compile-check production Infrastructure, Web.Tests и Infrastructure.Tests — без предупреждений/ошибок. Полные наборы не запускались. [Команды и границы проверки](../../../Technical%20documentation/Testing.md#storage-seals-0404-2026-11-15).

Стоимость сохранена и описана: каждый durable apply экспортирует полный образ, пишет body и packaged snapshot, выполняет полные чтения/проверки и SQL checkpoint плюс малый seal. Публикации сериализованы, стоимость линейна размеру образа; до watermark/reclaim растёт число полных snapshot. Разреженные seals без отдельного доказательства промежуточного префикса не вводились. [Текущий протокол и стоимость](../../../Technical%20documentation/Local%20installation%20setup.md#целостность-wal-и-публикация-seal).

Не проверены production нагрузка/latency, SQL atomicity/locking, fsync/power loss, реальные выборы/сеть/Ubuntu. При аварийном завершении native commit может отстать от SQL/seal: неполная evidence требует offline recovery даже при пригодном snapshot. Полный побитовый клон/откат вместе с секретами локально неотличим — прежнее ограничение дизайна сохранено, автоматический isolation proof не создаётся. Полный Join/snapshot install следующего узла не объявляется проверенным.
