# 04.02. Mode-проверка ManagedRestart до эффектов

Статус: `completed`. Зависимости: [04.01](04.01-preflight-recheck.md)

Работа возобновлена по поручению пользователя. Правка 04.02 реализована и проверена 2026-11-15: сборки успешны, все 13 затронутых ManagedRestartTests прошли без ошибок и пропусков.

## Цель и результат

Fail-fast отказ неправильному режиму без частично установленного доверия.

Основание: [обзор этапа](main.md), [общий план](../main.md), [согласованный контракт](../technical-design.md#enrollment). При расхождении краткой задачи с полным объёмом этапа требования не ослаблять; противоречие зафиксировать до зависимой работы.

## Границы и работы

- Перенести проверку Mode=Restart в начало ManagedRestartPreparation.PrepareAsync до Publish/TLS install и других эффектов.
- Сохранить прежние locks/identity/storage/barrier проверки; не расширять допустимые способы восстановления.

Затрагиваемые части: Application trust/admission, Infrastructure Installation/Cluster/Identity/crypto/HTTP, Web setup/enrollment, тесты и актуальная техническая документация.

## Проверки и критерии готовности

- Для каждого недопустимого Mode убедиться в отсутствии Publish/TLS/native/file side effects.
- Для допустимого Restart сохраняется карантинный путь и отдельный fresh Enable.

Использовать только разрешённые статические, compile-check и изолированные проверки. Приложение, БД, Docker, сеть, браузер и Telegram этим файлом не разрешаются; внешнее подтверждение относится к этапу 07.

После успешной подготовки возвращается `true`. Прежние проверки profile/process/phase, seal/manifest/WAL, accepted identity, сертификатов и BootstrapAccount provenance сохранены; quarantine и новый Enable не обходятся.

Она проверяет отказ без admission/TLS, открытия native store/barrier, изменения профиля, seal/manifest или состава файлов; повтор с удалённым seal подтверждает ранний отказ до чтения storage. В существующий успешный Restart-сценарий добавлена проверка установки TLS; проверки quarantine и нового ProcessEpoch/Enable сохранены.
