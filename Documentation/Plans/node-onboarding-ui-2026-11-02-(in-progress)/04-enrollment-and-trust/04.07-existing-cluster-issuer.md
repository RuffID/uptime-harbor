# 04.07. Issuer для существующего ручного кластера

Статус: `completed`. Зависимости: [04.05](04.05-bootstrap-and-invitation-proof.md)

Работа возобновлена по поручению пользователя 2026-11-15 после завершения 04.06. Подтверждён разрешённый изолированный объём 04.07; весь этап 04 остаётся `in-progress`.

## Цель и результат

Готовый сценарий issuer provisioning для уже работающего ручного кластера.

Основание: [обзор этапа](main.md), [общий план](../main.md), [согласованный контракт](../technical-design.md#enrollment). При расхождении краткой задачи с полным объёмом этапа требования не ослаблять; противоречие зафиксировать до зависимой работы.

## Границы и работы

- Подготовить production provisioning локального dedicated application CA и RegisterEnrollmentIssuer по fresh accepted Administrator.
- Требовать capability/schema всех voters, accepted apply и majority barrier; существующие CA/pins сохранять для действующих credentials.

Затрагиваемые части: Application trust/admission, Infrastructure Installation/Cluster/Identity/crypto/HTTP, Web setup/enrollment, тесты и актуальная техническая документация.

## Проверки и критерии готовности

- Legacy root/operator key не импортируется; до commit выдача закрыта; повтор Register возвращает прежний результат.
- Структурные IssuerRegistered/Rejected события пишутся по принятому итогу, ключи не входят в snapshot/DTO.

Использовать только разрешённые статические, compile-check и изолированные проверки. Приложение, БД, Docker, сеть, браузер и Telegram этим файлом не разрешаются; внешнее подтверждение относится к этапу 07.

## Фактический результат

Реализован первоначальный provisioning/Register локального issuer существующего ручного Legacy-кластера через `/api/admin/cluster/enrollment-issuers`. Fresh accepted Administrator и password reauthentication повторно проверяются после await; прежняя credential revision не заменяется новой при сохранении trust Pending. До файловых эффектов и при принятии Register проверяются majority, native/accepted voters и authenticated capability/schema каждого voter. Повтор с прежним OperationId сохраняет key/ref/DER и исходную protected команду; потерянный ответ после apply возвращает прежний принятый результат без нового ключа/события.

Создаётся новый dedicated P-256 CA/pathLen=0 с локальным AES-GCM key. Legacy root/operator key не импортируется; существующие Operations/CA/pins не меняются. Local SQL ref сохраняется до Pending/transport. Ключ сам не разрешает выдачу: до accepted регистрации и exact accepted issuance signer отказывает, после них всё равно требует fresh majority. Committed при потере post-commit barrier остаётся Committed с IssuanceReady=false. Structured IssuerRegistered/IssuerRejected пишутся только по accepted итогу; ключи/refs не входят в общий образ и browser DTO. Неизвестные ключи после отказа local save не выбираются автоматически.

Проверки: 47 новых Web issuer tests и 35 затронутых Web regressions (финальный прогон 82 теста), отдельно 7 Infrastructure signer/legacy-trust tests — успешно, 0 ошибок/пропусков. Production Infrastructure/Web и оба тестовых проекта — compile-check без предупреждений/ошибок. Проверены в том числе три voters, устаревшая/отсутствующая capability, schema/identity/challenge/term/membership/size mismatch, смена voter address/storage во время проверки, изменение actor revision, expiry, held Pending, lost response и отказ local commit. [Точные команды и границы](../../../Technical%20documentation/Testing.md#issuer-ручного-кластера-0407-2026-11-15).

Новая миграция не потребовалась; БД/SQLite/SQL, host/native Start, реальные сеть/DNS/TLS, Docker и deployment не запускались. Live majority/SQL durability/Ubuntu ACL/fsync не подтверждены, внешняя приёмка — 07. Нужны явно настроенные persistent Installation volumes; config/defaults не изменены. Сценарий требует локального leader и исходного local Pending/ref. Remote issuer/follower — 04.08, replacement/retirement — 04.11, общий crash reconciliation — 04.15. Snapshot/membership/Ready второго не открыты. Следующий пункт — 04.08, автоматически не начат.
