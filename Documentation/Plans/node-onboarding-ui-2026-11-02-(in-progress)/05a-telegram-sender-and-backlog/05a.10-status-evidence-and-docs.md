## Цель и результат

Готовая независимая доставка/сводки и контракт UI без автоматического failover.

Основание: [обзор этапа](main.md), [общий план](../main.md), [согласованный контракт](../technical-design.md#telegram). При расхождении краткой задачи с полным объёмом этапа требования не ослаблять; противоречие зафиксировать до зависимой работы.

## Границы и работы

- Подготовить safe API status: назначение/связь/token readiness/Waiting/plan/part result/ACK, без секретного Bot API URI/текста.
- Свести fake-time/transport матрицу, проверить durable safe events без poll/replay duplication и обновить владельцев Notifications/Cluster runtime/storage/Web/Configuration/Testing/AGENTS.

Затрагиваемые части: Domain delivery state/commands, Application sender/queue, Infrastructure consensus/dispatcher/results, Web status DTO и тесты.

## Проверки и критерии готовности

- Лидер меняется без второго sender; потеря sender оставляет исправным большинство 2/3 при остальных условиях.
- Provider atomicity и настоящие Telegram/three-node faults подтверждаются только разрешённой приёмкой 07.

Использовать только разрешённые статические, compile-check и изолированные проверки. Приложение, БД, Docker, сеть, браузер и Telegram этим файлом не разрешаются; внешнее подтверждение относится к этапу 07.
