# 06. Интерфейс узлов

Статус: `not-started`. Зависимости: [01](01-scenarios-and-decisions.md)–[05](05-join-orchestration.md), К02–К04 для соответствующих пользовательских веток.

## Цель

Предоставить короткий понятный путь «адрес + приглашение» и объяснять ожидаемый результат без требований разбираться в Raft, JSON или служебных файлах.

## Работы

1. Добавить административный раздел «Узлы» со списком собственного и остальных узлов: адрес, связь, состояние подключения/догона, последнее актуальное подтверждение и доступные действия. Не смешивать кластерные узлы с контролируемыми объектами панели мониторинга.
2. «Добавить узел» открывает modal выдачи приглашения с адресом первого сервера, копированием кода, временем действия и краткой инструкцией для второго. Кнопка не обещает успешную выдачу, пока общий журнал её не подтвердил. Секрет не попадает в URL/history/localStorage/SignalR.
3. На новой второй установке создать защищённый мастер: выбор присоединения, адрес, приглашение, «Подключить», этапы и понятный результат. Технические IDs/revisions и служебные доказательства не включать в обязательные поля пользователя; диагностические сведения доступны отдельно без секретов.
4. Различать проверку связи, принятое разрешение, получение данных, состав и рабочую готовность. Для неизвестного итога показать ожидание/проверку прежней операции, а не новое подключение. Не показывать фиктивные проценты или срок до завершения.
5. Поддержать закрытие/возврат страницы, reconnect и восстановление процесса: перечитать серверный статус исходной попытки. Не повторять mutating-команду от простого открытия страницы. После Join предложить вход общим аккаунтом; не переносить cookie первого сервера.
6. Добавить понятные ветки ошибок: неверный/истёкший/использованный код, нет двусторонней связи, несовместимая версия, непустая установка, потеря большинства, отозванные права и необходимая настройка по месту установки. Нормальный retry использует прежний ID; опасную очистку не предлагать.
7. Показать отдельно назначенные проверки и готовность Telegram по К03/К04. Условия работы двух voters по К02 объяснять до подтверждения изменения состава, без обещания автоматической независимости оставшегося сервера.
8. Кнопки отзыва/остановки показывать только там, где действие ещё возможно. При уже принятом voter объяснить, что он подключён, и использовать стандартное управление составом с отдельной авторизацией.
9. Использовать существующие Bootstrap, modal, таблицы, общий HTTP helper, TypeScript и DOM API. Не добавлять перезагрузки обычных страниц; контролируемый restart процесса по Т02 отображать отдельно. Не ломать текущие Index/Users/Notifications и Disabled-режим.
10. Обновить ближайшие AGENTS.md и актуальные Web application/Cluster operations. UI-получение статуса не создаёт собственных success-логов сверх владеющего backend-сценария; переходы, требующие логирования, сохраняют единый источник.

## Затрагиваемые части

Web Pages/Shared, новая страница узлов и setup-страница, TypeScript pages/api/ui/state по фактической сложности, API status models. Новые папки собственного кода получают локальные AGENTS.md; generated dist не редактируется вручную.

## Проверки и приёмка

- Обычный успешный путь выполняется согласованными действиями без технических полей и скрытого вызова CLI.
- Изолированные frontend-тесты проверяют переходы, ограничения кнопок, таймаут/retry, отмену и возврат после закрытия страницы через fake HTTP/state; UI не показывает преждевременный успех.
- Проверены id/name/label, клавиатура, фокус, ошибки внутри формы и modal. Секрет не появляется в DOM после закрытия выдачи/завершения там, где он больше не нужен.
- Compile-check не изменяет штатные outputs вне разрешённой сборки. Визуальная проверка, mobile/desktop и реальное восстановление UI фиксируются этапом 07, а не объявляются выполненными DOM-заглушками.

## Результат

Пока не выполнен. Наличие страницы и успешно нарисованных состояний не подтверждает подключение серверов: требуется этап 07.
