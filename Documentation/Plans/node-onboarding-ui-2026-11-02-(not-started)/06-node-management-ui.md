# 06. Интерфейс узлов

Статус: `not-started`. Зависимости: [01](01-scenarios-and-decisions.md)–[05](05-join-orchestration.md), [03а](03a-standalone-migration-preflight.md)/[03б](03b-standalone-migration-cutover.md), [05а](05a-telegram-sender-and-backlog.md).

## Цель

Предоставить короткий понятный путь «адрес + приглашение» и объяснять ожидаемый результат без требований разбираться в Raft, JSON или служебных файлах.

## Работы

1. Добавить административный раздел «Узлы» со списком собственного и остальных узлов: адрес, связь, состояние подключения/догона, последнее актуальное подтверждение и доступные действия. Не смешивать кластерные узлы с контролируемыми объектами панели мониторинга.
2. «Добавить узел» открывает modal с адресом первого сервера, GUID v4, копированием, сроком 15 минут, отзывом/новой выдачей и краткой инструкцией. До принятого подтверждения код не считается готовым. На действующем standalone сначала показать preflight и переход с сохранением данных этапов 03а/03б, затем разрешить выдачу. Секрет не попадает в URL/history/localStorage/SignalR.
3. На новой второй установке после локального административного входа создать защищённый мастер: выбор присоединения, адрес, приглашение, «Подключить», этапы и понятный результат. Не требовать отдельного установочного секрета, технических IDs/revisions, ручных сертификатов или служебных доказательств; диагностические сведения доступны отдельно без секретов.
4. Различать проверку связи, принятое разрешение, получение данных, состав и рабочую готовность. Для неизвестного итога показать ожидание/проверку прежней операции, а не новое подключение. Не показывать фиктивные проценты или срок до завершения.
5. Поддержать закрытие/возврат страницы, reconnect и восстановление процесса: перечитать серверный статус исходной попытки. Не повторять mutating-команду от простого открытия страницы. После Join предложить вход общим аккаунтом; не переносить cookie первого сервера.
6. Добавить понятные ветки ошибок: неверный/истёкший/использованный код, нет двусторонней связи, несовместимая версия, непустая установка, потеря большинства, отозванные права и необходимая настройка по месту установки. Нормальный retry использует прежний ID; опасную очистку не предлагать.
7. После синхронизации открыть отдельный шаг выбора объектов без автоматического назначения всех проверок. Показать подтверждённые назначения отдельно от синхронизации. Объяснить целевые три voters и большинство два, а также ограничения промежуточного состава из двух до изменения состава.
8. Кнопки отзыва/остановки показывать только там, где действие ещё возможно. При уже принятом voter объяснить, что он подключён, и использовать стандартное управление составом с отдельной авторизацией.
9. Использовать существующие Bootstrap, modal, таблицы, общий HTTP helper, TypeScript и DOM API. Подключение и перенос не перезапускают Web-приложение и не требуют перезагрузки страницы; краткую паузу отдельных операций показывать явно. Не ломать текущие Index/Users/Notifications и Disabled-режим.
10. Обновить ближайшие AGENTS.md и актуальные Web application/Cluster operations. UI-получение статуса не создаёт собственных success-логов сверх владеющего backend-сценария; переходы, требующие логирования, сохраняют единый источник.
11. На странице Telegram показать назначенного отправителя независимо от лидера, его доступность и состояние «Ожидается сервер отправки» без предложения копировать токен. После восстановления показывать результат сводки за простой; отсутствие токена на остальных узлах не обозначать ошибкой их подключения.

## Затрагиваемые части

### Контракт, разработанный этапом 01

Реализовать [текстовые макеты/таблицы переходов](01-scenarios-and-decisions.md#screens) для «Узлы», «Добавить узел», local login/setup, переноса, progress/resume, выбора объектов и Telegram. Каждый указанный отказ и следующий шаг обязателен. Не предлагать общий login до готовой проекции; после Join setup закрыт и нужен общий вход. Новый первый общий account не сливать с setup. Pending не рисовать Ready/Delivered, после ≥10 секунд подтверждение устарело, ≥30 секунд нет связи. UI читает прежний server attempt и не повторяет mutations от открытия вкладки.

Проектные параметры, Direct/HTTPS/schema предпосылки и границы cancel/rollback отображать простым языком по [дизайну](technical-design.md). Перед кодированием frontend читать site-typescript-rules/razor-ajax-core и профильные DOM/HTTP правила. Backend остаётся источником success-логов. Проверки макетов/прав/возраста/секретов/клавиатуры не заменяют внешний browser/TLS сценарий 07.

Web Pages/Shared, новая страница узлов и setup-страница, TypeScript pages/api/ui/state по фактической сложности, API status models. Новые папки собственного кода получают локальные AGENTS.md; generated dist не редактируется вручную.

## Проверки и приёмка

- Обычный успешный путь выполняется согласованными действиями без технических полей и скрытого вызова CLI.
- Только локальный администратор запускает Join; завершённый Join закрывает setup-доступ. Перенос первого сохраняет данные и не показывает приглашение до успешной сверки.
- Нет автоматического выбора всех объектов; назначенный follower и ожидание Telegram после отказа отображаются без ложного обещания failover.
- Изолированные frontend-тесты проверяют переходы, ограничения кнопок, таймаут/retry, отмену и возврат после закрытия страницы через fake HTTP/state; UI не показывает преждевременный успех.
- Проверены id/name/label, клавиатура, фокус, ошибки внутри формы и modal. Секрет не появляется в DOM после закрытия выдачи/завершения там, где он больше не нужен.
- Compile-check не изменяет штатные outputs вне разрешённой сборки. Визуальная проверка, mobile/desktop и реальное восстановление UI фиксируются этапом 07, а не объявляются выполненными DOM-заглушками.

## Результат

Пока не выполнен. Наличие страницы и успешно нарисованных состояний не подтверждает подключение серверов: требуется этап 07.
