# 03. Первоначальная настройка

Статус: `not-started`. Зависимости: [01](01-scenarios-and-decisions.md), К01, Т01–Т03.

## Цель

Сделать новую установку доступной владельцу для первоначальной настройки, не открывая рабочий UI и не создавая заранее несвязанные данные, мешающие Join.

## Работы

1. Ввести явный setup-профиль до legacy bootstrap и до запуска рабочих Cluster workers. Выбор «Создать новый кластер» / «Подключиться» не выводится из отсутствия объектов или первой HTTP-сессии.
2. Реализовать доказательство владения установкой по Т03, ограниченные setup routes/assets и однозначное выключение установочного доступа после готовности. Сохранять общую авторизацию и peer/browser разделение; не открывать весь API исключением из middleware.
3. Реализовать минимальный preflight: схема, содержимое известных shared-таблиц/identity/cursor, storage/manifest, версии, постоянные тома и доступные адреса. На несовместимой/непустой установке отказ без удаления или «исправления» данных запасной веткой.
4. Подготовить долговременный локальный профиль и keys на владеющей конфигурационной границе по Т02. Создавать новые файлы атомарно, ограничить пути и ACL, проверять согласованность SQL/storage identity после обрыва. Не переписывать полный config и секреты оператора.
5. Для новой первой установки координировать BootstrapAccount и начальное членство через существующие инварианты с законными online-authority из Т01. Не устанавливать Ready/Activated вручную. После проверенной готовности дать общий вход и доступ к созданию приглашения.
6. Для нового второго узла сохранить локальные NodeId/storage/AttemptId/private key, не создавать независимого общего администратора или второй Bootstrap. Перезапуск восстанавливает ту же попытку.
7. Реализовать поддержанный переход к рабочему процессу, включая контролируемый restart только по решению Т02. Неподдерживаемую установку объяснить до внешних изменений, не вызывать shell-команды из HTTP.
8. Логировать начало настройки, успешный preflight, безопасную причину отказа и переход профиля после durable результата. Установочный credential, ключи, connection string и пароль нового администратора не логировать.

## Затрагиваемые части

Web composition/configuration, boundary middleware, startup registration, Infrastructure initialization/options/control и локальное хранение. Изменения Program.cs остаются вызовами модулей. Синхронизировать местные AGENTS.md и Configuration, Web application, Cluster operations, Deployment после реализации.

## Проверки и приёмка

- Свежий узел доступен только с действующим setup-допуском; посторонний и cross-site запрос отклоняются.
- Непустая SQL-проекция, legacy-account без целей, старый manifest и клон identity не запускают новый Join/Bootstrap.
- Нормальные Disabled-установки не меняют поведение без явного выбора поддержанного перехода.
- Перезапуск не теряет AttemptId и не переиспользует challenge предыдущего процесса.
- В production/setup графе DI нет двойного старта workers, преждевременного WAL resolve и обхода closed gates.
- Новый первый кластер становится источником приглашения через согласованный UI-путь. Неподдержанный перенос standalone с данными остаётся явным отказом до расширения К01.

## Результат

Пока не выполнен. Готовность setup не означает принятый Join или работоспособность Telegram. Реальная смена процесса и права файлов проверяются отдельно на Ubuntu.
