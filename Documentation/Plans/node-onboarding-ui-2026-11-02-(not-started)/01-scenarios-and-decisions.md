# 01. Сценарии и решения

Статус: `not-started`. Зависимости: ответы и решения из [open-questions.md](open-questions.md).

## Цель

Зафиксировать полный путь от двух установок до работающей общей сетки без скрытой ручной подготовки, которую пользователь обнаружит после ввода кода.

## Работы

1. Уточнить К01: готовый кластер, новая первая установка и существующий standalone с данными. Для каждого состояния записать допустимое действие. Автоматическое создание legacy-admin не считать доказательством пустоты; текущие данные не очищать.
2. Описать экраны «Узлы», «Добавить узел», первоначальную настройку второй установки, возобновление и ошибки. Основной путь остаётся «адрес + приглашение».
3. Зафиксировать К02–К04: эксплуатационный состав, назначение проверок, подготовку Telegram. Отделить «данные синхронизированы» от «назначены проверки» и «готов отправлять уведомления».
4. Закрыть Т01–Т03 архитектурными решениями: доверие/полномочия, профиль запуска, владение setup. Внести точные результаты в technical-design.md и зависимые этапы; не держать их только в переписке.
5. Разделить установочные предпосылки и действия пользователя: адреса, обратная связность, SQL-схема, storage, сертификаты и поддерживаемый способ запуска. Определить, что проверяется автоматически и что приложение не может исправить самостоятельно.
6. Установить семантику code/reservation/admission lifetime, отмены до и после membership, reauthentication инициатора, недоступности лидера и срока актуальности состояния «Синхронизирован». Числа, не вытекающие из старого протокола, обосновать как проектные параметры.
7. Согласовать перечень критичных событий и безопасных данных логирования со ссылкой на действующие правила; не вводить отдельную систему аудита без необходимости.

## Затрагиваемые части

Документы нового плана; исследование текущих Web/Infrastructure/Application Cluster contracts. Код приложения на этом этапе меняется только по отдельному поручению, охватывающему начало реализации.

## Проверки и приёмка

- Для каждого экрана указаны входное состояние, права, действие, результат, отказ и следующий шаг.
- Нет действий «получить доступ к ещё не готовому общему аккаунту» и «войти в закрытый readiness UI».
- Истёкший код, использованный код, непустой второй сервер, обрыв, restart и уже принятый voter имеют понятное поведение.
- Недостающий issuer/supervisor не скрыт в слове «автоматически».
- Решение К01=Б требует добавить самостоятельные этапы сохранения/импорта/cutover до зависимой реализации; этот файл не считается разрешением на импорт.

## Результат

Пока не выполнен. Готовность этапа подтверждается непротиворечивыми требованиями, закрытыми блокирующими вопросами и актуальной таблицей основного плана. Внешний runtime на этапе уточнения не запускается.
