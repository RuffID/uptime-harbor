# 07. Проверки и ввод

Статус: `not-started`. Зависимости: [02](02-invitations-and-contracts.md)–[06](06-node-management-ui.md), [03а](03a-standalone-migration-preflight.md)/[03б](03b-standalone-migration-cutover.md), [05а](05a-telegram-sender-and-backlog.md).

## Цель

Подтвердить реальное подключение через UI и подготовить короткую эксплуатационную инструкцию. Изолированную проверку отделять от окружения и рабочего ввода.

## Работы

1. Завершить узкую регрессию Domain/Application/Infrastructure/Web и frontend по изменённым сценариям. Перед запуском соблюдать статические проверки и исключения действующих AGENTS.md/скиллов; не запускать весь набор, содержащий запрещённые provider/сетевые сценарии.
2. Отдельно согласовать и провести provider-level проверку reservation/consume, атомарного принятия/проекции, interrupted resume и совместимости миграции на разрешённой копии SQL Server. Проверить перенос непустого standalone: пользователей/вход, объекты/связи, чаты/bindings, полную историю и очередь; сверить значения/IDs/связи до и после. Сохранить backup, проверить восстановление и границы возврата; сам план не разрешает SQL, backup/restore или применение migrations.
3. На трёх отдельно разрешённых тестовых Ubuntu-узлах проверить новый первый кластер и отдельно перенос действующего непустого первого. Проверить общий вход, выдачу приглашения, локальный административный вход на втором/третьем, Join, синхронизацию, закрытие setup-доступа и последующие общие изменения. На промежуточном составе из двух не обещать отказоустойчивость.
4. Проверить реальные HTTPS/mTLS и автоматическую встроенную выдачу/обновление/отзыв сертификатов без внешнего сервиса и ручных файлов. Подтвердить browser/peer routes, Nginx при использовании, ACL/постоянные тома, переход без перезапуска Web-host и восстановление после внешнего рестарта. Проверка одной конфигурации не считается поддержкой всех вариантов Docker/systemd.
5. Прервать соединение и процесс в критичных точках: после резервирования, после принятого AdmitNode, в середине snapshot, после native AddMember до ConfirmMembership и после финального Enable до ответа браузеру. Подтвердить возобновление той же попытки без клона и второго voter.
6. Проверить expiry/revoke, неверный код, чужую установку, wrong TLS/ClusterId, несовместимую версию и непустой второй сервер. После отказа исходные данные и рабочий первый узел сохраняются.
7. В целевом составе из трёх поочерёдно отключить каждый узел и подтвердить большинство 2 из 3, общие изменения и назначенные проверки при прочих условиях готовности. Отдельно проверить промежуточные два voters: потеря одного блокирует требующие большинства действия и не уменьшает состав автоматически.
8. Проверить отдельный выбор объектов после Join без автоматического назначения. Для Telegram использовать один общий бот с токеном только на назначенном сервере: подтвердить отправку с follower, смену лидера без второго sender, ожидание при отказе отправителя и сводку после возврата вместо старой очереди. Проверить срез backlog, события после среза, повтор после сбоя, unbind/disable и неизвестный исход ранее начатой отправки. Реальные сообщения отправлять только с отдельным разрешением на выбранный чат; HTTP 202/Committed не считать доставкой.
9. Проверить UI в браузере: desktop/mobile, длинные адреса и ошибки, клавиатуру/фокус/modal, скрытие кода, закрытие/возврат вкладки и refresh после рестарта. Проверить логи всех стадий на отсутствие секретов и ложного/дублирующего успеха.
10. Обновить текущие Configuration, Web application, Cluster operations, Cluster control files, Deployment, Testing и затронутые AGENTS.md по фактическим изменениям. Новые документы добавить в оглавления и solution. Старые завершённые планы не менять.

## Итоговая инструкция пользователя

Должна содержать: предпосылки установки и локального административного входа; перенос первого с сохранением данных; выдачу GUID на 15 минут; ввод адреса/кода на втором и третьем; критерий синхронизации и отдельный выбор объектов; назначенного отправителя и сводку после его простоя; действия при expiry/обрыве/незавершённой операции. Объяснить большинство 2 из 3 и ограничения промежуточных двух узлов, отсутствие Telegram-failover, короткую паузу без перезапуска и процедуру обслуживания. Не превращать UI-сценарий в ручной перенос control-файлов.

## Критерии приёмки

- Есть фактические результаты для нормального подключения трёх Ubuntu-узлов, переноса непустого первого, отказа каждого одного и обязательных прерываний, с безопасными IDs/версиями и наблюдаемым итогом.
- Подтверждены права на приглашение/setup, одноразовость, отсутствие клона, сохранность данных, реальный catch-up и отдельная готовность workers.
- Подтверждены отсутствие штатного перезапуска Web-host, автоматические сертификаты, отдельный выбор объектов, единственный sender-follower с локальным токеном и сводка после его простоя.
- Необязательные дополнительные платформы/нагрузочные сценарии имеют явно ограниченный объём; отсутствие обязательного Ubuntu/UI/TLS сценария оставляет этап в `verification`, а весь план — незавершённым.
- Рабочий ввод пользователя фиксируется отдельно от приёмки тестовых установок. План не исполняет deployment автоматически.

## Результат

Пока не выполнен. При завершении записать проведённые категории проверки и существенные непроверенные сценарии, синхронизировать статусы этапа/main и общий статус папки со ссылками/solution items. До фактической проверки статусы не повышать.
