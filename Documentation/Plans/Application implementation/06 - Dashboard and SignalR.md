# Этап 6. Главная страница и SignalR

## Статус

**В работе.** Dashboard и recipient resolution используют два отдельных materialized query-контракта; server-side visibility/search, пакетные users/roles/permissions, отсутствие endpoint URL и минимальный SignalR payload проверены изолированно. Клиент coalesce-ит refresh окном 200 мс и отменяет stale fetch; reconnect перечитывает snapshot. Локальный SignalR asset версии 10.0.11 и CSP P2-5 подключены и проверены изолированно; browser-сценарий burst/cancellation и CSP/runtime остаются ручными.

## Цель

Создать основную тёмную панель мониторинга с поиском, разграничением данных и обновлениями без перезагрузки.

## Работы

1. Создать query-модель главной страницы, не передавая EF-сущности напрямую в UI.
2. Загрузить только доступные текущему пользователю серверы и контейнеры.
3. Отобразить серверы и вложенные контейнеры с обязательными полями ТЗ.
4. Рассчитывать uptime контейнера из `startedAtUtc` и текущего UTC-времени.
5. Создать понятное визуальное различие статусов:

   - «Доступен»;
   - «Недоступен»;
   - «Неизвестно».

6. Реализовать поиск по имени и описанию серверов и контейнеров.
7. Подключить SignalR hub и отправлять минимальные события изменения объекта.
8. При получении события перечитывать или точечно обновлять только разрешённые пользователю данные.
9. Реализовать автоматическое переподключение SignalR.
10. После переподключения загружать актуальный snapshot, чтобы не зависеть от пропущенных событий.
11. Сделать интерфейс адаптивным для мобильного экрана.
12. Добавить состояния загрузки, отсутствия объектов и отсутствия результатов поиска.
13. Объединять серию refresh-событий небольшим debounce и отменять прежний незавершённый snapshot fetch.
14. Не раскрывать endpoint URL в dashboard/read DTO и загружать permissions получателей пакетно.

## Требования SignalR

- клиент не выбирает произвольного пользователя или группу доступа;
- принадлежность соединения определяется сервером по аутентифицированному пользователю;
- обычный пользователь не получает события скрытых объектов;
- SignalR не является источником истины: актуальное состояние хранится в PostgreSQL;
- разрыв соединения не влияет на выполнение мониторинга.

## Тесты

- query возвращает полный список администратору;
- query фильтрует список обычному пользователю;
- поиск учитывает имя и описание без учёта регистра;
- скрытый объект не попадает в SignalR-обновление пользователя;
- uptime корректно рассчитывается для UTC;
- snapshot после переподключения заменяет устаревшие клиентские данные.
- статическое TypeScript wiring содержит coalescing, `AbortController`, отдельный `AbortError` и обязательный reconnect snapshot;
- фактический browser burst/cancellation проверяется вручную, без подмены статическим тестом.

## Результат этапа

Пользователь получает готовую главную страницу мониторинга с актуальными данными и без ручного обновления браузера.

Реализованный push payload содержит только тип и GUID объекта. После monitoring- или administrative-события, а также после reconnect клиент перечитывает полный защищённый snapshot; ошибка SignalR не влияет на сохранение и дальнейшую работу monitoring worker.
