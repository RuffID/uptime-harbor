# Этап 7. Telegram-уведомления

## Статус

**Завершён.** Application-контракты и use case, per-binding состояние частичной доставки, Telegram HTTP-адаптер, MVC API, AJAX-only Razor/TypeScript UI и миграция `AddNotificationDeliveryState` проверены отдельными сборками и 155 изолированными тестами.

## Цель

Добавить один Telegram-бот, несколько чатов и управляемые привязки уведомлений к объектам.

## Работы

1. Создать внутреннюю абстракцию канала уведомлений, не привязанную к Razor Pages и движку проверок.
2. Реализовать Telegram-адаптер с токеном из типизированных options.
3. Создать административное управление чатами:

   - Telegram chat ID;
   - понятное название;
   - добавление, изменение и удаление;
   - отправка тестового сообщения.

4. Создать привязки server-to-chat и container-to-chat.
5. При переходе в «Недоступен» сформировать одно уведомление на текущий инцидент.
6. После восстановления сформировать одно recovery-уведомление только при ранее отправленном outage-уведомлении.
7. Отправить сообщение во все привязанные чаты независимо.
8. Не блокировать проверки других объектов во время обращения к Telegram.
9. Не считать ошибку Telegram ошибкой проверяемого объекта.
10. Логировать ошибку доставки без токена и чувствительных данных.

## Содержание сообщения

Уведомление должно включать:

- тип объекта;
- имя либо GUID, если имя ещё не получено;
- описание при наличии;
- имя родительского сервера для контейнера;
- новый статус;
- время события в UTC.

Recovery-сообщение для контейнера дополнительно может включать полученное время запуска и рассчитанный uptime.

## Правило фиксации уведомления

Признак отправленного outage-уведомления обновляется согласованно с результатом отправки. Нужно заранее определить поведение частичного успеха, если один чат получил сообщение, а другой нет. Для первой версии рекомендуется хранить состояние доставки по каждой привязке текущего инцидента либо выполнять идемпотентную повторную доставку только неуспешным чатам.

Это текущее техническое состояние, а не история уведомлений, и после завершения инцидента оно удаляется или сбрасывается.

## Тесты

- одно сообщение после третьей ошибки;
- отсутствие повторов при четвёртой и последующих ошибках;
- одно recovery-сообщение после успеха;
- отсутствие recovery без outage;
- отправка в несколько чатов;
- отсутствие отправки непривязанному чату;
- ошибка одного чата не мешает остальным;
- тестовое сообщение доступно только администратору;
- токен не попадает в логи.

## Результат этапа

Администратор управляет Telegram-чатами, а пользователи получают однократные уведомления о начале и завершении каждого инцидента.

Текущая реализация хранит на объекте только идентификатор текущего/последнего незавершённого для доставки инцидента. Каждая привязка отдельно хранит идентификаторы инцидента успешной outage- и recovery-доставки. Следующая обработка отправляет сообщение только получателям без соответствующего успешного маркера; новый инцидент перезаписывает текущее состояние без накопления истории.
