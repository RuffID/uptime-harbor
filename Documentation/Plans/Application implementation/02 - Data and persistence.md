# Этап 2. Данные и хранение

## Статус

**В работе.** Доменная модель, persistence, scenario Unit of Work, read-only списковые Application-контракты, специализированные materialized dashboard/recipient queries, optimistic concurrency, durable outbox cancellation и Telegram unique constraints проверены metadata/SQLite/isolated classifier tests. Runtime provider переведён на SQL Server; baseline-миграция `20260831015604_InitialSqlServerSchema` создана и не изменялась исправлением. Её применение, SQL Server locking и реальные 2601/2627 остаются ручным release-шагом.

## Цель

Создать доменную модель, схему SQL Server и инфраструктуру сохранения текущего состояния без истории проверок.

## Работы

1. Разместить доменные сущности и правила в `UptimeHarbor.Domain`, контракты репозиториев и сценарных Unit of Work — в `UptimeHarbor.Application`, а `DbContext`, EF-конфигурации, миграции и реализации репозиториев — в `UptimeHarbor.Infrastructure`.
2. Создать сущности:

   - `MonitoredServer`;
   - `MonitoredContainer`;
   - `TelegramChat`;
   - привязки уведомлений;
   - разрешения видимости серверов и контейнеров;
   - Identity-пользователь и роли.

3. Для сервера и контейнера предусмотреть:

   - GUID;
   - endpoint URL;
   - описание;
   - признак включённого мониторинга;
   - последнее имя из endpoint;
   - текущий статус;
   - счётчик последовательных ошибок;
   - время последней и последней успешной проверки;
   - идентификатор текущего инцидента для согласованной per-binding доставки уведомлений.

4. Для контейнера дополнительно хранить последнее `startedAtUtc` и обязательную связь с сервером.
5. Реализовать доменные операции переходов статуса, не допуская произвольного изменения связанных полей внешним кодом.
6. Настроить `DbContext`, ограничения, индексы, длины строк, каскадное удаление и UTC-конвертацию в Infrastructure.
7. Создать первую миграцию SQL Server в проекте Infrastructure, используя Web как startup project.
8. Реализовать слой доступа к данным с явными границами транзакций и отдельными сценарными Unit of Work без единого агрегирующего Unit of Work.
9. Определить безопасный способ применения миграций при развёртывании.
10. Настроить сохранение ключей ASP.NET Core Data Protection вне временной файловой системы контейнера.

## Основные ограничения данных

- GUID генерируется приложением до сохранения;
- одинаковые полученные имена разрешены;
- URL обязателен и должен использовать HTTP или HTTPS;
- описание имеет заданную максимальную длину;
- `startedAtUtc` хранится как UTC;
- разрешение контейнера не может ссылаться на контейнер другого сервера;
- привязка уведомления должна ссылаться ровно на один тип объекта;
- удаление сервера каскадно удаляет дочерние и связанные записи.

## Тесты

- переходы `Неизвестно → Доступен → Недоступен → Доступен`;
- сброс счётчика при успехе;
- перевод в «Неизвестно» при отключении;
- отсутствие recovery-события после ручного отключения;
- ограничения URL и UTC;
- каскадное удаление модели;
- уникальность составных связей разрешений и уведомлений.
- атомарная terminal cancellation recovery job при disable/endpoint change;
- конкурентные duplicate chat/binding и безопасная классификация известных SQL Server unique violations.

## Результат этапа

Подготовлена модель текущего состояния UptimeHarbor и baseline-миграция SQL Server. Применение baseline и provider-specific runtime-проверка остаются отдельным release-шагом.
