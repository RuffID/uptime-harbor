# Этап 5. Движок мониторинга

## Статус

**В работе.** HTTP adapter ограничен 64 KiB и не следует redirect; списковые цели читаются через materialized `IReadOnlyList`, stale monitoring write отклоняется optimistic concurrency без SignalR/outbox events. Fake transport и SQLite provider tests проходят; остаётся ручная PostgreSQL runtime-проверка после migration.

## Цель

Реализовать надёжные периодические HTTP-проверки и корректные переходы текущего состояния объектов.

## Работы

1. Создать DTO контрактов server и container endpoint.
2. Создать валидаторы ответов:

   - HTTP `2xx`;
   - корректный JSON;
   - непустое имя;
   - корректный `startedAtUtc` в UTC для контейнера;
   - отсутствие времени запуска из будущего.

3. Настроить `IHttpClientFactory` и timeout 30 секунд.
4. Реализовать фоновый планировщик с интервалом 30 секунд.
5. Получать список включённых объектов из PostgreSQL на каждом цикле либо безопасно обновлять рабочий набор при изменении настроек.
6. Проверять разные объекты параллельно, не допуская одновременных проверок одного объекта.
7. Для результата проверки атомарно обновлять:

   - имя;
   - `startedAtUtc` контейнера;
   - текущий статус;
   - счётчик ошибок;
   - время последней и последней успешной проверки;
   - состояние текущего инцидента.

8. Публиковать внутреннее событие только после успешного сохранения изменения.
9. Обрабатывать отмену при штатной остановке приложения.
10. Изолировать ошибки объектов: исключение одной проверки не завершает общий фоновый сервис.
11. Ограничить response body 64 KiB и явно запретить HTTP redirect.
12. Защитить запись результата optimistic concurrency от административных изменений.

## Семантика планирования

- цикл начинается каждые 30 секунд;
- предыдущая незавершённая проверка конкретного объекта не запускается повторно;
- отдельного retry внутри цикла нет;
- после трёх последовательных циклов с ошибкой статус становится «Недоступен»;
- после одной успешной проверки статус восстанавливается;
- выключенные объекты не вызываются.

## Тесты

Использовать управляемый fake HTTP handler без реальных внешних endpoint для сценариев:

- успешный server JSON;
- успешный container JSON;
- timeout;
- сетевое исключение;
- HTTP `4xx` и `5xx`;
- пустое имя;
- слишком длинное имя;
- некорректный JSON;
- отсутствующий, неверный, не-UTC или будущий `startedAtUtc`;
- три ошибки подряд;
- ошибка, успех, ошибка — без перехода в «Недоступен»;
- восстановление после недоступности;
- отключённый объект не проверяется;
- сервер и его контейнер проверяются независимо;
- разные объекты проверяются параллельно;
- отсутствие параллельных проверок одного объекта;
- ошибка одного объекта не останавливает цикл;
- событие публикуется только после успешного сохранения;
- DI validation проходит без открытия реальной БД;
- остановка через cancellation token.
- oversized `Content-Length`, обычное и chunked тело;
- redirect на другой host и redirect loop;
- cancellation и timeout во время чтения;
- provider-level гонки monitoring/admin и отсутствие событий после конфликта.

## Результат этапа

Приложение непрерывно поддерживает актуальное состояние всех включённых серверов и контейнеров.
