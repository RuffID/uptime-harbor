# Этап 4. Администрирование объектов

## Статус

**В работе.** Административные use case используют единую Application administrator policy, а MVC API и TypeScript UI — `Version`; stale update/delete возвращает HTTP `409`. После commit обезличенный SignalR refresh является best-effort: transport exception журналируется и не превращает сохранённую операцию в HTTP-ошибку, а после access/save failure или conflict publisher не вызывается. SQL Server runtime-проверка зависит от создания и ручного применения baseline-миграции.

## Цель

Предоставить администратору полный интерфейс управления серверами, контейнерами и переключателями мониторинга.

## Работы

1. Создать административную страницу списка серверов.
2. Реализовать добавление и изменение сервера:

   - URL endpoint;
   - описание;
   - переключатель мониторинга.

3. Реализовать страницу или секцию контейнеров выбранного сервера.
4. Реализовать добавление и изменение контейнера с теми же административными полями.
5. Выполнить серверную валидацию:

   - обязательность URL;
   - только HTTP/HTTPS;
   - ограничения длины описания;
   - существование родительского сервера.

6. При создании присваивать GUID и статус «Неизвестно».
7. При выключении мониторинга атомарно:

   - установить статус «Неизвестно»;
   - обнулить число ошибок;
   - закрыть текущий инцидент без recovery-уведомления.

8. Реализовать удаление контейнера с подтверждением.
9. Реализовать каскадное удаление сервера с показом количества дочерних контейнеров.
10. После административных изменений уведомлять открытые панели через внутренний механизм обновлений.
11. Считать refresh-сигнал best-effort после commit и не изменять результат сохранения при ошибке SignalR transport.

## UX-требования

- формы показывают ошибки рядом с соответствующими полями;
- опасные действия визуально отделены от обычных;
- удаление требует явного подтверждения;
- до первого успешного ответа показываются «Имя не получено» и сокращённый GUID;
- изменение URL не сохраняет старое имя как подтверждённое новым endpoint.

## Тесты

- создание и изменение сервера;
- создание контейнера только для существующего сервера;
- отклонение некорректных URL;
- независимость переключателей сервера и контейнера;
- каскадное удаление сервера, разрешений и уведомлений;
- запрет всех операций обычному пользователю.

## Результат этапа

Администратор может полностью подготовить список объектов к мониторингу без прямого доступа к SQL Server.
