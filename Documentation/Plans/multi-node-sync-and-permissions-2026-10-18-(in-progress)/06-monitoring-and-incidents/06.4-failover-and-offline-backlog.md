# Подэтап 06.4. Смена главного и накопленные наблюдения

Статус: completed

## Цель и результат

Новый главный продолжает инцидент и безопасно обрабатывает старые накопленные наблюдения.

## Зависимости и границы

Зависимости: [06.3](06.3-incidents-and-delivery-intents.md).

[Общий план](../main.md) содержит сводные статусы; [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) определяют согласованное поведение. Подготовка документа не разрешает реализацию, запуск приложения, внешние проверки или включение функции.

## Работы

- [x] При смене главного восстановить принятую историю и получателей до обработки backlog; не создавать независимый инцидент для уже принятого события.
- [x] При восстановлении узла синхронизировать его наблюдения и accepted state, сохраняя follower-роль. Не допускать возврата старых status/incident поверх более новых ревизий.
- [x] Подготовить читаемую диагностику времени последнего подтверждения, отставания и причины incident. Обновить локальные `AGENTS.md` и фактическую документацию мониторинга.

- [x] После восстановления главного завершённые накопленные аварии передавать сводкой без предела давности с сохранением полной истории; открытые аварии сообщать отдельно. Уже уведомлённым чатам направлять обычный recovery. Согласовать со слоем доставки durable состав сводки без потери intents и повторной отправки её исходных событий.

- [x] Возвращать полное покрытие после догона общих данных с целевым сроком один час от восстановления связи при трёх узлах и около 30 приложениях с проверкой раз в минуту. Диагностировать прогресс; не удалять накопленные события и intents по возрасту до завершения обработки, несмотря на годовой срок завершённой истории.

- [x] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию в пределах реализованного изменения; новые документы включить в навигацию и solution.

## Проверки

Проследить вернувшийся после длительного offline узел и давние ещё не доставленные события; восстановление Telegram не оценивается по временному нормативу.

Проверить backlog со старыми завершёнными и открытыми авариями, обычный recovery ранее уведомлённому чату и replay сводки без потери исходных событий.

Проверить outage/recovery до и после смены главного, длительный offline backlog, старый accepted state и возвращение прежнего главного ведомым.

Общие сценарии [родительского этапа](main.md#проверки) сохраняются. Изолированные проверки подтверждают алгоритм; реальные БД, peer HTTP, процессы, браузер и Telegram учитываются отдельно в [этапе 10](../10-verification-and-acceptance/main.md).

Команды из плана не являются разрешением их запускать. Непроведённая обязательная проверка остаётся открытой; готовность кода при ожидающей приёмке обозначается `verification`.

## Критерии приёмки

- [x] История не откатывается, GUID инцидента не пересоздаётся из той же аварии, порядок событий сохранён.
- [x] Старые завершённые аварии входят в сводку, открытые доставляются отдельно; уже полученная проблема закрывается обычным recovery.
- [x] Backlog сохраняется до обработки; полнота покрытия не объявляется до фактического догона, часовая цель сохраняется для самостоятельного наблюдения без обязательного нагрузочного прогона.
- [x] Работы и применимые проверки подэтапа выполнены, результат и ограничения зафиксированы.
- [x] Статус согласован с таблицами родительского этапа и общего плана; незавершённая внешняя приёмка не объявлена выполненной.

## Результат выполнения

Реализованы bounded historical assembly до watermark, ротация целей и отказ live до догона диапазона; term/leader/recovery guards сохраняют историю. Durable summary parts/cut/source IDs охватывают старые завершённые аварии без age cutoff, сохраняют исходные intents/events и обычный recovery предупреждённых чатов. Поздний backlog в том же term обработан повторным составом без дублей. Snapshot/настоящий локальный WAL reopen воспроизвели production reducer/recovery с тем же incident ID и порядком. Safe MonitoringProgress не объявляет покрытие при недогоне; часовая цель не измерялась.

Фактические команды, проверки и ограничения — [Testing.md](../../../Technical%20documentation/Testing.md#проверка-этапа-06). БД/SQL/SQLite, приложение/hosting, Docker, реальные peers/endpoints/Telegram и deployment не запускались; Git не выполнялся. Fake storage не доказывает SQL semantics, локальный WAL reopen — crash/fsync или majority, статический/API test — browser acceptance. Admission/trust/activation/delivery и browser/worker/sender gates остаются закрытыми. Этапы 07–09 и самостоятельный этап 10 не начинались; после 06.4 работа остановлена.
