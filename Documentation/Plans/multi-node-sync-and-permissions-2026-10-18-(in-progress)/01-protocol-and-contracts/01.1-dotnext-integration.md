## Bootstrap, join и изменение адреса

1. При пустых общих данных вручную создать manifest: ClusterId, ClusterGeneration=1, NodeId, StorageGeneration, разрешённый canonical peer HTTPS URI, корень доверия. Проверить отсутствие прежнего cluster marker/WAL/общих пользователей. Закрепить manifest до старта и закрыть повторный bootstrap.
2. Одноразово ColdStart=true создаёт состав из первого URI. Первые принятые прикладные команды создают общий Administrator и ручной рабочий режим; до них sender закрыт. Ошибка между шагами возобновляет тот же bootstrap по стабильному ID, не создаёт ещё одну сетку/пользователя.
3. Новый узел имеет только собственные локальные реквизиты, пустые общие данные и ColdStart=false. Доверие выдаётся ограниченно для admission, затем лидер выполняет AddMemberAsync с WarmupRounds=10. Нельзя предварительно вписывать его в голосующий состав вручную. DotNext warmup не равен готовности SQL/checks/sender.
4. После snapshot/replay, сверки аккаунтов, cursor и конфигурации узел рабочий ведомый. Пока join не завершён, его наблюдения и команды не принимаются как от обычного участника. При разрыве join возобновляется по тому же MembershipChangeId и фактическому составу.
5. Удаление — принятое намерение администратора, закрытие gate/периода отправителя, RemoveMemberAsync, сверка committed configuration, затем отзыв доверия. Не удалять последнего участника; смена отправителя требует нового gate. Удалённый NodeId остаётся в истории, его пользователи сохраняются.

**Различать NodeId и DotNext ClusterMemberId.** В HTTP-реализации `ClusterMemberId.FromEndPoint(UriEndPoint)` выводится из адреса. Поэтому NodeId — прикладной постоянный UUID, а соответствие NodeId ↔ canonical URI ↔ Raft member ID — часть принятого membership. Обычная смена IP за тем же DNS и обновление TLS-сертификата его не меняют. Смена URI/домена — контролируемая замена transport member (временный другой экземпляр и его storage generation, по одному изменению), с запретом двух процессов под одним NodeId. На время замены sender закрыт; нельзя переименовать URI в файле и сохранить прежний голос. Переход через два участника имеет снижённую доступность.

## Размер сетки и источник истины

| Голосующих в принятом составе | Majority | Что возможно при отказах |
| --- | --- | --- |
| 1 | 1 | Первый локальный узел принимает команды и может быть готовым отправителем; потеря его БД/диска останавливает всё, резервирования нет |
| 2 | 2 | Нужны оба, partition 1+1 блокирует принятие и новые отправки; второй узел не добавляет отказоустойчивость |
| 3 | 2 | Один отказ переносится; при 2+1 только часть 2 может подтвердить лидера/команды, часть 1 сохраняет Pending и наблюдения |
| 5 (справочно) | 3 | При 3+2 действует часть 3, ожидать исчезновения старого главного для обоих узлов меньшинства не требуется |

Источник состава — принятая DotNext configuration, не health-список. Точка принятия — protocol commit конфигурации; durable storage и WAL обслуживает Infrastructure consensus adapter, SQL-карточка состава — проекция. Нет атомарной транзакции WAL + файл состава + SQL: старт сверяет конфигурационную версию и journal intent/result и довосстанавливает проекцию; расхождение закрывает readiness. Новое большинство разрешается только после безопасного завершения предыдущего изменения состава.

## Статический разбор и последующие минимальные проверки

По коду проверена цепочка persisted vote → restart без нового bootstrap; append → majority replication → commit/apply; join warmup → configuration log → apply. По таблице majority разобраны 1/2/3 узла. Это трассировка проектирования, не выполненные crash-тесты.

При реализации достаточно узкого compile-check адаптера, изолированных проверок большинства/gate и восстановления принятой позиции с fake storage; реальное поведение fsync, остановки процесса, SQL и TLS учитывается отдельно в этапе 10. Не требуется полный стенд или прототип для закрытия документального результата 01.1. Неподтверждённые runtime-свойства не считаются доказанными.
