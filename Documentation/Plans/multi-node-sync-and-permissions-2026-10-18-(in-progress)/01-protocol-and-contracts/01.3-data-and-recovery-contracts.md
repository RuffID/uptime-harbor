## 1. Идентичность, команда и результат

- UUID (случайные 128 bit) для ClusterId, NodeId, UserId, EntityId, OperationId, AttemptId и прочих самостоятельных IDs. NodeId не является домашним узлом пользователя. ClusterGeneration/StorageGeneration/BootId различают восстановление, экземпляр durable state и запуск процесса.
- Общая позиция = `(ClusterId, ClusterGeneration, LogIndex, Term)`. LogIndex — 64-bit индекс **принятого** Raft-префикса; term не заменяет индекс. AppRevision = позиция принятого прикладного изменения; в индексах допустимы пробелы для Raft no-op/configuration. Из разных ClusterId индексы не сравниваются.
- ConfigRevision, UserRevision, BindingRevision и MembershipVersion меняются только соответствующими принятыми изменениями. Проверки не увеличивают ConfigRevision. Текущий `MonitoredObject.Version` остаётся локальным concurrency token до замены в 02, не общей ревизией.
- Command envelope: ProtocolVersion, SchemaVersion, ClusterId/Generation, OperationId, OriginNodeId, ActorUserId либо SystemSource, ActorUserRevision, Kind, EntityId, BaseRevision/набор ExpectedRevisions, PayloadVersion, CanonicalPayloadDigest, CreatedAtUtc, Payload. Для изменения пароля — только результат password hashing и новый stamp, никогда исходный пароль. Digest — SHA-256 канонического payload; порядок полей/нормализация фиксируются схемой.
- Actor берётся Web из проверенной сессии; Origin — из mTLS. Доверенный peer заверяет серверный actor context, а reducer повторно проверяет активный принятый аккаунт, роль и UserRevision на позиции выполнения. Клиент не выбирает actor/system source. System commands разрешены только конкретным согласованным producer/назначенным observer/current sender; не универсальный обход авторизации.
- Результат: OperationId, Digest, Status, DecisionPosition, AppliedEntityRevision, ReasonCode, ConflictId/ReplacedBy при наличии. Статусы: LocalPending, AwaitingDecision, Committed, Conflict, Rejected, Cancelled, Replaced; отдельно transport UnknownResult. `Committed` означает успешно принятое предметное изменение; терминальный отказ/отмена тоже имеют принятую DecisionPosition.
- OperationId уникален внутри сетки. Повтор того же ID/digest возвращает прежний результат, не выполняется заново; иной digest — IdempotencyKeyReuse. Lookup результата требует активного администратора и не раскрывает secret payload. HTTP success/202 означает приём заявки, не Committed; timeout не означает Rejected. Application возвращает `ServiceResult<CommandReceiptDto>` для подачи и отдельный `OperationResultDto` для решения; ошибки остаются semantic ServiceError, HTTP-маппинг выполняется только Web. `ServiceResult.Ok` квитанции не доказывает принятие настройки.

### Курсор и протокол догона

Request: AfterPosition (ClusterId/Generation/LogIndex), MaxEntries<=100, MaxBytes<=1 MiB. Response: FromExclusive, ThroughInclusive, CommittedHead, MinReplayPosition, Entries с position/digest и NextCursor. Лидер отдаёт только доказанный committed prefix. SnapshotRequired возвращается при другой generation, cursor ниже MinReplayPosition или несовместимой схеме; самовольный переход на MaxIndex запрещён. Проверка полученного диапазона и hash выполняется до durable inbox, SQL ProjectionCursor сдвигается только с транзакцией apply. Повтор диапазона безопасен, пропуск прикладной записи вызывает запрос недостающего диапазона. Отдельно показываются ReceivedCursor, LastCommittedEntryIndex и ProjectionCursor; подтверждение получения не означает применения.

### Точка принятия и детерминизм

Raft commit фиксирует порядок command envelope; **семантический результат** определяется последовательным детерминированным reducer на принятом префиксе. Между protocol commit и apply допустимо AwaitingDecision. Предварительная валидация лидера — оптимизация, не окончательный арбитр. Все реплики вычисляют одинаковый результат по одному принятому состоянию; случайные IDs/stamps/времена включаются в команду либо выводятся из позиции/устойчивого ключа, не генерируются заново при replay. Ошибка IO/apply не превращается в Rejected: узел останавливает рабочую роль и восстанавливается.

## 2. Pending, замена, отмена и конфликт

Локальная транзакция Pending сохраняет payload, actor/base, OperationId, submit state и retry metadata; действующую настройку не меняет. Исправление формы до передачи может менять локальный draft, но переданный OperationId неизменяем. После передачи UI сохраняет отдельное намерение Replace/Cancel и показывает ожидание подтверждения.

| Порядок принятого журнала | Атомарный результат |
| --- | --- |
| Execute(O1: A→Б) раньше Cancel(O1) или Replace(O1,O2: A→В) | O1=Committed; control возвращает AlreadyCommitted и его позицию. Автоматического отката/применения O2 нет; новая правка подаётся отдельно от текущей базы |
| Cancel(O1) раньше Execute(O1), даже если Execute ещё не поступил | Терминальная запись O1=Cancelled с ожидаемым digest/actor; поздний Execute не применяется |
| Replace(O1,O2) раньше Execute(O1) | Одна команда закрывает O1=Replaced и рассматривает O2 с новым payload/base. Если O2 допустима — применяется только В; при конфликте O2 сохраняет Conflict, Б всё равно запрещено |
| Два Replace/Cancel одного O1 | Побеждает первый принятый control; второй получает прежний терминальный результат. Для новой правки нужен текущий head/новый ID |
| Потерян ответ на любую из операций | Повтор/query по тем же IDs возвращает принятую пару результатов; local timeout/старый Pending не меняют исход |

Control имеет собственный OperationId и ExpectedHead/TargetDigest, проверяет активного администратора и версию целевой операции. Подтверждённые Cancelled/Replaced нельзя отменить поздним retry. Отмена локально ещё не отправленного draft может завершиться локально только если durable outbox доказывает, что передача не начиналась; иначе требуется общий control.

Две правки одной EntityId/BaseRevision: первая применимая остаётся действующей. Вторая создаёт Conflict с base, first-accepted revision, предложением и ID; не пишет base обратно и не отменяет monitoring/delivery. ResolveConflict — новая команда с актуальными ExpectedRevisions; конфликт закрывается только вместе с новым принятым результатом. Секретные предложения пользователей доступны reducer, но UI получает только причину/IDs, без hash/stamp. Update после tombstone не воскрешает EntityId; восстановление сущности — отдельное создание с новым ID. Уникальные login/server name/chat ID и пары binding проверяются по принятому состоянию; второй конкурентный create получает Conflict, записи не объединяются.

## 3. Общий Administrator и защищённый вход

Account record: общий UserId, UserName, NormalizedUserName, используемые реквизиты входа, PasswordHash, PasswordHashFormatVersion, IsEnabled, UserRevision, SecurityStamp, shared ConcurrencyStamp, DeletedAt/Revision. Единственная роль — стабильный RoleId, Name/NormalizedName=`Administrator`; активный аккаунт всегда состоит в ней. RoleId фиксируется bootstrap manifest и snapshot. ACL, owners, User/operator role отсутствуют.

Create/UpdateCredential/Enable/Disable/DeleteUser — атомарные принятые команды account + role membership + normalized login index + result + cursor. Уникальность login — Unicode normalization FormKC, Trim, invariant uppercase, ordinal comparison; одинаковый алгоритм на всех узлах, в SQL хранится нормализованный ключ с уникальным индексом. Existing login semantics окончательно переключаются только в 05; старых развёрнутых данных для миграции нет.

Self-disable/self-delete запрещены. Reducer последовательно считает активных принятых администраторов: при двух конкурентных отключениях первый может пройти, второй не убирает последнего. Bootstrap создаёт первого один раз; restart не включает отключённого пользователя и не запускает нынешний локальный bootstrap поверх общей модели. Узел join не создаёт своих пользователей.

Для первого выпуска выбрать ASP.NET Core Identity V3 PBKDF2-HMAC-SHA512, 100000 iterations, salt/subkey в стандартном формате V3; версия формата включена в protocol compatibility. Пароль обрабатывается только origin Identity adapter в памяти и удаляется после hashing; pending/log/snapshot содержат только protected representation. PasswordHash проверяется на каждом узле, не пересчитывается при replay. Автоматическая локальная rehash-on-login запись **не допускается**: при необходимости обновление hash становится общей credential-командой; до отдельной реализации rehash выключен. Не добавлять MFA/email/token providers, которых нет в текущем входе.

Cookie, Data Protection keys, session epoch, access-failure count, LockoutEnd и временные lockout локальны. Применение shared полей не перезаписывает локальные счётчики; локальный sign-in не меняет shared поля в обход журнала. Identity adapter использует тот же DbContext/транзакцию, что projection UoW; нельзя делать отдельные автокоммиты UserManager после cursor.

После применения disable/delete/смены PasswordHash или SecurityStamp validator каждого запроса отвергает старую сессию; SignalR отключает/перепроверяет соединения после account event и при новом защищённом вызове. В изоляции вход/чтение доступны по последнему принятому аккаунту, это не немедленная блокировка всей сетки. Test-send повторно проверяет actor при BeginDeliveryAttempt, обычный background incident не требует пользовательской сессии.

PasswordHash/stamps — чувствительные данные: только доверенный peer transport и защищённое локальное хранение (ACL процесса и шифрование диска/backup), без обычных DTO/SignalR/логов/диагностических дампов. CA key, bot token, DB connection и cookie keys в общий snapshot не входят.

## 4. Журнал и SQL: атомарность и восстановление

**Общий источник истины — committed Raft log + published snapshot.** SQL Server хранит восстанавливаемую общую проекцию и локальные Pending/observations. SQL commit сам по себе не создаёт majority acceptance. Не вводить dual-write «сначала SQL как принятое, потом когда-нибудь WAL» и распределённую транзакцию.

Последовательность: durable proposal → Raft append/majority commit → ordered reducer → SQL transaction → apply acknowledgement → безопасный сигнал UI. В одной SQL-транзакции: рабочие записи, аккаунт/роль или зависимости, результаты операций, conflicts/tombstones, incident/events/intents/recipient ledger и ProjectionCursor. No-op/отказ не меняет сущности, но сохраняет decision/result. Внешних HTTP-вызовов в транзакции/apply нет.

Application задаёт независимый ProjectionApply use case с узким `IProjectionApplyUnitOfWork : IUnitOfWorkScope` и доменными change sets; он не раскрывает все CRUD repositories приложения. Это один упорядоченный replication apply, не глобальный UoW. Отдельные сценарии — PendingControl UoW, ObservationCapture UoW и DeliveryResult UoW. Infrastructure реализует транзакции/EF/Identity/codec, Domain — инварианты, Application — reducer/authorisation.

| Точка сбоя | Восстановление |
| --- | --- |
| Pending записан, до сети | Повтор по прежнему OperationId; effective configuration прежняя |
| Append есть, majority неизвестно | AwaitingDecision; запрос результата/повтор, не отменять по timeout. Непринятый хвост может быть заменён Raft |
| Majority commit есть, SQL ещё не применён | Readiness/gate закрыты; replay от ProjectionCursor+1 по принятому префиксу |
| SQL rollback/ошибка Identity adapter | Cursor и все эффекты откатываются; apply не ACK, рабочая роль остановлена, повтор после исправления |
| SQL commit есть, WAL applier/process упал до ACK | Повторный entry обнаруживает уже применённую позицию/digest, возвращает прежний result, не повторяет эффект |
| WAL compaction уже убрал нужный SQL хвост | Установить целостный актуальный snapshot, затем replay; не объявлять данные потерянными и не пропускать cursor |
| Cursor впереди доказанного committed/snapshot prefix или digest не совпал | Quarantine; проверка набора backup/restore, без уменьшения cursor и без «починки» пустым bootstrap |

DotNext пропускает payloadless no-op и передаёт configuration entry state machine как пустую после записи configuration storage. Поэтому различаются LastCommittedEntryIndex, WAL LastAppliedIndex и SQL ProjectionCursor последней прикладной/config callback позиции. Пробелы индексов не считаются потерей; adapter подтверждает отсутствие неприменённых **прикладных** записей до barrier. Snapshot cut включает общий log index и соответствующее SQL состояние без пропуска command. Проверено чтением [WriteAheadLog.Applier](https://github.com/dotnet/dotNext/blob/3499aedecf58b3c27a5d87af700d99e6b973cfde/src/cluster/DotNext.Net.Cluster/Net/Cluster/Consensus/Raft/StateMachine/WriteAheadLog.Applier.cs).

Сначала восстановить snapshot manager/SQL checkpoint, потом создать WriteAheadLog, InitializeAsync/replay, сверить membership и projection head, потом запустить workers. Предпочтён собственный IStateMachine/ISnapshotManager adapter, который знает SQL snapshot install; не использовать SimpleStateMachine с единственной in-memory моделью. Будущий hosting обязан предотвратить раннее разрешение IPersistentState через DI.

## 5. Наблюдения, freshness и доступность

Набор observers — часть принятой конфигурации каждой цели. Взаимные проверки узлов — отдельные NodeHealth streams, маршрутизация задаётся по NodeId. Удаление узла требует явного согласованного изменения назначений: оно не скрывает недостающее покрытие автоматически.

Raw observation: ObservationId, ObserverNodeId, StorageGeneration, TargetId, CheckGeneration, ConfigRevision, durable sequence, CheckedAtUtc, Duration, Success/FailureKind, внутреннее имя/StartedAtUtc успешного ответа. CheckGeneration меняется при endpoint/enable/назначениях/порогах; seq резервируется и результат сохраняется одной локальной транзакцией. Один stream — TargetId + ObserverNodeId + StorageGeneration + CheckGeneration. Повтор ObservationId/digest без эффекта, gap запрашивает отсутствующий диапазон, меньший seq не заменяет live head. При потере диска новая storage generation требует admission, не начинает старый seq с нуля.

Наблюдатель сохраняет результат локально даже без большинства и передаёт немедленно при наличии связи. Окончательная общая история получает его через `RecordObservations` в accepted log; не каждый follower самостоятельно создаёт incident/outbox. Принятое наблюдение прежнего CheckGeneration/удалённой цели остаётся историческим фактом, не меняет текущий live result и не создаёт новый live incident.

Параметры первого выпуска: interval=60 с, endpoint timeout=10 с, fresh window=150 с (2 × interval + timeout + 20 с запаса). Иной interval задаёт то же выражение; не путать эти 60 с с peer heartbeat 5 с. CheckedAtUtc проверяется по NTP/clock health (допустимое отклонение 5 с); сомнительное время даёт historical-only/ClockUnknown, не «свежее сейчас». ReceivedAtUtc не омолаживает старый результат. Сроки — выбранные параметры, их фактическая достаточность не измерена.

Течение времени само по себе не запускает независимые переходы на репликах: лидер предлагает `EvaluateAvailability` с EvaluationTimeUtc, config revision и observation frontier; reducer использует это принятое время. Последовательность ошибок считается отдельно по непрерывному stream; успех сбрасывает counter, gap/новое поколение сбрасывают доказанность серии. Сохраняется текущий FailuresBeforeUnavailable; одновременные ошибки разных узлов не складываются. Свежая ошибка ниже порога не остаётся успехом бесконечно: последнее подтверждение учитывается только до fresh deadline, затем направление PendingConfirmation/Unknown.

| Свежие направления текущего поколения | Общая доступность / coverage |
| --- | --- |
| Все ожидаемые подтверждены Success | Available / Complete |
| Есть Success и подтверждённый Failure | Partial с точным набором проблемных направлений; coverage отдельно Complete/Incomplete |
| Все ожидаемые подтверждены Failure | Unavailable / Complete |
| Есть Success, остальные Unknown/не подтверждены | Доступен по известным направлениям / Incomplete, не полный отказ |
| Есть Failure, остальные Unknown, успехов нет | Unknown / Incomplete с известными ошибками, не доказанный полный отказ |
| Нет свежих подтверждений | Unknown / Lost |

Coverage имеет отдельный incident lifecycle Complete → Degraded → Lost → Complete; смена Degraded/Lost создаёт устойчивое событие, одинаковое состояние — нет. Восстановление полного coverage уведомляет только подтверждённых получателей warning. Неполнота не открывает target outage и не закрывает ранее принятый outage; восстановление цели подтверждается свежими результатами всех ожидаемых направлений. Новое назначение получает grace=fresh window от принятия конфигурации; до первой проверки UI показывает Initializing, затем отсутствие данных становится отдельной потерей наблюдения. Смена назначения не создаёт синтетический recovery старой аварии. Старое поколение закрывается административным SupersededConfiguration с сохранением истории и отменой неначатых доставок; подтверждённое восстановление цели этим не подменяется.

Metadata (name/start time) сохраняются по observer. При различиях показывать каждое значение и источник; не выбирать случайный общий ответ/uptime. Различие metadata не меняет успешность. Partial обычной цели не меняет исправного главного с majority.

### Delayed/offline observations

Исторические данные не отбрасываются по live freshness или давности доставки. Для backlog принимать упорядоченные диапазоны каждого stream с acknowledged seq, durable batch ID и checked-time watermark. Исторический reducer отдельно от live head обрабатывает зафиксированный набор диапазонов по (CheckedAtUtc, ObserverNodeId, seq); время не арбитр настроек. Пока диапазон ожидаемого observer отсутствует, полнота исторического вывода Unknown; gap не считается отказом. Не достраивать вымышленные проверки в пустых минутах.

Принятый исторический event привязан к сохранённой frontier/набору диапазонов и детерминированному event key; поздний batch продолжает незакрытую историческую сборку, не создаёт второй incident за тот же переход. Зафиксированная история не переписывается приходом более старой записи: она сохраняется как late evidence и связывается с уже принятым историческим incident либо незавершённой сборкой. Открытые сборки и необработанные диапазоны защищены от очистки. При окончательной потере stream фиксируется явная неполнота, а не ложный полный outage/recovery. Catch-up включает восстановление stream cursors/frontiers и свежие live checks; старые successes не делают узел Ready по наблюдениям.

## 6. Инцидент, delivery intent и результат

IncidentId — стабильный ключ TargetId + CheckGeneration + первый принятый transition key; EventId — IncidentId + EventSequence + Kind. Одна принятая `AdvanceIncident` атомарно обновляет availability/problem directions, события и delivery intents по текущим bindings. Partial → Full → Partial → Recovered — одна история; новый event при смене подтверждённых проблемных направлений, без повтора неизменного набора. CoverageIncidentId и NodeIncidentId — отдельные виды, не подменяют target incident.

DeliveryKey = IncidentId + EventId/Kind + ChatEntityId; initial problem/recovery дополнительно имеют уникальный logical key IncidentId + problem/recovery + chat, чтобы rebind не повторял уже известную доставку. BindingGeneration нужна для проверки отмен, не для обхода дедупликации. Payload revision/адресат фиксируются в intent, текст строится из принятой версии и metadata с источником.

Состояния намерения: Planned → AttemptStarted → Succeeded либо RetryDue/Failed/Cancelled/SuppressedBySummary. `BeginDeliveryAttempt` атомарно сохраняет номер попытки, SenderEpoch, AttemptId, решение по отмене/actor и запрет параллельного claim того же DeliveryKey. Только затем gate 01.2 допускает HTTP; локальная SQL claim-строка не является распределённым разрешением.

`RecordDeliveryResult` включает AttemptId, safe failure kind, Telegram message ID при успехе и время. Поздний успех ранее принятой попытки можно принять от бывшего лидера. Повтор результата идемпотентен; success не откатывается поздней ошибкой. In-flight при смене главного становится Unknown до сверки/drain; после этого разрешён retry в общем бюджете. До вызова HTTP отменённая attempt не расходует transport-попытку; неизвестная после допуска учитывается как возможная внешняя попытка. Не более 5 внешних попыток, backoff 5 с/30 с/2 мин/5 мин; лимит общий между лидерами. После исчерпания Failed сохраняется, ручной и бесконечный retry исключены.

Telegram success до принятия DeliverySucceeded — неопределённый результат: повтор возможен. Принятый Succeeded не отправляется штатно повторно. Старый success без соответствующего AttemptId/intent не даёт права пометить чат уведомлённым. Потеря quorum после Telegram success оставляет локальный durable result на origin до передачи, не подменяет общую фиксацию.

### Привязки, recovery и сводки

- Bind к открытой проблеме: атомарно binding + intent текущей проблемы, если logical success ещё не известен.
- Unbind до BeginAttempt: атомарно generation change + cancellation неначатой проблемы. После известного/позднего Succeeded проблемы сохраняется RecoveryEntitlement(IncidentId, chat); один recovery даже без binding. Rebind сам по себе entitlement/успех не обнуляет.
- Delete target/chat: tombstone блокирует **все новые** sends, включая recovery; внешний in-flight может завершиться. Поздний успех сохраняется для истории, но entitlement не преодолевает удаление.
- Coverage warning использует тот же per-chat ledger; recovery только предупреждённым. Node incident получает чаты только из NodeId routing, не произвольные чаты.
- Test-send: отдельный принятый intent с OperationId/ActorUserId; одинаковый gate, повторная проверка активного аккаунта, без обхода через локальный controller sender.

Перед возобновлением backlog принять `PlanBacklogDelivery` с cut position, набором incidents/events и recipient ledger. SummaryId = стабильный ID принятого плана + ChatId + PartNumber. Для завершённых инцидентов, не доставленных данному чату, план атомарно назначает summary и помечает исходные pending intents SuppressedBySummary; записи не удаляются. Если была Unknown in-flight, сначала сверка: неизвестный внешний успех всё равно допускает редкий дубль.

Уведомлённому о проблеме чату планирует обычный recovery того же incident; открытые проблемы идут отдельно. Итог не зависит от возраста инцидента. Большая сводка разбивается на устойчивые части до 3500 символов, одна часть/чат имеет собственный DeliveryKey, retry не пересоздаёт список. Принятый состав сводки неизменяем, новый backlog получает следующий план. Успех/ошибка summary сохраняется по chat/part; исходные сообщения и summary не отправляются вместе штатно. Pending summary защищает все ссылки на исходные события даже старше года.

## 7. Удаление, snapshot, compaction и старая копия

Delete-команда атомарно пишет tombstone с EntityId/Revision, меняет связи, отменяет неначатые intents и сохраняет result/cursor. Server delete отвязывает контейнеры, сохраняя их и bindings; user delete не удаляет созданные им объекты; chat/target delete удаляет bindings и запрещает новые sends. Смена endpoint/disable создаёт новое CheckGeneration и terminal cancellation старых неначатых уведомлений; история старого инцидента сохраняется, искусственный recovery не отправляется.

Snapshot manifest: SnapshotId, ClusterId/Generation, SnapshotFormatVersion, Protocol/Command/HashFormat versions, cut LogIndex/Term, configuration version, schema version, total bytes, chunk hashes и общий SHA-256, created UTC. Содержимое: **все** принятые общие сущности, пользователи/hash/stamps/роль, uniqueness keys, tombstones, operation results/control ledger, conflicts, observers/frontiers, incidents/events, intents/results/entitlements/summary plans, membership/trust public registry и maintenance state. Нельзя ограничиться настройками и потерять delivery ledger.

1. Producer замораживает consistent projection cut коротким snapshot barrier/локальной SQL snapshot transaction и сохраняет snapshot file; live state после cut может продолжать работу. Writer не читает несогласованную смесь таблиц разных ревизий.
2. Записать временный файл, проверить формат/hash/длину, flush и атомарно опубликовать manifest + неизменяемый snapshot. До публикации нельзя удалять WAL prefix. Корень доверия snapshot получен из закреплённого peer trust, а не из непроверенного manifest.
3. Receiver в Recovering загружает chunks с restart cursor, проверяет целостность/идентичность/схему. Устанавливает **только общие** таблицы + cursor одной локальной транзакцией (при необходимости staging tables). Local secrets/Pending/raw observations не стираются; они изолированы до сверки.
4. При crash install SQL rollback оставляет старый cursor; скачивание повторяется. Если SQL commit есть, а manifest pointer не переключён, старт сверяет SnapshotId/hash/cut в SQL и доводит pointer; не применяет старую копию поверх нового state.
5. Replay принятого хвоста, сверка результатов/Identity/membership, затем новые live checks и рабочий follower. SQL restore без парного WAL/snapshot marker — Quarantine, не обычный startup.

Completed history удаляется не ранее **одного года после завершения** incident/delivery/resolved conflict. Открытые incidents/conflicts, LocalPending, неисполненные intents, Unknown attempts, summary references, recovery entitlements и незавершённые controls/сборки не удаляются по возрасту. Подробный result payload после срока может сокращаться, но компактный OperationId + digest + terminal outcome/position сохраняется на срок жизни ClusterGeneration. Аналогично компактный tombstone ID/revision остаётся в snapshot: возраст не позволяет старой заявке воскресить удаление.

Raft WAL compaction разрешён только после проверенного опубликованного snapshot cut и подтверждения сохранности нужного хвоста. Реплика с cursor ниже MinReplayPosition принудительно проходит full snapshot-rejoin; нельзя держать журнал бесконечно ради выключенного узла и нельзя давать ему писать старый state обратно. Snapshot GC учитывает reader watermark DotNext. Годовой retention прикладной истории и удаление WAL prefix — разные операции; snapshot сохраняет защищённые данные независимо от возраста.

Обычный restart использует неизменённые NodeId/storage generation/WAL и новый BootId, не обнуляет term/vote. После snapshot/restore локальный SessionEpoch меняется и прежние cookie/SignalR-сессии отклоняются, даже если сохранены локальные Data Protection keys; сессии из копии не возобновляются. Старый backup/клон изолируется до запуска: проверить, что прежний экземпляр остановлен; отозвать его credential, выполнить Remove/Add через актуальное большинство с новым storage generation (для замены диска — новый NodeId), установить актуальный snapshot. Копировать устаревший vote/term поверх действующего member нельзя. Endpoint можно повторно использовать только после удаления старого transport member и fencing экземпляра.

Pending backup сверяется по OperationId/digest: Committed/Cancelled/Replaced не повторяется, Conflict остаётся конфликтом. Для оставшихся неизвестных заявок статус NeedsUserConfirmation, затем проверка актуального actor/base и новая разрешённая подача со ссылкой на старый ID; без автоматической очереди по старой форме. Local outbox и delayed observations также сначала сверяются; restore не включает старую отправку. При потере большинства используется отдельная процедура [01.2](01.2-consensus-and-sender-contracts.md#ручное-восстановление-после-утраты-большинства), допускающая явно подтверждённые потери выбранной копии.

## 8. Совместимость, обслуживание и безопасные логи

Peer handshake фиксирует DotNext release, ProtocolMajor/Minor, CommandSchema, SnapshotFormat, SQL schema и PasswordHashFormat. В первом выпуске все узлы используют **одинаковый protocol/schema и DotNext 6.10.0**; mixed-version rolling upgrade не обещается. Неизвестный обязательный command kind/version — остановка apply и readiness, а не пропуск записи. Minor-расширения допустимы только после отдельной спецификации; текущий контракт fail-fast.

Будущее несовместимое обновление: принятый EnterMaintenance + локальные durable Disabled latches на всех известных экземплярах → закрыть UI/checks/sender/vote, drain → сохранить согласованный backup manifest → обновить binaries/schema офлайн → восстановить/сверить snapshots и projections → ручное включение разработчиком той же maintenance generation. Restart, таймер и обновление пакетов latch не снимают. Откат на бинарник, не читающий новый log/snapshot/schema, запрещён без согласованного восстановления всех хранилищ и fencing; допустимая точка описывается в 09, не исполняется сейчас.

Information-логи важных действий: Pending submitted/replaced/cancelled, Command committed/conflicted/rejected, Account changed, Membership/trust changed, Observer set changed, Delivery plan/result и Recovery/Maintenance transition. Английские шаблоны, whitelist IDs: ActorUserId отдельно от SubjectUserId, OperationId, EntityId, NodeId, DecisionPosition, safe reason/count. Actor только из серверного контекста; system source явно назван.

Pending saved логируется как локальное сохранение; Committed — только после majority decision и SQL transaction. Apply/retry не пишет повторный business success на каждой реплике: владеющий origin/leader пишет итог, replay — Debug с тем же event ID. Лог не заменяет durable result. Нет паролей, hash/stamps, token/сертификатов с private key, login, cookies, URL с секретами, payload/response body, текстов сообщений и raw provider exceptions. Чтения/heartbeat/каждая минута checks не превращаются в Information audit.

## 11. Статическая трассировка и минимальная проверка

Документально прослежены:
- O1/Cancel/Replace в обоих порядках и потерянный ответ: один terminal head, без промежуточного Б при подтверждённой замене.
- A→Б затем A→В: Б остаётся, Conflict хранит В, новый Resolve проверяет текущую базу.
- Два одинаковых login и два отключения последних admin: упорядоченный reducer сохраняет uniqueness/последнего; self-action запрещён.
- Majority до SQL и SQL до apply ACK: replay/position guard не дублирует принятую операцию.
- Один/all observer устарели: отдельный coverage warning, не target outage; восстановление требует свежих результатов, metadata по узлам.
- Старые завершённые incidents + открытая проблема + уже уведомлённый чат: summary/обычный problem/recovery распределены по recipient ledger; unbind/in-flight/delete сохраняют описанные пределы.
- Очистка после года: незавершённый intent/summary/control/frontier защищает историю; старый snapshot не воскрешает ID, restore Pending требует сверки.
- Maintenance/recovery: нет автоматического enable, новая идентичность не заменяет внешнее fencing.

Это анализ переходов, **не выполненные тесты**. Минимальные будущие изолированные проверки по этапам: majority/gate с fake time/quorum; Execute/Cancel/Replace + конфликт + apply retry с fake stores; активный администратор/unique login/last-admin; observation reducer + per-chat recovery/summary при затронутом коде. Не требуются тест на каждую строку справочной матрицы, полный стенд или нагрузочный прогон. Часовая цель catch-up остаётся для трёх узлов/~30 приложений, 60 с на назначенного observer; замеров нет. SQL atomicity, fsync/crash, mTLS/Nginx, настоящий Identity sign-in/SignalR, Telegram, restore/compaction и drift остаются непроверенными runtime-свойствами.
