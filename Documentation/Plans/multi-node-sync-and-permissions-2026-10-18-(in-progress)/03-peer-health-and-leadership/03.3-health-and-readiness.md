# Подэтап 03.3. Самодиагностика и готовность узла

Статус: completed

## Цель и результат

Readiness различает локальную неисправность и отсутствие peer-связи, управляет остановкой рабочих компонентов.

## Зависимости и границы

Зависимости: [03.2](03.2-durable-raft-and-membership.md).

Родительский [этап 03](main.md) задаёт общие ограничения и критерии. [Общий план](../main.md) содержит сводные статусы; [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) определяют согласованное поведение. Подготовка документа не разрешает реализацию, запуск приложения, внешние проверки или включение функции.

## Затрагиваемые части проекта

Будущие peer/cluster модули в Application и Infrastructure, durable storage в `Infrastructure/Persistence`, `Infrastructure/Monitoring`, `Infrastructure/Telegram`, `Web/Configuration`, `Web/Controllers`, `Web/Program.cs`; конфигурационные примеры без секретов, соответствующие тесты и локальные `AGENTS.md`.

Работа ограничена перечисленными ниже сценариями; смежные компоненты изменяются только при необходимости выполнить результат подэтапа.

## Работы

- [x] Реализовать частые проверки связи и статусы Web/БД/worker/Telegram с возрастом результата. Health не отправляет реальные сообщения в чаты и не маскирует неизвестную причину сетевого отказа.
- [x] При неисправной БД немедленно перевести узел в проблемный неготовый режим, остановить рабочие writers/checks/sender и не использовать его подтверждения рабочих изменений. Не уменьшать согласованный состав; после восстановления БД выполнить догон и вернуть follower.

- [x] Диагностировать одного общего Telegram-бота на всех отправителях без вывода токена. Возвращать актуальный статус доступности отправки через готового главного, известную причину и отсутствие свежих данных; не обещать норматив времени восстановления.

- [x] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию в пределах реализованного изменения; новые документы включить в навигацию и solution.

## Проверки

Проверить смену главного с тем же ботом, отсутствие токена/несовпадающую идентичность при вводе узла, общую недоступность Telegram и устаревший статус.

Fake time/health: БД отказала при отвечающем HTTP, устарел health, упал worker, недоступен Telegram, запрещён один чат; проверить запрет работы до догона.

Общие сценарии [родительского этапа](main.md#проверки) сохраняются. Минимальные изолированные проверки подтверждают production policy, storage и adapter API в указанном ниже объёме; выборы DotNext и crash recovery ими не объявляются проверенными. Реальные БД, peer HTTP, процессы, браузер и Telegram учитываются отдельно в [этапе 10](../10-verification-and-acceptance/main.md).

Команды из плана не являются разрешением их запускать. Непроведённая обязательная проверка остаётся открытой; готовность кода при ожидающей приёмке обозначается `verification`.

## Критерии приёмки

- [x] Неисправная БД закрывает рабочую готовность без изменения membership; восстановление требует подтверждённого догона.
- [x] Ошибка отдельного чата не становится общим Telegram outage; статус отправки не выдаёт неизвестное состояние за доступность и не обещает срок возобновления.
- [x] Работы и применимые проверки подэтапа выполнены, результат и ограничения зафиксированы.
- [x] Статус согласован с таблицами родительского этапа и общего плана; незавершённая внешняя приёмка не объявлена выполненной.

## Результат выполнения

2026-10-29: Реализованы локальная DB readiness, monotonic age/staleness, безопасная peer connection диагностика, Telegram getMe/BotId без тестовых сообщений и контракт реального worker progress. Отказ БД инвалидирует recovery, закрывает новые writers/ACK/vote/sender, supervisor останавливает Raft без изменения состава. После ремонта требуется новый подтверждённый replay/catch-up. Проверены DB failure/repair со старым proof, неподтверждённые аккаунты/догон, staleness, Telegram global/chat/rate-limit границы через fake HTTP. Реальные БД, общий бот и восстановление проекций не проверялись; reducer принадлежит 04.

Сборки и общий минимальный набор этапа — [Testing.md](../../../Technical%20documentation/Testing.md#проверка-этапа-03). Будущие accepted recovery/account/trust/authority порты по умолчанию закрыты; соседние этапы не реализованы и функция не включена.
