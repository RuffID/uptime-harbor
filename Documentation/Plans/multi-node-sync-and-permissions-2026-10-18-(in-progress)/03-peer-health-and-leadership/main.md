# Этап 03. Связь узлов, диагностика и главный

Статус: completed

## Цель

Обеспечить доверенную связь узлов и выбор главного большинством, отделив факт роли от действующего права отправлять уведомления.

## Зависимости и границы

После [01](../01-protocol-and-contracts/main.md) и [02](../02-domain-and-persistence/main.md). На этом этапе не включать реальные Telegram-отправки. Адреса указываются явно, автоматического сетевого обнаружения не требуется.

## Затрагиваемые части проекта

Будущие peer/cluster модули в Application и Infrastructure, durable storage в `Infrastructure/Persistence`, `Infrastructure/Monitoring`, `Infrastructure/Telegram`, `Web/Configuration`, `Web/Controllers`, `Web/Program.cs`; конфигурационные примеры без секретов, соответствующие тесты и локальные `AGENTS.md`.

## Границы ответственности подэтапов

03 реализует транспорт, durable Raft и gate. Прикладной журнал, проекции SQL Server, snapshot и догон реализуются в 04. В 03 проверяется контракт готовности к догону: до подтверждения gate закрыт; завершение этого этапа не включает рабочую отправку. Подключение реального восстановления — 04/07, controlled enable — 09.

## Проверки

Изолированно с fake transport/time/durable store: 3 узла, 2+1, один из двух недоступен, одновременные кандидаты, асимметричная связь, дубли/задержка heartbeat, restart с сохранённым vote, pause старого главного и clock jump. Отдельно — неверная peer-аутентификация, несовместимая версия, слишком большой body, общий Telegram outage и ошибка конкретного чата.

Настоящий HTTP, независимые процессы, SQL Server и сетевое разделение — отдельная разрешаемая приёмка этапа 10; fake transport её не заменяет.

## Критерии приёмки

- [x] Большинство считается по принятому составу; одиночный узел меньшинства не получает право отправки.
- [x] Переключение выдерживает требование 30 секунд и не оставляет старому главному бессрочное разрешение.
- [x] Рестарт/возврат узла не обнуляет защиту от старого term и не даёт дополнительного голоса.
- [x] Readiness объясняет причину недоступности отправителя без ложных утверждений о причинах удалённого timeout; проблемный из-за БД узел не участвует в работе и возвращается только после догона.
- [x] Сценарий 3+2 работает, даже если один узел меньшинства продолжает видеть прежнего главного; partial обычной цели сам по себе не запускает выборы.
- [x] Есть серверный gate, который следующие этапы обязаны использовать для всех Telegram-путей.

- [x] Состав и доверие меняет активный администратор; отдельного оператора нет, большинство и peer trust обязательны.

## Результат выполнения

2026-10-29 завершены 03.1–03.4: typed configuration и отдельный mTLS perimeter, DotNext 6.10.0 с persistent WAL/configuration и recovery lifecycle, accepted-admin membership boundary, readiness/health и sender authority. Контракты 04/05/06/07 закрыты до достоверного accepted state; legacy workers/UI/sender в enabled-режиме заблокированы. Реальные узлы и отправки не запускались.

Четыре production-проекта собраны отдельно без предупреждений/ошибок. Application: 139 passed, выбранные Infrastructure Cluster: 38 passed, Web Cluster: 16 passed; ошибок и пропусков нет. Изолированные health-quorum/gate tests не доказывают выборы DotNext; настоящий WAL/configuration reopen и adapter API wiring не доказывают power-loss fsync/crash recovery. Реальные TLS/Nginx, многопроцессные elections/partitions, SQL replay и Telegram остаются отдельными непроведёнными наблюдениями этапа 10. Полные [команды и ограничения](../../../Technical%20documentation/Testing.md#проверка-этапа-03), [фактическое устройство](../../../Technical%20documentation/Cluster%20runtime.md).

Этапы 01/02 не переписаны; общий план остаётся in-progress. Работа остановлена после 03, controlled enable не выполнялся.
