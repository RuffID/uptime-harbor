# Подэтап 05.4. Bootstrap, жизненный цикл аккаунтов и возврат узла

Статус: not-started

## Цель и результат

Первый администратор, блокировка аккаунтов и восстановление пользователей согласованы с жизненным циклом сетки.

## Зависимости и границы

Зависимости: [05.3](05.3-acl-commands-and-owners.md).

Родительский [этап 05](main.md), [общий план](../main.md), [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) задают границы. Подготовка документа не разрешает реализацию, запуск приложения или внешние проверки.

## Затрагиваемые части проекта

Infrastructure/Identity, bootstrap и snapshot/replay 03/04, диагностика и эксплуатационные инструкции. Профильные тесты, ближайшие `AGENTS.md` и актуальная техническая документация обновляются при будущей реализации.

## Работы

- [ ] Создавать первого администратора только при первом bootstrap новой сетки. Присоединяемый узел не создаёт собственных пользователей или роли с независимыми ID и получает общий UserId/RoleId в snapshot/replay.
- [ ] Сохранять общие UserId при удалении или замене узла; пользователи не принадлежат узлам создания.
- [ ] При rejoin/restore сверять состояние пользователей и их tombstones с принятой историей до открытия входа; не воскрешать удалённый аккаунт и старый пароль.
- [ ] Оставить сессии, cookie, локальные ключи и временные счётчики ошибок входа собственными для узла; не создавать общий журнал каждого входа.
- [ ] Описать поведение offline-узла: до догона последнее принятое состояние, после apply актуальное отключение/пароль и недействительность старых сессий.
- [ ] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию; новые документы включить в навигацию и solution.

## Проверки

Один bootstrap-пользователь, join без дополнительного локального администратора, удаление узла создания пользователя, старый backup с удалённым аккаунтом/паролем, partition и последующий догон.

Изолированные проверки и compile-check не подменяют SQL Server, реальные peer HTTP, браузер и Telegram. Внешняя приёмка учитывается отдельно в [этапе 10](../10-verification-and-acceptance/main.md); команды из плана не разрешены автоматически.

## Критерии приёмки

- [ ] У пользователя нет домашнего узла; join и snapshot содержат пользователей и роль.
- [ ] Старый backup не восстанавливает принятые удаления и прежние данные входа; локальные сессии не переносятся.
- [ ] Работы и применимые проверки выполнены; непроведённая внешняя приёмка остаётся открытой.
- [ ] Статус согласован с родительским этапом и общим планом.
