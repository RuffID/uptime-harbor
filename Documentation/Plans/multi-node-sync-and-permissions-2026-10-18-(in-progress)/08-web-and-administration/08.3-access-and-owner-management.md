# Подэтап 08.3. Общие пользователи и настройки уведомлений

Статус: completed

## Цель и результат

Администратор управляет общими аккаунтами и всеми привязками без формы отдельных прав.

## Зависимости и границы

Зависимости: [08.2](08.2-pending-editors-and-deletion.md).

Родительский [этап 08](main.md), [общий план](../main.md), [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) задают границы. Подготовка документа не разрешает реализацию, запуск приложения или внешние проверки.

## Затрагиваемые части проекта

Страницы Users/Notifications и frontend-модули, команды пользователей и привязок, Web authorization. Профильные тесты, ближайшие `AGENTS.md` и актуальная техническая документация обновлены по фактической реализации.

## Работы

- [x] Показывать один общий список пользователей с любого узла и единственную роль «Администратор» без выбора роли, узла пользователя, владельцев или отдельных разрешений.
- [x] Создание/редактирование, смену данных входа, отключение и удаление передавать в готовый pipeline 05/04; показывать действующее/ожидающее состояние и отказ при self-disable/self-delete или последнем активном администраторе.
- [x] Разрешить каждому активному администратору управлять любыми чатами/привязками и отдельными назначениями чатов инцидентов каждому NodeId. Изменения согласуются и безопасно логируются.
- [x] Test-send доступен любому активному администратору через главного. При привязке к открытой аварии пояснять немедленное планирование проблемы, при unbind — отмену не начатого outage и один recovery уведомлённому чату.
- [x] Защищённые данные пароля не возвращать из API; конфликт аккаунтов показывать без хешей/stamps/текста пароля.
- [x] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию; новые документы включить в навигацию и solution.

## Проверки

Общий пользователь на двух узлах, создание одинакового login, pending/отказ/успех аккаунта, защита последнего администратора, назначение чатов А/Б, test-send, привязка/unbind и отключение отправителя до внешнего запроса.

Изолированные проверки не подменяют SQL Server, peer HTTP, браузер и Telegram. Внешняя приёмка учитывается отдельно в [этапе 10](../10-verification-and-acceptance/main.md); команды из плана не разрешены автоматически.

## Критерии приёмки

- [x] Все активные пользователи имеют одну роль и одинаковое управление; UI отдельных разрешений и владельцев отсутствует.
- [x] UI/API соблюдают инварианты аккаунта и согласованные последствия привязки/unbind; test-send проходит общий gate.
- [x] Работы и применимые проверки выполнены; непроведённая внешняя приёмка остаётся открытой.
- [x] Статус согласован с родительским этапом и общим планом.

## Результат выполнения

2026-10-29. Реализованы единый список Administrator, Create/Update/Password/SetEnabled/Delete через account pipeline, безопасные Pending/result и controls/conflict resolution. Выбора роли/владельца/узла/permissions нет. Все чаты, bindings и независимые NodeChatRoute доступны администратору. TestDelivery с устойчивым ID возвращает 202 как очередь, реальная доставка показана отдельно. Привязка/unbind/final recovery объяснены в UI. Изолированно проверены account controls/уникальность login/self/last-admin/disable, отдельные маршруты и очередь; регрессии 07 сохраняют общий sender gate и recovery entitlements.

Общий итог этапа: 504 .NET + 15 frontend tests, без ошибок/пропусков; четыре production compile-check без предупреждений. [Команды и ограничения](../../../Technical%20documentation/Testing.md#проверка-этапа-08). Приложение, SQL/provider tests, peers, Telegram, Docker и браузер не запускались; внешняя приёмка остаётся отдельной непроведённой категорией. Gates/default Disabled сохранены. Этапы 09/10 не начинались.
