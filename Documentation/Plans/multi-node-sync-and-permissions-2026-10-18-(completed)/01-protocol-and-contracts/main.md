# Этап 01. Архитектура и контракты сетки

Статус: completed

## Цель

Получить проверенный проект протокола и модели согласования до реализации распределённых изменений и отправок.

## Зависимости и границы

Зависимостей нет. Основа — [пользовательские требования](../business-requirements.md) и [предварительное проектирование](../technical-design.md). Этап не разрешает запуск узлов, запросы к Telegram, подключение к БД или реализацию остальных этапов.

## Затрагиваемые части проекта

Текущие границы `Domain`, `Application/Abstractions`, `Infrastructure/Monitoring`, `Infrastructure/Telegram`, `Infrastructure/Persistence`, `Web/Configuration`, `Web/Controllers`, `Web/Hubs`; их локальные `AGENTS.md`. Документы об архитектуре, конфигурации, мониторинге, доставке и данных в `Documentation/Technical documentation`.

Новые модули и публичные имена пока не существуют: окончательные места и контракты определить здесь, без создания пустых типов ради плана.

## Границы ответственности подэтапов

01.1 подтверждает интеграцию выбранной технологии; 01.2 фиксирует majority/readiness/право отправки; 01.3 — данные, авторизацию и восстановление. Подэтапы не разрешают реализацию следующих этапов или непрошедший согласование запуск прототипа.

## Проверки

Проектные сценарии: partition 2+1 и 3+2, кандидаты, асимметрия, process pause, конкурентные правки, одинаковое имя входа и отключение последних администраторов, смена пароля, Telegram success без фиксации и несовместимая peer-версия.

API DotNext 6.10.0 проверены по NuGet metadata и закреплённым исходникам; проектные сценарии разобраны статически в каждом подэтапе. Прототип не требовался для документального результата и не создавался. Проверка не подтверждает компиляцию адаптера, SQL Server, сеть или crash recovery; будущая реализация проверяется минимально по этапу 10.

## Критерии приёмки

- [x] Для всех записываемых общих данных определены источник истины, точка принятия, версия и способ восстановления.
- [x] Алгоритм большинства/отправки объясняет перечисленные отказы без двух независимо действующих главных.
- [x] Зафиксирована последовательность обработки наблюдения до одного общего инцидента и доставки.
- [x] Интеграция выбранного DotNext/Raft и правила partial/readiness формализованы для реализации; оставшиеся проверки не подменены отметкой об окончании этапа.
- [x] Контракты учитывают замену/отмену, конфликт без отката, общих пользователей с единственной ролью и одинаковый вход на догнавших узлах.
- [x] Есть карта новых модулей, миграции, минимальных изолированных проверок и справочных сценариев самостоятельной приёмки.

- [x] Формализованы общие аккаунты и membership/trust для администратора, полная диагностика, observers, metadata по узлам и отдельная маршрутизация инцидентов узлов.

## Связанные вопросы


Открытых вопросов нет. Условия HTTPS-связи, рабочий масштаб и порядок самостоятельной проверки закреплены в [техническом проектировании](../technical-design.md#11-среда-масштаб-и-порядок-проверки).

Согласованное поведение закреплено в [требованиях](../business-requirements.md); клиентских блокирующих вопросов нет.

Проверка API, параметров и поведения при отказах — работы этапа, а не повторное согласование выбранной технологии.

## Результат выполнения

Этап 01 и подэтапы 01.1–01.3 завершены 2026-10-29 **как архитектурное исследование и спецификация контрактов**. Официальные API проверены по метаданным/исходникам, сценарии разобраны статически; распределённая функция ещё не реализована.

- [01.1](01.1-dotnext-integration.md#зафиксированная-версия-и-уровень-доказательства): DotNext 6.10.0/net10.0/MIT, durable WAL/term/vote/configuration, snapshot-before-WAL, bootstrap/join/membership, ограничения 1/2/3 узлов.
- [01.2](01.2-consensus-and-sender-contracts.md#https-и-взаимное-доверие): mTLS/Nginx, trust lifecycle, readiness отдельно от выборов, majority authority и per-attempt gate, pause/in-flight и аварийное внешнее fencing.
- [01.3](01.3-data-and-recovery-contracts.md): commands/results/controls/conflicts, общий Administrator, WAL→SQL/replay, observations/freshness, incidents/delivery/summary, snapshot/retention/compatibility, матрица владения и карта компонентов.

Проверены 132 относительные ссылки (включая 16 якорей), 25 уникальных внешних URL официальных материалов и все 57 документов плана как solution items. XML/пути `.slnx`, статусы, UTF-8 и окончания строк сохранены; старых входящих путей нет. После последующей вычитки проверки повторены. Содержимое 02–10 побайтово не менялось при переименовании папки. Код/проекты не менялись; актуальные technical docs продолжают описывать однопроцессную реализацию с прежними permissions, её замена принадлежит 02–08.

Уровень подтверждения API — исходники конкретного NuGet commit, без compile/runtime. Не проверены NuGet restore с локальными DLL, durability на целевой ОС, SQL atomicity/Identity, TLS/proxy, процессы/clock drift, Telegram и restore. Прототипы/тесты не создавались и не запускались; часовая цель догона не измерялась. Отсутствие полного стенда/нагрузочного прогона не блокирует этот документальный этап; будущие минимальные тесты не объявлены выполненными.

**Остановка после 01:** этапы 02–10 не выполнялись, 09.2/09.3 сохраняют cancelled. Завершение всего плана и пользовательская приёмка не объявлены.
