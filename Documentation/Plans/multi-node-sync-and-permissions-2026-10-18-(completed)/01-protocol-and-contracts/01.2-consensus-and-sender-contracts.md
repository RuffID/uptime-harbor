## HTTPS и взаимное доверие

Выбран **mTLS для peer-трафика**: отдельное DNS-имя peer virtual host каждого узла, публично доверенный обновляемый серверный TLS-сертификат и отдельный клиентский сертификат узла от частного cluster CA. Browser host не требует client certificate; peer host не принимает browser cookie как аутентификацию. VPN не нужен.

- На peer Nginx обязательны `ssl_verify_client on`, `ssl_client_certificate` и актуальный CRL через `ssl_crl`; TLS 1.2/1.3, TLS early data отключён. Проверять серверные SAN/hostname/chain и срок; `DangerousAcceptAnyServerCertificateValidator` запрещён.
- Клиентский сертификат содержит clientAuth EKU и SAN URI с ClusterId/ClusterGeneration/NodeId. Приложение дополнительно проверяет SHA-256 fingerprint публичного сертификата по принятому trust registry, generation, NodeId, назначение admission/active и отзыв. Доверия всей CA без allowlist недостаточно.
- Nginx заменяет входящие `ssl-client-cert` и verification-заголовки собственными значениями, передаёт URL-encoded `$ssl_client_escaped_cert`. Приложение принимает их только от явно разрешённого proxy, с certificate forwarding до peer authentication; проверка SAN/allowlist действует на **каждый запрос**, в том числе на существующем TLS-соединении.
- Внутренний HTTP разрешён только через loopback/изолированную сеть конкретного Nginx с запретом прямого доступа к Kestrel. Если изоляции нет — TLS/mTLS до приложения. Одних ForwardedHeaders/KnownNetworks недостаточно для доверия certificate header.
- Исходящий DotNext handler получает собственный client certificate через `HttpClusterMemberConfiguration.ClientHandlerName` и `IHttpMessageHandlerFactory`; это подтверждённая точка подключения, конкретная конфигурация handler проверяется при 03.1. Аналогичный защищённый клиент обслуживает прикладные peer API.
- Доменная TLS-ротация не меняет NodeId/доверие клиентского сертификата. Не отключать проверку hostname на время обновления.

### Первоначальное доверие, ротация и отзыв

1. При bootstrap офлайн provision закрепляет cluster CA fingerprint и manifest; приватный CA key хранится вне узлов. Узел генерирует собственный private key локально. Через независимый канал администратор сверяет ClusterId, NodeId и fingerprint CSR/сертификата; открытого endpoint «доверять первому позвонившему» нет.
2. Активный общий администратор принимает `AdmitNode` с URI/fingerprint/сроком действия приглашения (15 минут, одно использование). До включения в protocol membership доверие admission разрешает только handshake, warmup и snapshot/replay конкретной сетки, без голосов и обычных команд. После включения URI в принятую DotNext configuration и успешного SQL apply узел может подтверждать Raft RPC; прикладные команды/checks/sender ещё закрыты до `ActivateNode`. Активация не является предварительным условием участия в majority для принятия самой ActivateNode: иначе переход 1→2 заблокируется. Bootstrap первого администратора остаётся отдельной локальной процедурой.
3. Клиентские сертификаты выдавать на 90 дней; ротацию начинать за 14 дней. Принятая `TrustNewCredential` добавляет новый fingerprint. После подтверждения установки и свежего mTLS handshake всеми текущими участниками — `RetireCredential` старого; штатное перекрытие не более 24 часов. Просрочка закрывает peer-доступ, не включает запасную общую учётную запись/секрет.
4. Плановая ротация CA: принять новый public root, установить на всех proxy, проверить новый credential, затем принять удаление старого root. Приватные ключи/сертификаты с private key не синхронизируются. Аварийный отзыв — приоритетная `RevokeCredential`, обновление CRL и закрытие соединений; приложение сразу запрещает отозванный fingerprint после apply.
5. Изменение trust/membership и подробная диагностика доступны любому принятому активному Administrator; actor проверяется перед согласованием. Отзыв не уменьшает состав: потеря кворума останавливает принятие. На изолированном узле немедленный отзыв не обещается; устаревшее доверие не даёт меньшинству право отправки.
6. При подозрении на компрометацию, которая затрагивает большинство, обычного отзыва недостаточно: остановка сетки, внешнее fencing и отдельное восстановление. Raft рассчитан на отказы доверенных узлов, не на Byzantine-участников.

### Peer envelope и пределы

Один HTTPS peer host обслуживает DotNext protocol path и `/internal/cluster/v1/*` (handshake, health, commands/results, observations, snapshot chunks). Пользовательские API — отдельные контроллеры с cookie/antiforgery. Не заменять native Raft RPC собственными HTTP OK.

Каждый прикладной запрос/ответ включает ProtocolMajor=1, Minor=0, ClusterId, ClusterGeneration, FromNodeId, ToNodeId, CredentialId, RequestId (UUID), IssuedAtUtc; ответ повторяет RequestId и challenge. При несовместимом major, generation, fingerprint или адресате — отказ до десериализации прикладного payload. На native RPC те же проверки идут в middleware/header wrapper до DotNext handler, не меняя его wire format.

Replay: TLS защищает канал, 0-RTT выключен; принимается окно времени ±30 секунд, случайный nonce 128 bit/RequestId уникален для отправителя. Прикладной inbox сохраняет nonce на 2 минуты локально, повтор возвращает сохранённый ответ или безопасный отказ без повторного эффекта; бизнес-идемпотентность отдельно по OperationId. Перед каждым сетевым retry новый RequestId, OperationId прежний. Native Raft retry защищён term/index и механизмом DotNext request journal; прикладной nonce не должен блокировать его штатные повторы. После restart health требует новый challenge; старый ответ не продлевает право отправки. При неопределённом времени/резком скачке часов доверенные операции закрываются до сверки, часы не «исправляют» конфликты данных.

| Ограничение | Решение |
| --- | --- |
| Health | Цикл 5 с, timeout 3 с, тело <= 64 KiB; статус старше 10 с — Unknown |
| Команда | <= 256 KiB; пакет <= 100 записей и <= 1 MiB; одно изменение не разрывать между пакетами |
| Наблюдения | Пакет <= 100/1 MiB, один observer stream в порядке seq; fair queue между узлами |
| Snapshot | Chunk <= 1 MiB, manifest с общей длиной и SHA-256; потоковая запись, лимит свободного диска до приёма, без загрузки всего snapshot в RAM |
| HTTP | Command timeout 10 с; chunk 30 с; connect 3 с. Нет redirect, proxy cache, автоматического proxy retry mutating-запросов или неограниченного тела |
| Retry/backpressure | 1/2/5/10/30 с с jitter до 20%; ограниченная очередь, durable backlog, 429/Retry-After и прогресс по cursor; исчерпанный HTTP timeout означает UnknownResult |

Ограничения Nginx/Kestrel/DotNext transport согласуются в 03.1/04.4: native snapshot stream не обрезать лимитом обычной команды; admission не разрешает произвольную загрузку файла. Это проектные пределы, не измеренная пропускная способность.

## Membership, readiness и лидер

Membership — только принятой конфигурации DotNext по [01.1](01.1-dotnext-integration.md). Health, наблюдения и доверие не являются новым списком голосующих. Для join/leave есть MembershipChangeId и состояния Requested → CatchingUp → ProtocolCommitted → Activated/Removed; timeout оставляет сверку результата, не обратный Remove/Add. Разрешено одно изменение за раз; незавершённое восстанавливается из журнала и durable config. Применяется порядок остановки sender ниже.

Health возвращает NodeId/generation, BootId, protocol/schema/hash-format, term/role, membership version, committed/applied/snapshot positions, Database/Monitoring/TelegramTransport/Clock/Storage statuses, время/возраст и контролируемый reason code. Health не отправляет сообщения в чаты и не читает секретные поля аккаунтов. Диагностика БД по возможности использует последний локальный health snapshot без обязательного запроса к сломанной БД.

| Состояние | Разрешено |
| --- | --- |
| Quarantine / Maintenance | Только ограниченная диагностика/recovery, нет рабочих UI/checks/vote/sender |
| Recovering | Защищённый догон; нет рабочих правок, голосов при неисправной проекции и sender |
| Working follower без связи, исправная БД | Вход/чтение принятого состояния, durable Pending и назначенные checks; нет принятия без большинства |
| Candidate | Только выборы/догон и локальная работа по принятому состоянию; sender закрыт |
| Elected leader | Выборы завершены, но sender ещё закрыт до barrier, догона и ready authority |
| Ready sender | Текущий лидер, применён весь подтверждённый префикс, восстановлены intents/results, есть свежая authority и исправны локальные зависимости |

При ошибке собственной БД/проекции/storage немедленно закрыть gate, рабочие правки/checks/apply, отвергать рабочие Raft RPC (включая vote/AppendEntries ACK) и остановить cluster, сохраняя неизменный состав. Простого `Standby` недостаточно: принимающий log участник тоже может войти в majority commit. После ремонта восстановить WAL/SQL, принимать только recovery-синхронизацию, затем ведомый. Промежуточное участие в warmup не подтверждает рабочие изменения до завершения SQL apply.

Monitoring readiness означает живой scheduler и обработку его очереди, а не успех каждого endpoint: обычный partial/outage цели не вызывает выборы. Progress watchdog — max(2 × check interval + check timeout, 30 с); пустой набор целей всё равно имеет отметку успешного цикла.

Telegram readiness проверяет наличие локального token и общий BotId. В будущей реализации — ограниченный `getMe` без сообщений: при старте/смене token и не чаще раза в минуту, timeout 5 с; успех актуален 90 с. Успешный send также обновляет transport health. 401/неверный BotId — локальная неисправность; общий network/5xx — transport unavailable, 403 одного чата — только его доставка, 429 — rate-limit/backoff, не повод циклически менять лидера. Неизвестный transport status закрывает sender. Эти вызовы в этапе 01 не выполнялись.

### Окно 30 секунд

Health запрашивается каждые 5 с, но наличие HTTP/Raft heartbeat не продлевает **готовность** неработоспособного главного. LastReadyAck фиксируется только для matching challenge, текущего term/membership и готового лидера. Через 30 с без такого подтверждения начинается согласование смены, а не открывается Telegram. При известной локальной неисправности главный закрывает gate и отказывается от рабочей роли сразу.

Для DotNext зафиксировать LowerElectionTimeout=30000 ms, UpperElectionTimeout=36000 ms, HeartbeatThreshold=1/6 (около 5 с), RpcTimeout=3 с, RequestTimeout=10 с, AggressiveLeaderStickiness=true, IsLeaderLeaseEnabled=false. Рандомизация Raft означает, что 30 с — порог начала, не обещание избрания в точную миллисекунду. Health supervisor не является вторым алгоритмом выборов.

Если Raft-heartbeat продолжается, а readiness отсутствует, локальный supervisor главного переводит его в standby/останавливает Raft. Для зависшего supervisor большинство обменивается свежими authenticated health acknowledgements: после 30 с и подтверждения одним и тем же большинством неготовности текущего лидера инициирует его relinquish через `ICluster.ResignAsync`; при отсутствии ответа изолирует RPC этого term/лидера в собственном peer guard до смены term. Так прекращается продление выбора техническим HTTP-ответом; дальнейшие prevote/election выполняет DotNext. Одна жалоба/timeout меньшинства не запускает relinquish исправного главного с большинством. Повтор term не снимает локальную блокировку; для того же term нужны новые ready proofs большинства. Согласование 30 с не означает, что новый главный уже способен отправлять.

Для health-quorum нужны уникальные NodeId **того же membership**, свежие challenge/nonce, взаимные подтверждения наблюдений и отсутствие локального противоречия Ready; произвольный relay не считается голосом. Асимметрия может задержать переключение, но не разрешает выбор «по числу HTTP OK». Реализация peer guard/supervisor и соответствие таймеров DotNext проверяются в 03.3/03.4 изолированно; наличие такого health-механизма не приписывается библиотеке.

## Выдача и истечение права отправки

Выбрана короткая **прикладная authority с majority renewal и отдельным разрешением каждой попытки**, а не сохранённый IsLeader или built-in read lease. Authority key = ClusterId + ClusterGeneration + membership version + term + LeaderNodeId + SenderEpoch.

1. После `WaitForLeadershipAsync` и write/apply barrier закрытый sender восстанавливает общий результат, SQL cursor, инциденты и доставки. Новый SenderEpoch открывается принятой командой. При новой роли/составе выдерживается 12 с без новых отправок, даже если старая authority считается погашенной.
2. `RenewSenderAuthority` принимается через Raft не реже каждых 5 с с уникальным round ID. Инициатор считает deadline от **начала** запроса по monotonic TimeProvider; срок не более 10 с, поздний ответ его не продлевает. Authority не восстанавливается из SQL, snapshot или restart. Ответ должен соответствовать текущим term/epoch/membership и применённому результату. Нет majority renewal — нет новых попыток.
3. Для каждого primary/retry/recovery/summary/test-send принять `BeginDeliveryAttempt` с DeliveryKey, AttemptId, SenderEpoch; проверить отмены, получателя, лимит попыток и активного actor для теста. До транспорта применить результат и ещё раз проверить authority, readiness, epoch/tokens, отсутствие паузы и срок. От начала запроса разрешения до вызова транспорта — не более 2 с; превышение требует нового разрешения/сверки без HTTP-вызова.
4. Gate и вызов transport идут подряд, без ожидания очереди/локальной SQL-транзакции между ними. Перед каждой попыткой после pause > 5 с authority сбрасывается и требуется новый quorum round; скачок wall clock/нарушение monotonic progress/host resume закрывают gate. Проверяется elapsed deadline, а не только CancellationToken, таймер которого мог не выполниться при паузе.
5. Step-down, потеря readiness, leadership/consensus token, отзыв credentials, maintenance или смена membership закрывают gate и отменяют локальные requests. При planned membership закрыть renewal, дождаться истечения authority + 12 с drain, затем менять состав и открывать новый epoch. Старый узел после восстановления начинает ведомым.
6. Принятый `DeliverySucceeded` не требует, чтобы отправитель всё ещё был лидером: доверенный узел может передать поздний результат ранее принятого AttemptId; это не разрешает новый send.

Предположение сроков: monotonic clocks включают паузы процесса, их относительная скорость отклоняется не более чем в 1.1 раза; 12 с drain перекрывает прежние 10 с. При неизвестном состоянии часов/возобновлении ОС gate закрыт. Это проектное условие, не измеренная характеристика окружения. Без доверенных часов использовать те же per-attempt majority barriers, но не открывать authority до ручного устранения clock fault.

**Граница гарантии:** финальная проверка gate считается началом попытки; процесс может быть остановлен сразу после неё, до фактического socket write. Ни lease, ни term, ни cancellation не образуют атомарную операцию с Telegram. Такую уже допущенную попытку считать in-flight/Unknown; она может завершиться после смены главного. Новый главный ждёт drain и сверяет результаты, но это не доказывает отсутствия задержанного внешнего эффекта. Строгий внешний fencing потребовал бы участия Telegram/отдельного отправляющего посредника и в план не входит. Два узла не получают независимо новые прикладные полномочия в одном принятом состоянии; отсутствие дублей во внешнем API не обещается.

## Ручное восстановление после утраты большинства

Это отдельная аварийная процедура, не ForceRemove и не bootstrap сохранившегося меньшинства.

1. Администратор выбирает сохранившуюся копию и проверяет manifest, snapshot/hash, последний доказанный committed/applied index, аккаунт и состояние незавершённых операций. Непринятый хвост WAL не объявляется принятым. Зафиксировать RecoveryId, выбранный source cursor/hash и известный/неизвестный диапазон потерь.
2. **До активации новой сетки внешне остановить/изолировать все прежние экземпляры**, включая автоматический restart, копии дисков и старые peer/UI ingress. При невозможности подтвердить fencing старой сетки восстановление остаётся закрытым. Новая generation сама по себе не останавливает старое большинство.
3. Отозвать прежний bot token и выпустить новый token **того же бота**, не передавая его старым узлам. Отозвать старую peer CA/credentials и ingress старой generation. Это обеспечивает внешнее fencing будущих Telegram-вызовов; уже принятый Telegram запрос остаётся неопределённым.
4. Получить явное подтверждение администратора возможной потери отсутствующих изменений, в том числе аккаунтов, паролей, удалений и delivery results. Сохранить протокол подтверждения вне потерянной сетки и в recovery manifest. Из отсутствующей истории нельзя обещать восстановление утраченных отмен или доставок.
5. Офлайн создать новый ClusterId и ClusterGeneration, новые NodeId/storage generation/peer credentials; сохранить PreviousClusterId/RecoveryId как provenance. В выбранную принятую копию включить все общие данные по 01.3, переобозначить её как recovery baseline, не копировать старый term/vote в новую сетку. Рабочий режим — Quarantine.
6. Пересобрать SQL и общий аккаунт/роль из baseline; очистить локальные сессии, сверить Pending/intents. Unknown внешние попытки могут дать редкий дубль; непринятые заявки требуют подтверждения. Выполнить controlled singleton bootstrap новой идентичности и только вручную разрешить работу.
7. Все прежние узлы возвращаются только как пустые rejoin с новыми credentials/identity и актуальным snapshot. Их старый WAL/общая SQL/outbox не вливаются. Прежние manifests и token остаются заблокированными, даже если поздно вернулось старое большинство.

Точка аварийного принятия — ручное подтверждение recovery baseline после fencing; атомарность ограничена новым локальным manifest/хранилищем, не потерянной сеткой. Исполняющий слой — будущая Infrastructure recovery orchestration, управление и отчёт — Application/Web. Процедура здесь спроектирована, не выполнена.
