# Подэтап 05.4. Bootstrap, жизненный цикл аккаунтов и возврат узла

Статус: completed

## Цель и результат

Первый администратор, блокировка аккаунтов и восстановление пользователей согласованы с жизненным циклом сетки.

Родительский [этап 05](main.md), [общий план](../main.md), [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) задают границы. Подготовка документа не разрешает реализацию, запуск приложения или внешние проверки.

## Затрагиваемые части проекта

Infrastructure/Identity, bootstrap и snapshot/replay 03/04, диагностика и эксплуатационные инструкции. Профильные тесты, ближайшие `AGENTS.md` и актуальная техническая документация обновлены по фактической реализации.

## Работы

- [x] Создавать первого администратора только при первом bootstrap новой сетки. Присоединяемый узел не создаёт собственных пользователей или роли с независимыми ID и получает общий UserId/RoleId в snapshot/replay.
- [x] Сохранять общие UserId при удалении или замене узла; пользователи не принадлежат узлам создания.
- [x] При rejoin/restore сверять состояние пользователей и их tombstones с принятой историей до открытия входа; не воскрешать удалённый аккаунт и старый пароль.
- [x] Оставить сессии, cookie, локальные ключи и временные счётчики ошибок входа собственными для узла; не создавать общий журнал каждого входа.
- [x] Описать поведение offline-узла: до догона последнее принятое состояние, после apply актуальное отключение/пароль и недействительность старых сессий.
- [x] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию; новые документы включить в навигацию и solution.

## Проверки

Один bootstrap-пользователь, join без дополнительного локального администратора, удаление узла создания пользователя, старый backup с удалённым аккаунтом/паролем, partition и последующий догон.

Изолированные проверки и compile-check не подменяют SQL Server, реальные peer HTTP, браузер и Telegram. Внешняя приёмка учитывается отдельно в [этапе 10](../10-verification-and-acceptance/main.md); команды из плана не разрешены автоматически.

## Критерии приёмки

- [x] У пользователя нет домашнего узла; join и snapshot содержат пользователей и роль.
- [x] Старый backup не восстанавливает принятые удаления и прежние данные входа; локальные сессии не переносятся.
- [x] Работы и применимые проверки выполнены; непроведённая внешняя приёмка остаётся открытой.
- [x] Статус согласован с родительским этапом и общим планом.

## Результат выполнения

2026-10-29 реализована аккаунтная часть bootstrap: только Mode=Bootstrap новой сетки, точная подготовленная команда из независимого trusted RecoveryAdmission и её digest разрешают первый аккаунт через существующий native writer/reducer. Join/Restart не создают отдельного пользователя/роли. Узкое bootstrap-исключение требует принятого replay, single voter/leader и здоровой проекции; общий gate не открывается. По умолчанию admission закрыт, готовность и proof не подставляются.

Recovery до native Raft сверяет snapshot/replay и SQL account/credential/role/tombstone состояние, а не только CanConnect/cursor. Invalidate удерживает accepted reader закрытым до подтверждённого восстановления. Локальный process epoch отзывается на restart/recovery; counters/keys/sessions исключены из общей репликации. UserId/RoleId не связаны с узлом создания.

AccountBootstrapTests/AdapterWiringTests проверили режимы и точный bootstrap; RevisionRecoveryTests использовал реальный локальный DotNext WAL: старый snapshot → смена hash → удаление → reopen/replay → подтверждение. Старые credential/session не вернулись, tombstone сохранился. Проекция подставная: это не SQL restore, crash/fsync, elections или живая сеть. Сохранение prepared command, внешнее fencing, provisioning/controlled enable и аварийные runbooks остаются этапом 09, без раннего запуска.
