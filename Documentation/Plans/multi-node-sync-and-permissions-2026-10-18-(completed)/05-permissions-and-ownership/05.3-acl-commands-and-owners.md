## Проверки

Create/update с любого узла, конкурентный одинаковый login, повтор OperationId, отключение актёра до commit, две конкурирующие попытки удалить последних администраторов, replay без дубля роли и утечки секретов.

Изолированные проверки и compile-check не подменяют SQL Server, реальные peer HTTP, браузер и Telegram. Внешняя приёмка учитывается отдельно в [этапе 10](../10-verification-and-acceptance/main.md); команды из плана не разрешены автоматически.

## Результат выполнения

2026-10-29 SharedUserManagementService подключил Create/Update/Password/SetEnabled/Delete с общими UserId/OperationId/base revision к готовому PendingCommandService → RevisionReducer → RevisionApplyEngine/projection UoW. Password validators/Identity V3 hash/stamps выполняются до durable записи; локальный singleton gate сохраняет исходный salted вариант при retry. Pending защищён Data Protection и не меняет accepted credentials. Нового WAL/алгоритма согласования нет.

Уникальный normalized login (включая tombstones), active actor/revision, self-disable/delete и last-active-admin проверяются при подаче/принятии. Retry/потерянный ответ возвращает исходный результат без нового side effect. Безопасный DTO содержит только operation/user/status/revision/conflict ID; варианты credentials не показываются. Аудит terminal outcome содержит достоверные actor/subject/node/operation IDs и не повторяется для Resolved. Account/delete/control используют готовую приоритетную репликацию 04.

SharedUserManagementTests, PendingReplicationTests и регрессии pipeline 04 прошли на production orchestration с изолированными зависимостями. API возвращает 202 для durable Pending; legacy enabled writers закрыты. SQL Server transaction/locking/constraints не доказываются fake storage; UI Pending/conflicts этапа 08 не реализован.
