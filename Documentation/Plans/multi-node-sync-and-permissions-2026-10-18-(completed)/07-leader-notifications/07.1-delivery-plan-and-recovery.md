# Подэтап 07.1. План доставки и восстановление очереди

Статус: completed

## Цель и результат

Очередь восстанавливается из принятой истории с устойчивыми per-chat delivery keys.

## Зависимости и границы

Зависимости: [05](../05-permissions-and-ownership/main.md), [06](../06-monitoring-and-incidents/main.md).

Родительский [этап 07](main.md) задаёт общие ограничения и критерии. [Общий план](../main.md) содержит сводные статусы; [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) определяют согласованное поведение. Подготовка документа не разрешает реализацию, запуск приложения, внешние проверки или включение функции.

## Затрагиваемые части проекта

`Application/Cluster` (DeliveryQueue/Reducer/Projection/Eligibility/Message), `Infrastructure/Cluster` (AcceptedDeliveryDispatcher/DeliverySenderConsensus/ClusterTestDelivery), `Infrastructure/Telegram/TelegramHttpNotificationSender`, Web sender lifecycle/test-send/peer boundary, существующие сценарные UoW и snapshot/recovery; изолированные tests, актуальные Notifications/Monitoring/Testing и ближайшие AGENTS.md.

Работа ограничена перечисленными ниже сценариями; смежные компоненты изменяются только при необходимости выполнить результат подэтапа.

## Работы

- [x] Отделить согласованный план доставки от локального outbox claim. Только принятые события получают право внешней отправки; локальная lease строки не даёт межузловой эксклюзивности.
- [x] После выборов догнать согласованную историю инцидентов/получателей/доставок и восстановить очередь до открытия gate. Не полагаться на очередь в погибшей БД.
- [x] Использовать стабильный delivery key incident + kind + chat, с отдельным учётом поколения binding и per-recipient состояния. Принятый известный успех исключается из штатного retry.

- [x] Для инцидента самого узла брать чаты из принятого назначения именно этому NodeId; один чат может быть назначен нескольким узлам. Сохранять/восстанавливать маршрутизацию при смене главного, не выбирать чат автоматически и не подменять её привязками произвольного объекта «сервер».

- [x] Планировать сводки завершённых offline-аварий без возрастного отсечения, открытые проблемы отдельно, а recovery ранее уведомлённым чатам — обычным сообщением. Хранить связь сводки с исходными событиями и принятыми intents, исключая их штатную двойную отправку.
- [x] Новая привязка получает открытую проблему; снятая привязка отменяет не начатый outage. Для подтверждённо уведомлённого чата хранить право на один recovery после unbind, включая поздний успех in-flight запроса. Стабильная логическая доставка incident + kind + chat исключает дубль при перепривязке; история binding сохраняется для проверки поколения и отмен.

- [x] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию в пределах реализованного изменения; новые документы включить в навигацию и solution.

## Проверки

Проверить реконструкцию сводки, её состава и прав на recovery после unbind при смене главного; rebind и replay не повторяют известный успех.

Проверить потерю локальной outbox, новый главный после принятого успеха и разные состояния получателей одного события. Проверить разные чаты для узлов А/Б, общий чат в обоих наборах, отсутствие назначения и восстановление маршрутизации новым главным.

Общие сценарии [родительского этапа](main.md#проверки) сохраняются. Изолированные проверки подтверждают алгоритм; реальные БД, peer HTTP, процессы, браузер и Telegram учитываются отдельно в [этапе 10](../10-verification-and-acceptance/main.md).

Команды из плана не являются разрешением их запускать. Непроведённая обязательная проверка остаётся открытой; готовность кода при ожидающей приёмке обозначается `verification`.

## Критерии приёмки

- [x] Локальный claim не заменяет межузловое право; известный принятый успех не попадает в штатный retry.
- [x] Инцидент узла доставляется по его собственному принятому набору чатов, без автоматического подбора получателей.
- [x] Очередь после выборов воспроизводит сводки, открытые проблемы и финальный recovery после unbind без потери истории и штатных дублей.
- [x] Работы и применимые проверки подэтапа выполнены, результат и ограничения зафиксированы.
- [x] Статус согласован с таблицами родительского этапа и общего плана; незавершённая внешняя приёмка не объявлена выполненной.

## Результат выполнения

Реализованы DeliveryQueue/DeliveryProjection и AcceptedDeliveryDispatcher: очередь выводится из принятой истории до renewal, без legacy outbox. Stable logical keys, binding generation, NodeChatRoute по NodeId, independent recipients, immutable summary composition и recovery entitlements сохраняются при restart/replay. Known success не становится due; поздний outage success после unbind сохраняет один recovery, удалённая цель/чат новых отправок не получает.

Production reducer tests проверяют keys/rebind/routes, summary/recovery и terminal состояния; dispatcher tests — восстановление без локального outbox/пользовательской сессии и lost result; настоящий локальный snapshot/WAL — attempts/results после reopen. [Фактические команды и результат](../../../Technical%20documentation/Testing.md#проверка-этапа-07). Все применимые минимальные изолированные проверки выполнены. SQL semantics/locking, живая сеть, процессы и Telegram не проверялись; их отсутствие не подменяется fake результатом и по согласованному порядку 10 не блокирует этот статус.
