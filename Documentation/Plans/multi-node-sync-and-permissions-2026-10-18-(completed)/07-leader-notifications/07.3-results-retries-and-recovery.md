# Подэтап 07.3. Результаты, retry и partial/recovery

Статус: completed

## Цель и результат

Intent и результат реплицируются, retry сохраняет независимость чатов и связь восстановления.

## Работы

- [x] Добавить сообщения о partial-доступности и восстановлении всех направлений с перечислением затронутых узлов. Повтор того же подтверждённого состояния не создаёт новую отправку; переходы используют общую историю цели и стабильные event IDs.
- [x] Сохранять intent до отправки; после transport success оперативно передавать результат в журнал. Потерянное подтверждение или crash до фиксации могут дать редкий дубликат; потерю намерения отправить не считать допустимой заменой дубля.
- [x] Сохранить частичную доставку, независимость ошибок разных чатов и связь recovery с доставленным сообщением о недоступности/partial того же incident. Восстановление partial получает понятный текст и только тех получателей, которым было доставлено соответствующее проблемное состояние. Исчерпание retry остаётся видимым terminal-состоянием, а не удалением события.
- [x] Учитывать Telegram `retry_after`, network/timeout, отказ токена и запрет конкретного чата; не переключать главного бесконечно из-за одной неверной привязки.

- [x] При включении endpoint-имени и времени запуска/работы в сообщение сохранять значения и узлы-источники; при расхождении не формировать вымышленное общее имя/uptime. Расхождение успешных metadata само по себе не создаёт событие отказа.

- [x] Сохранять результаты сводки вместе с её составом исходных событий, не уничтожая полную историю или accepted intents. Уже получивший outage чат получает обычный recovery; после снятия привязки — один заключительный recovery, затем уведомления прекращаются. Подтверждённый поздний успех in-flight outage также создаёт право на recovery; удалённая цель/чат новых отправок не получает.

- [x] Отправлять предупреждения о частичной/полной потере наблюдения и восстановление только чатам с доставленным предупреждением. Применять общие правила снятия привязки, удаления, идемпотентности и смены главного. После terminal exhaustion сохранять видимую ошибку, без ручной команды повтора и бесконечного retry.

- [x] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию в пределах реализованного изменения; новые документы включить в навигацию и solution.

## Проверки

Проверить частичную/полную потерю наблюдения, частичную доставку предупреждения, последующее восстановление и terminal exhaustion после устранения причины без автоматического или ручного повторного запуска.

Проверить успешную сводку и смену главного, unbind после outage, поздний успех in-flight outage и ровно один recovery; после удаления цели/чата новых вызовов нет.

Проверить retry_after, timeout после возможного Telegram success, crash до фиксации результата, terminal exhaustion и recovery только для получивших проблему. Проверить текст с различающимися metadata успешных наблюдений и отсутствие произвольно выбранного общего uptime.

Общие сценарии [родительского этапа](main.md#проверки) сохраняются. Изолированные проверки подтверждают алгоритм; реальные БД, peer HTTP, процессы, браузер и Telegram учитываются отдельно в [этапе 10](../10-verification-and-acceptance/main.md).

Команды из плана не являются разрешением их запускать. Непроведённая обязательная проверка остаётся открытой; готовность кода при ожидающей приёмке обозначается `verification`.

## Критерии приёмки

- [x] Intent не теряется; неопределённый внешний успех допускает редкий дубль, известный успех штатно не повторяется.
- [x] Сообщения с разными endpoint-данными показывают их по узлам, не меняя подтверждённую доступность из-за одного расхождения.
- [x] Смена главного/restart не повторяет известную доставку сводки и не теряет recovery уведомлённого до/при unbind чата.
- [x] Предупреждения наблюдения не повторяются на каждом цикле, восстановление не уходит непредупреждённому чату; исчерпанная доставка видна и вручную не перезапускается.
- [x] Работы и применимые проверки подэтапа выполнены, результат и ограничения зафиксированы.
- [x] Статус согласован с таблицами родительского этапа и общего плана; незавершённая внешняя приёмка не объявлена выполненной.

## Результат выполнения

DeliveryReducer принимает реальные attempts/results; DeliveryProjection, snapshot/recovery согласованы с полной историей. Transport success требует настоящего message_id; локальный capture UoW передаёт результат существующим журналом даже при отмене leadership token. Неизвестный результат после 30 секунд допускает bounded ambiguous retry; поздний success монотонен. До пяти attempts, backoff 5/30/120/300 с и retry_after; fatal token/chat/config ошибки terminal. Failed/exhausted не перезапускается после rebind, одна ошибка чата не блокирует остальные и не вызывает resign.

Сообщения различают partial/full recovery и coverage, перечисляют направления и metadata по узлам. Recovery только подтверждённо уведомлённым чатам, включая поздний success после unbind; успешная summary сохраняется с immutable sources/events/intents. Проверены retry_after/exhaustion, независимость чатов, timeout, success до принятия результата/потерянный ответ, поздний success и replay без повторного success-аудита. [Результаты](../../../Technical%20documentation/Testing.md#проверка-этапа-07). Exactly-once, реальные chat permissions/Telegram, SQL atomicity и crash/fsync не заявляются.
