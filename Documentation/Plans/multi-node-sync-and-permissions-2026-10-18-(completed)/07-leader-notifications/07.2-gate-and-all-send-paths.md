# Подэтап 07.2. Gate для всех путей отправки

Статус: completed

## Цель и результат

Первичная, повторная, recovery и тестовая отправки используют единый подтверждённый главный путь.

## Зависимости и границы

Зависимости: [07.1](07.1-delivery-plan-and-recovery.md).

Родительский [этап 07](main.md) задаёт общие ограничения и критерии. [Общий план](../main.md) содержит сводные статусы; [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) определяют согласованное поведение. Подготовка документа не разрешает реализацию, запуск приложения, внешние проверки или включение функции.

## Затрагиваемые части проекта

`Application/Cluster` (DeliveryQueue/Reducer/Projection/Eligibility/Message), `Infrastructure/Cluster` (AcceptedDeliveryDispatcher/DeliverySenderConsensus/ClusterTestDelivery), `Infrastructure/Telegram/TelegramHttpNotificationSender`, Web sender lifecycle/test-send/peer boundary, существующие сценарные UoW и snapshot/recovery; изолированные tests, актуальные Notifications/Monitoring/Testing и ближайшие AGENTS.md.

Работа ограничена перечисленными ниже сценариями; смежные компоненты изменяются только при необходимости выполнить результат подэтапа.

## Работы

- [x] Перед каждой начальной/retry/recovery/test попыткой проверять действующее право главного и готовность. Ведомый или меньшинство не начинает новый вызов sender, даже если в локальной БД есть due job.
- [x] Тестовую отправку с ведомого направлять через согласованный главный путь. Пользовательское право проверять до постановки заявки; существующий прямой вызов sender из административного use case не оставлять обходом gate.
- [x] Сохранить независимость Telegram-маршрутизации от пользовательской видимости чата. Токены локальны; каждый потенциальный отправитель должен иметь рабочие полномочия на настроенные чаты.

- [x] Для test-send проверять активного принятого администратора при подаче и перед отправкой; ведомый передаёт заявку главному. Отключение/удаление аккаунта до отправки запрещает вызов; общий gate обязателен.

- [x] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию в пределах реализованного изменения; новые документы включить в навигацию и solution.

## Проверки

Проверить test-send с ведомого активным администратором; запретить вызов анонимному/отключённому аккаунту, после применения отключения и при закрытом gate.

Fake sender: потеря большинства перед вызовом, смена term после claim, test-send на ведомом и фоновая доставка без открытой пользовательской сессии.

Общие сценарии [родительского этапа](main.md#проверки) сохраняются. Изолированные проверки подтверждают алгоритм; реальные БД, peer HTTP, процессы, браузер и Telegram учитываются отдельно в [этапе 10](../10-verification-and-acceptance/main.md).

Команды из плана не являются разрешением их запускать. Непроведённая обязательная проверка остаётся открытой; готовность кода при ожидающей приёмке обозначается `verification`.

## Критерии приёмки

- [x] Пользовательские и фоновые пути используют gate; test-send проверяет активного администратора, фоновые уведомления не зависят от пользовательской сессии.
- [x] Тест с ведомого доступен любому активному администратору и отправляется подтверждённым главным после повторной авторизации.
- [x] Работы и применимые проверки подэтапа выполнены, результат и ограничения зафиксированы.
- [x] Статус согласован с таблицами родительского этапа и общего плана; незавершённая внешняя приёмка не объявлена выполненной.

## Результат выполнения

DeliverySenderConsensus принимает renewal/attempt через существующий RevisionDispatcher/DotNext/apply. ClusterDeliveryWorker восстанавливает очередь перед renewal и обновляет authority независимо от in-flight. Initial/retry/recovery/summary/test вызываются одним AcceptedDeliveryDispatcher с финальной проверкой term/majority/authority, RecoveryVersion, readiness, текущего intent/configuration и cancellation. Unknown dependencies закрывают gate.

ClusterTestDelivery на follower сохраняет durable Pending с accepted actor; reducer и sender повторяют проверку активного Administrator. HTTP 202 означает постановку, background не требует сессии. Production DI graph проверен без host/WAL/HTTP; устранён цикл через ClusterRaftHandle. Проверены follower submission, disable до accept/send, minority/term/pause, закрытые gates и background без actor. [Результаты](../../../Technical%20documentation/Testing.md#проверка-этапа-07). Production activation/delivery proof не открыт; реальные Telegram/browser/peer проверки не проводились.
