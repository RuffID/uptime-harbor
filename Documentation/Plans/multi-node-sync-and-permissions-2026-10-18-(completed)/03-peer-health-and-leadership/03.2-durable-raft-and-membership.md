# Подэтап 03.2. Долговременный Raft и состав сетки

Статус: completed

## Цель и результат

Работают consensus adapter, term/vote/log, bootstrap и контролируемое изменение состава.

Подготовка документа не разрешает реализацию, запуск приложения, внешние проверки или включение функции.

## Затрагиваемые части проекта

Будущие peer/cluster модули в Application и Infrastructure, durable storage в `Infrastructure/Persistence`, `Infrastructure/Monitoring`, `Infrastructure/Telegram`, `Web/Configuration`, `Web/Controllers`, `Web/Program.cs`; конфигурационные примеры без секретов, соответствующие тесты и локальные `AGENTS.md`.

Работа ограничена перечисленными ниже сценариями; смежные компоненты изменяются только при необходимости выполнить результат подэтапа.

## Работы

- [x] Реализовать NodeId/ClusterId, bootstrap, проверку отсутствия клона NodeId, согласованный состав голосующих и безопасный порядок его изменения по этапу 01.
- [x] Подключить выбранный DotNext/Raft с долговременным term/vote/log и membership; реализовать majority commit, election и step-down, а не только флаг main/follower. Автоматическое исключение недоступных участников отключить.

- [x] Проверять активный общий аккаунт администратора для membership/trust. Логировать достоверные UserId/NodeId и подтверждённый результат на английском без секретов, ложного успеха или дублей при retry.

- [x] С первого запуска использовать единую новую модель общих администраторов и доставки: новая одноузловая сетка имеет большинство 1. Потеря двух участников настроенной трёхузловой сетки не разрешает оставшемуся создать одиночный состав автоматически.

- [x] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию в пределах реализованного изменения; новые документы включить в навигацию и solution.

## Проверки

Проверить bootstrap одного узла с большинством 1 и отказ самостоятельного уменьшения состава оставшимся узлом настроенной трёхузловой сетки.

Изолированно проверить кандидатов, majority commit, durable vote, клон NodeId и отказ участников. Membership/trust разрешён любому активному администратору, анонимный/отключённый получает отказ; безопасное логирование сохраняется.

Общие сценарии [родительского этапа](main.md#проверки) сохраняются. Минимальные изолированные проверки подтверждают production policy, storage и adapter API в указанном ниже объёме; выборы DotNext и crash recovery ими не объявляются проверенными. Реальные БД, peer HTTP, процессы, браузер и Telegram учитываются отдельно в [этапе 10](../10-verification-and-acceptance/main.md).

Команды из плана не являются разрешением их запускать. Непроведённая обязательная проверка остаётся открытой; готовность кода при ожидающей приёмке обозначается `verification`.

## Критерии приёмки

- [x] Состав не уменьшается автоматически, рестарт не создаёт второй голос; прикладные проекции и их догон остаются ответственностью 04.
- [x] Состав/доверие меняет активный администратор через согласованную процедуру без дополнительной роли.
- [x] Новая сетка из одного участника работает по новой модели; меньшинство прежнего состава не превращается в одноузловую сетку.
- [x] Работы и применимые проверки подэтапа выполнены, результат и ограничения зафиксированы.
- [x] Статус согласован с таблицами родительского этапа и общего плана; незавершённая внешняя приёмка не объявлена выполненной.

## Результат выполнения

2026-10-29: Подключён DotNext 6.10.0: настоящий replication API, WriteAheadLog с CRC64/flush, persistent configuration, восстановление до создания WAL и подтверждение replay до Start. Добавлены provisioned manifest/эксклюзивный lock/одноразовый singleton bootstrap, запрет обнуления старого state, административная проверка membership/trust и безопасный аудит. Проверены настоящий WAL reopen term/vote/payload, configuration reopen 1/3 voters, adapter API wiring, deny/confirmed/unconfirmed membership results. Локальный Commit в storage-тесте не выдаётся за majority acceptance; election/одновременные кандидаты/реальные partitions и crash durability не запускались. Полный клон с ключами требует внешнего fencing через recovery-контракт; его отсутствие не подтверждается фиктивно.

Сборки и общий минимальный набор этапа — [Testing.md](../../../Technical%20documentation/Testing.md#проверка-этапа-03). Будущие accepted recovery/account/trust/authority порты по умолчанию закрыты; соседние этапы не реализованы и функция не включена.
