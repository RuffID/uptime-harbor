# Подэтап 06.1. Наблюдения и взаимные проверки

Статус: completed

## Цель и результат

Наблюдения имеют устойчивую идентичность, сохраняются локально и передаются без потери порядка.

## Зависимости и границы

Зависимости: [03](../03-peer-health-and-leadership/main.md), [04](../04-revision-synchronization/main.md).

Родительский [этап 06](main.md) задаёт общие ограничения и критерии. [Общий план](../main.md) содержит сводные статусы; [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) определяют согласованное поведение. Подготовка документа не разрешает реализацию, запуск приложения, внешние проверки или включение функции.

## Затрагиваемые части проекта

`Domain/Monitoring`, `Application/Monitoring`, `Infrastructure/Monitoring`, новые peer health/observation сценарии, persistence инцидентов и журнала; Dashboard и SignalR read models. Тесты Domain/Application/Infrastructure; `Monitoring.md`, `Domain model.md` и ближайшие `AGENTS.md`.

Работа ограничена перечисленными ниже сценариями; смежные компоненты изменяются только при необходимости выполнить результат подэтапа.

## Работы

- [x] Все узлы проверяют друг друга через peer health. Инцидент узла имеет стабильный ID и отдельные чаты по NodeId, настраиваемые активным администратором. Не путать узел сетки с объектом мониторинга «сервер».
- [x] Сохранять ID/порядок наблюдения, узел-источник, поколение конфигурации, время проверки и классификацию ошибки. Не суммировать три одновременные ошибки разных observers как три последовательные проверки одной цели.
- [x] Передавать наблюдения и общие инциденты оперативно; без главного сохранять локальные данные для последующего согласования, не начинать Telegram-отправки.
- [x] Не применять результаты от удалённой/выключенной цели, прежнего endpoint или устаревшего поколения; сохранять текущую защиту повторной загрузки и конкурентных изменений.

- [x] Выполнять проверки сервера/контейнера только назначенными этой цели observers из принятой конфигурации; изменение набора проходит обычную авторизацию изменения цели. Не исключать пропавшего назначенного observer автоматически. Успешное наблюдение сохраняет имя приложения и время запуска со своим узлом-источником.

- [x] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию в пределах реализованного изменения; новые документы включить в навигацию и solution.

## Проверки

Проверить дубли наблюдений, offline накопление, старое поколение endpoint, disabled/deleted цель и отдельную идентичность самого узла. Проверить цель с назначенными двумя из трёх узлов, отсутствие проверок от неназначенного узла, потерю назначенного observer, смену набора и разные metadata успешных ответов.

Общие сценарии [родительского этапа](main.md#проверки) сохраняются. Изолированные проверки подтверждают алгоритм; реальные БД, peer HTTP, процессы, браузер и Telegram учитываются отдельно в [этапе 10](../10-verification-and-acceptance/main.md).

Команды из плана не являются разрешением их запускать. Непроведённая обязательная проверка остаётся открытой; готовность кода при ожидающей приёмке обозначается `verification`.

## Критерии приёмки

- [x] Один результат не применяется повторно или к новой конфигурации; отсутствие главного не теряет наблюдения и не открывает Telegram.
- [x] Проверки целей следуют их назначенному набору, взаимный peer health сохраняется для всех узлов; данные ответа и маршрутизация инцидентов узла связаны с правильным NodeId.
- [x] Работы и применимые проверки подэтапа выполнены, результат и ограничения зафиксированы.
- [x] Статус согласован с таблицами родительского этапа и общего плана; незавершённая внешняя приёмка не объявлена выполненной.

## Результат выполнения

Реализованы accepted назначения и node routes, durable capture/sequence через существующий UoW, bounded replication с accepted frontier ACK, generation/storage/dedup/gap guards и authenticated peer classification. Endpoint checks выполняются параллельно с отдельными capture scopes. Изолированно проверены retry/restart и отказ до/после commit, unassigned/stale/disabled/deleted результаты, metadata и отдельный NodeId. Capture без главного не начинает доставку; gates не открывались.

Фактические команды, проверки и ограничения — [Testing.md](../../../Technical%20documentation/Testing.md#проверка-этапа-06). БД/SQL/SQLite, приложение/hosting, Docker, реальные peers/endpoints/Telegram и deployment не запускались; Git не выполнялся. Fake storage не доказывает SQL semantics, локальный WAL reopen — crash/fsync или majority, статический/API test — browser acceptance. Admission/trust/activation/delivery и browser/worker/sender gates остаются закрытыми. Этапы 07–09 и самостоятельный этап 10 не начинались; после 06.4 работа остановлена.
