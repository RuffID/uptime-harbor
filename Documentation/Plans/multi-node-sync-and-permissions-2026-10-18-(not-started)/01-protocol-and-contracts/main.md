# Этап 01. Архитектура и контракты сетки

Статус: not-started

## Цель

Получить проверенный проект протокола и модели согласования до реализации распределённых изменений и отправок.

## Зависимости и границы

Зависимостей нет. Основа — [пользовательские требования](../business-requirements.md) и [предварительное проектирование](../technical-design.md). Этап не разрешает запуск узлов, запросы к Telegram, подключение к БД или реализацию остальных этапов.

## Затрагиваемые части проекта

Текущие границы `Domain`, `Application/Abstractions`, `Infrastructure/Monitoring`, `Infrastructure/Telegram`, `Infrastructure/Persistence`, `Web/Configuration`, `Web/Controllers`, `Web/Hubs`; их локальные `AGENTS.md`. Документы об архитектуре, конфигурации, мониторинге, доставке и данных в `Documentation/Technical documentation`.

Новые модули и публичные имена пока не существуют: окончательные места и контракты определить здесь, без создания пустых типов ради плана.

## Границы ответственности подэтапов

01.1 подтверждает интеграцию выбранной технологии; 01.2 фиксирует majority/readiness/право отправки; 01.3 — данные, авторизацию и восстановление. Подэтапы не разрешают реализацию следующих этапов или непрошедший согласование запуск прототипа.

## Проверки

Проектные сценарии: partition 2+1, недоступен один из двух, одновременно стартуют кандидаты, асимметричная связь, старый главный возвращается после pause, две конкурентные правки, оба владельца отзывают права друг у друга, Telegram принял сообщение без полученного подтверждения, несовместимая peer-версия.

Технология выбрана по документации DotNext и метаданным пакетов; ещё требуется проверка реальных API и интеграции. Исследование пакетов/документации не подтверждает работоспособность SQL Server или сетки. Сборка прототипа и запуск проверок требуют отдельного разрешённого объёма и профильных правил.

## Критерии приёмки

- [ ] Для всех записываемых общих данных определены источник истины, точка принятия, версия и способ восстановления.
- [ ] Алгоритм большинства/отправки объясняет перечисленные отказы без двух независимо действующих главных.
- [ ] Зафиксирована последовательность обработки наблюдения до одного общего инцидента и доставки.
- [ ] Интеграция выбранного DotNext/Raft и правила partial/readiness формализованы для реализации; оставшиеся проверки не подменены отметкой об окончании этапа.
- [ ] Есть карта новых модулей, миграции и обязательных сценариев приёмки для следующих этапов.
