# Подэтап 01.3. Контракты данных и восстановления

Статус: not-started

## Цель и результат

Определены наблюдения, команды, авторизация, атомарность проекций, snapshot и совместимость.

## Зависимости и границы

Зависимости: [01.2](01.2-consensus-and-sender-contracts.md).

Родительский [этап 01](main.md) задаёт общие ограничения и критерии. [Общий план](../main.md) содержит сводные статусы; [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) определяют согласованное поведение. Подготовка документа не разрешает реализацию, запуск приложения, внешние проверки или включение функции.

## Затрагиваемые части проекта

Текущие границы `Domain`, `Application/Abstractions`, `Infrastructure/Monitoring`, `Infrastructure/Telegram`, `Infrastructure/Persistence`, `Web/Configuration`, `Web/Controllers`, `Web/Hubs`; их локальные `AGENTS.md`. Документы об архитектуре, конфигурации, мониторинге, доставке и данных в `Documentation/Technical documentation`.

Новые модули и публичные имена пока не существуют: окончательные места и контракты определить здесь, без создания пустых типов ради плана.

Работа ограничена перечисленными ниже сценариями; смежные компоненты изменяются только при необходимости выполнить результат подэтапа.

## Работы

- [ ] Формализовать согласованную модель наблюдений: available/partial/unavailable и неполное покрытие, отдельный failure counter observer, freshness, смена состава и общая история инцидента. Partial вызывает уведомления, но не выборы исправного главного с большинством.
- [ ] Описать заявки, результаты, ревизии, курсоры, tombstones, конфликты и snapshot общих данных, включая все аккаунты, защищённые данные входа и единственную роль.
- [ ] Зафиксировать исправление и отмену непринятой заявки: применяется только последний вариант; подтверждённо отменённая/заменённая заявка не принимается поздним повтором. Описать гонку с принятием, потерянный ответ и восстановление результата после рестарта; уже принятое изменение исправляется новой командой.
- [ ] Зафиксировать конфликт без отката первой принятой правки и общий полный доступ активного администратора. Actor команды использует общий UserId; дополнительных прав, владельцев и оператора нет.
- [ ] Определить атомарные команды создания/изменения аккаунта и роли, изменения объектов/связей, удаления с зависимостями и инцидента с delivery intent. Разделить локальную транзакцию и majority commit.
- [ ] Определить совместимость будущих выпусков и безопасный первый запуск общих аккаунтов/workers. Основной путь — одноузловой bootstrap и пустой join/snapshot/replay; возврат старого backup — отдельный rejoin. Перенос v1, backfill и импорт непустых установок исключены.
- [ ] Определить безопасное логирование подачи/замены/отмены, изменений аккаунтов, membership/trust, observers и маршрутизации: достоверные actor/subject UserId, OperationId/EntityId/NodeId, английские сообщения без паролей, хешей, stamps и payload; без ложного успеха и дублей retry.
- [ ] Детализировать выбранные решения в активных документах плана, не выдавая их за реализованную архитектуру. Новые обнаруженные вопросы при необходимости вносить в `../open-questions.md`; решённые не сохранять как журнал ответов. При добавлении документов обновить навигацию и solution items.

- [ ] Закрепить набор observers в конфигурации цели, изменяемый любым активным администратором, без молчаливого исключения пропавших узлов. Endpoint-имя и время запуска сохранять по observer; расхождение metadata не считать отказом.
- [ ] Зафиксировать общий UserId, единственную роль Administrator, общие учётные данные и статус аккаунта, атомарное применение через Identity adapter, уникальность login и защиту последнего администратора. Пароли в открытом виде не хранятся; сессии и ключи узла локальны. Snapshot/replay включает пользователей; удаление узла их не удаляет.

- [ ] Формализовать сводку завершённых offline-аварий без отсечения по возрасту, отдельную доставку открытых аварий и обычный recovery уже уведомлённым чатам. Согласовать устойчивые IDs сводки/исходных событий/получателей, сохранение принятых intents и защиту от повторной отправки исходных сообщений вместе со сводкой.
- [ ] Зафиксировать новую привязку с текущей проблемой, отмену не начатого outage при unbind и один recovery после успешного outage. Учесть in-flight успех, удаление цели/чата; test-send доступен активному администратору через общий gate.
- [ ] Описать сверку Pending из старого backup по OperationId и принятым/отменённым/заменённым результатам; оставшиеся непринятые заявки передавать только после подтверждения пользователем и повторной проверки активного администратора/base revision. Логировать результаты сводки, изменения получателей и подтверждения заявок по общему безопасному контракту 01.3.

- [ ] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию в пределах реализованного изменения; новые документы включить в навигацию и solution.

## Проверки

Проследить сводку давних завершённых аварий, отдельную открытую проблему, три изменения привязок, поздний успех запроса и test-send активным администратором; сверить Pending из backup с отменой/заменой.

Проследить конкурирующие правки, замену/отмену, потерянный ответ, crash между WAL и SQL, создание одинакового login и конкурентное отключение последних администраторов, snapshot пользователей и старую копию после compaction.

Общие сценарии [родительского этапа](main.md#проверки) сохраняются. Изолированные проверки подтверждают алгоритм; реальные БД, peer HTTP, процессы, браузер и Telegram учитываются отдельно в [этапе 10](../10-verification-and-acceptance/main.md).

Команды из плана не являются разрешением их запускать. Непроведённая обязательная проверка остаётся открытой; готовность кода при ожидающей приёмке обозначается `verification`.

## Критерии приёмки

- [ ] Для каждого вида общих данных зафиксированы источник истины, точка принятия, идемпотентность и восстановление; контракт ресурсной проверки доступен до 04.2.
- [ ] Контракты определяют замену/отмену при гонке, действующую версию конфликта и проверку активного общего администратора.
- [ ] Определены общий вход и роль, состав синхронизируемого аккаунта и защита секретных полей, observers и маршрутизация чатов.
- [ ] Контракты однозначно задают сводку без возрастного отсечения, три последствия изменения привязок, право test-send и ручное подтверждение непринятых заявок из старого backup.
- [ ] Работы и применимые проверки подэтапа выполнены, результат и ограничения зафиксированы.
- [ ] Статус согласован с таблицами родительского этапа и общего плана; незавершённая внешняя приёмка не объявлена выполненной.
