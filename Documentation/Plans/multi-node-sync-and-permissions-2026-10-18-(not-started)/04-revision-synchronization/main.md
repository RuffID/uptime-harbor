# Этап 04. Синхронизация ревизий и конфликты

Статус: not-started

## Цель

Принимать изменения на любом узле, согласовывать их без молчаливого затирания и безопасно восстанавливать отставшие реплики.

## Зависимости и границы

После [02](../02-domain-and-persistence/main.md), [03](../03-peer-health-and-leadership/main.md) и раннего [05.1](../05-permissions-and-ownership/05.1-subjects-and-resource-policies.md). Использовать выбранный протокол согласования. Локальное сохранение Pending не означает принятие общей конфигурации.

## Затрагиваемые части проекта

Новые сценарии синхронизации в Application, сценарные UoW, journal/cursor/conflict/tombstone storage в Infrastructure, peer contracts и workers, настройки. Текущие `ObjectAdministrationService` и `NotificationAdministrationService` будут подключаться к этим сценариям в следующих этапах.

## Границы ответственности подэтапов

Единая проверка принятого активного администратора и доменные инварианты готовы в 05.1 и 02.1 до 04.1/04.2. Интеграция общего входа и UI выполняется в 05/08. Raft WAL — 03; прикладное применение и replay общих данных, включая пользователей и роль, — 04.

## Проверки

Изолированно: повторные/переставленные/пропущенные пакеты, crash до и после local commit, потерянный ответ на уже принятую команду, смена главного посреди согласования, несовместимый payload, конфликт одновременных правок, delete против старого update, отставший узел со snapshot и без него. Fake storage проверяет алгоритм, но не SQL Server transaction semantics.

Внешняя приёмка: действительные независимые БД, восстановление после остановки процесса, большие очереди и ограниченная сеть — по отдельному разрешению.

## Критерии приёмки

- [ ] Изменение можно сохранить на ведомом без связи; оно не применяется к действующему мониторингу до принятия.
- [ ] Непринятую заявку можно исправить/отменить с подтверждением; поздний повтор старого варианта не применяет его, гонка с принятием не выдаёт ложную отмену.
- [ ] Принятая команда даёт одинаковое общее состояние после догона всех узлов.
- [ ] Повторная доставка не создаёт новую ревизию того же действия и повторный side effect.
- [ ] Конфликты видимы, варианты не теряются, первая принятая настройка действует без автоматического отката; молчаливого перезаписывания нет.
- [ ] Snapshot/догон не заменяет локальные данные и не восстанавливает удалённые сущности.
