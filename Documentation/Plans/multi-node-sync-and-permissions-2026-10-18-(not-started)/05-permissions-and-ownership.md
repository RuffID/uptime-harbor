# Этап 05. Права, каталог пользователей и владельцы

Статус: not-started

## Цель

Обеспечить явные права на сущности для пользователей любых узлов, без административного обхода и потери последнего владельца.

## Зависимости и границы

После [04](04-revision-synchronization.md). Правила — разделы 5–8 [требований](business-requirements.md). Пользователи и аутентификация не становятся общими; реплицируются ресурсные назначения и минимальный справочник субъектов.

## Затрагиваемые части проекта

`Domain/Access`; `Application/Visibility`, `Application/Security`, `Application/Users`, `Application/ObjectAdministration`, `Application/Notifications`, `Application/Dashboard`; `Infrastructure/Identity`, `Persistence/Queries` и permissions storage; controller authorization и SignalR в Web. Все четыре тестовых слоя; локальные `AGENTS.md`, `Authentication and visibility.md` и `Domain model.md`.

## Работы

- [ ] Реализовать единые ресурсные политики видимости, изменения с удалением, управления доступом и управления привязками чата. Для операций над сущностями role-only проверка не заменяет права.
- [ ] Убрать обход `isAdministrator || ...` из чтения и доставки SignalR; роль не даёт доступ к скрытым данным через административные списки.
- [ ] Разрешить контейнер отдельно от сервера и без сервера. Фильтровать родительские поля, counts, поиск, selector DTO и события, чтобы они не раскрывали скрытый сервер.
- [ ] Добавить ACL чатов и фильтрацию targets/bindings. Управление привязками требует права чата и видимости цели; не показывать скрытую цель через строку привязки или подсказку.
- [ ] Реализовать каталог пользователей по NodeId/UserId с минимальными публичными атрибутами, защитой просмотра и обновлением состояния только доверенным домашним узлом.
- [ ] Создавать сущность и полный применимый набор прав её создателя одной согласованной командой. Не давать другим администраторам доступ автоматически.
- [ ] Разрешить владельцу назначать права другому локальному/удалённому пользователю; проверять целевого субъекта и запрет уменьшать собственные права по составному ID.
- [ ] Проверять последнего владельца на согласованном состоянии при ACL update, account disable/delete и исключении узла. Недоступность узла и временный login lockout не лишают его пользователей владения.
- [ ] Согласовать локальный жизненный цикл Identity с инвариантом: нельзя сначала удалить/отключить последнего владельца, а потом пытаться восстановить его права репликацией. При отсутствии большинства потенциально опасная операция ожидает/отклоняется, обычный вход/чтение не блокируется.
- [ ] Сохранить отдельную защиту self-disable/self-delete и последнего enabled локального администратора. Bootstrap не должен восстанавливать удалённые ресурсные права по одному признаку роли.
- [ ] Передавать grants/revokes и удаления оперативно; после получения отзыва очистить связанные локальные caches/представления/SignalR-получателей. На отключённом узле до получения действуют прежние права.
- [ ] При удалении/переносе родителя сохранять независимые права контейнера и владельцев; удалить старые cascade assumptions из сценариев, модели и тестов.
- [ ] Обновить соответствующие `AGENTS.md` и фактические документы. Не ослаблять security tests ради сохранения старого role-only контракта.

## Проверки

Изолированная матрица: обычный пользователь/администратор × нет прав/видеть/изменять/управлять доступом/привязками; сущность локальная/синхронизированная; совпадающий UserId на разных NodeId; скрытый родитель; прямой запрос, поиск, counts и SignalR.

Конкурентные команды: два владельца отзывают права друг у друга, отключаются два владельца на разных узлах, просроченная заявка от уже лишённого прав пользователя, удаление аккаунта с несколькими сущностями, self-revoke отдельного флага. Проверки storage/Identity с БД отдельно разрешаются и не подменяются fake-тестами.

## Критерии приёмки

- [ ] Администратор без явных прав получает тот же отказ доступа к сущности, что обычный пользователь.
- [ ] Контейнер можно видеть без сервера; скрытые родитель/чат/цель не раскрываются косвенно.
- [ ] Собственные права нельзя уменьшить ни прямым запросом, ни синхронизированной заявкой.
- [ ] Ни одна согласованная последовательность разрешённых команд не оставляет существующую сущность без владельца.
- [ ] Вход и чтение не зависят от наличия главного; stale grants на отключённой реплике применяются только до её догона, как согласовано.

## Связанные вопросы

Открытых вопросов нет. В основном сценарии общие данные и ACL приходят на пустой узел синхронизацией. Явная карта начальных владельцев собирается перед отдельным импортом существующих данных в этапе 09.

## Результат выполнения

Реализация не начата. Действующая v1 сохраняет прежние правила до отдельного выполнения миграции и включения новой модели.
