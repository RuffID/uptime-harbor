# Этап 03. Связь узлов, диагностика и главный

Статус: not-started

## Цель

Обеспечить доверенную связь узлов и выбор главного большинством, отделив факт роли от действующего права отправлять уведомления.

## Зависимости и границы

После [01](01-protocol-and-contracts.md) и [02](02-domain-and-persistence.md). На этом этапе не включать реальные Telegram-отправки. Адреса указываются явно, автоматического сетевого обнаружения не требуется.

## Затрагиваемые части проекта

Будущие peer/cluster модули в Application и Infrastructure, durable storage в `Infrastructure/Persistence`, `Infrastructure/Monitoring`, `Infrastructure/Telegram`, `Web/Configuration`, `Web/Controllers`, `Web/Program.cs`; конфигурационные примеры без секретов, соответствующие тесты и локальные `AGENTS.md`.

## Работы

- [ ] Реализовать NodeId/ClusterId, bootstrap, проверку отсутствия клона NodeId, согласованный состав голосующих и безопасный порядок его изменения по этапу 01.
- [ ] Создать отдельные защищённые peer endpoints и HTTP adapter. Валидировать отправителя, ClusterId, версию, payload, replay и timeout; не смешивать их с публичным анонимным контрактом проверяемых приложений.
- [ ] Ввести типизированные настройки: enable/mode, адреса/идентичность peers, heartbeat, timeout, 30-секундное окно, минутный интервал настроек и пределы передачи. Секреты не попадут в ответы или логи.
- [ ] Реализовать частые проверки связи и статусы Web/БД/worker/Telegram с возрастом результата. Health не отправляет реальные сообщения в чаты и не маскирует неизвестную причину сетевого отказа.
- [ ] Подключить выбранный DotNext/Raft с долговременным term/vote/log и membership; реализовать majority commit, election и step-down, а не только флаг main/follower. Автоматическое исключение недоступных участников отключить.
- [ ] По истечении 30 секунд без успешного подтверждения готовности запускать согласование нового главного. Повторные проверки в этом окне не продлевают его без реального успеха.
- [ ] Не ждать недоступности главного всем узлам: достаточное для согласования большинство может выбрать нового. Изолированный узел и partial-доступность обычной цели не меняют исправного главного, поддержанного большинством.
- [ ] При неисправной БД немедленно перевести узел в проблемный неготовый режим, остановить рабочие writers/checks/sender и не использовать его подтверждения рабочих изменений. Не уменьшать согласованный состав; после восстановления БД выполнить догон и вернуть follower.
- [ ] Предоставить независимый контракт проверки разрешения отправки: подтверждённое большинство, актуальное поколение и готовность. При утрате условий не начинать новые попытки, даже до окончания failure window.
- [ ] Не допускать немедленного возврата прежнего главного к отправкам; восстановление — догон состояния, затем follower.
- [ ] Сделать остановку/перезапуск/process pause безопасными: проверки срока полномочий перед работой, управляемое время, отмена и очистка локальных scopes.
- [ ] Обновить соответствующие `AGENTS.md`, фактические разделы `Architecture.md`, `Configuration.md`, `Monitoring.md` и описание доверенного peer-периметра.

## Проверки

Изолированно с fake transport/time/durable store: 3 узла, 2+1, один из двух недоступен, одновременные кандидаты, асимметричная связь, дубли/задержка heartbeat, restart с сохранённым vote, pause старого главного и clock jump. Отдельно — неверная peer-аутентификация, несовместимая версия, слишком большой body, общий Telegram outage и ошибка конкретного чата.

Настоящий HTTP, независимые процессы, SQL Server и сетевое разделение — отдельная разрешаемая приёмка этапа 10; fake transport её не заменяет.

## Критерии приёмки

- [ ] Большинство считается по принятому составу; одиночный узел меньшинства не получает право отправки.
- [ ] Переключение выдерживает требование 30 секунд и не оставляет старому главному бессрочное разрешение.
- [ ] Рестарт/возврат узла не обнуляет защиту от старого term и не даёт дополнительного голоса.
- [ ] Readiness объясняет причину недоступности отправителя без ложных утверждений о причинах удалённого timeout; проблемный из-за БД узел не участвует в работе и возвращается только после догона.
- [ ] Сценарий 3+2 работает, даже если один узел меньшинства продолжает видеть прежнего главного; partial обычной цели сам по себе не запускает выборы.
- [ ] Есть серверный gate, который следующие этапы обязаны использовать для всех Telegram-путей.

## Связанные вопросы

Открытых вопросов нет. Проверка интеграции выбранного DotNext и readiness выполняется по контрактам этапа 01; запасного `IsMain` вместо них нет.

## Результат выполнения

Реализация не начата. Узлы, peer HTTP и таймеры не запускались; проверки не проводились.
