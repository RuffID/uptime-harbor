## Работы

- [ ] Добавить постоянную идентичность узла/сетки и durable consensus state согласно выбранному adapter, не помещая сетевой транспорт в Domain.
- [ ] Добавить durable заявки и их результаты, OperationId с уникальностью, accepted journal, applied cursors, конфликты с вариантами и tombstones.
- [ ] Описать атомарные границы «аккаунт + единственная роль + версия + курсор», «принятое изменение + курсор», «инцидент + delivery intent», «удаление + зависимости» через сценарные UoW.
- [ ] Хранить отдельные результаты observers, partial-доступность/покрытие, общие инциденты и доставку по incident/event/chat так, чтобы новый главный мог восстановить очередь. Не ограничиваться текущим последним marker на объекте.
- [ ] Продумать индексы, ограничения размера, порядок зависимостей, cancellation уже ненужных jobs, безопасное хранение конфликтных payload и диагностики.
- [ ] Обновлять локальные `AGENTS.md` и тематическую документацию только в части фактически реализованной модели; новые документы добавлять в solution.

- [ ] Хранить всех общих пользователей и роль Administrator, защищённые данные входа, наборы observers и чаты инцидентов по NodeId; endpoint-данные сохранять по observer. Сессии и локальные секреты в общий snapshot не включать.

- [ ] Предусмотреть durable связь сводки с исходными событиями, per-chat результаты и право на один recovery после снятия привязки. При replay/смене главного принятые intents не теряются, известные успешные отправки не дублируются.

- [ ] Предусмотреть годовое хранение завершённых инцидентов, результатов доставки и разрешённых конфликтов. Очистка не удаляет открытые события/конфликты, Pending, неисполненные intents и ещё необходимые результаты отмены/замены или tombstones; сводка сохраняет исходные события до завершения доставки.

- [ ] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию в пределах реализованного изменения; новые документы включить в навигацию и solution.

## Проверки

С управляемым временем проверить границу года и сохранность давних незавершённых событий, неотправленной сводки и необходимых маркеров идемпотентности.

Проверить транзакционное сохранение состава сводки и исходных intents, replay без двойной доставки, recovery после unbind и восстановление маркеров после restart.

Проверить EF metadata, уникальность OperationId и нормализованного login, mappings пользователей/единственной роли, журналов/курсоров/инцидентов/observers/чатов; crash проверить fake store, provider semantics — отдельно.

Общие сценарии [родительского этапа](main.md#проверки) сохраняются. Изолированные проверки подтверждают алгоритм; реальные БД, peer HTTP, процессы, браузер и Telegram учитываются отдельно в [этапе 10](../10-verification-and-acceptance/main.md).

Команды из плана не являются разрешением их запускать. Непроведённая обязательная проверка остаётся открытой; готовность кода при ожидающей приёмке обозначается `verification`.

## Критерии приёмки

- [ ] Raft storage не смешан с SQL-проекцией; локальные атомарные границы выражены сценарными UoW, данные доставки позволяют восстановить очередь.
- [ ] Хранилище восстанавливает назначенные наборы и маршрутизацию по узлам; разные endpoint-данные не схлопываются в одну общую запись.
- [ ] История сводок и получателей, включая recovery после unbind, восстанавливается вместе с инцидентом и результатами доставки.
- [ ] Возрастная очистка сохраняет незавершённую работу, обязательную историю за год и данные безопасной синхронизации.
- [ ] Работы и применимые проверки подэтапа выполнены, результат и ограничения зафиксированы.
- [ ] Статус согласован с таблицами родительского этапа и общего плана; незавершённая внешняя приёмка не объявлена выполненной.
