# Подэтап 08.5. Диагностика сетки и обновления

Статус: not-started

## Цель и результат

Показаны роль/большинство/отставание и partial; reconnect и отключение аккаунта обновляют открытые представления.

Зависимости: [08.4](08.4-conflict-resolution.md).

[Общий план](../main.md) содержит сводные статусы; [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) определяют согласованное поведение. Подготовка документа не разрешает реализацию, запуск приложения, внешние проверки или включение функции.

`Web/Pages/Index`, `Pages/Admin`, `Controllers`, `Controllers/Models`, `Hubs`, `Http/JsonResultMapper`, `wwwroot/ts/pages`, shared/types; Application DTO/read queries, Dashboard и administration services. ## Работы

- [ ] Показать подробную диагностику всей сетки любому активному администратору: текущий узел, главный, большинство, время связи и отставание. Анонимный/отключённый аккаунт получает отказ; секреты не выводятся.
- [ ] Показать partial по observers и неполное покрытие всем администраторам. Проблемный из-за БД узел отличать от follower и исправного узла без peer-связи.
- [ ] После применения отключения аккаунта закрывать защищённый доступ и SignalR. Reconnect заново проверяет активный общий аккаунт и перечитывает конфигурацию и заявки.
- [ ] Обновить локальные `AGENTS.md` и фактические Web-документы; новые документы подключать только как solution items.

- [ ] Показывать назначенных observers и разрешённые результаты по каждому; разницу endpoint-имени/времени запуска отмечать и раскрывать по узлам. Не выбирать общий uptime при различиях и не выдавать отсутствие назначенного observer за успешное покрытие.

- [ ] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию в пределах реализованного изменения; новые документы включить в навигацию и solution.

## Проверки

Изолированно проверить stale response, reconnect, отключение аккаунта с открытым редактором и неполное покрытие; два администратора видят всю диагностику, анонимный/отключённый получают отказ. Browser/mobile — 10.4; metadata по observers сохраняется.

Общие сценарии [родительского этапа](main.md#проверки) сохраняются. Изолированные проверки подтверждают алгоритм; реальные БД, peer HTTP, процессы, браузер и Telegram учитываются отдельно в [этапе 10](../10-verification-and-acceptance/main.md).

Команды из плана не являются разрешением их запускать. Непроведённая обязательная проверка остаётся открытой; готовность кода при ожидающей приёмке обозначается `verification`.

## Критерии приёмки

- [ ] Полная диагностика доступна каждому активному администратору без секретов; неисправная БД отличима от follower без peer-связи.
- [ ] Подробная диагностика соблюдает границы сетка/свой узел/краткий статус; карточка показывает различия metadata по узлам без искусственного общего значения.
- [ ] Работы и применимые проверки подэтапа выполнены, результат и ограничения зафиксированы.
- [ ] Статус согласован с таблицами родительского этапа и общего плана; незавершённая внешняя приёмка не объявлена выполненной.
