# Этап 10. Проверка и приёмка сетки

Статус: not-started

## Цель

Подтвердить согласованное поведение прав, ревизий, выборов и доставки при реальных отказах, отдельно от изолированной проверки кода.

## Зависимости и границы

После этапов 01–09. Изолированные проверки выполняются также внутри каждого этапа, а здесь проверяются целостность и внешние условия. Нет разрешения запускать команды только потому, что они включены в этот документ.

Не выполнять Git-операции, SQL, подключение к БД, Web-host, браузер, Docker, реальные HTTP/Telegram-запросы или deployment без соответствующей отдельной просьбы. Проектные/пользовательские скрипты требуют точной команды и отдельного разрешения. Compile-check и тесты — по применимым профильным скиллам и локальным ограничениям; разрешённые frontend-тесты остаются строго изолированными.

## Затрагиваемые части проекта

`tests/UptimeHarbor.Domain.Tests`, `Application.Tests`, `Infrastructure.Tests`, `Web.Tests`, `tests/Frontend`, их локальные `AGENTS.md`, `Documentation/Technical documentation/Testing.md`. Будущий стенд — минимум три независимых узла и отдельные БД с тестовыми пользователями/чатами; отдельный сценарий для двух узлов. Для внешней проверки разделения 3+2 нужен состав из пяти узлов.

Работы распределены по документам подэтапов. Каждый подэтап включает обновление затронутых локальных `AGENTS.md` и фактической технической документации; проверки и статус фиксируются только по выполненному объёму. Сводный статус этапа учитывает все его подэтапы и общие критерии ниже.

Общая работа всех категорий:

- [ ] Подготовить и отдельно выполнить SQL Server-, HTTP-, browser- и Telegram-приёмку; каждый результат привязать к конкретной конфигурации/сценарию.

Изолированная проверка выполняется внутри каждого этапа; 10.1 сводит регрессию после интеграции. Матрица ниже остаётся единым реестром сценариев: каждая строка требует всех указанных применимых уровней доказательства, а не только одной категории.

## Границы ответственности подэтапов

10.1 — итоговая изолированная регрессия, 10.2 — SQL Server, 10.3 — процессы/peer HTTP/сеть, 10.4 — браузер, 10.5 — Telegram, 10.6 — миграция/restore и общая сверка. Категория закрывается только собственным подтверждением; UI-проверка не заменяет SQL/Telegram, а подготовка runbook не заменяет restore.

## Проверки

Проверки сгруппированы по сценариям и уровню доказательства; результаты отдельных категорий фиксируются раздельно.

## Критерии приёмки

- [ ] Для каждой строки матрицы есть подтверждённый результат на указанном применимом уровне, либо явно остающаяся незавершённая приёмка.
- [ ] Не нарушаются majority/gate, владелец, no-self-revoke, независимый ACL контейнера и отсутствие admin bypass.
- [ ] Журнал и принятые доставки переживают отказ одного узла без штатного повторения известных успехов и без потери intent.
- [ ] Реальные интеграционные результаты не подменяются SQLite/fake/static проверками.
- [ ] Все обязательные этапы и результаты синхронизированы с `main.md`; `completed` не ставится при непроведённых обязательных проверках.
