# Техническое проектирование

Документ задаёт проектируемую архитектуру, а не описание готовой функции. Обязательное пользовательское поведение находится в [требованиях](business-requirements.md). Для согласования выбран Raft через DotNext; точные API, параметры, таблицы и интеграция проверяются в [этапе 01](01-protocol-and-contracts/main.md). Предварительные имена ниже не являются уже существующими типами.

Пользовательские правила закреплены в [требованиях](business-requirements.md); в [общем реестре](open-questions.md) открытых вопросов нет. Условия связи, рабочий масштаб и порядок проверки определены ниже. Исследование API DotNext и выбор конкретных механизмов выполняются внутри назначенных этапов.

## 1. Границы слоёв

Сохранить `Web → Infrastructure → Application → Domain`.

- Domain: общие идентификаторы сущностей и пользователей, инварианты учётных записей и переходов. Никакого EF, HTTP, Identity или peer-клиента.
- Application: подача/согласование/применение изменений, проверка активного администратора, общие пользователи, конфликты, инциденты и доступность отправки. Независимые контракты и сценарные Unit of Work.
- Infrastructure: SQL Server, локальное долговременное состояние, consensus adapter, peer HTTP client, очередь синхронизации, таймеры, наблюдения и Telegram transport.
- Web: защищённые peer endpoints, локальные пользовательские API, composition root и интерфейс. Peer-аутентификация не использует пользовательскую cookie.

Не вводить глобальный Unit of Work и распределённую EF-транзакцию между БД. Локальная транзакция обеспечивает атомарность данных узла; межузловую согласованность обеспечивает журнал согласования.

## 2. Два вида локального состояния

Разделить принятые данные и несогласованные заявки. Сохранение формы не меняет действующую конфигурацию до принятия заявки. Нужны состояния не менее `Pending`, `Committed`, `Conflict`, `Rejected`, с причиной отказа и возможностью увидеть результат.

Ожидающую заявку можно исправить или отменить до принятия. Контракт включает подтверждённые результаты замены и отмены, долговременное хранение и защиту от поздних повторов прежней заявки. Замена оставляет к применению только последний вариант, отмена не меняет принятую конфигурацию. Гонка с принятием разрешается по авторитетному состоянию: если исходная команда уже принята, возвращается этот результат, а дальнейшая правка получает отдельную операцию. Локальный статус Pending или потерянный ответ не являются подтверждением отмены; конкретный механизм фиксируется в 01.3.

После принятия изменения данные и отметка применения ревизии фиксируются одной локальной транзакцией. Crash между получением и применением не должен создавать половину сущности или потерянное изменение. Обработка повторяется по ID операции.

Не смешивать сетевой статус заявки, конфликт версий и отказ неавторизованному/отключённому аккаунту. Разрешение конфликта требует активного администратора и актуальной версии.

## 3. Идентификаторы и ревизии

| Поле/понятие | Назначение |
| --- | --- |
| ClusterId, NodeId | Постоянная идентичность сетки и узла, независимая от адреса |
| UserId | Один общий пользователь на всех узлах; роль только Administrator, без домашнего узла |
| OperationId, OriginNodeId, Actor | Идемпотентность и проверяемый источник изменения |
| EntityId, EntityKind, BaseRevision | Цель и версия, на которой построена правка |
| ConfigRevision / UserRevision | Версии настроек и учётной записи, независимые от каждой HTTP-проверки |
| Term / epoch, committed log position | Поколение лидерства и согласованный порядок; хранение переживает рестарт |
| AppliedRevision / peer cursor | До какого места узел применил данные; это не локальное время |
| Tombstone | Принятое удаление с версией, которое запрещает воскрешение |

Одного номера, увеличиваемого каждым узлом независимо, недостаточно. Время изменения и максимальный timestamp не используются как арбитр конфликтов. Не переиспользовать текущий `MonitoredObject.Version` как общую конфигурационную ревизию: он растёт на каждой проверке и вызовет ложные конфликты.

Общая ревизия относится только к принятому журналу. Отдельно хранить предложенные/реплицированные, но ещё не принятые записи; не показывать их как действующие. После смены главного не теряется и не переупорядочивается принятая история.

## 4. Большинство, выбор и право отправки

Большинство считается по согласованному составу голосующих узлов, а не по числу ответивших HTTP-соседей. Автоматически уменьшать состав при отказе нельзя. Добавление/удаление узлов требует безопасной процедуры изменения состава; создание первой сетки — отдельного bootstrap, не независимого самоназначения каждого узла.

Использовать Raft из DotNext: `DotNext.Net.Cluster` и HTTP/ASP.NET Core integration `DotNext.AspNetCore.Cluster`. Raft обеспечивает выборы и порядок принятого журнала; правила сущностей, авторизацию, идемпотентность, проекции SQL Server и Telegram-доставку реализует UptimeHarbor. Простые `IsMain`, приоритет ID или «получил несколько HTTP OK» не заменяют этот механизм.

Проверенные источники для выбора: [Raft в DotNext](https://dotnet.github.io/dotNext/features/cluster/raft.html), метаданные [DotNext.Net.Cluster 6.10.0](https://www.nuget.org/packages/DotNext.Net.Cluster/6.10.0) и [DotNext.AspNetCore.Cluster 6.10.0](https://www.nuget.org/packages/DotNext.AspNetCore.Cluster/6.10.0). Метаданные этой версии указывают `net10.0` и лицензию MIT. Это подтверждает выбор технологии, но не готовую интеграцию с проектом; точные версии закрепить после проверки совместимости зависимостей в этапе 01.

Использовать долговременный журнал/term/vote и хранилище состава, переживающие рестарт, а не in-memory `ConsensusOnlyState` или in-memory конфигурацию. Локальный Raft WAL и проекции SQL Server согласовать по позиции применения и replay: успешная запись в одном хранилище не является атомарной транзакцией с другим. Повторное применение должно восстанавливать проекцию без дублирования side effects. Автоматическое удаление недоступных участников из состава отключить; изменение состава только через контролируемый согласованный путь.

Heartbeat по умолчанию каждые 5 секунд; failure window — 30 секунд от последнего успешного подтверждения готовности главного. Таймеры elapsed time должны переживать скачок wall clock без ложного продления полномочий; использовать управляемый источник времени. Числа не заменяют доказательства безопасности выборов.

Различать выбранного лидера протокола и готового отправителя: после выборов нужны актуальное принятое состояние, рабочие БД/мониторинг/Telegram и действующее подтверждение большинства. При потере права отправки новые попытки немедленно блокируются; нельзя просто продолжать все 30 секунд на основании старого флага.

Ожидание недоступности главного для всех узлов не требуется: большинство может выбрать нового, даже если меньшинство продолжает видеть прежнего. Частичная доступность обычной цели не запускает выборы, пока сам главный исправен и сохраняет большинство. Неисправность собственной БД означает немедленный выход из рабочей роли, а не ожидание полного сетевого отказа.

Проверка term и действующего разрешения нужна перед каждой попыткой, включая retry, recovery и тестовое уведомление. Одного term в локальной строке недостаточно, чтобы остановить старый процесс после partition/pause. Протокол должен описать срок разрешения, renewal, step-down и проверку после длительной паузы процесса. Telegram не понимает fencing token: запрос, начатый до потери полномочий, может завершиться позднее; это входит в допустимое неопределённое окно дубля.

Операции membership и изменения доверия выполняет любой активный администратор по принятому общему аккаунту. Состав и доверие меняются через безопасную согласованную процедуру; отдельного операторского назначения нет.

## 5. Здоровье и доверие между узлами

Отдельный peer health-контракт возвращает идентичность и совместимость протокола, роли/поколение, применённую ревизию и ограниченный набор статусов: Web, БД, последняя успешная работа мониторинга, общая готовность Telegram. Недоступность БД должна по возможности диагностироваться без зависимости всего health handler от той же БД; при невозможности ответа другой узел фиксирует только доступные сетевые факты.

При неисправной БД устанавливать проблемный неготовый режим: остановить monitoring, приём рабочих правок, применение общих данных и все Telegram-пути. Не использовать такой узел как подтверждение рабочих изменений, но не уменьшать знаменатель большинства. Реализация приостановки участия должна быть согласована с API DotNext, без самовольного переписывания membership. После восстановления — проверка durable state, догон проекций и роль follower до возможных последующих выборов. Потеря peer-связи при исправной локальной БД — другой случай: локальный пользовательский доступ сохраняется.

Не отправлять тестовые Telegram-сообщения каждые 5 секунд ради health. Выбрать безопасную ограниченную диагностику Telegram, актуальность её результата и состояние `Unknown`. Успешный HTTP peer-response не доказывает, что произвольный Telegram-чат доступен. `403` одного чата и `429`/`retry_after` не должны вызывать бесконечное переключение здоровых узлов.

Peer-протокол требует взаимной аутентификации, привязки запроса к ClusterId/NodeId, проверки версии, защиты от replay и ограничений размера/пакета/timeout. Не доверять переданному `Actor` из произвольного тела без подтверждённого узла-источника. Межузловая связь идёт по HTTPS через интернет без обязательного VPN; у узлов есть доменные имена и возможность выпуска/обновления сертификатов. Допустимо завершение TLS на Nginx с изолированным внутренним HTTP до приложения и доверенными proxy-заголовками. Конкретную взаимную аутентификацию и trust bootstrap выбрать в этапе 01; HTTPS не заменяет проверку доверенного участника. Секреты локальные и не возвращаются через UI/API.

Все возможные отправители используют одного общего Telegram-бота; токен задаётся локально на каждом узле. При вводе узла проверить идентичность бота и доступ к настроенным чатам без раскрытия токена. Диагностика показывает доступность отправки через текущего подтверждённого главного, актуальность и известную причину отказа; неизвестный статус не выдаётся за доступность. Норматив возобновления отправки отсутствует; 30 секунд определяют только начало смены главного.

Диагностические ответы для браузера отделены от доверенного peer health. Подробности всей сетки доступны любому активному администратору после серверной проверки входа. Секреты, хеши паролей и технические реквизиты защиты не выводятся.

## 6. Репликация и конфликты

Контракты авторизации и инвариантов — 01.3, доменные правила — 02.1, чтение принятого общего аккаунта и проверка активного администратора — [05.1](05-permissions-and-ownership/05.1-subjects-and-resource-policies.md) до 04.1/04.2. Интеграция синхронизируемых пользователей с Identity и входом — 05.2–05.4 после готовности 04.

1. Узел проверяет активный принятый общий аккаунт администратора и сохраняет заявку с базовой версией, общим UserId актёра и уникальным ID.
2. Заявки обычных настроек передаются в минутном цикле; изменения пользователей, удаления и события — приоритетным каналом без ожидания этого цикла.
3. Главный повторно проверяет активную общую учётную запись администратора, базовую версию, уникальность и ссылки. Доверенный peer не заменяет проверку пользователя; actor — общий UserId, origin — NodeId.
4. Принятое изменение попадает в долговременный согласованный журнал. Создание/изменение пользователя и единственной роли, составные изменения связей и удаления оформляются неделимыми командами.
5. Реплики применяют принятые команды в порядке журнала, сохраняют курсор и подтверждают его. Пропуск ревизии требует догрузки, а не применения последующих зависимых операций наугад.
6. Повтор OperationId возвращает уже известный результат, не создавая новую сущность или уведомление.

При update/update первая принятая правка остаётся действующей, поздний вариант той же базовой версии сохраняется как конфликт. Обнаружение конфликта не создаёт откат к исходной настройке и не отменяет результаты мониторинга или доставки. Выбор итога — новая авторизованная команда с актуальной базой.

Разбирать update/update, update/delete, удаление родителя, дубли имён входа/Telegram chat ID/имени сервера, изменение и удаление аккаунта, конфликт связей. Принятое удаление не отменяется старой правкой. Конфликтные варианты доступны администраторам, но секретные поля пользователей не выводятся.

Любой активный администратор создаёт и изменяет сущности через любой узел. Непринятая запись пользователя или её изменение не дают возможности входа. Ожидающее создание объекта не меняет принятую конфигурацию и право Telegram-отправки.

## 7. Общие учётные записи и единственная роль

Использовать общие UserId и RoleId одной синхронизируемой роли Administrator. Каждый активный пользователь — администратор всех объектов и узлов. Не вводить resource ACL, владельцев, grants/revokes, пары NodeId + UserId для субъектов или отдельного оператора. Источник запроса NodeId остаётся технической частью аудита.

Реплицировать данные общего аккаунта, требуемые для существующего входа: идентификатор, нормализованное уникальное имя, используемые реквизиты входа, PasswordHash, активность, версию/security stamp и единственную роль. Пароль в открытом виде не сохранять в Pending, журнале, snapshot, конфликтных payload и логах. Секретные поля, включая хеши и stamps, передаются только защищённым доверенным peer transport и не входят в обычные DTO, SignalR, сообщения об ошибках или интерфейс конфликтов.

Изменения пользователей проходят тот же accepted journal и атомарное применение с курсором, что настройки. Не создавать второй механизм синхронизации Identity целой БД. Инфраструктурный адаптер применяет принятые аккаунты и роль к Identity; типы Identity и EF остаются вне Application/Domain. Совместимость формата хешей фиксируется в 01.3/05.

Первый администратор создаётся один раз при bootstrap. Обычный join получает принятые аккаунты и роль в snapshot/replay, без локального bootstrap пользователя. Удаление узла не влияет на общий UserId и не удаляет аккаунты. Проверка уникальности имени и запрет отключения/удаления последнего активного администратора выполняются по принятому состоянию, включая конкурирующие команды. Непринятые новые аккаунты или пароли не используются для входа.

Cookie, сессии, локальные ключи защиты, счётчики ошибок входа и временный login lockout не реплицируются. На каждом узле вход выполняется отдельно с общими данными. После применения отключения/удаления или смены PasswordHash/security stamp старые данные входа и сессии больше не дают доступ; при разрыве связи изолированный узел действует по последней принятой версии. Не создавать запись в общем журнале при каждом успешном входе.

Авторизация страниц, API, SignalR, test-send и команд проверяет вход и активный принятый аккаунт администратора. Проверка повторяется перед принятием команды и внешней тестовой отправкой. Для обычных фоновых уведомлений после принятия события пользовательская сессия не требуется.

## 8. Наблюдения, инциденты и очередь

Разделить сырое наблюдение конкретного узла и единый согласованный инцидент сущности. Сохранить observer ID, последовательность/ID наблюдения, поколение конфигурации и времена. Устаревший результат от прежнего endpoint/удалённой сущности не создаёт новую аварию.

Для каждой цели хранить согласованный набор назначенных observers как часть конфигурации, изменяемой по праву изменения цели. Для каждого observer отдельно вести свежий подтверждённый результат и последовательность ошибок по текущему endpoint/config revision, включая имя приложения и время запуска из успешного ответа. Существующий порог обычных проверок применяется отдельно, не суммируется между observers. Набор берётся из принятой конфигурации цели, без автоматического удаления неисправного наблюдателя; потерянное наблюдение — `Unknown`, не неудачная проверка самой цели.

Применять правила [доступности с разных узлов](business-requirements.md#10-доступность-с-разных-узлов): все ожидаемые свежие успехи — available; свежий успех и подтверждённый отказ разных узлов — partial; все ожидаемые свежие подтверждённые отказы — unavailable; неполные данные отмечаются явно и не превращаются в полный отказ при имеющемся успехе. Срок свежести, порядок применения delayed observations и переходы состава формализовать и проверить в этапе 01.

Переходы полного покрытия в частичную/полную потерю наблюдения и обратно создают отдельные устойчивые события и delivery intents. Replay и неизменившийся цикл не повторяют предупреждение. Восстановление наблюдения доставляется только чатам с подтверждённым предупреждением; действуют общие отмены по unbind/удалению. Эти события не подменяют подтверждённые partial/full/recovery самой цели и не закрывают её аварию без свежих проверок.

Read model и сообщения сохраняют привязку endpoint-имени/времени запуска к observer; при различиях не выбирают произвольный общий ответ и не вычисляют общий uptime. Само расхождение metadata не является отказом. Применение delayed observations при изменении назначенного набора связывается с поколением конфигурации по контракту 01.3.

Маршрутизация инцидентов самого узла хранит отдельные назначения чатов для каждого NodeId. Любой активный администратор меняет их через общий журнал; новый главный восстанавливает назначения вместе с историей доставки.

Общий incident хранит подтверждённую доступность и направления частичного отказа. Переходы partial/full/recovered и изменение подтверждённых проблемных направлений должны иметь стабильные event IDs; повтор того же набора наблюдений не создаёт новое уведомление. Recovery частичного отказа отличается от восстановления полной аварии в тексте, но связан с той же общей историей цели. Нельзя просто запускать нынешний `MonitoringService` на всех репликах: он создаёт независимые случайные incident IDs и задания outbox.

Согласованные outage/partial/recovery и намерение доставки должны переживать отказ прежнего главного. Логический ключ доставки включает incident, вид события и чат; поколение привязки учитывается отдельно для проверки отмен и не создаёт дубль известной доставки при перепривязке. Локальный claim outbox не считается распределённым разрешением отправки. Перед новой попыткой новый главный восстанавливает журнал, список получателей, уже принятые успехи и terminal cancellations.

Состояния доставки передавать оперативно; успех транспортного вызова и его согласованная фиксация — разные моменты. Потеря процесса между ними допускает повтор. Уже принятые успехи не повторять штатно. Не уменьшать текущую гарантию сохранения задания при локальном рестарте. Исчерпание retry сохраняет диагностическое terminal-состояние и не стирает событие. Ручной повтор после исчерпания попыток и бесконечные автоматические повторы исключены.

Завершённые аварии из offline backlog доставляются сводкой без отсечения по возрасту; открытые — отдельно, а уже уведомлённым чатам приходит обычный recovery. Принятые intents и полная история сохраняются: состав сводки, исходные события и per-chat результаты имеют устойчивые идентификаторы, переживают выборы и replay и исключают штатную повторную отправку исходных сообщений вместе со сводкой.

Привязка к открытой аварии создаёт intent текущей проблемы. Unbind отменяет не начатый outage, но сохраняет право на один recovery для уведомлённого чата, включая поздний подтверждённый успех. Rebind/replay не дублируют известный успех incident + kind + chat. Удаление цели/чата блокирует новые отправки. Test-send доступен активному администратору, проверяемому при подаче и перед отправкой через общий gate.

## 9. Удаления, догон и восстановление

Применение tombstone атомарно обновляет рабочие сущности, связанные привязки и отмены неначатых доставок. Удаление сервера отвязывает контейнеры, сохраняя их как общие объекты всех администраторов. Удаление пользователя не удаляет созданные им объекты; принятая отметка удаления не позволяет восстановить аккаунт старым snapshot.

Догон — запрос по курсору. Для нового/сильно отставшего узла нужен snapshot общих данных с принятой ревизией и replay журнала, включая пользователей, PasswordHash, состояние аккаунтов и единственную роль. Это не замена всей БД: локальные настройки, секреты узла и сессии не переносятся.

Завершённая история инцидентов, доставки и разрешённых конфликтов хранится один год после завершения. Очистка не затрагивает открытые события/конфликты, Pending, неисполненные intents и результаты отмены/замены, ещё необходимые для идемпотентности. Целевой catch-up до актуальных данных и полного покрытия проверками — один час после восстановления связи. Ориентир — три узла и около 30 приложений с проверкой раз в минуту назначенными observers. Прогресс, backlog и фактическое время доступны для самостоятельного наблюдения; отдельные нагрузочные испытания и доказательство часовой цели на стенде в текущий объём не входят.

Срок хранения журнала/tombstones и допустимость compaction определяются подтверждениями реплик или безопасным принудительным snapshot-rejoin. Нельзя удалять tombstone по одному возрасту, пока старая реплика способна вернуть удалённую запись.

После restore backup нельзя запустить вторую копию с тем же NodeId или устаревшим голосом/term. Предусмотреть карантин, сверку идентичности и контролируемое восстановление/rejoin. Новая адресация не означает новую учётную запись узла, но клон диска не должен становиться вторым голосом.

## 10. Первый запуск и восстановление

Распределение реализации: схема — 02.3; bootstrap, membership и durable Raft — 03; общий журнал и snapshot/replay — 04; процедуры первого запуска и rejoin — 09. Догон прикладной проекции не реализуется второй раз в 03 или 09; до его подтверждения readiness/gate закрыты. Зависимости находятся в [общем плане](main.md#порядок-зависимостей-между-подсистемами).

Развёрнутых установок прежней версии нет. Перенос v1, импорт непустых установок и переключение старых workers исключены. С первого запуска действуют общие администраторы и новая доставка, включая одноузловую сетку с большинством 1. Меньшинство существующей сетки не может самостоятельно стать новой одноузловой сеткой.

Первый узел создаёт сетку и первого администратора; остальные присоединяются с пустыми общими данными и пользователями. Snapshot/replay включает аккаунты и единственную роль; readiness подтверждается после проверки проекций и догона. До голосования требуется предусмотренный DotNext догон. Несвязанные непустые данные, включая независимо созданных пользователей, отклоняются без merge.

Возврат старого узла/backup требует проверки ClusterId/NodeId, поколения durable state, курсора и истории. При невозможности догона общая проекция, включая пользователей, PasswordHash и роль, восстанавливается по актуальному snapshot; локальные секреты и сессии не копируются. Старая outbox ожидает сверки доставки. Pending сверяется по OperationId с принятыми/отменёнными/заменёнными результатами; оставшиеся непринятые заявки требуют подтверждения пользователем, активного аккаунта администратора и актуальной base revision. Обычный restart актуального state не равен restore старой копии.

При безвозвратной потере большинства отдельная ручная аварийная процедура использует выбранную администратором копию и явное подтверждение возможной потери отсутствующих изменений. Контракт 01.2/01.3 должен исключить параллельную работу прежней и восстановленной сетки, в том числе при возврате старых узлов; конкретный механизм fencing/идентичности и повторного join проверяется до реализации 09.4. Обычный membership по-прежнему требует большинства, автоматически уменьшать состав нельзя.

Создание и EF migrations схемы, безопасный bootstrap и будущий backup/restore остаются обязательными. Startup применяет миграции: реальный запуск требует отдельного разрешения. Будущие несовместимые выпуски допускают запланированную общую остановку UI/checks/sender без предельной длительности. Рабочие процессы включаются только вручную разработчиком после обслуживания; таймер, restart или окончание обновления не должны обходить этот порядок. Runbook обновления/отката разрабатывается отдельно от отсутствующего переноса v1.

Перечисление проверки или команды в документации не разрешает её выполнение. Реальные SQL Server, peer HTTP, Telegram, браузер и deployment пользователь проверяет самостоятельно по мере запуска узлов; результаты не приписываются изолированным тестам.

## 11. Среда, масштаб и порядок проверки

Межузловой транспорт — публичный HTTPS с действительными сертификатами доменных имён узлов, без обязательного VPN. Выпуск и обновление сертификатов доступны. Узлы проходят отдельную взаимную аутентификацию; обычный браузерный вход не даёт доступа к peer endpoints.

Рабочий ориентир — три узла UptimeHarbor и около 30 приложений мониторинга; каждое приложение проверяется раз в минуту назначенными ему узлами. Это не 30 проверок одного приложения в минуту и не жёсткий предел программы. Число наблюдений зависит от назначений observers. Производительность, срок offline и аппаратные пределы не объявляются измеренными; отдельный нагрузочный стенд не требуется.

При разработке достаточно минимального набора изолированных тестов критичных правил: большинство и sender gate, идемпотентность принятия/повтора и сохранность ожидающих событий, вход и активность общего администратора. Дополнительный тест нужен при конкретном изменении или обнаруженном дефекте, а не для автоматического покрытия всей матрицы.

Первый узел пользователь запускает на своём ПК разработчика и проверяет вручную. Затем самостоятельно и постепенно запускает продовые узлы, наблюдает работу, ошибки, очередь/догон, Telegram-статус и нагрузку на серверы. Пользователь сам подтверждает результат по фактической эксплуатации. Отдельный полный стенд, испытания на пяти узлах и обязательный прогон всей матрицы не входят в текущий объём; непроверенные сценарии остаются явно непроверенными и не блокируют завершение разработки только своим отсутствием. Конкретные запуски и внешние действия требуют отдельного разрешения.
