# Этап 01. Архитектура и контракты сетки

Статус: not-started

## Цель

Получить проверенный проект протокола и модели согласования до реализации распределённых изменений и отправок.

## Зависимости и границы

Зависимостей нет. Основа — [пользовательские требования](business-requirements.md) и [предварительное проектирование](technical-design.md). Этап не разрешает запуск узлов, запросы к Telegram, подключение к БД или реализацию остальных этапов.

## Затрагиваемые части проекта

Текущие границы `Domain`, `Application/Abstractions`, `Infrastructure/Monitoring`, `Infrastructure/Telegram`, `Infrastructure/Persistence`, `Web/Configuration`, `Web/Controllers`, `Web/Hubs`; их локальные `AGENTS.md`. Документы об архитектуре, конфигурации, мониторинге, доставке и данных в `Documentation/Technical documentation`.

Новые модули и публичные имена пока не существуют: окончательные места и контракты определить здесь, без создания пустых типов ради плана.

## Работы

- [ ] Проверить применимые профильные скиллы C#, ASP.NET Core, сценарных UoW, ServiceResult, EF migrations и frontend перед изменениями соответствующих областей.
- [ ] Проверить интеграцию выбранного Raft из `DotNext.Net.Cluster`/`DotNext.AspNetCore.Cluster`: точные версии и API для .NET 10, лицензия, durable term/vote/log, majority commit, crash recovery, snapshot и безопасное изменение состава. Не включать in-memory production state и автоматическое исключение недоступных участников.
- [ ] Описать bootstrap сетки, постоянный состав голосующих, join/leave, запрет автоматического уменьшения состава и поведение 1/2/3 узлов. Отдельно определить режим существующего одиночного экземпляра до включения сетки.
- [ ] Спроектировать жизненный цикл `Follower / Candidate / Leader` и отдельную готовность отправителя: 30 секунд от последней подтверждённой готовности, частые heartbeat, step-down, потеря большинства и восстановление прежнего главного ведомым.
- [ ] Определить выдачу и истечение права отправки, повторную проверку после process pause и ограничения уже начатого Telegram HTTP-запроса. Нельзя заявлять exactly-once или защиту внешнего API одним локальным term.
- [ ] Формализовать согласованную модель наблюдений: available/partial/unavailable и неполное покрытие, отдельный failure counter observer, freshness, смена состава и общая история инцидента. Partial вызывает уведомления, но не выборы исправного главного с большинством.
- [ ] Определить readiness БД/worker/Telegram, срок актуальности статусов, `Unknown`, отличия общей неисправности от ошибки одного чата. Неисправная БД немедленно выводит узел из рабочей роли без уменьшения состава; возврат только после догона. Обычная проверка health не отправляет сообщения клиентам.
- [ ] Зафиксировать peer transport: взаимная аутентификация, ClusterId/NodeId, версия протокола, replay protection, предел тела/пакета, timeout/backoff, trust bootstrap и настройки HTTP/HTTPS.
- [ ] Описать контракты заявок, результатов, ревизий, курсоров, подтверждений, tombstones, конфликтов, снимка общих данных и минимального каталога пользователей.
- [ ] Определить локальные атомарные команды: создание с владельцем, изменение ACL, удаление с зависимостями, принятый инцидент с намерением доставки. Разделить локальную транзакцию и majority commit.
- [ ] Определить правила совместимости при обновлении версий и безопасный порядок включения новых workers/ACL. Основной путь — пустой join/snapshot/replay; непустой импорт и восстановление старого узла оформить отдельными контрактами предварительного разбора и rejoin.
- [ ] Детализировать выбранные решения в активных документах плана, не выдавая их за реализованную архитектуру. Новые обнаруженные вопросы при необходимости вносить в `open-questions.md`; решённые не сохранять как журнал ответов. При добавлении документов обновить навигацию и solution items.

## Проверки

Проектные сценарии: partition 2+1, недоступен один из двух, одновременно стартуют кандидаты, асимметричная связь, старый главный возвращается после pause, две конкурентные правки, оба владельца отзывают права друг у друга, Telegram принял сообщение без полученного подтверждения, несовместимая peer-версия.

Технология выбрана по документации DotNext и метаданным пакетов; ещё требуется проверка реальных API и интеграции. Исследование пакетов/документации не подтверждает работоспособность SQL Server или сетки. Сборка прототипа и запуск проверок требуют отдельного разрешённого объёма и профильных правил.

## Критерии приёмки

- [ ] Для всех записываемых общих данных определены источник истины, точка принятия, версия и способ восстановления.
- [ ] Алгоритм большинства/отправки объясняет перечисленные отказы без двух независимо действующих главных.
- [ ] Зафиксирована последовательность обработки наблюдения до одного общего инцидента и доставки.
- [ ] Интеграция выбранного DotNext/Raft и правила partial/readiness формализованы для реализации; оставшиеся проверки не подменены отметкой об окончании этапа.
- [ ] Есть карта новых модулей, миграции и обязательных сценариев приёмки для следующих этапов.
