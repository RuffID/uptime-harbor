# Этап 02. Доменная модель и долговременное хранение

Статус: not-started

## Цель

Подготовить инварианты и схему отдельных БД для узлов, ревизий, заявок, владельцев, инцидентов и состояния доставки.

## Зависимости и границы

После [01](01-protocol-and-contracts.md). Схема и миграции создаются в рамках отдельно разрешённой реализации; применение миграций к БД не входит в автоматическую проверку. Исторические baseline migrations не переписываются.

## Затрагиваемые части проекта

`UptimeHarbor.Domain/Monitoring`, `Domain/Access`, `Domain/Notifications`; `Application/Abstractions/Persistence`, `Application/Abstractions/UnitOfWork`; `Infrastructure/Persistence`, его `Configurations`, `UnitOfWork`, `Repositories`, новые миграции. Соответствующие Domain/Application/Infrastructure tests, ближайшие `AGENTS.md`; актуальные документы `Domain model.md`, `Persistence.md`, `Database migrations.md`.

## Работы

- [ ] Добавить постоянную идентичность узла/сетки и durable consensus state согласно выбранному adapter, не помещая сетевой транспорт в Domain.
- [ ] Ввести составной идентификатор субъекта `NodeId + UserId` и минимальный каталог удалённых субъектов без синхронизации Identity.
- [ ] Спроектировать ресурсные права и владение для сервера, контейнера и чата; отдельное управление привязками чата. Право изменения включает удаление.
- [ ] Убрать из новой модели обязательную зависимость container ACL от server ACL. Независимые права контейнера переживают смену/удаление родителя.
- [ ] Разделить версию конфигурации, версию прав, оперативное состояние мониторинга и позицию общего принятого журнала. Сохранить локальную защиту EF-конкурентности там, где она нужна.
- [ ] Добавить durable заявки и их результаты, OperationId с уникальностью, accepted journal, applied cursors, конфликты с вариантами и tombstones.
- [ ] Описать явные транзакционные границы «создание + права создателя», «принятое изменение + курсор», «инцидент + намерение доставки», «удаление + зависимые изменения» через сценарные UoW.
- [ ] Хранить отдельные результаты observers, partial-доступность/покрытие, общие инциденты и доставку по incident/event/chat так, чтобы новый главный мог восстановить очередь. Не ограничиваться текущим последним marker на объекте.
- [ ] Запрет последнего владельца защищать согласованной сериализацией команд и локальным инвариантом, а не только FK или UI-проверкой количества.
- [ ] Подготовить миграцию без автоматического назначения всем администраторам доступа и без выдуманного автора исторических сущностей. Данные для backfill отделить от создания схемы.
- [ ] Продумать индексы, ограничения размера, порядок зависимостей, cancellation уже ненужных jobs, безопасное хранение конфликтных payload и диагностики.
- [ ] Обновлять локальные `AGENTS.md` и тематическую документацию только в части фактически реализованной модели; новые документы добавлять в solution.

## Проверки

Изолированно: локальные инварианты прав и владельцев, независимость контейнера, валидность версии и идентификаторов, EF metadata/индексы/связи без соединения. Провайдерные проверки конкурентности и атомарности на SQLite или SQL Server относятся к работе с БД и не выполняются при действующем запрете БД без отдельного разрешения.

Отдельная внешняя приёмка: миграция копии существующей SQL Server БД, constraints и rollback/restore. Compile-check не доказывает успешность миграции.

## Критерии приёмки

- [ ] Один и тот же UserId разных узлов не совпадает как субъект доступа.
- [ ] Общая ревизия не увеличивается локально произвольными writers и не меняется из-за каждой проверки endpoint.
- [ ] Новая сущность не может стать принятой без владельца; каскады не уничтожают владельцев сохранённых контейнеров.
- [ ] Повторное применение OperationId не создаёт вторую запись или повторный side effect.
- [ ] Миграция и mapping старых данных отделены; provider-зависимые проверки имеют честный отдельный статус.

## Связанные вопросы

Открытых вопросов нет. Детали интеграции DotNext закрепляются этапом 01. Если выполняется импорт непустой установки, реальные сопоставления и владельцы собираются в процедуре этапа 09; основной пустой join не требует карты старых данных.
