# Этап 10. Проверка и приёмка сетки

Статус: not-started

## Цель

Подтвердить согласованное поведение прав, ревизий, выборов и доставки при реальных отказах, отдельно от изолированной проверки кода.

## Зависимости и границы

После этапов 01–09. Изолированные проверки выполняются также внутри каждого этапа, а здесь проверяются целостность и внешние условия. Нет разрешения запускать команды только потому, что они включены в этот документ.

Не выполнять Git-операции, SQL, подключение к БД, Web-host, браузер, Docker, реальные HTTP/Telegram-запросы или deployment без соответствующей отдельной просьбы. Проектные/пользовательские скрипты требуют точной команды и отдельного разрешения. Compile-check и тесты — по применимым профильным скиллам и локальным ограничениям; разрешённые frontend-тесты остаются строго изолированными.

## Затрагиваемые части проекта

`tests/UptimeHarbor.Domain.Tests`, `Application.Tests`, `Infrastructure.Tests`, `Web.Tests`, `tests/Frontend`, их локальные `AGENTS.md`, `Documentation/Technical documentation/Testing.md`. Будущий стенд — минимум три независимых узла и отдельные БД с тестовыми пользователями/чатами; отдельный сценарий для двух узлов. Для внешней проверки разделения 3+2 нужен состав из пяти узлов.

## Работы

- [ ] Поддержать meaningful domain/application/fake-transport тесты по всем новым инвариантам и протоколу, без подмены ошибок запасными ветками.
- [ ] Собирать production-проекты отдельно без запуска Web-хоста; проверять только затронутые проекты и зависимости. Точные команды сверить с актуальной конфигурацией до разрешённого запуска.
- [ ] Изолированные .NET-тесты запускать через Microsoft Testing Platform отдельно по проектам. Не запускать полный Infrastructure-набор при запрете БД: в нём уже есть SQLite provider tests.
- [ ] Frontend-набор запускать только через разрешённый `node --experimental-strip-types --test` для `tests/Frontend/*.test.mts`, без сети, dev server или браузера.
- [ ] Подготовить и отдельно выполнить SQL Server-, HTTP-, browser- и Telegram-приёмку; каждый результат привязать к конкретной конфигурации/сценарию.
- [ ] Зафиксировать ограничения, отказы и непроведённые категории. Не закрывать `verification` по результатам одной сборки или fake-проверок.
- [ ] Обновить только фактические разделы документации, активные статусы и результаты. Проверить входящие ссылки/solution folder при смене общего статуса плана.

## Проверки

Проверки сгруппированы по сценариям и уровню доказательства; результаты отдельных категорий фиксируются раздельно.

### Матрица обязательных сценариев

Все строки ниже при создании плана имеют статус **не проверено**. В ходе реализации сохранять фактический результат, конфигурацию, дату проверки и ограничения; не заменять таблицу общим «всё работает».

| Сценарий | Ожидаемый результат | Уровень доказательства |
| --- | --- | --- |
| Обычный старт трёх узлов | Один готовый главный, единая принятая история после догона | Изолированный + peer HTTP/SQL Server |
| Главный выключен | После 30 секунд и согласования новый главный продолжает очередь | Изолированный + реальные процессы/HTTP |
| Partition 2+1 | Меньшинство не начинает отправки; большинство подтверждает главного | Изолированный + сетевой стенд |
| Partition 3+2, старого главного видит ещё один узел | Большинство может выбрать нового, не ожидая потери связи старого главного со всеми | Изолированный + сетевой стенд |
| Два узла потеряли связь | Нет отправителя, события сохраняются, UI доступен | Изолированный + сетевой стенд |
| Асимметричная связь/длительный pause | Нет самоназначения по одному timeout; старые полномочия не оживают | Изолированный + сетевой стенд |
| Возвращение прежнего главного | Догон до отправки, роль follower, без вытеснения нового | Изолированный + реальные процессы |
| Отказ БД/worker/общего Telegram | Разные причины/актуальность readiness, правильный gate | Изолированный + разрешённые внешние отказы |
| БД узла неисправна, но HTTP отвечает | Проблемный режим, рабочие проверки/изменения/отправки остановлены; состав не уменьшен, возврат после восстановления и догона | Изолированный + SQL Server/process |
| Цель доступна с Б/В, но недоступна с А | Partial с указанием направления А, Telegram-событие, без смены исправного главного с большинством | Изолированный + browser/HTTP/Telegram |
| Результат одного observer пропал или устарел | Неполное покрытие отмечено; отсутствие результата не выдано за полный отказ цели | Изолированный + HTTP |
| Partial повторяется, затем все направления восстановились | Нет сообщения на каждом цикле; одно событие подтверждённого перехода и связанное восстановление | Изолированный + Telegram |
| Ошибка одного Telegram-чата | Остальные доставляются, нет бесконечных выборов | Fake sender + Telegram |
| Создание/редактирование на ведомом offline | Pending сохраняется; старые настройки действуют до принятия | Изолированный + browser/HTTP |
| Две правки одной версии | Видимый конфликт с обоими вариантами, без silent overwrite | Изолированный + browser/SQL Server |
| Replay/пропуск пакета/crash при apply | Идемпотентность, догон, атомарность данных и курсора | Изолированный + SQL Server/process |
| Удаление и возвращение старой реплики | Нет воскрешения; зависимости/доставки обработаны | Изолированный + SQL Server/HTTP |
| Новый/отставший узел после compaction | Snapshot общих данных и replay без замены Identity/секретов | Изолированный + SQL Server/HTTP |
| Пустая сетка и пустой join | Контролируемый bootstrap, принятые общие данные приходят синхронизацией, права явно назначены | Изолированный + SQL Server/HTTP |
| Непустой join | Обычное присоединение не перетирает данные; есть отдельный предварительный разбор и согласованный импорт | Изолированный + SQL Server/browser |
| Администратор без прав | Нет доступа к сущности через UI/API/SignalR/поиск/selector | Изолированный + browser/HTTP |
| Контейнер без видимого сервера | Контейнер виден, сведения родителя не раскрыты | Изолированный + browser/HTTP |
| Назначение прав пользователю другого узла | Правильный NodeId/UserId, без переноса учётных данных | Изолированный + browser/HTTP |
| Self-revoke и два конкурентных владельца | Собственные права не уменьшаются, ноль владельцев невозможен | Изолированный + SQL Server/HTTP |
| Удаление/отключение последнего владельца | Операция не оставляет бесхозные сущности | Изолированный + Identity/SQL Server |
| Отзыв прав на отключённом узле | До догона старые права; после применения новые, без блокировки входа из-за partition | Изолированный + browser/HTTP |
| Скрытый пользователю Telegram-чат | Доставка по привязке продолжается независимо от ACL UI | Изолированный + Telegram |
| Crash после принятия Telegram | Intent не потерян; редкий дубликат допустим, известный успех штатно не повторяется | Fake sender + Telegram/process |
| Принятые outage/recovery и смена главного | Тот же incident, per-chat markers, recovery только после outage | Изолированный + Telegram/SQL Server |
| Миграция/restore/clone NodeId | Владельцы назначены явно, нет второго голоса/отправителя | Изолированный + SQL Server/process |
| Обновление разных версий | Несовместимый протокол не участвует в согласовании ошибочно | Изолированный + peer HTTP |

## Критерии приёмки

- [ ] Для каждой строки матрицы есть подтверждённый результат на указанном применимом уровне, либо явно остающаяся незавершённая приёмка.
- [ ] Не нарушаются majority/gate, владелец, no-self-revoke, независимый ACL контейнера и отсутствие admin bypass.
- [ ] Журнал и принятые доставки переживают отказ одного узла без штатного повторения известных успехов и без потери intent.
- [ ] Реальные интеграционные результаты не подменяются SQLite/fake/static проверками.
- [ ] Все обязательные этапы и результаты синхронизированы с `main.md`; `completed` не ставится при непроведённых обязательных проверках.
