# Несколько узлов, синхронизация и общие администраторы

Дата создания: 2026-10-18
Статус: not-started

## Цель и основание

Объединить экземпляры UptimeHarbor с отдельными БД: проверка узлов, главный по большинству, синхронизация настроек, инцидентов и доставки. Все пользователи общие, единственная роль — «Администратор» с полным доступом через любой узел.

Основание — согласованные в обсуждении этой задачи требования. План оформлен по `project-planning-docs`; правила оформления проверены также в чате «Скилл оформление планов проектов» (`01a14448-87e4-7c82-93ed-6a97f7b3eb69`). Создание плана разрешает только документационные изменения, не реализацию.

## Границы

Включены отдельные БД узлов, их взаимная проверка, главный, ревизии/конфликты, общие пользователи с единственной ролью «Администратор», синхронизация объектов/чатов/привязок/инцидентов/доставки, UI, первый запуск, восстановление, минимальные изолированные проверки и самостоятельная приёмка пользователем. Отдельных разрешений, владельцев и оператора нет. Проект не развёрнут, переноса прежних установок не требуется.

Для согласования выбран Raft через DotNext с долговременным журналом и отдельными проекциями БД. Частичная доступность цели отображается отдельно и вызывает Telegram-уведомления, но не смену исправного главного с большинством. Узел с неисправной собственной БД выводится из рабочей обработки. Основной путь подключения — пустые общие данные, присоединение, синхронизация; несвязанные непустые данные не объединяются при join, восстановление старой копии новой модели проходит отдельный rejoin.

Не включены перенос открытых сессий между узлами, дополнительные роли и ресурсные разрешения, общая БД, управление Docker/проверяемыми приложениями и exactly-once Telegram. Общая учётная запись с тем же паролем работает на любом догнавшем узле; сессии, ключи узла, bot token, подключения к БД и логи локальны.

Один общий Telegram-бот используется на всех узлах с локальными токенами. Потеря частичного/полного наблюдения вызывает отдельные предупреждения и восстановление предупреждённым чатам. Включено ручное аварийное восстановление администратором из выбранной копии с подтверждением возможной потери данных и изоляцией старой сетки. Завершённая история хранится год с защитой незавершённых операций; целевой догон — один час. Telegram-отправка имеет видимый статус без норматива восстановления. Будущие обновления допускают общую остановку без ограничения времени до ручного включения разработчиком.

Межузловая связь — HTTPS через интернет без обязательного VPN, с доменными именами, обновляемыми сертификатами и отдельной взаимной аутентификацией узлов. Рабочий ориентир — три узла и около 30 приложений, каждое проверяется раз в минуту назначенными observers. При разработке достаточно минимальных изолированных тестов критичных правил. Пользователь сначала проверяет один узел на своём ПК, затем постепенно запускает продовые узлы и сам оценивает работу, ошибки и нагрузку; полный стенд и нагрузочная приёмка не требуются.

Обновление фактической технической документации и ближайших `AGENTS.md` выполняется вместе с будущей реализацией соответствующего этапа, без объявления планируемого поведения уже работающим.

## Подэтапы и структура папок

В корне остаются общий план, требования, техническое проектирование и открытые вопросы. Каждый этап 01–10 расположен в собственной папке: `main.md` содержит его цель, сводный статус, зависимости и общие критерии; отдельные файлы `NN.M-*.md` — работы и приёмку подэтапов. Это части одного плана, а не самостоятельные планы с отдельными датами и вопросами.

Все 43 подэтапа перечислены ниже. Статус синхронизируется в документе подэтапа, таблице его этапа и этой таблице. Родительский этап не закрывается, пока открыты обязательные подэтапы или его общая приёмка. `verification` используется для действительно обязательных незавершённых проверок. Справочные внешние сценарии этапа 10 сами по себе не блокируют завершение разработки; фактическая пользовательская приёмка учитывается отдельно.

## Порядок зависимостей между подсистемами

Зависимость подэтапа означает готовность используемого контракта/механизма и необходимых минимальных изолированных проверок. Отдельный SQL/HTTP/browser/Telegram-стенд и прогон всех внешних сценариев не являются обязательными воротами завершения разработки. Пользовательская проверка начинается с одного локального узла, затем продовые узлы вводятся постепенно. Документ не разрешает агенту запуск или deployment; результаты каждой фактической проверки фиксируются отдельно.

- После 02 выполняется 05.1: проверка принятого активного администратора нужна до 04.1/04.2. Затем 04 и 05.2–05.4 подключают общий вход и синхронизацию аккаунтов; полного завершения 05 для начала 04 не требуется.
- 03 отвечает за peer transport, durable Raft, membership, readiness и gate. 04 — за Pending, прикладные команды, атомарные SQL-проекции, конфликты и snapshot/replay. До подтверждённого догона gate остаётся закрытым; в 03 это проверяется контрактом, а затем подключается реальное восстановление 04/07.
- 02.3 создаёт схему; 09 использует механизмы 02/03/04 для одноузлового bootstrap, пустого join и будущего восстановления. Подэтапы 09.2/09.3 отменены: прежних установок для переноса нет.
- Минимальные изолированные проверки критичных правил выполняются по необходимости внутри подэтапов; 10.1 сводит их результаты. 10.2–10.5 — необязательные внешние категории для самостоятельного наблюдения, 10.6 — итоговая фиксация результатов и непроверенного объёма. Сборка не выдаётся за SQL/HTTP/browser/Telegram-проверку.
- Промежуточные результаты не включают новые workers, общие аккаунты и sender на узлах. Первый запуск описывается в 09 и проверяется отдельно; реализация и реальные операции требуют разрешения.

## Порядок выполнения и общая приёмка

Реализация начинается только по отдельной просьбе в разрешённых границах этапа. Сначала проверка интеграции DotNext/Raft, модель и связь, затем ранний контракт активного администратора 05.1, синхронизация, общий вход/пользователи, инциденты, доставка и UI. Первое развёртывание новой модели без переноса v1 требует отдельного разрешения.

- [ ] Главного подтверждает большинство настроенного состава узлов; без большинства новые Telegram-отправки не начинаются, события сохраняются.
- [ ] Через 30 секунд без успешного подтверждения работоспособности главного запускается согласование нового; вернувшийся прежний главный становится ведомым после синхронизации.
- [ ] Неисправная БД выводит узел из работы без автоматического уменьшения состава; потерю межузловой связи отличают от локальной неисправности.
- [ ] Подтверждённая частичная доступность цели видна по узлам и вызывает уведомление; пропущенные наблюдения не выдаются за полный отказ, исправный главный не меняется по этой причине.
- [ ] Каждый активный администратор видит все объекты и может создавать, изменять и удалять серверы, контейнеры и чаты; дополнительных назначений нет.
- [ ] Непринятую заявку можно исправить или отменить с подтверждением результата: применяется только последнее значение; уже принятое изменение исправляется отдельной новой правкой.
- [ ] При конфликте первая принятая настройка продолжает действовать без отката к базе; оба варианта сохранены, итог выбирается новой согласованной командой.
- [ ] В системе только роль Administrator; неавторизованные, отключённые, удалённые и непринятые аккаунты не имеют доступа.
- [ ] Все пользователи, защищённые данные входа, единственная роль и состояние аккаунта синхронизируются; общий UserId не зависит от узла создания.
- [ ] Уникальные имена входа и последний активный администратор сетки защищены при конкурентных командах; запрет self-disable/self-delete сохраняется.
- [ ] Удаление администратором действует на всю сетку и не воскрешается старой репликой; удаление узла не удаляет его пользователей.
- [ ] Изолированный узел с исправной БД допускает вход по последнему принятому состоянию пользователей и принимает Pending; после догона применяет отключения и смену данных входа.
- [ ] Первый узел создаёт общего администратора и сетку с большинством 1; пустой join получает аккаунты/роль и остальные общие данные. Старый backup сверяется с принятой историей, непринятые заявки ждут подтверждения.
- [ ] Любой активный администратор управляет membership/trust и видит общую диагностику; безопасное большинство и peer trust сохраняются.
- [ ] Сессии локальны; после применения отключения/удаления или смены защищённых данных входа прежние данные и сессии не дают доступ. Хеши/секреты не попадают в UI и логи.
- [ ] Цель проверяет назначенный ей набор узлов, изменяемый администратором; пропавший observer не исключается молча, endpoint-данные показаны по узлам.
- [ ] Чаты инцидентов назначаются отдельно каждому узлу любым активным администратором.
- [ ] Завершённые offline-аварии доставляются сводкой без возрастного отсечения, открытые отдельно; уведомлённые чаты получают обычное восстановление.
- [ ] Новая привязка получает открытую проблему; снятие отменяет не начатую отправку, но сохраняет один recovery после успешной проблемы, включая поздний успех in-flight запроса. Удалённым целям/чатам новые сообщения не уходят.
- [ ] Test-send доступен активному администратору, проходит через главного с повторной проверкой аккаунта.
- [ ] Не теряются согласованные инциденты и очередь доставки при штатном отказе одного узла в трёхузловой сетке; редкий Telegram-дубликат в неопределённом окне допустим.
- [ ] Общий бот сохраняется при failover; интерфейс показывает актуальную доступность Telegram-отправки без норматива её возобновления, terminal failure не имеет ручного повтора.
- [ ] Частичная/полная потеря наблюдения вызывает предупреждения только при изменении состояния, восстановление получают предупреждённые чаты без ложной аварии цели.
- [ ] Годовое хранение завершённой истории не удаляет открытые события, Pending, неисполненные intents и необходимые tombstones; часовая цель догона сохранена для самостоятельного наблюдения без обязательного нагрузочного испытания.
- [ ] Аварийное восстановление после потери большинства выполняется вручную с подтверждением потерь; старая сетка не продолжает работу. Обслуживание завершается только ручным включением разработчиком без временного лимита.
- [ ] Выполнены необходимые минимальные изолированные тесты; подготовлен порядок самостоятельного запуска одного локального узла и постепенного ввода продовых. Фактические результаты и непроверенные сценарии разделены по категориям [этапа 10](10-verification-and-acceptance/main.md).

`completed` требует реализации согласованного объёма и необходимых минимальных проверок, а не одного compile-check. Отсутствие необязательного полного стенда, нагрузочных испытаний или всей внешней матрицы не удерживает готовую разработку в `verification`. Самостоятельная приёмка пользователем и непроверенные внешние сценарии фиксируются честно; отсутствие результатов не означает успешную проверку.
