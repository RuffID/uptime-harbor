# Этап 04. Синхронизация ревизий и конфликты

Статус: not-started

## Цель

Принимать изменения на любом узле, согласовывать их без молчаливого затирания и безопасно восстанавливать отставшие реплики.

## Зависимости и границы

После [02](02-domain-and-persistence.md) и [03](03-peer-health-and-leadership.md). Использовать выбранный протокол согласования. Локальное сохранение Pending не означает принятие общей конфигурации.

## Затрагиваемые части проекта

Новые сценарии синхронизации в Application, сценарные UoW, journal/cursor/conflict/tombstone storage в Infrastructure, peer contracts и workers, настройки. Текущие `ObjectAdministrationService` и `NotificationAdministrationService` будут подключаться к этим сценариям в следующих этапах.

## Работы

- [ ] Сохранение заявки: OperationId, origin, actor, target, base revision и payload одной локальной транзакцией. Доступ локально проверяется по принятой версии, не по собственным неподтверждённым grant.
- [ ] Обычные настройки передавать раз в минуту по умолчанию, интервал брать из конфига. Приоритетные изменения прав/удалений/инцидентов/доставки отправлять сразу с отдельным retry, без ожидания минутного цикла.
- [ ] Повторно проверять права и инварианты при принятии главным; изменение состава/права автора между созданием и принятием может дать Rejected.
- [ ] Назначать общую ревизию только принятой записи; переносить результаты Pending/Committed/Conflict/Rejected обратно на исходный узел.
- [ ] Применять команды последовательно и идемпотентно: изменения данных и курсор фиксируются атомарно, повторный OperationId возвращает прежний результат.
- [ ] Для update/update сохранять оба варианта, base/current versions и действующую версию; выбор варианта — новая авторизованная команда с актуальной базой.
- [ ] Разобрать update/delete, конфликты ACL, уникальные имена серверов и Telegram chat ID, зависимые операции и удаление родителя. Не использовать last-write-wins по часам узла.
- [ ] Реплицировать tombstones, отменять зависимые ожидающие действия и исключать воскрешение удалённой сущности отставшей репликой.
- [ ] Поддержать курсоры, проверку пропусков, пагинацию/лимиты и backpressure. Ошибка конкретного пакета не должна молча сдвигать курсор вперёд.
- [ ] Реализовать snapshot общих данных для join/догоняющего узла: проверка ревизии, целостности и совместимости, атомарное переключение, replay хвоста. Не заменять локальный Identity и секреты.
- [ ] Определить retention/compaction по подтверждениям либо обязательному snapshot-rejoin старых узлов; не удалять tombstones только по возрасту.
- [ ] Ввести диагностику отставания, ожидающих/отклонённых команд и ошибок без секретов. Обновить локальные `AGENTS.md` и фактическую документацию синхронизации; новый тематический документ добавить в навигацию и solution.

## Проверки

Изолированно: повторные/переставленные/пропущенные пакеты, crash до и после local commit, потерянный ответ на уже принятую команду, смена главного посреди согласования, несовместимый payload, конфликт одновременных правок, delete против старого update, отставший узел со snapshot и без него. Fake storage проверяет алгоритм, но не SQL Server transaction semantics.

Внешняя приёмка: действительные независимые БД, восстановление после остановки процесса, большие очереди и ограниченная сеть — по отдельному разрешению.

## Критерии приёмки

- [ ] Изменение можно сохранить на ведомом без связи; оно не применяется к действующему мониторингу до принятия.
- [ ] Принятая команда даёт одинаковое общее состояние после догона всех узлов.
- [ ] Повторная доставка не создаёт новую ревизию того же действия и повторный side effect.
- [ ] Конфликты видимы, варианты не теряются, молчаливого перезаписывания нет.
- [ ] Snapshot/догон не заменяет локальные данные и не восстанавливает удалённые сущности.
