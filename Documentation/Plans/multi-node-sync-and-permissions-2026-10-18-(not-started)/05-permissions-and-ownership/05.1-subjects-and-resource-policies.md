# Подэтап 05.1. Общий аккаунт и единая проверка администратора

Статус: not-started

## Цель и результат

Готова проверка активного принятого администратора для command pipeline и Web.

## Зависимости и границы

Зависимости: [02](../02-domain-and-persistence/main.md).

Родительский [этап 05](main.md), [общий план](../main.md), [требования](../business-requirements.md) и [техническое проектирование](../technical-design.md) задают границы. Подготовка документа не разрешает реализацию, запуск приложения или внешние проверки.

## Затрагиваемые части проекта

Application/Security и Users, Infrastructure/Identity и accepted user storage, Web authorization. Профильные тесты, ближайшие `AGENTS.md` и актуальная техническая документация обновляются при будущей реализации.

## Работы

- [ ] Ввести чтение общего принятого аккаунта по UserId и единую проверку входа/активности/единственной роли Administrator. Отдельных разрешений, владельцев и операторов нет.
- [ ] Убрать существующие проверки отдельных разрешений и зависимость доступа к контейнеру от сервера, назначения object permissions, дополнительные роли и связанные интерфейсы. Оставить одну административную проверку; эта работа выполняется при реализации, а не текущей правкой плана.
- [ ] Применить одну проверку ко всем сущностям, пользователям, диагностике, membership/trust, observers, привязкам и test-send.
- [ ] Повторно проверять активность перед принятием команды и тестовой отправкой. Доверенный peer и неподтверждённая локальная заявка не заменяют проверку пользователя.
- [ ] Подготовить контракт до 04.1/04.2 без второго механизма репликации пользователей.
- [ ] Актуализировать затронутые локальные `AGENTS.md` и фактическую техническую документацию; новые документы включить в навигацию и solution.

## Проверки

Активный общий администратор получает доступ ко всем объектам; анонимный, отключённый, удалённый или ещё непринятый аккаунт получает отказ; повторная проверка после отключения.

Изолированные проверки и compile-check не подменяют SQL Server, реальные peer HTTP, браузер и Telegram. Внешняя приёмка учитывается отдельно в [этапе 10](../10-verification-and-acceptance/main.md); команды из плана не разрешены автоматически.

## Критерии приёмки

- [ ] Единственная роль даёт полный доступ без ресурсной матрицы.
- [ ] Command pipeline читает только принятое состояние аккаунта, а не локальный неподтверждённый вариант.
- [ ] Работы и применимые проверки выполнены; непроведённая внешняя приёмка остаётся открытой.
- [ ] Статус согласован с родительским этапом и общим планом.
