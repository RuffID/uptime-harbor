# Telegram-уведомления

## Состояние реализации

Доменная модель Telegram-чатов и привязок, EF-конфигурации, репозитории и `INotificationSettingsUnitOfWork` реализованы. Telegram client, sender, administrative use case и обработка переходов пока не реализованы.

## Хранение

`TelegramChat` содержит внутренний `Guid`, уникальный Telegram chat ID и имя для администратора.

`NotificationBinding` связывает чат ровно с одним сервером или контейнером. Это правило защищено доменной фабрикой и check constraint. Уникальные filtered indexes запрещают повторную привязку одной цели к одному чату.

## Целевой поток

1. После сохранения перехода `BecameUnavailable` загружаются привязанные чаты.
2. Outage-сообщение отправляется каждому чату независимо.
3. Повторные проверки того же инцидента не создают новые сообщения.
4. После `Recovered` отправляется recovery только для инцидента с успешным outage-уведомлением.
5. Ошибка Telegram не меняет результат HTTP-проверки и не блокирует другие объекты.

Сообщение включает тип объекта, имя или идентификатор, описание при наличии, новый статус и UTC-время события. Для контейнера также указывается родительский сервер; recovery может включать время запуска и uptime.

## Частичная доставка

Если объект связан с несколькими чатами, состояние доставки нужно учитывать по каждой привязке текущего инцидента. Успех одного чата не должен скрывать ошибку другого, а retry не должен повторно отправлять сообщение уже успешному получателю.

Модель такого состояния ещё не реализована и должна быть окончательно определена до завершения этапа уведомлений.

## Секреты и логирование

Bot token поступает через `TelegramOptions`, не хранится в БД и не выводится в логи. Ошибки доставки логируются с идентификатором объекта/чата без содержимого секретов.
