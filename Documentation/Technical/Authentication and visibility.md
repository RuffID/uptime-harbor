# Аутентификация и видимость

## Состояние реализации

Identity, cookie pipeline и адаптеры пользователей находятся в Infrastructure; application use case вычисляют доступ и управляют permissions; Web содержит страницы входа/выхода и защищённые MVC endpoints. Административная страница `/Admin/Users` позволяет без перезагрузки создавать обычных пользователей, включать/блокировать, удалять и заменять видимость серверов и контейнеров. Контейнеры доступны в UI только при выбранном родительском сервере; текущий администратор не может отключить или удалить себя.

## Identity-модель

Пользователь и роль используют `Guid` как ключ. `ApplicationUser` дополнительно хранит `IsEnabled` и изменяет его только методами `Enable`/`Disable`.

Identity-типы находятся в Infrastructure, потому что наследуют типы ASP.NET Core Identity. Domain хранит permissions только как независимые идентификаторы пользователя и объекта.

## Аутентификация

- Самостоятельная регистрация отсутствует.
- Начальный администратор создаётся из валидированных options только при отсутствии администратора.
- Повторный bootstrap не меняет существующий пароль.
- Весь пользовательский интерфейс требует аутентификации.
- Административные endpoints требуют роль `Administrator`.
- Заблокированный пользователь не должен продолжать получать доступ после завершения или инвалидации сессии.

`InitialAdministratorBootstrapper` идемпотентно создаёт роли `Administrator` и `User`, а администратора создаёт только при отсутствии пользователей в административной роли. `BootstrapAdminOptions` валидируются при фактической необходимости создать администратора; повторный запуск не меняет пароль существующего пользователя.

Web pipeline вызывает authentication до authorization. Cookie имеет `HttpOnly`, `SameSite=Lax` и `Secure=Always`. Security stamp проверяется на каждом запросе. Блокировка меняет `IsEnabled`, обновляет security stamp, а cookie validator немедленно отклоняет сессию заблокированного пользователя.

Страницы `/Account/Login` и `/Account/Logout` используют одинаковую ошибку для неизвестного логина, неверного пароля и заблокированной записи. Публичной регистрации и восстановления пароля нет. Все Razor Pages, кроме входа и страницы ошибки, требуют аутентификации.

## Видимость объектов

`ServerVisibilityPermission` связывает пользователя и сервер. `ContainerVisibilityPermission` хранит пользователя, сервер и контейнер.

Составные внешние ключи требуют, чтобы permission контейнера ссылался на permission того же пользователя к родительскому серверу и на контейнер этого сервера.

Application use case обязан фильтровать данные до формирования DTO. UI-скрытие не считается защитой. Те же правила применяются к controller endpoints и SignalR-событиям.

Администратор получает полный список без отдельных permissions. Обычный пользователь не получает контейнеры только на основании доступа к серверу.

`AccessibleObjectsService` остаётся Application-сервисом общего списка и прямого чтения. `ObjectsController` использует его для всех прямых чтений и возвращает `NotFound` для скрытого объекта.

`ObjectVisibilityPolicy` единообразно требует server permission для сервера и одновременно server + container permissions для контейнера. `DashboardQuery` применяет эту политику до формирования dashboard DTO. `MonitoringEventRecipientResolver` применяет ту же политику к каждому включённому пользователю и возвращает только разрешённые server-side SignalR user-id; администраторы получают события всех объектов.

`UserManagementService` повторно проверяет административную роль внутри use case и поддерживает создание с начальным паролем, включение, блокировку, удаление и замену permissions. Контейнер проверяется вместе с родительским сервером до транзакционного изменения permissions. Удаление пользователя удаляет permissions; схема БД дополнительно закрепляет это каскадами.
