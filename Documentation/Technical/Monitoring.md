# Движок мониторинга

## Состояние реализации

Доменные переходы и persistence-контракты подготовлены, но фоновый планировщик, HTTP-валидаторы и публикация обновлений ещё не реализованы. Этап движка мониторинга имеет статус «Не начат» до появления рабочего end-to-end сценария.

## Контракты endpoint

Проверка выполняется HTTP GET без авторизации.

Ответ сервера должен быть успешным JSON-документом с непустым `name`.

Ответ контейнера должен дополнительно содержать `startedAtUtc` в UTC. Время запуска не может находиться в будущем относительно времени проверки.

Неуспешный HTTP status, timeout, сетевое исключение, некорректный JSON или неверное обязательное поле считаются неудачной проверкой одного объекта, а не системной ошибкой всего worker.

## Планируемый цикл

- Каждые 30 секунд выбираются включённые объекты.
- Разные объекты могут проверяться параллельно.
- Для одного объекта одновременно допускается только одна проверка.
- Внутри цикла нет немедленного retry.
- Ошибка одного объекта не завершает обработку остальных.
- Штатная остановка передаётся через `CancellationToken`.

HTTP-клиенты создаются через `IHttpClientFactory`. Интеграционная реализация остаётся в Infrastructure, а Application получает независимый результат проверки.

## Сохранение результата

Use case загружает объект через `IMonitoringUnitOfWork`, вызывает доменный метод перехода и сохраняет изменения через тот же Unit of Work.

Событие для SignalR и уведомлений публикуется только после успешного сохранения. PostgreSQL является источником истины; сообщения и Web-события не заменяют сохранённое состояние.

## Конкурентность

Однопроцессная первая версия может использовать keyed in-memory coordination для запрета одновременной проверки одного объекта. Защита должна корректно освобождаться при успехе, исключении и отмене. Если появится несколько экземпляров приложения, потребуется отдельное распределённое решение, но оно не входит в первую версию.
