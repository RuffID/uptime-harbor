# Этап 2. Данные и хранение

## Цель

Создать доменную модель, схему PostgreSQL и инфраструктуру сохранения текущего состояния без истории проверок.

## Работы

1. Создать сущности:

   - `MonitoredServer`;
   - `MonitoredContainer`;
   - `TelegramChat`;
   - привязки уведомлений;
   - разрешения видимости серверов и контейнеров;
   - Identity-пользователь и роли.

2. Для сервера и контейнера предусмотреть:

   - GUID;
   - endpoint URL;
   - описание;
   - признак включённого мониторинга;
   - последнее имя из endpoint;
   - текущий статус;
   - счётчик последовательных ошибок;
   - время последней и последней успешной проверки;
   - признак отправленного уведомления о текущем инциденте.

3. Для контейнера дополнительно хранить последнее `startedAtUtc` и обязательную связь с сервером.
4. Реализовать доменные операции переходов статуса, не допуская произвольного изменения связанных полей внешним кодом.
5. Настроить `DbContext`, ограничения, индексы, длины строк, каскадное удаление и UTC-конвертацию.
6. Создать первую миграцию PostgreSQL.
7. Реализовать слой доступа к данным с явными границами транзакций для административных операций и обновления состояния.
8. Определить безопасный способ применения миграций при развёртывании.
9. Настроить сохранение ключей ASP.NET Core Data Protection вне временной файловой системы контейнера.

## Основные ограничения данных

- GUID генерируется приложением до сохранения;
- одинаковые полученные имена разрешены;
- URL обязателен и должен использовать HTTP или HTTPS;
- описание имеет заданную максимальную длину;
- `startedAtUtc` хранится как UTC;
- разрешение контейнера не может ссылаться на контейнер другого сервера;
- привязка уведомления должна ссылаться ровно на один тип объекта;
- удаление сервера каскадно удаляет дочерние и связанные записи.

## Тесты

- переходы `Неизвестно → Доступен → Недоступен → Доступен`;
- сброс счётчика при успехе;
- перевод в «Неизвестно» при отключении;
- отсутствие recovery-события после ручного отключения;
- ограничения URL и UTC;
- каскадное удаление модели;
- уникальность составных связей разрешений и уведомлений.

## Результат этапа

Создана мигрируемая схема PostgreSQL и протестированная модель текущего состояния UptimeHarbor.
